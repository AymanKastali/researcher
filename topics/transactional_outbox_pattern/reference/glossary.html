Reference · Transactional Outbox

Glossary

The vocabulary an interviewer will use. Use these words exactly — precision here is most of the signal.

Terms marked ·covered· have appeared in a lesson. The rest are here so the map is complete; they arrive in later lessons.

The problem

Dual-write problem ·covered· One logical operation must write to two systems that share no atomic commit — a database and a message broker. No ordering of the two writes is safe: crash after the first and you either lose an event or emit a phantom one. Lesson 01
Phantom event ·covered· A message announcing a state change that was never committed. The failure mode of publish-then-commit.
Two-phase commit (2PC / XA) ·covered· A distributed transaction protocol with a coordinator, a prepare phase and a commit phase. Rejected here because SQS and NATS do not support it, RabbitMQ's transactions are channel-local rather than distributed, and it couples the service's availability to the broker's while risking in-doubt transactions holding locks.

The pattern

Transactional outbox ·covered· Write the outgoing message into a table in the same local transaction as the business state, then publish it asynchronously from there. Reduces two commits to one.
Outbox table ·covered· The table holding undelivered messages. Lives in the service's own database — the same database as the business rows, or the guarantee evaporates.
Message relay ·covered· The separate process that moves rows from the outbox to the broker and records that it did. The only component that talks to the broker.
Polling publisher ·covered· A relay implemented by repeatedly querying the outbox table. Works on any SQL database; per microservices.io its drawback is that it is "tricky to publish events in order." The choice for this stack, decided in Lesson 04.
Transaction log tailing / CDC ·covered· A relay implemented by reading the database's write-ahead log instead of querying — Postgres logical decoding, MySQL binlog. Named benefits: "No 2PC", "guaranteed to be accurate". Named drawbacks: database-specific, and "tricky to avoid duplicate publishing". Debezium is the reference implementation. Replaces the relay, never the outbox table — and it is still at-least-once. Lesson 04
Aggregate / aggregate id ·covered· The entity the event is about (order, #7f3a…). Outbox rows carry both because the relay routes and orders by them. Crucially it is a consistency boundary: concurrent writes to one aggregate contend on its row, so they commit in sequence — which is the entire reason per-aggregate ordering is cheap. Lesson 05

Ordering

Global total order ·covered· One agreed sequence for every event in the system. Buyable — one publisher, one queue, one consumer — and ruinous, because it costs all concurrency. Name it, price it, decline it. Lesson 05
Per-aggregate order ·covered· Events about the same aggregate delivered in sequence; unrelated aggregates unconstrained. Almost always the real requirement, and reachable from a polling relay. Lesson 05
Sequence order vs. commit order ·covered· nextval fires at insert, not at commit, so a slow transaction holds a low id and commits late. Verified: a row inserted first became visible second, and the relay published the later event alone. Only logical decoding gives true commit order. Lesson 05
Shard / partition key ·covered· A hash of the aggregate id, used both as the relay's claim filter and as the broker routing key. Gives one aggregate exactly one owner by arithmetic, with no coordination. Compute it once, as a stored generated column (hashtext(aggregate_id) & 3) — two hash implementations that must agree is a bug waiting for the day they do not. Costs: uneven shards, and a drain before changing the count. Lesson 05
Single active consumer is not enough ·covered· SAC guarantees one consumer; it does not guarantee one message in flight. Measured over 460 events: zero ordering violations clean, 15 across 12 aggregates once 5% of deliveries were requeued at prefetch 20, and zero again at prefetch 1. The per-aggregate guarantee needs shard + SAC + prefetch 1. Lesson 05
Advisory lock ·covered· "Locks that have application-defined meanings… the system does not enforce their use." The xact variants release at commit. Not usable in a claim query's WHERE: the filter runs before LIMIT, so one worker locks every aggregate in the backlog. Lesson 05
Single active consumer (SAC) ·covered· x-single-active-consumer on a classic or quorum queue. "Only have one consumer at a time consuming from a queue. If the active consumer is cancelled or disconnects, another registered consumer takes its place." Guarantees ordered dispatch, not ordered handling. Lesson 05
Version gate / aggregate cursor ·covered· Per-aggregate version on the event plus a stored high-water mark per consumer; anything not greater is dropped and acked. Makes out-of-order delivery self-correcting. Valid for state-carrying events only — never for deltas. Lesson 05
State-carrying vs. delta event ·covered· "Order 42 is now shipped" versus "add 5 to the balance." A stale state event is safe to skip because the newer one subsumes it; a delta must be applied exactly once and in sequence. Decides whether the version gate is available at all. Lesson 05

Delivery semantics

At-least-once ·covered· Every message arrives, possibly more than once. What the outbox gives you, because the relay can publish and then die before marking the row sent.
At-most-once ·covered· Every message arrives zero or one times. What naive fire-and-forget publishing gives you. Not what the outbox gives you.
Exactly-once delivery ·covered· Not achievable across a network — the sender cannot distinguish a lost message from a lost ack, so it must either retry (duplicate) or not (loss). Do not claim it.
Exactly-once processing ·covered· What people actually mean, and it is achievable — but built, not bought: at-least-once delivery plus an idempotent consumer. Correcting the word is worth more than the rest of the answer. Lesson 03
Idempotent consumer ·covered· A consumer that produces the same result whether it sees a message once or five times. The mandatory other half of the outbox pattern. Reached either naturally (assignment to an absolute value; a unique constraint on the business key) or by recording processed message ids.
Inbox pattern ·covered· The mirror of the outbox on the consuming side: a table keyed on (consumer_name, message_id), inserted in the same transaction as the business write. Splitting them into two commits recreates the dual-write problem on the consuming side. Lesson 03
Idempotency key ·covered· A stable client-supplied id sent to a remote service so it can collapse a retry — the only defence when the side effect leaves your database and ROLLBACK cannot undo it. Payment APIs require one for this reason.
The crash window ·covered· The one instant in the relay loop where a crash produces a duplicate: after the broker confirms and before the published_at update commits. Observed with a SIGKILL — the row stays unpublished while the consumer has already done the work, so the restarted relay publishes it again. Naming the window precisely is the answer; "somewhere in the middle" is not. Lesson 07
redelivered flag ·covered· RabbitMQ's marker for its own second attempt at a delivery. Measured: the duplicate the relay manufactures arrives with redelivered=False, because to the broker it is a fresh publish of a message it has never seen. Deduplicating only when the flag is true is broken in the silent direction. Lesson 07
Late, not lost The asymmetry the whole pattern buys. Crash before the publish and the event is republished on restart; crash after it and the event is duplicated. Both are recoverable. Without an outbox the same crash between the business commit and the publish loses the event permanently, because nothing records that a message was owed.
Delivery limit ·covered· A quorum queue's count of failed deliveries, 20 by default since RabbitMQ 4.0, after which the message is dropped or dead-lettered. It does not count every return. The counter moves for reject, AMQP 1.0 modify with delivery_failed=true, and channel termination — but "unlimited explicit returns (via nack…) are allowed without counting toward the delivery limit". Measured: 12 polite nacks against a limit of 3, still cycling. Lesson 06
Requeue displacement ·covered· A requeued message returns to the head of the queue, not the tail. What moves it out of position is the consumer's own prefetch buffer — deliveries already handed out that the broker will not take back. Measured: with prefetch n, the message reappears n positions later. Prefetch 1 preserves order across a retry. Lesson 05

Postgres primitives

FOR UPDATE SKIP LOCKED ·covered· A SELECT locking clause: rows another transaction already holds are skipped rather than waited on. The docs are explicit that this "provides an inconsistent view of the data, so this is not suitable for general purpose work, but can be used to avoid lock contention with multiple consumers accessing a queue-like table." An outbox is exactly such a table. PG docs
NOWAIT ·covered· The sibling option: error immediately instead of waiting. Useful for a single-owner claim, wrong for a worker pool.
LISTEN / NOTIFY ·covered· Postgres pub/sub. Lets the relay be woken on insert instead of polling on a timer. A latency optimisation layered on top of polling — never a replacement, since notifications are not durable across a disconnect. Treat the payload as a doorbell, not as data. Lesson 04
Partial index ·covered· An index with a WHERE clause, so it stores only matching rows. On an outbox, WHERE published_at IS NULL indexes the backlog rather than all history, keeping the claim query's cost tied to work outstanding. Lesson 02

Logical decoding and CDC

The machinery behind log tailing. Named in the mission as new ground, and the source of the strongest argument against CDC.

Logical decoding ·covered· Postgres turning WAL into a stream of row changes for a client. Two guarantees worth quoting: "concurrent transactions are decoded in commit order", and "aborted transactions and their contents never get decoded." The first is the one thing polling cannot buy. Lesson 04
Replication slot ·covered· Server-side state tracking one consumer's position in the stream. The liability: slots "persist across crashes and know nothing about the state of their consumer(s). They will prevent removal of required resources even when there is no connection using them" — WAL is retained and VACUUM is blocked, and "in extreme cases this could cause the database to shut down to prevent transaction ID wraparound." A connector that is switched off is a database incident, not a messaging one.
Checkpointed slot position ·covered· Why CDC is still at-least-once: "a logical slot will emit each change just once in normal operation. The current position of each slot is persisted only at checkpoint, so in the case of a crash the slot might return to an earlier LSN." The inbox stays.
wal_level = logical ·covered· "Adds information necessary to support logical decoding", and "can only be set at server start" — so enabling CDC is a restart of the primary. It also "will increase the WAL volume."
max_slot_wal_keep_size ·covered· The only lever against a stalled slot, and a choice between two failures. Default -1: slots "may retain an unlimited amount of WAL files" until the disk fills. Set it, and past the limit the consumer "may no longer be able to continue replication due to removal of required WAL files."
Outbox Event Router ·covered· Debezium's transform for outbox tables. Default columns: id uuid, aggregatetype (selects the topic), aggregateid (becomes the message key, hence per-aggregate ordering), type, payload jsonb. Treats the table as append-only — inserts only, deletes filtered out — so there is no published_at to maintain and pruning emits nothing.
Heartbeat (heartbeat.interval.ms) ·covered· Manufactured traffic that lets a connector confirm an LSN. Needed because slots are per-database: a quiet captured database on a busy server never advances its slot, and the shared WAL grows anyway. Pair with heartbeat.action.query and a heartbeat table that is part of the publication.

RabbitMQ specifics

The broker was pinned to RabbitMQ on 2026-09-10. These are the terms that matter for running an outbox against it.

Publisher confirm ·covered· Enabled per channel with confirm.select (publisher_confirms=True, aio-pika's default). The broker replies basic.ack when it has taken responsibility: for a persistent message on a durable queue, "this means persisting to disk"; on a quorum queue, once "a quorum replicas have accepted and confirmed the message to the elected leader." Without confirms, publishing is fire-and-forget. Lesson 03
mandatory ·covered· The publish flag that makes an unroutable message come back instead of being dropped. Critical, because unroutable messages are confirmed anyway — a relay without mandatory can mark every row published while the exchange bins them. Default is false. The alternative fix is an alternate exchange.
Manual vs. automatic ack ·covered· Automatic ack acks on delivery, before your handler runs, and the docs call it "unsafe": a dropped connection loses the message. Manual ack (basic.ack after your transaction commits) is the only option compatible with at-least-once.
Prefetch (basic.qos) ·covered· "The max number of unacknowledged deliveries that are permitted on a channel." Docs suggest 100–300 for throughput. Unbounded means a crashed consumer requeues its whole in-flight backlog at once. Not an ordering control in either direction: prefetch above one does not reorder deliveries, and a prefetch of one does not buy order. Lesson 05
Quorum queue ·covered· The replicated, durable queue type — "should be considered the default choice when needing a replicated, highly available queue." Also the only type that counts redeliveries, in x-delivery-count.
Delivery limit ·covered· Quorum-queue cap on redelivery attempts, defaulting to 20 since RabbitMQ 4.0. Past it "the message will be dropped (removed) or dead-lettered (if a DLX is configured)" — so without a DLX the default outcome is deletion.
redelivered flag ·covered· Set true when a delivery may be a repeat. Useless for deduplication: it never says whether you processed it, and "a consumer can receive a message that was previously delivered to another consumer."

Operational hazards

Poison message ·covered· A message that fails every time it is tried. Two sides, two mechanisms. In the outbox: a row at the head of a shard that never publishes stops the shard, because ORDER BY id means the head must move first and SKIP LOCKED does not help (nobody holds the row between attempts). In the queue: the broker counts for you. Escape hatch is a max-attempt limit on both sides. Lesson 06
Parked aggregate ·covered· The correct unit to skip when a poison row hits the attempt limit. Skipping the row publishes an aggregate's later events after dropping an earlier one — order 42 shipped without ever being paid — which reintroduces the ordering bug of Lesson 05. Park the whole aggregate, drain the rest of the shard around it, and treat unparking as a human decision. Lesson 06
Broker-side dedup window ·covered· Publish-deduplication, and its two limits: it dedups the send, not the delivery, and only inside a time window. RabbitMQ core offers none at all, which settles the question for us. For contrast: SQS FIFO MessageDeduplicationId = 5 minutes, NATS JetStream Nats-Msg-Id = 2 minutes by default — both shorter than a real outage. A volume reduction, never the guarantee. Lesson 03
Commit-then-ack ·covered· The consumer's ordering rule: commit the local transaction, then ack the broker. Acking first means a failed commit loses the message with nothing left to redeliver it. Mirror of the relay's publish-then-mark — always fail toward the duplicate.
Delivery limit ·covered· The broker's poison-message counter. Quorum queues track failed deliveries in the x-delivery-count header and, past the limit, drop or dead-letter the message. Defaults to 20 since RabbitMQ 4.0; -1 disables it and the docs advise against that, since "repeated requeues can threaten the stability of a queue or RabbitMQ cluster". Set it by policy, not by queue argument. Lesson 06
Dead-letter exchange (DLX) ·covered· Where a message goes once it is rejected without requeue, expires, overflows a length limit, or exceeds the delivery limit. The dead-lettered copy carries an x-death header — queue, reason, count — "ordered by recency", which is your triage data. Lesson 06
Dead-letter strategy ·covered· The hole in the graveyard. at-most-once is the quorum-queue default and the docs are explicit: dead-lettered messages are "re-published without publisher confirms turned on internally… not guaranteed to be safe. Messages can be lost if the target queue is not available." Ask for at-least-once instead. Volunteering this is what separates a read answer from an operated one. Lesson 06
Relay lag ·covered· Age of the oldest unpublished outbox row, grouped by shard. The one health metric. Count cannot separate busy from stuck — 40,000 rows draining fast is healthy, one row stuck nine minutes is an outage — while age is the relay's end-to-end latency as a single number, bounded in a healthy system by one poll interval plus one publish. Per shard, because one worker owns each shard and a global average hides a dead one. Lesson 06
Outbox bloat ·covered· Dead tuples accumulating from the pattern's own write shape: every row inserted, updated once when published, then deleted. Measured on 200k rows — the single published_at update doubled the heap (52 → 106 MB), and deleting 91% of rows then plain-vacuuming returned nothing to the OS. It does not slow the relay down: the partial index keeps the claim query on the backlog (104 buffers on that 106 MB table), so nothing degrades until the disk fills. Monitor table size directly. Lesson 06
VACUUM vs. VACUUM FULL ·covered· Plain VACUUM marks dead space reusable but "will not return the space to the operating system, except in the special case where one or more pages at the end of a table become entirely free" — and a retention job frees pages at the front, so the exception never applies. VACUUM FULL rewrites the table and does return the space, under an ACCESS EXCLUSIVE lock for the duration. Lesson 06
Retention by partition ·covered· Range-partition the outbox by day so retention is a DROP TABLE, which "entirely avoid[s] the VACUUM overhead caused by a bulk DELETE". Measured: 9 ms to drop a 200k-row partition versus 122 ms to delete plus 29 ms to vacuum, with the space returned only in the first case. Costs the claim query nothing measurable (203 buffers partitioned, 202 flat — a Merge Append over each partition's local partial index). The real cost is planning time once partitions run to the thousands. Lesson 06
Claim / lease ·covered· How a relay worker reserves rows. Two variants: hold the row lock across the publish (the lock is the claim, and dies with the worker), or stamp a claimed_at lease and commit first (short transactions, but leaked claims need an expiry and a reaper). Lesson 02
High-water-mark cursor ·covered· The tempting WHERE id > last_seen_id optimisation, and a message-eater. Sequence ids are assigned at insert, not at commit, so a slow transaction's row can appear behind a cursor that has already passed it — never published, no error raised. Use the nullable published_at flag instead.
