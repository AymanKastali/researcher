Lesson 02 · Transactional Outbox

The Message Relay

The table, the claim query, and the one design decision the whole relay turns on.

The win for this lesson: by the end you can write the outbox DDL and the claim query from memory, justify every clause in both, and answer the follow-up that separates people who have read about this from people who have run it — how long do you hold the lock? This is the lesson with the primitive you flagged as new, so it goes slowly and it earns each line.

Lesson 01 ended with one commit and no publisher. Something still has to publish. That something is the message relay: a separate process, the only component in the system that talks to the broker.

What the relay must do

Three steps, in a loop, forever:

  1. Claim a batch of unpublished rows — and stop any other worker claiming the same ones.
  2. Publish each to the broker.
  3. Mark them done so they are never published again.

Every one of those steps can fail, and there will be several relay workers running at once — you do not get to assume a single instance, because a single instance is a single point of failure and cannot be deployed without downtime. Hold both facts while you read the rest.

The table

CREATE TABLE outbox_message (
    id            bigint GENERATED ALWAYS AS IDENTITY PRIMARY KEY,
    message_id    uuid        NOT NULL DEFAULT gen_random_uuid(),
    aggregate_type text       NOT NULL,
    aggregate_id  uuid        NOT NULL,
    event_type    text        NOT NULL,
    payload       jsonb       NOT NULL,
    created_at    timestamptz NOT NULL DEFAULT now(),
    published_at  timestamptz,
    attempts      smallint    NOT NULL DEFAULT 0,
    last_error    text
);

CREATE INDEX outbox_unpublished_idx
    ON outbox_message (id)
    WHERE published_at IS NULL;

Ten columns and one index. The index is not an optimisation — see below.

Why each column is there, because you will be asked:

ColumnWhat it buys you
id bigint identity A cheap monotonic insertion order to sort and page by. Not a commit order — that distinction has its own trap below.
message_id uuid The stable business identity of the message, generated once at insert and carried onto the broker. Redeliveries share it, which is what lets a consumer deduplicate. Separate from id on purpose: id is a storage detail, message_id is part of your contract.
aggregate_type, aggregate_id What the event is about. Drives routing, and later drives per-aggregate ordering. Debezium's outbox router uses exactly this pair, which is a good sign you have the shape right.
payload jsonb The message body, already serialised. The relay must never need to load your domain objects — it is a dumb pipe, and that is a feature.
published_at NULL means "owed". The entire work queue is defined by this one nullable column.
attempts, last_error Your only defence against a poison message. Add them now; retrofitting them during an incident is not fun.
Why the index is partial

WHERE published_at IS NULL means the index contains only the backlog — normally a handful of rows — no matter how many million published rows sit in the table. The claim query's cost tracks work outstanding rather than history. A plain index on (published_at, id) would grow forever and you would feel it. This one line is the difference between a relay that stays fast for years and one that slowly dies.

First attempt, and why it breaks

The obvious query:

SELECT * FROM outbox_message
WHERE published_at IS NULL
ORDER BY id
LIMIT 100;

Run two workers. Both take the snapshot, both see the same hundred rows, both publish them. Every message goes out twice, forever — not as a rare crash artefact but as the steady state. Unacceptable.

So reach for a lock:

SELECT * FROM outbox_message
WHERE published_at IS NULL
ORDER BY id
LIMIT 100
FOR UPDATE;

This is correct. It is also useless. Worker B blocks on the first row worker A has locked, and waits there until A commits. Postgres then re-checks the row, finds published_at is no longer NULL, and drops it from B's result. B was safe, and B did nothing for the length of A's entire publish batch. You have bought correctness by serialising your worker pool down to one worker. Add nine more and throughput does not move.

Note what FOR UPDATE costs even when nothing contends. The Postgres docs are blunt: "locking a row might cause a disk write, e.g., SELECT FOR UPDATE modifies selected rows to mark them locked, and so will result in disk writes." Claiming is a write, not a read.

SKIP LOCKED

The fix is one clause. From the primary source:

With SKIP LOCKED, any selected rows that cannot be immediately locked are skipped. Skipping locked rows provides an inconsistent view of the data, so this is not suitable for general purpose work, but can be used to avoid lock contention with multiple consumers accessing a queue-like table. PostgreSQL docs — SELECT, The Locking Clause

Learn that sentence. It concedes the flaw and licenses the exception in the same breath, and an outbox is precisely the licensed case: a queue-like table with multiple consumers, where an inconsistent view is fine because no worker needs to see the whole queue — it only needs some rows nobody else is touching.

SELECT id, message_id, event_type, payload
FROM outbox_message
WHERE published_at IS NULL
ORDER BY id
LIMIT 100
FOR UPDATE SKIP LOCKED;

The claim query. Write this from memory until it is boring.

ClauseWhat it buys
WHERE published_at IS NULL Defines the work queue, and matches the partial index exactly.
ORDER BY id Oldest first, so nothing starves. Read the caveat below before you claim it gives you ordering.
LIMIT 100 Bounds the transaction. Too small and you round-trip constantly; too large and you hold locks and an open transaction for a long time.
FOR UPDATE Takes an exclusive row lock, held until the transaction ends — that duration is the whole design decision, below.
SKIP LOCKED Rows another worker already holds are passed over instead of waited on. This is what turns N workers into N× throughput.
SKIP LOCKED arrived in PostgreSQL 9.5. Its sibling NOWAIT raises an error instead of skipping — right for a single-owner claim, wrong for a worker pool, where erroring out on any contention is exactly the behaviour you are trying to avoid.

Two things the docs say that will trip you

ORDER BY runs first

The docs: "It is possible for a SELECT command running at the READ COMMITTED transaction isolation level and using ORDER BY and a locking clause to return rows out of order. This is because ORDER BY is applied first." Sorting happens before locking, so with SKIP LOCKED your batch is "up to 100 of the oldest candidate rows, minus whichever were already claimed" — not "the oldest 100". Holes are normal. If you said ORDER BY id gives you ordered delivery, you would be wrong, and this is where Lesson 05 starts.

The second is about LIMIT: "If a LIMIT is used, locking stops once enough rows have been returned to satisfy the limit (but note that rows skipped over by OFFSET will get locked)." The parenthesis is the point — never paginate an outbox with OFFSET. You would lock rows you are not even going to look at, blocking other workers from claiming them for nothing.

The real decision: how long do you hold the lock?

The row lock lasts until the transaction ends. The publish is a network call to the broker. So: does the publish happen inside the claiming transaction, or do you commit the claim first and publish after? This is the question behind "so how does your relay work?", and it is where an interviewer finds out whether you have thought about it.

ApproachWhat you get, what you pay
A — hold the lock across the publish
claim → publish → mark → COMMIT		 Get: the lock is the claim, so there is no separate bookkeeping and no way to leak a claim — a dead worker's transaction dies with its connection and every row is instantly free.
Pay: an open transaction spanning a network call. A slow broker holds your transaction open, which pins the vacuum horizon and can bloat the table. A hung broker parks a connection from your pool indefinitely.
B — lease, then publish
claim + stamp claimed_at → COMMIT → publish → mark		 Get: transactions measured in milliseconds. Broker latency never touches the database.
Pay: the lease can leak. A worker that dies after committing its claim leaves rows stamped and unpublished, so you need an expiry and a reaper — and reaping means republishing rows that may already have gone out. More duplicates.

Pick A by default, and say why out loud: with a bounded batch and an aggressive publish timeout, the transaction stays short, and you have removed an entire class of bug (leaked leases, reaper races) rather than managing it. Move to B when you have measured a real problem — a broker whose tail latency you do not control, or transaction duration showing up in your vacuum metrics. That is the shape of a good answer: a default, a reason, and a named trigger for changing your mind.

Neither one is exactly-once

In A, the publish can succeed and the COMMIT then fail — republished on restart. In B, the mark-as-published can fail after the publish — republished when the lease expires. Lesson 01's price is not an accident of implementation; it survives every implementation. Say so before you are asked.

Approach A in Python

from sqlalchemy import func, select
from sqlalchemy.ext.asyncio import AsyncSession

BATCH = 100

async def drain_once(session: AsyncSession, broker: Broker) -> int:
    """Claim, publish and mark one batch. Returns rows handled."""
    async with session.begin():                     # one transaction, start to finish
        rows = (
            await session.scalars(
                select(OutboxMessage)
                .where(OutboxMessage.published_at.is_(None))
                .order_by(OutboxMessage.id)
                .limit(BATCH)
                .with_for_update(skip_locked=True)  # ← the whole lesson
            )
        ).all()

        for row in rows:
            await broker.publish(
                row.event_type,
                row.payload,
                message_id=str(row.message_id),     # consumer dedup key, Lesson 03
            )
            row.published_at = func.now()           # clock stays in the database

    return len(rows)                                # COMMIT released the locks

with_for_update(skip_locked=True) is how SQLAlchemy 2.0 spells it. read=True would give you FOR SHARE — not what you want.

And the loop around it. Note the back-off: a full batch means there is more waiting, so go straight round again; an empty batch means sleep rather than hammer the database.

MIN_SLEEP = 0.05
MAX_SLEEP = 1.0

async def run_relay(sessionmaker: async_sessionmaker, broker: Broker) -> None:
    sleep_for = MIN_SLEEP
    while True:
        async with sessionmaker() as session:
            handled = await drain_once(session, broker)

        if handled == BATCH:
            sleep_for = MIN_SLEEP
            continue                          # backlog remains — go straight round again

        sleep_for = min(sleep_for * 2, MAX_SLEEP) if handled == 0 else MIN_SLEEP
        await asyncio.sleep(sleep_for)

A fresh session per batch. That sleep is the latency floor for every event in the system — it only grows while the queue is genuinely empty, and collapses back the moment work appears.

Postgres LISTEN/NOTIFY can wake the relay the instant a row lands, collapsing that latency floor. It layers on top of polling and never replaces it — notifications are not durable, so anything sent while the relay is disconnected is simply lost. Polling is the guarantee; NOTIFY is the speed-up.

Approach B, if you need it

The lease claim is one statement: a sub-select that locks, wrapped in an UPDATE … RETURNING that stamps. The docs cover the sub-select case explicitly — "When a locking clause appears in a sub-SELECT, the rows locked are those returned to the outer query by the sub-query" — so the lock and the stamp cannot disagree.

WITH claimed AS (
    SELECT id FROM outbox_message
    WHERE published_at IS NULL
      AND (claimed_at IS NULL OR claimed_at < now() - interval '5 minutes')
    ORDER BY id
    LIMIT 100
    FOR UPDATE SKIP LOCKED
)
UPDATE outbox_message o
   SET claimed_at = now(),
       claimed_by = $1,
       attempts   = o.attempts + 1
  FROM claimed c
 WHERE o.id = c.id
RETURNING o.id, o.message_id, o.event_type, o.payload;

The claim commits with the transaction; the publish happens after. The five-minute clause is the reaper: expired leases simply become claimable again.

This needs two columns the DDL above does not have, and leaving them out of the main schema is deliberate — Approach A never touches them, and a column nobody writes is a column that will confuse the next person. Add them when you adopt B, not before:

ALTER TABLE outbox_message
    ADD COLUMN claimed_at timestamptz,
    ADD COLUMN claimed_by text;

Both nullable, both meaningless under Approach A. The cost of B is not really these two columns — it is that claimed_at is now a piece of state with a clock attached, and every reasoning step about the relay has to account for a lease that can expire while the worker holding it is alive and merely slow.

Incrementing attempts during the claim rather than on failure is deliberate: a row that kills the worker mid-publish still gets counted, so a poison message cannot loop forever undetected. Filtering on attempts < 10 then quarantines it instead of letting it block the queue.

The trap that eats messages

Never track progress with a cursor

It is tempting to drop the published_at flag and keep a high-water mark: WHERE id > last_seen_id. It is fast, and it silently loses messages.

id is assigned by nextval when the row is inserted, not when its transaction commits. Transaction T1 takes id 100 and stays open; T2 takes id 101 and commits. Your relay reads, sees 101, records last_seen_id = 101. T1 then commits — and row 100 becomes visible behind your cursor. It is never published, and nothing anywhere reports an error. The docs also guarantee gaps outright: "the value obtained by nextval is not reclaimed for re-use if the calling transaction later aborts… PostgreSQL sequence objects cannot be used to obtain 'gapless' sequences."

The nullable published_at column is immune to all of it. A row is owed until someone marks it done, whenever it happens to become visible. Cheap, boring, correct — and knowing why the clever version is wrong is a strong signal in an interview.

What you can now do

Write the table and the claim query from memory; justify the partial index, the FOR UPDATE, and the SKIP LOCKED separately; scale the relay horizontally without double-publishing; and answer the lock-duration follow-up with a default, a reason and a trigger to switch.

Name what is still broken

Three things this lesson deliberately did not fix. Naming them yourself, unprompted, reads as experience:

  • Ordering is gone. SKIP LOCKED guarantees it: workers take disjoint, out-of-order slices, so message 5 can hit the broker before message 4. That is the microservices.io drawback — "tricky to publish events in order" — and it is Lesson 05.
  • Duplicates are still yours to handle. The message_id column exists for it, but nothing consumes it yet. Lesson 03.
  • The table grows forever. Marking rows published keeps them. Lesson 06.

Check yourself

One attempt per question — guessing until it turns green is recognition, not recall.

  1. Two relay workers run the claim query with plain FOR UPDATE (no SKIP LOCKED). What happens?

    That is the no-locking failure. FOR UPDATE does prevent it — at the cost of throughput.

    That is NOWAIT. Plain FOR UPDATE waits rather than erroring.

    Correct — and say both halves. Safe, but serialised: B waits on the first locked row, then finds it no longer matches published_at IS NULL and drops it. Ten workers do one worker's work.

    No. Nothing distributes rows for you; that is exactly the job SKIP LOCKED does.

  2. Why is SKIP LOCKED acceptable here when the docs warn it gives an inconsistent view of the data?

    It is not append-only — published_at gets updated. And the inconsistency comes from skipping, not from writes.

    Exactly. The docs license precisely this case: "multiple consumers accessing a queue-like table". Correctness needs disjoint claims, not a complete view.

    Duration is irrelevant — a short transaction with an inconsistent view is still inconsistent. The workload is what makes it safe.

    The index affects which rows are cheap to find, not which are locked. Skipping happens at lock time regardless.

  3. The relay publishes to the broker inside the claiming transaction. What is the main cost?

    Right. Broker latency becomes database transaction duration: locks held longer, vacuum horizon pinned, a pool connection tied up if the broker hangs. It is still the right default — just know the price.

    Duplicates are possible either way. Commit can fail after a successful publish; that is at-least-once, and it is unavoidable.

    SKIP LOCKED is what stops that — other workers skip past and claim different rows.

    It cannot be. The broker is not a transaction participant — that was the whole point of Lesson 01.

  4. Why not replace published_at with a stored high-water mark (WHERE id > last_seen_id)?

    Gaps are real, but harmless on their own — skipping an id that never existed costs nothing. The lethal part is ordering.

    A bigint will not overflow in any timeframe you need to care about.

    Retry is a real consequence, but secondary. The primary failure is silent message loss.

    Yes — and this is the answer that impresses. nextval fires at insert, not at commit, so a long transaction's row becomes visible behind a cursor that has already moved past it. Never published, no error anywhere.

  5. What does WHERE published_at IS NULL on the index buy that a plain index on the same column would not?

    That is FOR UPDATE SKIP LOCKED. An index never provides mutual exclusion.

    Correct. A few backlog rows indexed instead of every row ever published — the claim query stays the same speed on day 1 and year 3.

    No constraint is being enforced; a partial index on a non-unique column enforces nothing.

    Locking always touches the heap — the docs note it may even cause a disk write.

Say it out loud

Whiteboard, no notes, 90 seconds: draw the outbox table (columns and the index), write the claim query, and talk through what each clause buys — then answer "how long do you hold the lock?" before anyone asks you. Then reveal and compare.

"The table is id, message_id, aggregate type and id, event type, jsonb payload, created_at, a nullable published_at, and attempts plus last_error for poison messages. The index is partial — on id, WHERE published_at IS NULL — so it only contains the backlog and the claim query never gets slower as history grows.

The relay polls: SELECT … WHERE published_at IS NULL ORDER BY id LIMIT 100 FOR UPDATE SKIP LOCKED. FOR UPDATE stops two workers taking the same row; without SKIP LOCKED that would be correct but serialised, since the second worker just blocks on the first locked row. SKIP LOCKED makes them skip past to rows nobody holds, so workers take disjoint slices and scale horizontally. The docs call it unsuitable for general work but right for multiple consumers on a queue-like table — which is exactly what this is.

I publish inside that transaction and commit, so the lock is the claim and a dead worker frees its rows automatically. The cost is an open transaction across a network call — bounded batch and a tight publish timeout keep it short. If broker tail latency became a problem I would switch to leasing: stamp claimed_at, commit, publish after, and accept a reaper for expired leases.

Either way it is at-least-once — publish can succeed and the commit fail. And the ordering is genuinely gone, because SKIP LOCKED hands out out-of-order slices by design."

Score the parts you dropped, not the wording. Dropping "without SKIP LOCKED it serialises" or the lock-duration trade-off is what costs you the follow-up.
