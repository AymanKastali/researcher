Lesson 07 · Transactional Outbox

Run It

Six lessons of design, all of it argued. This one puts Postgres and RabbitMQ in Docker, runs the relay and the consumer as real processes, and kills one of them with SIGKILL in the exact millisecond that matters.

The win for this lesson: you stop saying "the outbox gives you at-least-once" as a slogan and start saying it as something you have watched happen. By the end you can describe the crash window precisely — which line the process died on, what each of the three stores contained a second later, and what arrived twice.

Everything below is output from a run on this machine. Nothing in this lesson is reasoned from mechanism; where a number appears, it was measured. Versions: PostgreSQL 17.11, RabbitMQ 4.3.5 (Erlang 27), Python 3.13, SQLAlchemy 2.0.52, asyncpg 0.31.0, aio-pika 10.0.1.

Four moving parts

Two containers and three processes. The schema is Lessons 02, 03 and 05 with nothing added except a shipment table, so that "did the work happen twice?" is a question the database can answer.

CREATE TABLE outbox_message (
    id             bigint GENERATED ALWAYS AS IDENTITY PRIMARY KEY,
    message_id     uuid        NOT NULL DEFAULT gen_random_uuid(),
    aggregate_type text        NOT NULL,
    aggregate_id   text        NOT NULL,
    event_type     text        NOT NULL,
    payload        jsonb       NOT NULL,
    created_at     timestamptz NOT NULL DEFAULT now(),
    published_at   timestamptz,
    attempts       int         NOT NULL DEFAULT 0,
    last_error     text
);
CREATE INDEX outbox_unpublished_idx ON outbox_message (id) WHERE published_at IS NULL;

CREATE TABLE inbox_message (
    message_id   uuid PRIMARY KEY,
    processed_at timestamptz NOT NULL DEFAULT now()
);

CREATE TABLE shipment (                     -- the consumer's side effect
    id       bigint GENERATED ALWAYS AS IDENTITY PRIMARY KEY,
    order_id text NOT NULL
);

message_id is generated by the database, at insert time, in the business transaction. That matters more than it looks: it is the identity the consumer deduplicates on, so it has to be fixed before anything leaves the transaction. A uuid minted by the relay would be a new one on every retry.

The producer writes the business row and the event in one transaction. This is the entire pattern, and it is six lines:

async with engine.begin() as db:                       # one transaction
    order_id = (await db.execute(INSERT_ORDER, {"cents": 4200})).scalar_one()
    row = (await db.execute(INSERT_EVENT, {
        "agg": str(order_id),
        "etype": "order.paid",
        "payload": json.dumps({"order_id": order_id, "total_cents": 4200}),
    })).one()

The relay is Lesson 02's claim query wrapped in a loop, with Lesson 03's publisher confirms and mandatory turned on:

CLAIM = text("""
    SELECT id, message_id, aggregate_id, event_type, payload
    FROM outbox_message
    WHERE published_at IS NULL
    ORDER BY id
    LIMIT 100
    FOR UPDATE SKIP LOCKED
""")

channel = await conn.channel(publisher_confirms=True)

while True:
    async with engine.begin() as db:                   # transaction opens
        rows = (await db.execute(CLAIM)).mappings().all()
        for r in rows:
            await exchange.publish(                    # blocks until confirmed
                Message(json.dumps(r["payload"]).encode(),
                        message_id=str(r["message_id"]),
                        delivery_mode=DeliveryMode.PERSISTENT),
                routing_key=r["event_type"],
                mandatory=True,
            )
            await db.execute(MARK, {"id": r["id"]})
    await asyncio.sleep(POLL)                          # transaction committed

Read the transaction boundary carefully, because the whole lesson lives inside it. The publish happens during an open Postgres transaction, and the UPDATE that records the publish is only durable when that transaction commits — one poll's worth of rows later.

The consumer is Lesson 03's idempotent consumer: inbox row and work in one transaction, then ack.

async for message in it:
    async with engine.begin() as db:                   # one transaction
        claimed = await db.execute(CLAIM_ONCE, {"mid": message.message_id})
        if claimed.rowcount == 0:
            log("DUPLICATE — inbox has it, no work done")
        else:
            await db.execute(DO_WORK, {"order_id": body["order_id"]})
    await message.ack()                                # commit, THEN ack

It works

14:43:16.934 relay    row 1 confirmed by broker
14:43:16.937 relay    row 1 marked published
14:43:16.992 consumer processed  e734c311… order=1 redelivered=False

Commit to side effect in 166 ms, most of it waiting for the next poll. Three processes, two containers, one event. That is the baseline everything below is a deviation from.

The crash window, opened on purpose

There is exactly one instant in the relay loop where a crash is interesting: after the broker has confirmed the message and before the UPDATE is durable. Every description of the outbox pattern hand-waves at this window. Here it is, held open with a SIGKILL on the line between them.

await exchange.publish(...)                # the broker now has it, for good
log(f"row {r['id']} confirmed by broker")

os.kill(os.getpid(), signal.SIGKILL)       # <- the window

await db.execute(MARK, {"id": r["id"]})    # never runs
14:44:11.067 relay    row 1 confirmed by broker
14:44:11.067 relay    row 1 published — SIGKILL before UPDATE
relay exit=137

 id | still_unpublished        inbox | shipments
----+-------------------      -------+-----------
  1 | t                            1 |         1

One millisecond of window, and the two stores now disagree. RabbitMQ delivered the message and the consumer did the work — one inbox row, one shipment. Postgres rolled the relay's transaction back, so as far as the outbox is concerned the event was never published.

Now restart the relay. It is doing nothing clever; it runs the same claim query, and the row is still published_at IS NULL, so it is still a candidate.

14:44:13.401 relay    polling
14:44:13.456 relay    row 1 confirmed by broker
14:44:13.458 relay    row 1 marked published
14:44:13.458 consumer DUPLICATE e341130b… redelivered=False — inbox has it, no work done

 inbox | shipments
-------+-----------
     1 |         1
This is at-least-once, and it is not a bug

The event was delivered twice because the relay cannot make the broker and the database commit together — that is the dual-write problem from Lesson 01 reappearing one layer down, and it is unkillable. What the outbox does is not eliminate the second delivery. It moves the problem to a place where you have a transaction to fight it with.

The final count is the whole point: two deliveries, one shipment. The inbox row and the work committed together, so the duplicate found the door already locked.

Measured: the duplicate says redelivered=False

Look at the flag on the second delivery. It is False, exactly as it was on the first.

And it should be. From the broker's point of view this is not a redelivery — it is a new publish of a message it has never seen before, carrying an application-level message_id RabbitMQ attaches no meaning to. redelivered only ever covers the broker's own half: a delivery that was un-acked and handed out again.

So a consumer that branches on redelivered to decide whether to deduplicate is broken, and broken in the silent direction. The relay-side duplicate — the one the outbox actually manufactures — sails straight past it. Deduplicate on every message, unconditionally.

The same crash, one line earlier

Move the kill to before the publish and the outcome inverts. Nothing was sent, nothing was marked, and the restarted relay simply publishes it:

### A. WITH an outbox — SIGKILL before the publish
    14:50:34.026 producer committed order 1 + outbox row 1
    14:50:34.362 relay    row 1 claimed — SIGKILL before publish
    outbox row 1: unpublished=true
    --- restart the relay ---
    14:50:34.738 relay    row 1 confirmed by broker
    14:50:34.739 relay    row 1 marked published

Now the control. Same crash, same instant — but no outbox. The order is committed directly and the event published afterwards, which is what a service does before somebody teaches it this pattern:

async with engine.begin() as db:
    order_id = (await db.execute(INSERT_ORDER)).scalar_one()   # committed

os.kill(os.getpid(), signal.SIGKILL)                           # <- same window

await exchange.publish(...)                                    # never runs
### B. NO outbox — SIGKILL between the commit and the publish
    14:50:41.754 dualwrt  order 2 COMMITTED — money is taken
    14:50:41.754 dualwrt  SIGKILL before the publish

### final state
 orders | outbox_rows | shipments
--------+-------------+-----------
      2 |           1 |         1
Lesson 01, measured

Two orders paid. One shipment. Order 2 is committed, the customer has been charged, and no message describing it exists anywhere — not in the outbox, not in the broker, not in a log. There is nothing to retry, because nothing recorded the intent. That order is lost until a human reconciles it.

Order 1 took the identical SIGKILL at the identical point and survived, because its event was a row in the same transaction as the business fact. That contrast, in eight lines of output, is the entire argument for the pattern.

Two relays, one outbox

Lesson 02 claimed that FOR UPDATE SKIP LOCKED makes the relay safe to run more than once. Two processes, 500 events, both polling every 20 ms:

### writing 500 events
    500 committed
### starting two relays at once
    relay-A published 200 rows
    relay-B published 300 rows
    broker confirms total: 500

 outbox_rows | unpublished | inbox | shipments | orders_shipped_twice
-------------+-------------+-------+-----------+----------------------
         500 |           0 |   500 |       500 |                    0

500 confirms for 500 rows — not 501. The split is uneven (200 / 300) and that is expected: whoever gets to a batch first takes it, and SKIP LOCKED sends the other one past the locked rows instead of queueing behind them. Note what this does not show — the two relays were unsharded, so nothing here preserves per-aggregate order. That is what Lesson 05's shard filter is for.

What polling actually costs

Lesson 04 chose polling over CDC and admitted it had no number for the latency this buys. Here is the number. 120 events arriving as a trickle, one every 50 ms, measured from the business commit to the consumer's commit:

Poll intervalEnd-to-end latency, commit to side effect
50 msp50 34 ms · p95 63 ms · max 74 ms
200 msp50 118 ms · p95 216 ms · max 220 ms
1 sp50 558 ms · p95 1007 ms · max 1040 ms

Single-node containers on one laptop, no network, no load. Do not quote these as capacity numbers — quote the shape, which is exact and portable.

The relationship is the answer, not the milliseconds

In all three rows, p50 lands at half the poll interval and p95 lands at the poll interval. That is not a coincidence, it is arithmetic: an event committed at a uniformly random moment waits on average half a cycle for the next poll, and at worst a full one. Publishing and consuming cost single-digit milliseconds and vanish into the noise.

So the answer to "what latency does a polling relay give you?" is not a number you memorise, it is "about your poll interval, and I choose that." Which reframes the CDC argument from Lesson 04: you are not trading latency for operational cost, you are trading database load for latency, and the exchange rate is one you set.

This is also the sharpest argument for LISTEN/NOTIFY, still the unbuilt sidenote from Lesson 04. It removes the half-interval wait for the common case while leaving the poll as the safety net — you keep correctness from the poll and latency from the notification.

Name what is still not true

This ran, but it did not run everything. Be precise about the gap when you talk about it:

  • No failover was tested. The pipeline now runs against a three-node RabbitMQ cluster with a quorum replica on every node, so the code path is real — but no run here kills the queue leader under load, which is where Lesson 05's guarantee is actually stressed. The claim that quorum queues survive losing a node remains the vendor's, not ours.
  • No retention, no partitions. The bloat measurements from Lesson 06 were taken in SQL against a synthetic table, not against this pipeline over time.
  • The dead-letter hop was not watched end to end. The delivery-limit behaviour in Lesson 06 is measured; a counted-out message actually arriving on a bound DLQ, carrying its x-death array, is quoted from the docs rather than observed.
  • These milliseconds are one laptop. No network, no competing load. The shape of the latency result is arithmetic and portable; the numbers are not.

Check yourself

One attempt per question. Two of these reach back to earlier lessons on purpose.

  1. The relay is killed after the broker confirms the message and before the UPDATE commits. What is true a second later?

    Backwards on both halves. The UPDATE died with the transaction, and the consumer had already done the work before the relay was killed.

    A confirmed message is the broker's responsibility from that moment — that is what the confirm means. It was delivered, not discarded.

    Correct, and measured: still_unpublished = t alongside one inbox row and one shipment. The two stores disagree, which is exactly why the restart produces a duplicate.

    Half right — the row is unpublished — but the message was already delivered and acked before the kill landed.

  2. That duplicate arrives at the consumer. What does its redelivered flag say?

    The relay published twice, but the broker has no memory tying the two together. redelivered is not an application-level concept.

    Correct, and measured. It is a brand-new publish of a message RabbitMQ never saw, so the flag is False — which is why branching on it to decide whether to deduplicate is silently broken.

    message_id is an application property. RabbitMQ carries it and attaches no meaning to it — there is no dedup on it anywhere.

    Right answer, wrong reason, and the reason is what is being tested. The ack of the first copy is irrelevant; this is a different message.

  3. Two orders are paid, both processes die in the same window, and one shipment exists. Which order was lost, and why?

    Correct. The order committed, the publish never happened, and nothing anywhere records that a message was owed. There is nothing to retry, which is what makes it unrecoverable rather than merely late.

    That one survived. The rollback lost only the published_at mark, and the event row was still there for the restarted relay to find.

    Order of publishing is not what separated them. One had its event inside the business transaction and the other did not.

    The missing inbox row is the symptom, not the cause. No message ever arrived for the consumer to record.

  4. Two unsharded relays drained 500 rows and the broker logged 500 confirms. What does that demonstrate?

    Only the first half. The relays were deliberately unsharded, so two aggregates' events could interleave freely — nothing in this run constrains order.

    The split was 200 / 300, not even. Whoever reaches a batch first takes it, and SKIP LOCKED sends the other one past.

    Confirms tell the publisher the broker has the message. Exclusivity came from the row lock — SKIP LOCKED — in Postgres.

    Correct, and the discipline is the point. The experiment isolates one property; claiming the other from the same run is how you get caught.

  5. Reaching back to Lesson 04. Measured p50 was half the poll interval and p95 was the whole interval. Why that shape?

    Batching affects throughput, not this shape. The distribution comes from arrival time, and a batch of one shows the same thing.

    Correct. Uniform arrivals against a fixed cycle give a mean wait of half the interval and a worst case of one — so the latency of a polling relay is a number you choose, not one you discover.

    The publish and the confirm were single-digit milliseconds at every interval, which is exactly why the shape stayed constant as the interval changed.

    The claim lock lives only for the duration of one batch's transaction. It has no relationship to the sleep between polls.

  6. Reaching back to Lesson 03. Why must the consumer ack after its transaction commits rather than before?

    Prefetch bounds in-flight deliveries. Refilling sooner is a throughput effect, and it costs you no correctness.

    The count matters for poison messages, but losing it is not the failure here — losing the message is.

    Correct. The ack is the consumer's promise that the work is durable. Ack first and the broker drops its copy, so a crash before the commit destroys the only remaining record.

    Order is unaffected — the same consumer handles the same queue in the same sequence either way.

Say it from memory

Close the page. Ninety seconds, out loud: "walk me through what happens if your relay dies halfway through publishing."

There's exactly one window that matters: after the broker confirms the message and before the relay's UPDATE to published_at commits. If the process dies there, the two stores disagree — RabbitMQ has delivered the message and the consumer has already done the work, while Postgres rolled the relay's transaction back so the row is still unpublished.

Nothing recovers it cleverly. The relay restarts, runs the same claim query, and the row is still a candidate because published_at IS NULL — so it publishes it again. That's the duplicate, and it's unavoidable: the relay can't commit to Postgres and to the broker atomically, which is the dual-write problem one layer down. The outbox doesn't remove the duplicate, it moves the problem somewhere I have a transaction to fight it with — the inbox. Second delivery, the insert conflicts, no work runs. Two deliveries, one shipment.

One detail I'd volunteer: that duplicate arrives with redelivered=False. From the broker's point of view it's a brand-new publish, not a redelivery — the message_id is an application property RabbitMQ attaches no meaning to. So any consumer that only deduplicates when redelivered is true is broken, and broken silently. Deduplicate on every message.

The window in the other direction is safe. If it dies before the publish, nothing was sent and nothing was marked, so the restart just publishes it — late, not lost. That asymmetry is the whole pattern: I'd rather be duplicated than lost, because I can fix duplicated with a primary key. Without an outbox the same crash between the commit and the publish loses the event permanently — the order is paid and nothing anywhere records that a message was owed, so there's nothing to retry.

And the relay is safe to run more than once: FOR UPDATE SKIP LOCKED means two workers take disjoint batches. I ran two against 500 rows and got 500 confirms, not 501.

Scoring: the two costly omissions are failing to name the window precisely — between the confirm and the commit, not "somewhere in the middle" — and describing the duplicate as prevented rather than absorbed. Bonus for the redelivered trap, and for saying "late, not lost" about the other direction.
