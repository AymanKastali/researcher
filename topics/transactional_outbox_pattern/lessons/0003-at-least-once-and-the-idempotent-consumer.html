Lesson 03 · Transactional Outbox

At-Least-Once and the Idempotent Consumer

The other half of the pattern. Where every duplicate comes from, and the one transaction boundary that makes them harmless.

The win for this lesson: by the end you can enumerate every place a duplicate is born, state the difference between exactly-once delivery and exactly-once processing without flinching, write the inbox table and handler from memory, and say what your broker does and does not do for you. An outbox without this half is an incomplete answer, and interviewers know it.

Lessons 01 and 02 both ended on the same admission: at-least-once. Lesson 01 called it the price; Lesson 02 showed it survives both relay designs. This lesson is where you stop apologising for it and start engineering around it.

Where duplicates are born

Name all three. Candidates who name one have read a blog post; candidates who name three have thought about the system.

HopHow the duplicate happens
1 · Relay → broker The publish succeeds and the COMMIT that marks the row published then fails — or the worker dies in the gap. The row is still published_at IS NULL, so the next poll publishes it again. Unavoidable in both Lesson 02 approaches.
2 · Broker → consumer Redelivery. The consumer takes the message, does the work, and dies before acking. The broker sees an unacked message and hands it to someone else. This happens even if the relay published exactly once.
3 · Relay restart A relay that crashes mid-batch replays the whole batch, because the claim was never committed. Approach B's reaper does the same thing when a lease expires on a worker that actually did publish.

Notice that these are independent. Fixing one does nothing for the others — which is exactly why broker features that dedup hop 1 do not remove the need to handle hop 2.

The distinction that gets you marked correct

Delivery vs. processing

Exactly-once delivery is not achievable across a network. The sender cannot distinguish "the message was lost" from "the ack was lost", so it must either retry (risking a duplicate) or not retry (risking a loss). There is no third option.

Exactly-once processing is achievable, and is what people actually mean. It is built, not bought: at-least-once delivery plus an idempotent consumer. If an interviewer offers you "exactly-once", correct the word gently and then describe how you build the real thing. That exchange is worth more than the rest of the answer.

Idempotence, precisely

A handler is idempotent when running it twice leaves the same state as running it once. Two ways to get there, and you should reach for them in this order:

1. Make the operation naturally idempotent

Free, and no extra table. The test is whether the operation's result depends on the current state:

StatementIdempotent?
UPDATE orders SET status = 'shipped' WHERE id = $1 Yes. Assignment to an absolute value. Run it a thousand times.
UPDATE accounts SET balance = balance + 10 WHERE id = $1 No. Read-modify-write. Every replay moves the value.
INSERT INTO shipments (order_id, …) VALUES ($1, …) Only with a unique constraint on order_id. Then the duplicate raises instead of inserting, and the database is the dedup.

That last row is worth pausing on. A unique constraint on the business key is often all the idempotence you need, and it is stronger than a dedup table because it holds even against duplicates you never anticipated. Check for it before you build anything.

2. Record what you have processed

When the operation cannot be made naturally idempotent, remember the message. From the canonical statement of the pattern:

Make a consumer idempotent by having it record the IDs of processed messages in the database. […] After starting the database transaction, the message handler inserts the message's ID into the PROCESSED_MESSAGE table. Since the (subscriberId, messageID) is the table's primary key the INSERT will fail if the message has been already processed successfully. Pattern: Idempotent consumer — microservices.io

The inbox table

CREATE TABLE inbox_message (
    consumer_name text        NOT NULL,
    message_id    uuid        NOT NULL,
    processed_at  timestamptz NOT NULL DEFAULT now(),
    PRIMARY KEY (consumer_name, message_id)
);

Three columns. The composite primary key is the mechanism — it is not a modelling nicety.

Two things to defend:

  • message_id is the outbox's message_id, carried across the broker untouched. This is why Lesson 02 gave the outbox a message_id uuid separate from its bigint primary key: id is storage, message_id is the contract, and it is the contract that has to survive the trip.
  • consumer_name is in the key because a message usually has several independent consumers — billing, search indexing, email. Each must decide separately whether it has seen the message. Key on message_id alone and the first consumer to finish silently suppresses the message for everyone else.

The whole lesson in one boundary

Everything above is setup. This is the part that matters:

The dedup record and the side effect commit together

The inbox INSERT and the business write go in the same local transaction. One commit, both or neither.

Why it has to be that way — walk the alternatives and watch the dual-write problem reappear, this time on the consuming side:

OrderWhat goes wrong
Insert the id, commit, then do the work Message loss. Die in the gap and the message is permanently marked processed while nothing happened. Redelivery finds the row and drops it. Nothing anywhere reports an error — the worst failure mode there is.
Do the work, commit, then insert the id Duplicate work. Not fatal, but you built a dedup table and it does not dedup. You have paid for a guarantee you do not have.
Both in one transaction Correct. A crash rolls back both, redelivery replays cleanly, and the second attempt is genuinely the first.

It is the same argument as Lesson 01, reflected. The outbox exists because you cannot atomically write to a database and a broker. The inbox exists because you cannot atomically write to a database and ack a broker. Both are solved the same way: put the second write into the first database, and make it one commit.

The consumer in Python

import json
from uuid import UUID

from aio_pika.abc import AbstractIncomingMessage
from sqlalchemy.dialects.postgresql import insert
from sqlalchemy.ext.asyncio import AsyncSession

CONSUMER = "billing"

async def handle(session: AsyncSession, message: AbstractIncomingMessage) -> bool:
    """Process a message exactly once. Returns False if it was a duplicate."""
    async with session.begin():                       # ONE transaction for both writes
        claimed = await session.execute(
            insert(InboxMessage)
            .values(
                consumer_name=CONSUMER,
                message_id=UUID(message.message_id),  # the outbox row's uuid, intact
            )
            .on_conflict_do_nothing()                 # ← seen before? no rows affected
        )
        if claimed.rowcount == 0:
            return False                              # already processed; ack and move on

        await apply_business_effect(session, json.loads(message.body))

    return True                                       # both writes committed together

on_conflict_do_nothing() is Postgres' ON CONFLICT DO NOTHING, imported from the postgresql dialect rather than the generic sqlalchemy namespace. Checking rowcount is what turns a swallowed conflict into a decision. Catching a raised IntegrityError works too, but it poisons the transaction and you have to roll back to a savepoint — this is cleaner.

Now the loop around it, where the second ordering rule lives:

from aio_pika.abc import AbstractQueue

async def consume(sessionmaker: async_sessionmaker, queue: AbstractQueue) -> None:
    async with queue.iterator() as messages:          # manual ack — never no_ack=True
        async for message in messages:
            async with sessionmaker() as session:
                await handle(session, message)        # commits, or raises

            await message.ack()                       # only after the commit succeeded

If handle raises we never reach the ack, so the delivery stays unacknowledged and RabbitMQ requeues it when the channel closes. That is the behaviour you want — and it is also why the delivery limit matters, because a message that always raises would otherwise loop forever.

Commit, then ack. Never the reverse.

Ack first and you have told the broker to forget the message while your own transaction may still fail. Nothing will ever redeliver it: the work is lost with no error. Commit first and the worst case is that the ack fails, the broker redelivers, and the inbox catches it on the next pass. The asymmetry is total — one ordering risks a duplicate you have already defended against, the other risks silent loss.

The relay had the mirror-image rule: publish, then mark. Same reasoning both times — always fail toward the duplicate.

What RabbitMQ gives you — and what it does not

Broker pinned: RabbitMQ. That simplifies this section, because the answer is no deduplication at all — and the docs say so outright rather than burying it:

Due to this behavior, consumers must be prepared to handle redeliveries and otherwise be implemented with idempotence in mind. RabbitMQ — Consumer Acknowledgements and Publisher Confirms

There is no broker feature to reach for instead, so the inbox table is not belt-and-braces — it is the entire mechanism. Do not be tempted by the redelivered flag, either. It tells you a delivery might be a repeat; it never tells you whether you already processed it, and the docs warn that "a consumer can receive a message that was previously delivered to another consumer." You cannot deduplicate on a boolean.

Other brokers do offer publish-side dedup. SQS FIFO: "If you retry the SendMessage action within the 5-minute deduplication interval, Amazon SQS doesn't introduce any duplicates into the queue" — a fixed five minutes, not a setting. NATS JetStream: "For two minutes after a message is stored, the server turns away a second message that carries the same Nats-Msg-Id header" — two minutes is the default and the window is configurable. Worth a sentence in an interview, but note what they are: they dedup the send, inside a window shorter than a real outage, and neither touches redelivery. Even there the inbox stays. RabbitMQ just makes the choice for you.

Four consumer settings that are not optional

SettingWhy, in the docs' words
Manual acknowledgement
never auto-ack		 Auto-ack acks on delivery, before your handler has run: "if consumers's TCP connection or channel is closed before successful delivery, the message sent by the server will be lost. Therefore, automatic message acknowledgement should be considered unsafe." It quietly converts your at-least-once pipeline into at-most-once.
Prefetch
basic.qos		 "The value defines the max number of unacknowledged deliveries that are permitted on a channel." Leave it unbounded and one crashed consumer requeues its entire in-flight backlog at once. The docs suggest "values in the 100 through 300 range usually offer optimal throughput."
Quorum queues They "should be considered the default choice when needing a replicated, highly available queue", and they change what a publisher confirm means: for quorum queues the ack arrives only once "a quorum replicas have accepted and confirmed the message to the elected leader."
Delivery limit + a DLX Quorum queues count redeliveries in an x-delivery-count header, and since RabbitMQ 4.0 "the delivery limit for quorum queues defaults to 20." Past it, "the message will be dropped (removed) or dead-lettered (if a DLX is configured)." Read that as: configure the dead-letter exchange, or the default is deletion.

The trap on the relay side

Lesson 02's relay called await broker.publish(...) and moved on. On RabbitMQ that one line hides two decisions, and either of them left at its default turns your relay into a shredder.

First, the publish has to wait for a confirm. Without confirm.select publishing is fire-and-forget: the call returns, you set published_at, and the message may never have reached the broker. With confirms on, the ack means something strong — "for persistent messages routed to durable queues, this means persisting to disk." In aio-pika publisher_confirms=True is the channel default and exchange.publish() returns the confirmation, so check it rather than assuming it.

A confirm does not mean the message reached a queue

The docs, precisely: "For unroutable messages, the broker will issue a confirm once the exchange verifies a message won't route to any queue (returns an empty list of queues)." And unroutable is not an error by default — "the publisher set the mandatory message property to false (this is the default), the message is discarded."

Hold those two against your relay. One typo in a routing key, or a queue nobody declared: the exchange routes the message nowhere, discards it, and confirms it to you anyway. Your relay marks the row published. The outbox now reports one hundred per cent delivery while every message goes in the bin — and the outbox was supposed to be the component that made loss impossible.

Publish with mandatory=True and treat a returned message as a failed publish, leaving published_at NULL so the row is retried; or bind an alternate exchange to catch strays. Doing neither is the most expensive default in this lesson.

One correction worth carrying, because it cuts the other way. That quoted default is the AMQP protocol's. Your client library may not share it — and this one does not: aio-pika 10.0.1 declares mandatory: bool = True on Exchange.publish (checked in aio_pika/exchange.py and abc.py), so it is already on unless you switch it off. Set it explicitly anyway. You are stating an intention that a library upgrade must not silently reverse, and in an interview "I never rely on a client default for a durability property" is the stronger sentence.

import json

from aio_pika import DeliveryMode, Message
from aio_pika.abc import AbstractExchange
from pamqp.commands import Basic

async def publish(exchange: AbstractExchange, row: OutboxMessage) -> None:
    """Publish one outbox row, or raise. Raising leaves published_at NULL."""
    confirmation = await exchange.publish(
        Message(
            body=json.dumps(row.payload).encode(),
            message_id=str(row.message_id),        # the consumer's dedup key
            type=row.event_type,
            content_type="application/json",
            delivery_mode=DeliveryMode.PERSISTENT, # pointless without a durable queue
        ),
        routing_key=f"{row.aggregate_type}.{row.event_type}",
        mandatory=True,                            # unroutable -> raises, not silence
        timeout=5.0,                               # bounds Lesson 02's open transaction
    )
    if not isinstance(confirmation, Basic.Ack):
        raise RuntimeError(f"broker did not ack {row.message_id}")

This is the body of Lesson 02's broker.publish, made honest. Every raise path leaves the row unpublished, so Approach A's transaction rolls back and the next poll retries it — the duplicate you are defended against, never the loss you are not. Note where message_id lands: AMQP's standard message_id property, which is exactly what the consumer's inbox will key on.

The one duplicate you cannot roll back

The inbox works because the dedup record and the effect share a transaction. That argument collapses the moment the effect leaves the database — sending an email, charging a card, calling a partner API. ROLLBACK does not un-send an email.

Two honest answers, and having them ready is a mark of experience:

  • Push idempotence to the remote side. Send a stable idempotency key — your message_id again — and let the provider collapse the retry. This is exactly why payment APIs ask for one.
  • Order the work so the duplicate is the cheap failure. Commit local state first, then make the external call from a follow-up step that can be safely retried. You have now reinvented the outbox: the external call becomes another row in another outbox table. Say that out loud — noticing the pattern recurring is the point.
What you can now do

Enumerate the three sources of duplicates; separate exactly-once delivery from exactly-once processing and say why one is impossible; write the inbox DDL and handler from memory; justify the single transaction and the commit-then-ack ordering; and configure RabbitMQ so that neither an unroutable publish nor an auto-ack quietly eats a message.

Name what is still broken

  • The inbox grows forever, exactly like the outbox. It needs a retention policy tied to your maximum plausible redelivery delay — delete rows older than that and duplicates beyond it slip through. Lesson 06.
  • Ordering is still gone. Idempotence makes replays harmless; it does nothing about message 5 arriving before message 4. A handler can be perfectly idempotent and still apply a stale update over a fresh one. Lesson 05.
  • A poison message now fails in two places — the relay cannot publish it, or the consumer cannot process it. Different queues, different escape hatches. Lesson 06.

Say it out loud

Whiteboard, no notes, 90 seconds. The prompt is: "your outbox is at-least-once — so what?" Cover where duplicates come from, the delivery/processing distinction, the inbox table, the transaction boundary, the ack ordering, and the RabbitMQ settings that stop a message vanishing. Then reveal and score what you dropped.

"Duplicates come from three places. The relay can publish and then fail to mark the row published, so it republishes. The broker redelivers anything a consumer did not ack. And a relay that dies mid-batch replays that batch on restart. They are independent, so fixing one does not help the others.

Exactly-once delivery isn't achievable — the sender can't tell a lost message from a lost ack, so it either retries and risks duplicates or doesn't and risks loss. What is achievable is exactly-once processing: at-least-once delivery plus an idempotent consumer.

First I check whether the handler is already idempotent — setting a status is, adding to a balance isn't — or whether a unique constraint on the business key gives it to me free. If not, I add an inbox table keyed on consumer name plus message id, where message id is the one the outbox row generated and carried across the broker. Consumer name is in the key because several consumers see the same message and each has to dedup independently.

The handler inserts the id with ON CONFLICT DO NOTHING and does the business write in the same transaction. If rowcount is zero it's a replay, and I ack and drop it. Splitting those into two commits recreates the dual-write problem on the consumer side — insert-first loses messages silently, work-first duplicates.

Then I commit and only then ack. Acking first means a failed commit loses the message with nothing to redeliver it. Always fail toward the duplicate.

RabbitMQ contributes nothing here — no core deduplication, and the docs say plainly that consumers must be implemented with idempotence in mind. So the inbox isn't a backstop, it's the mechanism. On the consumer: manual acks, because auto-ack is documented as unsafe and turns at-least-once into at-most-once; a bounded prefetch; and quorum queues with the delivery limit and a dead-letter exchange, so a poison message leaves the queue instead of looping twenty times and being silently deleted.

On the relay I publish with confirms and mandatory set. An unroutable message gets confirmed anyway and then discarded, so without mandatory the outbox would report perfect delivery straight into a bin. The outbox row's message_id goes in the AMQP message_id property — that is what the inbox keys on."

Score the parts you dropped, not the wording. The three most costly omissions are the single transaction, commit-then-ack, and "a confirm does not mean it was routed".
