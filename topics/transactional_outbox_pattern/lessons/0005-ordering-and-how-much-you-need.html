Lesson 05 · Transactional Outbox

Ordering, and How Much You Need

Three lessons have ended by deferring this one. The fix is not a cleverer query — it is refusing the requirement you were handed, then buying the smaller one cheaply.

The win for this lesson: by the end you can answer "how do you keep events in order?" without promising something you cannot deliver. You will separate the three different requirements that hide behind that one word, name the four places order dies between a business transaction and a side effect, and buy per-aggregate order end to end for a price you can state.

Ordering is named in the mission as one of the failure modes that bites in production, and it is where a confident answer separates from a rehearsed one. Most candidates say "use a partition key". That is a third of the answer, and the least interesting third.

Ask what "in order" means before you fix it

Three requirements travel under one word. They have wildly different prices, and the person asking usually has not decided which one they want.

What is being asked forWhat it costs
Global total order. Every event in the system delivered in one agreed sequence — order-7 paid before user-3 registered because it committed first. Ruinous. One publisher, one queue, one consumer, no concurrency anywhere in the pipeline. You have built a single-threaded system with extra steps. Almost nobody needs this, and nobody who asks for it has costed it.
Per-aggregate order. Order 42's paid arrives before order 42's shipped. Order 42 and order 99 have no relationship at all. Cheap, and nearly always the real requirement. Concurrency is preserved across aggregates and given up only within one — which is where the business logic was already serial.
None. Each event is an independent fact: a metric, an audit line, a notification. Nothing about applying one depends on another having landed. Free. Do not spend anything on this case, and notice how much of your event traffic is actually in it.
The first move is a question, not a mechanism

"Which events actually need to be ordered relative to each other?" converts an impossible problem into a routing problem. If the answer is "events about the same order", you have per-aggregate ordering, and the rest of this lesson delivers it.

An interviewer asking about ordering is usually probing whether you will over-engineer. Naming global order as available-but-ruinous, and then declining it, is the answer.

Four places order dies

Between "the business transaction committed" and "the side effect happened", ordering is lost four separate times. Fixing three of them and missing the fourth buys nothing, which is why the partition-key answer on its own is not enough.

WhereWhat happens
1. At insert id is assigned by nextval when the row is inserted, not when the transaction commits. A slow transaction takes a low id and commits late, so id order is not commit order. Lesson 02 planted this; it is demonstrated below.
2. At claim The docs are explicit that sorting happens before locking — "It is possible for a SELECT command running at the READ COMMITTED transaction isolation level and using ORDER BY and a locking clause to return rows out of order. This is because ORDER BY is applied first." A SKIP LOCKED batch is a disjoint slice, not the oldest N.
3. At publish RabbitMQ's ordering promise is scoped to one channel: "When publishing on a single channel, messages are enqueued in publishing order in every queue they are routed to." Two relay workers are two channels, so the promise does not apply between them.
4. At consume "Multiple active consumers on the same queue: the broker still dequeues in FIFO, but any redelivery can change order." And even with one consumer, the docs are blunt about concurrency: "once dispatched, concurrent processing of deliveries will result in a natural race condition between the threads doing the processing."

Sources, in order: PostgreSQL — SELECT, The Locking Clause; RabbitMQ — Queues, "Message ordering" and "When messages can be reordered"; RabbitMQ — Consumers.

A prefetch of 1 is not an ordering fix — but it is half of one

On its own it only bounds one channel to one unacknowledged delivery. It says nothing about the three other consumers attached to the same queue. You would pay the full throughput price of serial processing and still not own the guarantee.

The other half is the part the docs leave open. "Any redelivery can change order" does not say how, so it was worth asking the broker directly. Publish 1 2 3 4 5 into an empty quorum queue, reject message 1 once with requeue, and watch what arrives:

prefetch=1   ->  1  1* 2  3  4  5      quorum and classic alike
prefetch=2   ->  1  2  1* 3  4  5      quorum
prefetch=5   ->  1  2  3  4  5  1*     both
                                       (* = redelivered flag set)

The requeued message goes back to the head of the queue, not the tail. It is not the requeue that reorders anything — it is the messages already in flight, which the broker has handed out and will not take back. The displacement is the prefetch window. Set prefetch to 1 and the guarantee survives a retry; set it to 20 and a single failure moves an event twenty places.

The experiment worth running once

Failure 1 is the one people nod along to without believing. It is worth seeing. Two transactions write events for the same order; the first one is slow.

-- session A                       -- session B (starts one second later)
BEGIN;
INSERT INTO outbox_message
  (..., event_type) VALUES (..., 'paid');
                                   INSERT INTO outbox_message
                                     (..., event_type) VALUES (..., 'shipped');
-- still open, six seconds                                   -- commits immediately
COMMIT;

Run against PostgreSQL 17.11 in Docker while writing this lesson, using Lesson 02's table unchanged. A is inserted first and commits last.

A relay polling in the gap — exactly what your relay does, every 50 milliseconds — sees this:

 id | event_type
----+------------
  8 | shipped

-- and only after A finally commits:

 id | event_type
----+------------
  7 | paid
  8 | shipped

Row 7 was created first and became visible second. The relay published shipped for an order it had never announced as paid.

Now run the same race, but have each transaction touch the order row first — an UPDATE orders SET status = … before the outbox insert, which is what a real handler does anyway:

 pid | wait_event_type |  wait_event   | q
-----+-----------------+---------------+-------------------------------
 243 | Lock            | transactionid | UPDATE orders SET status='ship…

 id | event_type
----+------------
  9 | paid
 10 | shipped

B blocked on A's row lock for the whole six seconds. Ids and commit order agree, and nothing was ever visible out of sequence.

Why per-aggregate order is nearly free

Writes to one aggregate already serialise, because they contend on that aggregate's own row. That is not a lucky side effect — it is the definition of an aggregate: a consistency boundary. Within that boundary, id order is commit order.

Global order has no such row to contend on, which is exactly why it is unbuyable at any reasonable price and per-aggregate order is nearly free. Say this in an interview and you have explained the whole trade-off from one mechanism.

The precondition is worth stating out loud, because it is where it breaks: this holds only if writes to the aggregate genuinely touch a shared row. Two handlers that append events for order 42 without ever locking order 42 get no ordering from anything.

Fixing the relay: shard, do not lock

The relay must never hand two workers events for the same aggregate. The tempting fix is an advisory lock per aggregate, right in the claim query — Postgres offers exactly the primitive, "locks that have application-defined meanings", released automatically at transaction end.

SELECT * FROM outbox_message
WHERE published_at IS NULL
  AND pg_try_advisory_xact_lock(
        ('x' || md5(aggregate_id::text))::bit(64)::bigint)   -- looks right
ORDER BY id
LIMIT 100
FOR UPDATE SKIP LOCKED;

Do not ship this. The reason is in the plan below.

Verified: the lock fires on rows you never claim

A WHERE clause is evaluated before LIMIT can apply, so the lock function runs on every candidate row — and transaction-level advisory locks are held until commit. One worker asking for a single row silently locks every aggregate in the backlog, and the other workers get nothing.

Measured, not reasoned. EXPLAIN ANALYZE with LIMIT 1 against a six-row backlog spanning two aggregates:

Limit (actual rows=1 loops=1)
  ->  LockRows (actual rows=1 loops=1)
        ->  Sort (actual rows=1 loops=1)
              ->  Bitmap Heap Scan on outbox_message (actual rows=6 loops=1)
                    Recheck Cond: (published_at IS NULL)
                    Filter: pg_try_advisory_xact_lock(...)

One row returned, six rows filtered, two advisory locks held. A second worker running the identical query concurrently claimed zero rows.

So do not make ownership dynamic. Make it static: hash the aggregate id into a shard, and give each relay worker its own shards. A given aggregate then belongs to exactly one worker by arithmetic, with no coordination at all.

SELECT * FROM outbox_message
WHERE published_at IS NULL
  AND abs(hashtext(aggregate_id::text)) % :worker_count = :worker_index
ORDER BY id
LIMIT 100
FOR UPDATE SKIP LOCKED;

SKIP LOCKED stays — it still protects against two copies of the same worker overlapping during a rolling deploy. Ordering now comes from the shard filter, not from the lock.

Two honest caveats, both worth volunteering before you are asked. Shards are uneven: in the six-row fixture above, both aggregates hashed into shard 0 of 2, leaving the other worker idle. And changing worker_count reassigns aggregates mid-flight, so a scale-up needs the outbox drained first — trading an operational chore for the coordination you just avoided.

hashtext() is immutable and stable within a major version, but it is an internal function and is not in the documented function list. If that bothers you, an md5-derived key is documented and stable across versions; the only consequence of a hash changing under you is a transient reshard, not corruption.

Fixing the broker hop

The shard the relay computed is the routing key. Publish it, bind one queue per shard, and the per-aggregate stream now has exactly one queue to travel through.

Do not compute the shard twice. A hash function in SQL and a matching one in Python is a coupling that looks harmless and is not: the two must agree on every input forever, and the day they disagree an aggregate silently splits across two queues and loses its order with no error anywhere. Let the database compute it once, as a stored generated column, and have the publisher read it:

shard smallint NOT NULL GENERATED ALWAYS AS
                          (hashtext(aggregate_id) & 3) STORED

Legal because hashtext() is immutable — a generated column will not accept anything less. The bitmask replaces % deliberately: hashtext returns a signed int, and abs() of the most negative one overflows. Masking requires a power-of-two shard count, which is the trade.

async def publish(exchange: AbstractExchange, row: OutboxMessage) -> None:
    await exchange.publish(
        Message(
            body=json.dumps(row.payload).encode(),
            message_id=str(row.message_id),          # consumer dedup key, Lesson 03
            delivery_mode=DeliveryMode.PERSISTENT,
        ),
        routing_key=f"{row.event_type}.s{row.shard}",   # read, never recomputed
        mandatory=True,                              # never rely on the default, Lesson 03
    )

One implementation, in the one place that sees every insert. The shard is now as durable as the row, which also means a reshard is a migration you can see rather than a deploy that quietly changes an answer.

One queue per shard is not yet enough, because several consumers can attach to one queue. RabbitMQ has the exact primitive: "Single Active Consumer (SAC) makes it possible to only have one consumer at a time consuming from a queue. If the active consumer is cancelled or disconnects, another registered consumer takes its place." The docs name our use case outright — "Consuming with only one consumer is useful when messages must be consumed and processed in the same order they arrive in the queue."

queue = await channel.declare_queue(
    "order.3",
    durable=True,
    arguments={
        "x-queue-type": "quorum",           # Lesson 03's choice, unchanged
        "x-single-active-consumer": True,   # one consumer at a time; the rest wait
    },
)

Available on classic and quorum queues. Not on streams over AMQP 0-9-1 — the docs say that attempt "will not work". The waiting consumers are not idle capacity going to waste; they are your failover.

SAC gives you one consumer, not one thing at a time

Your process is still free to pull ten deliveries and hand them to ten coroutines. The docs are explicit that ordered dispatch is where the guarantee stops: "once dispatched, concurrent processing of deliveries will result in a natural race condition between the threads doing the processing." With SAC, the correct handler is the sequential async for loop from Lesson 03 — awaited one message at a time, no gather, no task group.

The escape hatch: make order stop mattering

Everything above buys order by removing concurrency somewhere. There is a cheaper answer for a large class of events: carry a per-aggregate version and let the consumer discard what it has already moved past. Out-of-order delivery becomes self-correcting rather than prevented.

The version is assigned in the same transaction as the business write, so it inherits the serialisation the aggregate row already provides — the mechanism verified above, reused.

async def handle(session: AsyncSession, message: AbstractIncomingMessage) -> bool:
    """Extends Lesson 03's inbox consumer with a per-aggregate version gate."""
    event = json.loads(message.body)

    async with session.begin():                       # still ONE transaction
        claimed = await session.execute(
            insert(InboxMessage)
            .values(consumer_name=CONSUMER, message_id=UUID(message.message_id))
            .on_conflict_do_nothing()
        )
        if claimed.rowcount == 0:
            return False                              # duplicate, Lesson 03

        advanced = await session.execute(
            insert(AggregateCursor)
            .values(
                consumer_name=CONSUMER,
                aggregate_id=UUID(event["aggregate_id"]),
                last_version=event["version"],
            )
            .on_conflict_do_update(
                index_elements=["consumer_name", "aggregate_id"],
                set_={"last_version": event["version"]},
                where=AggregateCursor.last_version < event["version"],   # ← the gate
            )
        )
        if advanced.rowcount == 0:
            return True                               # stale event; drop it, ack it

        await apply_business_effect(session, event)

    return True

Same shape as Lesson 03 — a conditional insert whose rowcount is the decision — applied twice for two different questions. The inbox asks "have I seen this message?"; the cursor asks "have I already moved past this state?"

This only works for state-carrying events

If the event says "order 42 is now shipped", skipping a stale one is correct: the newest state already includes everything the older one would have told you.

If it says "add 5 to the balance", every event must be applied exactly once and in sequence — a delta is meaningless out of order and catastrophic when dropped. For delta events you are back to the ordering machinery above, and the better fix is usually to stop emitting deltas.

Knowing which kind of event you are designing, and saying so unprompted, is the answer that marks someone who has done this.

The ladder, priced

Say this out loud and you have answered the whole question, because each rung buys order and pays for it in the same currency.

RungOrder bought · concurrency paid
Nothing No guarantee at all · full parallelism everywhere. Correct for independent facts, and that is more of your traffic than you think.
Version gate on the consumer Stale events discarded, newest state wins · nothing given up. Works only for state-carrying events.
Shard the relay, one queue per shard, SAC Per-aggregate order end to end · serial within a shard, parallel across shards. This is the working answer.
One queue, one consumer, one relay worker Something close to total order · all concurrency, and you still do not get true commit order without CDC. Refuse this rung and explain why.
What you can now do

Separate global from per-aggregate from unordered, and make the asker choose; name the four places order dies and cite the two doc sentences that prove two of them; explain from the aggregate row lock why per-aggregate order is nearly free and global order is not; reject the advisory-lock claim query with the plan that condemns it; specify shard-plus-SAC end to end; and offer the version gate as the cheaper answer where events carry state.

Measured: the ladder, checked against a real pipeline

Everything above is a design argument. Here it is run — Postgres 17.11 and a three-node RabbitMQ 4.3.5 cluster, 23 aggregates × 20 events, eight concurrent writers. The producer bumps customer_order.version under the aggregate row lock, so the version is the commit order and the consumer's arrival order can be compared against it. An ordering violation is any aggregate where a later arrival carries a smaller version.

Configuration, 460 events each timeOrdering violations
Sharded, one active consumer per shard, prefetch 20, no failures 0
The same, with 5% of first deliveries rejected and requeued 15, across 12 aggregates
The same again, with prefetch 1 0
Unsharded, one queue, three parallel consumers, no failures 0
Unsharded, three parallel consumers, 5% requeued 2, across 2 aggregates

Every run published all 460 rows and processed all 460 exactly once — this is purely about order. The producer-side check (per aggregate, outbox id order versus commit order) was 0 in every run: the row lock does its job, always.

Single active consumer is not enough on its own

Row two is the result worth carrying. The recommended configuration — shard the relay, one queue per shard, single active consumer — lost per-aggregate order the moment retries entered the picture, and it lost it at a 3% rate. Nothing was misconfigured; the only change was a handler that sometimes fails.

Row three says why, and the requeue probe earlier in this lesson had already predicted it: the requeued message returns to the head, and what displaces it is the consumer's own prefetch buffer. SAC guarantees one consumer. It does not guarantee one message in flight, and order needs both.

Note also that the unsharded control is not reliably wrong — 0 violations in one run, 2 in another. That is the dangerous property, not a reassuring one: a fan-out that loses order 0.4% of the time passes every test you write and fails in production.

And the thing the pattern does not buy, on the same clean run: checked for global order across all aggregates, the sharded pipeline showed 185 inversions. Per-aggregate order held perfectly while total order was thoroughly scrambled. That is not a defect. That is the deal.

Name what is still broken

  • Prefetch 1 is a throughput decision you now have to defend. The measured fix for row two costs you pipelining on every ordered shard. More shards is the compensation, and nobody has measured what that costs.
  • Nobody is watching any of this. A sharded relay has a per-shard backlog, and the health metric is still the age of the oldest unpublished row — now with a GROUP BY. Lesson 06.
  • One stuck aggregate now blocks a whole shard. Serialising a shard means a poison message stops every aggregate that hashes into it. The delivery limit and dead-letter exchange from Lesson 03's table are what stop that, and they need configuring. Lesson 06.
  • Two tables to prune, not one. The aggregate cursor joins the outbox and the inbox as state that grows and that nobody owns. Lesson 06.

Check yourself

One attempt per question — guessing until it turns green is recognition, not recall. Two of these reach back to earlier lessons on purpose; spaced retrieval is the point.

  1. A stakeholder says "the events must arrive in order". What is the first thing you say?

    A queue is FIFO, but that guarantee dies at the first requeue or second consumer — and it says nothing about how the two events reached the queue.

    That is part of the eventual answer, offered before knowing the requirement. If the true need is global order, routing keys do not deliver it; if it is none, you just spent money for nothing.

    Correct. Global, per-aggregate and none have wildly different prices, and the asker has usually not chosen. Scoping the requirement is the move that turns an impossible problem into a routing problem.

    CDC buys commit order at the source, and Lesson 04 showed it is lost again downstream. It is also not a decision to make before knowing what order is needed.

  2. Why is per-aggregate ordering cheap when global ordering is not?

    Volume is not the mechanism. A hot aggregate with thousands of events still gets ordering; a rare global event still cannot.

    Exactly. The aggregate is a consistency boundary, so concurrent writers contend on the same row and commit in sequence — id order becomes commit order inside the boundary. Global order has no such row, which is precisely why nothing makes it cheap.

    The sequence behind the identity column is global to the table. Nothing about it is per-aggregate.

    Routing gets a stream into one queue, which helps — but it cannot repair order that was already lost upstream at claim or publish.

  3. Why does calling pg_try_advisory_xact_lock in the claim query's WHERE clause starve the other relay workers?

    Advisory locks never escalate — they are a separate namespace with application-defined meaning and no relationship to table locks.

    The transaction-level variant is released at commit; that is the whole point of the xact form. The session-level one behaves as you describe, which is a good reason to avoid it here.

    They coexist without conflict. SKIP LOCKED concerns row locks; the advisory lock is separate — and both were held at once in the measured plan.

    Correct, and the plan proves it: one row returned, six rows filtered, two aggregates locked to end of transaction. A concurrent worker claimed nothing at all.

  4. You have one queue per shard with single active consumer enabled. What can still reorder your per-aggregate stream?

    Correct. SAC guarantees ordered dispatch to one consumer and stops there — the docs call concurrent processing "a natural race condition between the threads". Await one message at a time.

    Prefetch alone is fine. It controls how many deliveries are in flight, and they still arrive in order — what breaks the guarantee is processing them at the same time.

    That is exactly what SAC prevents. The second consumer registers and waits to be promoted rather than consuming.

    Sharding already stopped that: one aggregate maps to one shard, so only one worker ever publishes its events.

  5. Reaching back to Lesson 03. The version gate drops a stale event. What must the consumer do with that delivery?

    Requeueing guarantees an infinite loop: it will be just as stale next time, and it reorders the queue on the way back in.

    Correct. "Deliberately skipped" is a successful outcome, not a failure. Same rule as a duplicate caught by the inbox — ack it and move on, because the work it represents is genuinely done.

    A dead-letter is for messages you could not handle. You handled this one by correctly deciding it needed no effect.

    That eventually trips the delivery limit and dead-letters a message that was never a problem, while pinning the queue meanwhile.

  6. Reaching back to Lesson 02. After sharding, why keep FOR UPDATE SKIP LOCKED in the claim query at all?

    The partial index is chosen because of the WHERE published_at IS NULL predicate. Locking has nothing to do with it.

    Evaluation order works against you here, as the advisory-lock plan showed. The locking clause does not control it.

    Correct. Sharding stops two different workers colliding; nothing stops the old and new instance of the same shard running together mid-deploy. Locking is still what makes claims disjoint.

    The docs say the opposite — ORDER BY is applied before locking, so the clause can hand rows back out of order.

Say it from memory

Close the page. Ninety seconds, out loud: "how do you guarantee your events are processed in order?" Answer it the way you would to someone who has operated this.

First I'd ask which events need ordering relative to which. Global total order across the system is buyable but ruinous — one publisher, one queue, one consumer, no concurrency left anywhere — and almost nobody actually needs it. The real requirement is nearly always per-aggregate: order 42's events in sequence, with order 99 unrelated.

That distinction isn't arbitrary, it comes from a mechanism. Writes to one aggregate contend on that aggregate's row, so they commit in sequence and id order matches commit order inside the boundary. Global order has no shared row to serialise on, which is exactly why it's expensive and per-aggregate order is nearly free.

Then I'd name where order dies, because there are four places. Ids are assigned at insert rather than at commit, so a slow transaction commits behind a lower id. The claim query sorts before it locks — the docs say ORDER BY is applied first — so a SKIP LOCKED batch isn't the oldest N. RabbitMQ's publishing-order promise is per channel, so two relay workers void it. And at the consumer, redelivery reorders, and concurrent processing of deliveries is a plain race.

To buy per-aggregate order I'd hash the aggregate id into a shard, give each relay worker its own shards, use the shard as the routing key with one queue per shard, and enable single active consumer on those queues. Keep SKIP LOCKED for rolling deploys. Then process one message at a time — SAC guarantees ordered dispatch, not ordered handling. I would not use an advisory lock in the claim query: the filter runs before LIMIT, so one worker locks every aggregate in the backlog and starves the rest.

And often the better answer is to make order stop mattering. Carry a per-aggregate version, have the consumer drop anything it has already moved past, and out-of-order delivery becomes self-correcting. That works for state-carrying events and not for deltas — "order 42 is now shipped" is safe to skip, "add 5 to the balance" is not.

Scoring: the three costly omissions are refusing to scope the requirement before answering, missing the aggregate-row-lock mechanism (which is the whole reason the cheap option exists), and stopping at the routing key without saying what the consumer must do. Bonus for volunteering the state-versus-delta distinction unprompted.
