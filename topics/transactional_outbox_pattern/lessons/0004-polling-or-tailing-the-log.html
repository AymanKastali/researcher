Lesson 04 · Transactional Outbox

Polling or Tailing the Log

The comparison question. What change data capture actually buys you, what it does not, and why the bill arrives on your primary database.

The win for this lesson: by the end you can answer "why not just use CDC?" in ninety seconds from mechanism rather than vibes — naming the one guarantee log tailing gives you that polling cannot, the guarantee it does not give you however often people claim otherwise, and the operational liability it puts on your primary. Then you can pick one, for this stack, and defend it.

This is a mission criterion in its own right, and it is the question interviewers reach for when they want to find out whether you have run this in anger or only read about it.

Both answers to the same question

Read the two pattern pages side by side and the first thing you notice is that they open identically. Both state their Context as "You have applied the Transactional Outbox pattern", and both state the same Problem:

How to publish messages/events into the outbox in the database to the message broker? Pattern: Polling publisher and Pattern: Transaction log tailing — microservices.io

One answers "publish messages by polling the database's outbox table." The other answers "tail the database transaction log and publish each message/event inserted into the outbox to the message broker."

CDC is not an alternative to the outbox

It is an alternative to the relay loop. The table from Lesson 02 stays, the single-transaction insert from Lesson 01 stays, the inbox from Lesson 03 stays. Only the mechanism that moves rows out of the table changes.

Say this early in an interview and you have reframed the question from "which pattern" to "which relay implementation" — which is the correct frame, and a much easier argument to win.

There is a genuinely different design in which CDC replaces the outbox table entirely — tail the orders table itself and derive events from row changes. That is a real option and a bad one: your events become your schema, every column rename is a breaking public API change, and you cannot emit an event that does not correspond to a row. Naming that design and rejecting it is worth a sentence. It is not what this lesson compares.

What disappears when you tail the log

Here is the table Debezium's Outbox Event Router expects by default, straight from the documentation:

Column        |          Type          | Modifiers
--------------+------------------------+-----------
id            | uuid                   | not null
aggregatetype | character varying(255) | not null
aggregateid   | character varying(255) | not null
type          | character varying(255) | not null
payload       | jsonb                  |

Five columns. id is the event's unique identifier, aggregatetype selects the destination topic, aggregateid becomes the message key — which is what gives you per-aggregate ordering downstream — and payload is the event body. All of them are remappable if your column names differ. Source: Debezium — Outbox Event Router.

Hold that against Lesson 02's table and notice what is missing: no published_at, no attempts, no last_error, no partial index on unpublished rows. The router treats the outbox as an append-only queue — only INSERTs are expected, DELETEs are filtered out, and an UPDATE is a configuration error you can escalate to fatal.

That single design choice deletes most of Lesson 02:

Polling relayLog tailing
SELECT … FOR UPDATE SKIP LOCKED to claim a batch Gone. There is one reader and it reads a stream, so there is nothing to claim and no contention to skip.
UPDATE … SET published_at = now() after publishing Gone. Progress lives in the replication slot's position, not in your table. The row is never written twice.
Poll interval, batch size, a second query every 200 ms forever Gone. Changes are pushed as they are decoded, so the latency floor that polling imposes disappears.
Duplicate source 3: a relay dying mid-batch replays the batch Gone. There is no batch to replay. Sources 1 and 2 from Lesson 03 survive intact — see below.
Retention: delete rows once published_at is set Still yours, and easier — the router filters deletes out, so pruning the table emits nothing.

An honest summary: log tailing removes a component you wrote and maintain, along with every bug in it. That is a real benefit and you should say so before you attack it.

The middle option: keep polling, but ring a doorbell

Between a timer and a replication slot there is a third choice that costs almost nothing: keep the polling relay exactly as it is, and wake it with LISTEN/NOTIFY fired from the producer's own transaction. Near-push latency, no slot, no new component.

The property that makes it safe is that NOTIFY is transactional, and the PostgreSQL manual is explicit: "if a NOTIFY is executed inside a transaction, the notify events are not delivered until and unless the transaction is committed." A relay woken by the notification therefore always finds the row already visible. There is no window in which the doorbell rings before the row exists.

Three details to have ready, all from the same page:

  • Duplicate signals collapse — "If the same channel name is signaled multiple times with identical payload strings within the same transaction, only one instance of the notification event is delivered." One wake-up per commit, not one per row, which is what you want.
  • The payload is small — "In the default configuration it must be shorter than 8000 bytes." Treat it as a doorbell, never as the event.
  • The queue can fill, and the failure lands on the writer: "If this queue becomes full, transactions calling NOTIFY will fail at commit." It is 8 GB by default, and it only backs up when a session holds a long transaction after LISTEN — but the consequence is a failed business commit, so keep the fallback timer and treat a missed notification as ordinary.

It does not fix ordering, and it does not remove the sweep. It just moves the common case from "up to one poll interval" to "as fast as the relay can wake up".

The one thing polling cannot buy

Commit order. Not "roughly the order things happened" — the actual order the database committed them in, as a guarantee:

Concurrent transactions are decoded in commit order, and only changes belonging to a specific transaction are decoded between the begin and commit callbacks. PostgreSQL — Logical Decoding Output Plugins

Recall the trap Lesson 02 planted. A polling relay orders by id, and id comes from a sequence — but nextval fires when the row is inserted, not when its transaction commits. A long transaction can take id 100 and commit after a short one that took id 101. Your relay reads id 100 first and publishes two events in the wrong order, having done nothing wrong. The locking clause makes it worse: "ORDER BY is applied first", so a SKIP LOCKED batch is not even the oldest N rows.

The write-ahead log has no such gap, because the log is the commit record. There is nothing to infer. The related guarantee falls out for free — "aborted transactions and their contents never get decoded" — though be precise: a polling relay never sees rolled-back rows either, because they were never committed. That one is a wash, and claiming it as a CDC advantage is the kind of over-reach an interviewer notices.

Order is won at the source and lost downstream

Commit order at the log is necessary, not sufficient. Publish those events to RabbitMQ, run four consumers with a prefetch of 100, and they are reordered again immediately. CDC buys you a correctly-ordered stream; keeping that order to the point of effect is a separate problem, and it is Lesson 05.

What does not change — and this is the answer that scores

Log tailing is still at-least-once. Its own pattern page lists both "Guaranteed to be accurate" as a benefit and "Tricky to avoid duplicate publishing" as a drawback, which sounds contradictory until you know the mechanism. Here it is:

A logical slot will emit each change just once in normal operation. The current position of each slot is persisted only at checkpoint, so in the case of a crash the slot might return to an earlier LSN, which will then cause recent changes to be sent again when the server restarts. PostgreSQL — Logical Decoding Concepts

"Just once in normal operation" is not a guarantee; it is a description of the happy path. The slot's position is checkpointed, so a crash rewinds it and replays whatever fell between the last checkpoint and the failure. Add the connector's own crash-and-restart, and the publish-then-record gap that exists in any relay, and duplicate source 1 from Lesson 03 is exactly where it was.

"CDC gives you exactly-once"

It does not, and this is the most common wrong answer in the whole topic. Log tailing removes one of the three duplicate sources — the mid-batch replay — and leaves the other two. The inbox table from Lesson 03 is unchanged: same (consumer_name, message_id) key, same single transaction, same commit-then-ack. Your outbox row still needs a stable id to carry across, which is precisely what Debezium's id uuid column is for.

If someone offers you "guaranteed to be accurate" as if it meant exactly-once, the correction is: accurate about what committed, not about how many times you will hear it.

The bill: a replication slot on your primary

Everything above is a fair fight. This section is where the decision usually gets made.

First, logical decoding is a server-level setting, not a per-application one. "Finally, logical adds information necessary to support logical decoding" — and "this parameter can only be set at server start." So enabling it is a restart of the primary, and it is not free afterwards: "using a level of logical will increase the WAL volume, particularly if many tables are configured for REPLICA IDENTITY FULL and many UPDATE and DELETE statements are executed."

Then the slot itself, which is the part to memorise:

Replication slots persist across crashes and know nothing about the state of their consumer(s). They will prevent removal of required resources even when there is no connection using them. This consumes storage because neither required WAL nor required rows from the system catalogs can be removed by VACUUM as long as they are required by a replication slot. In extreme cases this could cause the database to shut down to prevent transaction ID wraparound. So if a slot is no longer required it should be dropped. PostgreSQL — Logical Decoding Concepts
The asymmetry that decides it

A polling relay that is down is a messaging problem. Rows pile up in a table, lag rises, you get paged, you restart it, it catches up. The database does not care.

A CDC connector that is down is a database availability problem. The slot holds WAL that cannot be recycled and catalog rows that cannot be vacuumed, and it does so silently until the disk is full. Postgres offers you exactly one escape, and it is not a good one: max_slot_wal_keep_size, which defaults to -1 meaning "replication slots may retain an unlimited amount of WAL files." Set it, and "the standby using the slot may no longer be able to continue replication due to removal of required WAL files."

So the choice under a long outage is: fill the disk, or invalidate the slot and lose the changes it had not yet read. Both are incidents. Neither is one your polling relay could have caused.

There is a second-order version of this that catches people who did everything right. Replication slots are per-database, so a quiet captured database sharing a server with a busy one produces no changes to confirm, the slot's position never advances, and the shared WAL grows anyway. Debezium's answer is to manufacture traffic: heartbeat.interval.ms, with heartbeat.action.query writing to a heartbeat table so there is something in the captured database to acknowledge. The same fix covers idle RDS instances, where background writes you never see keep the WAL moving. The connector docs have a section titled "WAL disk space consumption" — the existence of that heading is the honest summary of this whole section.

Choosing, out loud

Three questions, answered in order. The first one that gives a hard answer decides it.

QuestionWhat the answer means
Do you already run the CDC platform? If Debezium and Kafka Connect are already deployed and someone already owns the slots, tailing is nearly free and polling is duplicated effort. If not, you are adopting a distributed system to avoid writing a loop.
Do you need global commit order? If yes, polling cannot give it to you and no amount of tuning will. If per-aggregate order is enough — it usually is — polling plus a partition key gets you there, and that is Lesson 05.
Who carries the pager for the primary? If that is not your team, you are proposing to put a disk-filling liability on someone else's database. Expect to justify the heartbeat and monitoring story before you get the slot.

The answer for this stack

Poll. Postgres, RabbitMQ, SQLAlchemy async, no existing streaming platform: the reference deployment for Debezium is a Kafka Connect source connector, and the Outbox Event Router is a Kafka Connect transform. The obvious escape from that is Debezium Server, which runs a connector standalone and writes to a sink of your choice — so the question is whether RabbitMQ is one of those sinks.

Checked: RabbitMQ is not a Debezium Server sink

The sink list in the Debezium Server documentation is Kinesis, Google Cloud Pub/Sub, Pub/Sub Lite, HTTP Client, Pulsar, Azure Event Hubs, Redis Streams, NATS Streaming, NATS JetStream, Apache Fluss, Apache Kafka, Pravega, and Infinispan. RabbitMQ is not on it.

So for this stack the CDC route is not "swap the relay for Debezium". It is: adopt Kafka and Kafka Connect, or write and operate a custom sink, or use the generic HTTP sink and build the bridge to RabbitMQ yourself — and then still own delivery semantics across that bridge. That is a much larger commitment than the comparison table makes it look, and it is the sentence that settles the decision.

Either way you would be adding a streaming platform to feed a broker you already have, and paying for it with a replication slot on the primary.

Against that, the polling relay is roughly forty lines you have already read, its worst failure mode is lag, and its headline drawback — "tricky to publish events in order" — is one you can largely design around. Revisit the decision when you outgrow the latency floor, when a second and third service want the same mechanism, or when the ordering requirement hardens from per-aggregate to global.

What you can now do

State that CDC replaces the relay and not the outbox; name commit order as the single guarantee polling cannot buy, and explain the sequence-versus-commit gap that causes it; refuse the exactly-once claim and say which duplicate source actually disappears; describe the replication slot's failure mode and the max_slot_wal_keep_size dilemma; and pick one for a given scenario with three questions rather than a shrug.

Name what is still broken

  • Order still dies downstream. Even a perfectly ordered stream is scrambled by concurrent consumers and a prefetch above one. Per-aggregate keys, single- consumer queues, and when "out of order" is actually fine — Lesson 05.
  • Nobody is watching the relay. Both designs need a health metric, and it is the same one: the age of the oldest unpublished row, or the slot's lag. Lesson 06.
  • Retention is unowned in both designs. CDC makes pruning safe but does not do it for you, and the inbox has the same problem. Lesson 06.

Say it out loud

Whiteboard, no notes, 90 seconds. The prompt is: "why are you polling a table instead of just tailing the WAL?" Cover what CDC replaces, the one thing it buys, the thing it does not buy, the cost on the primary, and your actual decision. Then reveal and score what you dropped.

"First, they are answers to the same question, not competing patterns. Both assume you have already applied the outbox: the table, the single-transaction insert and the idempotent consumer are identical either way. What changes is only how rows leave the table.

What tailing buys is commit order. Postgres decodes concurrent transactions in commit order, because the log is the commit record. A polling relay can't match that — it sorts by a sequence, and nextval fires at insert, so a long transaction can hold a lower id and commit after a shorter one. It also removes a component: no claim query, no mark-as-published update, no poll interval, and no mid-batch replay when the relay dies. Debezium's router even treats the table as append-only — inserts only, deletes filtered out — so pruning is free of side effects.

What it does not buy is exactly-once. A logical slot emits each change once in normal operation, but its position is only persisted at checkpoint, so a crash rewinds it and replays. Its own pattern page lists 'tricky to avoid duplicate publishing' as a drawback. So the inbox stays, keyed on consumer name plus message id, and the outbox row still needs a stable uuid to carry across.

The cost is a replication slot on the primary. wal_level has to be logical, which is a restart and more WAL volume. Worse, slots know nothing about their consumer: a connector that is switched off still pins WAL and blocks vacuum, and in extreme cases that ends in a shutdown to prevent transaction ID wraparound. The only lever is max_slot_wal_keep_size, and setting it just changes the failure — the slot becomes unable to continue instead. There is a subtler version too: slots are per-database, so a quiet captured database on a busy server never advances its slot and the WAL grows anyway, which is what heartbeats are for.

So for this system: Postgres, RabbitMQ, no Kafka. Debezium's reference deployment is a Kafka Connect connector, so I'd be adding a streaming platform to reach a broker I already run, and paying for it with a slot on the primary. Polling is forty lines whose worst failure is lag. I'd revisit it if we needed global ordering, if the latency floor started to hurt, or if a third service wanted the same mechanism — at that point one connector beats three relays."

Score the parts you dropped, not the wording. The three most costly omissions are "CDC replaces the relay, not the outbox", "still at-least-once, because the slot position is only checkpointed", and the replication-slot liability.
