Lesson 01 · Transactional Outbox

The Dual-Write Problem

Why there is no safe order in which to do two writes — and what the outbox actually buys you.

The win for this lesson: by the end you can stand at a whiteboard, enumerate every way a database-write-plus-publish can fail, and show why the outbox is the only move left. This is the part interviewers probe. Most candidates say "you might lose the message"; strong candidates derive it.

The setup

A service handles POST /orders. It must do two things:

  1. Persist the order row in Postgres.
  2. Tell the warehouse service, by publishing order.placed to RabbitMQ (or SQS, or NATS — the argument is identical).

Two systems. Two independent commit points. No shared notion of "commit together". Here it is in the stack you'll be writing:

# The obvious implementation. It is broken, and the bug is unfixable
# by reordering, retrying, or try/except.

async def place_order(session: AsyncSession, broker: Broker, cmd: PlaceOrder) -> UUID:
    order = Order(id=uuid4(), customer_id=cmd.customer_id, total=cmd.total)
    session.add(order)
    await session.commit()                      # ① Postgres commits

    await broker.publish(                       # ② …and here be dragons
        "order.placed",
        {"order_id": str(order.id), "total": str(order.total)},
    )
    return order.id

SQLAlchemy 2.0 async. The dragons live in the gap between ① and ②.

We mint the UUID in Python (id=uuid4()) rather than letting Postgres default it. That matters later: the outbox row needs the order's id before anything is flushed. Get in the habit now.

Enumerate the failures

The process can die — SIGKILL, OOM, a node eviction, a network partition — at any instruction. So walk the orderings. There are only four things you can try.

StrategyWhat breaks
Commit, then publish Crash in the gap. The order exists and is billable, but no downstream service will ever hear about it. Silent, permanent divergence — and nothing in your logs says a message was owed.
Publish, then commit Crash in the gap, or the transaction rolls back on a constraint violation. Now a phantom event is loose: the warehouse picks stock for an order that does not exist and never will.
Publish, then compensate on failure The compensating publish (or delete) is itself a second write that can fail in the same gap. You have not removed the problem, you have recursed into it.
Two-phase commit (XA) Ruled out on availability and support, not elegance. See below.
The load-bearing insight

The failure window is not "a rare millisecond". It includes every timeout — cases where the publish neither clearly succeeded nor clearly failed and you have no way to find out. You cannot shrink your way out of it, and you cannot try/except your way out of it, because the handler is one more thing that can die.

Why 2PC is off the table

The honest answer is not "2PC is slow". Chris Richardson lists it as a force on the pattern:

2PC is not an option […] the database and message broker might not support it, and coupling the service to both is undesirable. microservices.io — Pattern: Transactional outbox

Concretely, for your brokers: SQS and NATS have no XA support at all, and RabbitMQ's transactions are not distributed transactions — they are channel-local. Even where XA exists, a 2PC transaction means the service is only as available as the least available participant, and an in-doubt transaction can hold locks in your database while a coordinator recovers.

Pat Helland made this the field's default position in Life beyond Distributed Transactions (CIDR 2007): at scale you abandon distributed transactions and build on local transactions plus at-least-once messaging with idempotence. Worth citing by name.

The move

If you cannot make two commits atomic, stop having two commits.

Treat the outgoing message as business state. It is a fact your service has decided; persist it the way you persist any other fact — in the same table space, in the same transaction:

async def place_order(session: AsyncSession, cmd: PlaceOrder) -> UUID:
    order = Order(id=uuid4(), customer_id=cmd.customer_id, total=cmd.total)
    session.add(order)

    session.add(                                # the message, as a row
        OutboxMessage(
            aggregate_type="order",
            aggregate_id=order.id,
            event_type="order.placed",
            payload={"order_id": str(order.id), "total": str(order.total)},
        )
    )

    await session.commit()   # ONE commit. Both rows, or neither. No gap.
    return order.id

No broker client in sight. That absence is the whole point.

Nothing publishes anything here. A separate process — the message relay — reads the outbox table and does the publishing. That relay is Lesson 02.

What you just achieved

Atomicity is restored by reduction: two writes across two systems became one write inside one system, and Postgres already knows how to make one write atomic. You did not add a guarantee — you removed the need for one.

Name the price

Do not stop at "and now it works" — that is the answer that gets you probed. Say what you traded:

The trade you made

The relay can publish a message and then die before it records that it published. On restart it publishes again. So the outbox buys you at-least-once delivery, never exactly-once. Duplicates are not a bug in your relay — they are a property of the design, and the consumer must be idempotent. Richardson lists it plainly among the pattern's drawbacks: the message relay may publish a message more than once, so consumers must be idempotent.

There is a second, sharper-edged cost worth having on your tongue: the pattern relies on developer discipline. Richardson's other listed drawback is that "the developer might forget to publish the message/event" — nothing in the type system stops someone committing an order without its outbox row. Real codebases push the outbox insert into a domain-event mechanism so it cannot be skipped.

Check yourself

One attempt per question — guessing until it turns green is recognition, not recall.

  3. What does inserting into the outbox table actually change?

  4. Which delivery guarantee does the finished pattern give you?

    The insert happens once; the publish need not. That distinction is the whole answer.

    Inverted. The row is durable in Postgres, so nothing is dropped — it is republished, possibly more than once.

    Correct, and say the mechanism out loud: publish succeeds, process dies before marking the row sent, restart republishes.

    A single instance removes concurrent duplicates, not crash duplicates. One relay crashing at the wrong moment still republishes.

Say it out loud

Close this page in your head. In under 60 seconds, out loud: state the dual-write problem, both failure orderings, why 2PC is rejected, the outbox move, and the price. Then reveal and compare.

"A command has to change local state and tell someone else. That's two commits in two systems with no shared atomicity. Commit-then-publish loses the event on a crash in between; publish-then-commit emits a phantom event for something that never happened; compensating logic is just another write that can fail the same way. 2PC would close it but SQS and NATS don't support XA, and it couples my availability to the broker's plus risks in-doubt transactions holding locks.

So instead I make the message part of the state: insert an outbox row in the same transaction as the business change. One commit — both rows or neither. A separate relay process reads the outbox and publishes. The cost is that the relay can publish and die before marking the row sent, so this is at-least-once delivery and consumers must be idempotent."

Score yourself on the parts you dropped, not the wording. Dropping "at-least-once" is the expensive omission.
