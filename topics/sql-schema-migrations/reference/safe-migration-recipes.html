Safe migration recipes

The step sequences, each annotated with the lock it takes and the sentence in the manual that makes it legal.

There are only ever two moves. Move the long work out from under the strong lock, or avoid the operation entirely. Every recipe below is one or the other. SQL marked “written for this reference” is not quoted from any manual; the sentences that justify each step are.

The decision, first

Which move applies.
If the operation… Then
is metadata-only Just run it — with lock_timeout, because a brief lock you must wait for is still an outage
scans Split it. NOT VALID then VALIDATE, or CONCURRENTLY then adopt
rewrites Nothing makes it safe. Use expand/contract, or accept the outage
is compatible-breaking (a rename) Expand/contract — the cost is a deployment problem, not a database one

1. Every migration: bound the wait

SQL Written for this reference 
SET lock_timeout = '2s';
-- ...the DDL...
-- On failure: wait and retry. Do NOT raise the timeout.

Why: waiting is unbounded by default — “a transaction seeking either a table-level or row-level lock will wait indefinitely for conflicting locks to be released” (13.3.1) — and a waiting ACCESS EXCLUSIVE request stalls everything behind it. The failure is the feature.

2. Add a constraint without a long lock

SQL Written for this reference 
-- Step 1. No scan, so the lock is momentary. Needs lock_timeout.
ALTER TABLE orders
  ADD CONSTRAINT orders_total_positive CHECK (total > 0) NOT VALID;

-- Step 2. Scans, under SHARE UPDATE EXCLUSIVE. Reads and writes continue.
ALTER TABLE orders VALIDATE CONSTRAINT orders_total_positive;

Why step 2 is safe: “The validation step does not need to lock out concurrent updates, since it knows that other transactions will be enforcing the constraint for rows that they insert or update; only pre-existing rows need to be checked.” — ALTER TABLE, Notes.

Remember what NOT VALID does

It removes the scan, not the lock. ADD CHECK … NOT VALID still takes ACCESS EXCLUSIVE. Only ADD FOREIGN KEY gets a weaker lock, and that is a separate fact about a different subform.

3. SET NOT NULL without the scan

SQL Written for this reference 
-- 1. Instant. ACCESS EXCLUSIVE held momentarily.
ALTER TABLE orders
  ADD CONSTRAINT orders_shipped_at_not_null
  CHECK (shipped_at IS NOT NULL) NOT VALID;

-- 2. Long. SHARE UPDATE EXCLUSIVE -- blocks nothing you care about.
ALTER TABLE orders VALIDATE CONSTRAINT orders_shipped_at_not_null;

-- 3. Instant. The scan is SKIPPED because a valid CHECK proves no NULL.
ALTER TABLE orders ALTER COLUMN shipped_at SET NOT NULL;

-- 4. Separate statement. Merging 3 and 4 defeats the optimisation.
ALTER TABLE orders DROP CONSTRAINT orders_shipped_at_not_null;

Why step 3 skips its scan: “if a valid CHECK constraint exists (and is not dropped in the same command) which proves no NULL can exist, then the table scan is skipped.” — ALTER TABLE. The parenthesis is why steps 3 and 4 must not be batched.

Step 3 is not optional

A CHECK (col IS NOT NULL) is not a NOT NULL constraint. Stop at step 2 and the column is still nullable to the catalog, the planner, and every tool that reflects your schema.

4. Add a foreign key

SQL Written for this reference 
-- Step 1. SHARE ROW EXCLUSIVE on BOTH tables -- blocks writes, briefly.
ALTER TABLE order_lines
  ADD CONSTRAINT order_lines_order_fk
  FOREIGN KEY (order_id) REFERENCES orders (id) NOT VALID;

-- Step 2. SHARE UPDATE EXCLUSIVE here, ROW SHARE on orders.
ALTER TABLE order_lines VALIDATE CONSTRAINT order_lines_order_fk;
The referenced table is locked too

“ADD FOREIGN KEY also acquires a SHARE ROW EXCLUSIVE lock on the referenced table, in addition to the lock on the table on which the constraint is declared.”

Adding a key to a small child blocks writes to the large parent you did not name. And the mode is self-exclusive, so two FKs pointing at the same parent serialise against each other.

5. Add a unique constraint without blocking

SQL Written for this reference 
-- Step 1. Long, blocks nothing. CANNOT run inside a transaction block.
CREATE UNIQUE INDEX CONCURRENTLY orders_reference_key ON orders (reference);

-- Check it actually succeeded -- a failure here is silent.
SELECT indisvalid FROM pg_index
 WHERE indexrelid = 'orders_reference_key'::regclass;

-- Step 2. Instant. Adopts the index rather than building a new one.
ALTER TABLE orders
  ADD CONSTRAINT orders_reference_key UNIQUE USING INDEX orders_reference_key;

The only multi-step recipe PostgreSQL blesses outright: “Adding a constraint using an existing index can be helpful in situations where a new constraint needs to be added without blocking table updates for a long time. To do that, create the index using CREATE INDEX CONCURRENTLY, and then install it as an official constraint using this syntax.” Restrictions: b-tree, default sort order, no expressions, not partial, not partitioned.

Concurrent builds stall silently

A concurrent build “must wait for all existing transactions that could potentially modify or use the index to terminate”. One forgotten idle in transaction session stalls it indefinitely — nothing blocks, nothing errors, it simply never finishes. And only one concurrent build per table at a time (regular builds may overlap freely).

6. Add a column

SQL Written for this reference 
-- Safe: metadata-only. Non-volatile default is evaluated once and stored.
ALTER TABLE orders ADD COLUMN status text DEFAULT 'pending';
ALTER TABLE orders ADD COLUMN created_at timestamptz DEFAULT now();  -- STABLE

-- REWRITES THE TABLE: volatile default needs a distinct value per row.
-- ALTER TABLE orders ADD COLUMN token uuid DEFAULT gen_random_uuid();

-- Instead: add nullable, backfill in batches, then set the default.
ALTER TABLE orders ADD COLUMN token uuid;
-- UPDATE orders SET token = gen_random_uuid()
--  WHERE id IN (SELECT id FROM orders WHERE token IS NULL LIMIT 1000);
ALTER TABLE orders ALTER COLUMN token SET DEFAULT gen_random_uuid();

The criterion is non-volatile, not “constant” — any IMMUTABLE or STABLE expression qualifies. The tutorial’s “constant default value” is narrower than the reference page; prefer the reference page. Fast path added in PostgreSQL 11.

7. Expand/contract — when nothing else works

SQL Written for this reference 
-- Instead of: ALTER TABLE users RENAME COLUMN email TO email_address;

-- Deploy 1 -- EXPAND
ALTER TABLE users ADD COLUMN email_address text;
-- ship code that writes BOTH columns, reads the OLD one

-- Deploy 2 -- MIGRATE
-- backfill in bounded batches:
--   UPDATE users SET email_address = email
--    WHERE id IN (SELECT id FROM users WHERE email_address IS NULL LIMIT 1000);
-- ship code that reads the NEW column

-- Deploy 3 -- CONTRACT
-- ship code that stops writing the old column, then:
ALTER TABLE users DROP COLUMN email;
Sourcing, and the half that gets skipped

No vendor manual documents this pattern. It is practitioner writing: Danilo Sato, Parallel Change, 13 May 2014, crediting Joshua Kerievsky (2006). Not Fowler.

Sato’s own warning: “If the contract phase is not executed you might end up in a worse state than you started, therefore you need discipline to finish the transition successfully.” Two phases is not a partial success.

8. Serialise two migration runs (Alembic has nothing)

Python Written for this reference — a sketch, not a recipe with an owner 
# env.py, inside run_migrations_online()
from sqlalchemy import text

MIGRATION_LOCK_KEY = 0x4D494752  # any constant; all migrators must share it

with connectable.connect() as connection:
    context.configure(connection=connection, target_metadata=target_metadata)
    with context.begin_transaction():
        if not connection.scalar(
            text("SELECT pg_try_advisory_xact_lock(:k)"), {"k": MIGRATION_LOCK_KEY}
        ):
            return          # someone else is migrating; exit zero
        context.run_migrations()
    # transaction-level lock released automatically at transaction end
Why the _xact_ form

PgBouncer lists session-level advisory locks as Yes under session pooling and Never under transaction pooling (PgBouncer Features). PostgreSQL’s manual does not discuss pooling at all.

Limitation: a transaction-scoped lock cannot span a multi-transaction run, so transaction_per_migration=True or an autocommit_block steps outside its protection.

What has no safe form

Operation Why, and what to do instead
ALTER COLUMN … TYPE (not binary coercible) Rewrites the table and every index. No option removes it. Use expand/contract with a new column
ADD COLUMN … DEFAULT <volatile> Rewrites. Add nullable, backfill in batches, then set default
RENAME COLUMN Cheap, and incompatible the instant it commits. Expand/contract
DROP COLUMN on a live column Cheap, and breaks any instance still selecting it. Ship the code change first

Every quoted sentence is from the PostgreSQL 16 manual unless attributed otherwise: ALTER TABLE, CREATE INDEX, 13.3. Explicit Locking. Back to the topic.
