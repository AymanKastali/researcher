Reference

Glossary

The vocabulary of changing a schema safely. Where a term has a quoted definition in a vendor manual, that quotation is the authority and the entry here is its compression.

Canonical source: GLOSSARY.md in this topic. The two are kept in step; this page is the readable rendering.

What the engine guarantees

DDL

Data Definition Language — the statements that change the schema rather than the rows. The distinction matters here only because engines treat DDL and DML differently inside a transaction.

Avoid: schema statement, structural query.
transaction block

What BEGIN opens: “all statements after a BEGIN command will be executed in a single transaction until an explicit COMMIT or ROLLBACK is given”. Without one, every statement gets its own implicit BEGIN/COMMIT.

PostgreSQL 16, BEGIN. Avoid: transaction scope, the transaction.
transactional DDL

The property that DDL participates in a transaction block, so several schema changes commit or roll back together. PostgreSQL has it; PostgreSQL never says so. The property is established by the enumeration of statements that cannot run inside a transaction block.

Avoid: rollback-able DDL, safe DDL, transactional schema.
atomic DDL

MySQL 8.0’s crash atomicity for one statement: dictionary update, engine work and binary-log write “either committed […] or […] rolled back, even if the server halts during the operation”. Explicitly not transactional DDL, in MySQL’s own Note. InnoDB only.

MySQL 8.0 §15.1.1. Avoid: transactional DDL (the manual’s own warning), atomic migration.
implicit commit

MySQL’s behaviour whereby a DDL statement “implicitly end[s] any transaction that is active in the current session, as if you had done a COMMIT before executing the statement”. The mechanical reason two MySQL DDL statements cannot be rolled back together.

Avoid: autocommit (different thing), silent commit.
MVCC-unsafe DDL

TRUNCATE and the table-rewriting forms of ALTER TABLE, which after committing make the table “appear empty to concurrent transactions, if they are using a snapshot taken before the DDL command committed”.

PostgreSQL 16 §13.6. Avoid: unsafe DDL, non-transactional ALTER.

The physical work

table rewrite

Rewriting the entire table and all its indexes into new files. Triggered by a volatile DEFAULT on ADD COLUMN and by a type change that is not binary coercible. The expensive outcome, and the one that cannot be made safe by care.

Avoid: table copy, full ALTER, repack.
table scan

Reading every row to verify something, without rewriting. What ADD CHECK and SET NOT NULL do. Cheaper than a rewrite, still long — and the thing NOT VALID removes.

Avoid: full scan, validation pass, check.
metadata-only change

A change recorded in the catalog with no row touched. ADD COLUMN with no default or a non-volatile one. Still takes ACCESS EXCLUSIVE, but holds it briefly.

Avoid: instant change, free change, cheap ALTER.
binary coercible

The relation between two types that lets ALTER COLUMN … TYPE skip the rewrite, because the stored representation need not change.

ALTER TABLE. Avoid: compatible type, same-size type.
non-volatile default

An IMMUTABLE or STABLE default expression, whose value is “evaluated at the time of the statement and the result stored in the table’s metadata”. The criterion for the no-rewrite fast path — broader than “a constant”, which is the tutorial’s looser word. Arrived in PostgreSQL 11.

ALTER TABLE. Avoid: constant default, static default, literal default.
invalid index

The index left behind when CREATE INDEX CONCURRENTLY fails: “ignored for querying purposes […] however it will still consume update overhead”. If unique, it also goes on rejecting duplicates. Reported by psql \d as INVALID and by pg_index.indisvalid as false.

CREATE INDEX. Avoid: broken index, partial index (different thing), failed index.
online DDL

MySQL’s name for operations that permit concurrent DML, exposed as a five-column matrix per operation. “Online” does not mean lock-free: LOCK=NONE governs the execution phase, not the brief exclusive metadata lock at commit.

Avoid: zero-downtime DDL, non-blocking ALTER.
ALGORITHM / LOCK clause

MySQL’s statement-level assertions: naming one “requires the operation to use the specified algorithm […] or fail with an error otherwise”. They turn a silent downgrade into a loud failure. PostgreSQL has no equivalent.

MySQL 8.0 §15.1.9. Avoid: hint, option, preference.

Locks

lock mode

A named member of the conflict table. “The only real difference between one lock mode and another is the set of lock modes with which each conflicts” — so a mode means nothing except who it excludes.

PostgreSQL 16 §13.3.1. Avoid: lock level, lock strength, lock type.
ACCESS EXCLUSIVE

Conflicts with every mode; “guarantees that the holder is the only transaction accessing the table in any way”. The default for ALTER TABLE subforms — the page states the default, so silence is not ambiguity. The only mode that blocks a plain SELECT.

Avoid: exclusive lock, write lock, table lock.
SHARE ROW EXCLUSIVE

Conflicts with ROW EXCLUSIVE and above; “protects a table against concurrent data changes, and is self-exclusive”. Permits reads, blocks every write. What ADD FOREIGN KEY takes — on both tables.

Avoid: row lock (it is table-level), write-blocking lock.
SHARE UPDATE EXCLUSIVE

Conflicts with schema changes and VACUUM, not with reads or writes. What VALIDATE CONSTRAINT and CREATE INDEX CONCURRENTLY take. The mode that makes the two-step patterns worth doing.

Avoid: weak lock, light lock, concurrent lock.
lock queue convoy

A waiting ACCESS EXCLUSIVE request blocking the requests queued behind it, so SELECTs stall behind DDL that is itself stalled. PostgreSQL never documents this. MySQL states the equivalent outright: “a pending exclusive metadata lock requested by an online DDL operation blocks subsequent transactions on the table.”

MySQL 8.0 §17.12.2. Avoid: lock storm, pile-up — and never cite PostgreSQL for it.
lock_timeout

“Abort any statement that waits longer than the specified amount of time while attempting to acquire a lock […] The time limit applies separately to each lock acquisition attempt.” The per-attempt scoping means it does not bound a multi-relation statement.

PostgreSQL 16 §20.11.2. Avoid: statement timeout (a different setting that pre-empts this one).
advisory lock

A lock “that ha[s] application-defined meanings […] because the system does not enforce their use”. The mechanism you must supply yourself to serialise two migration runs — preferably the _xact_ form, which a transaction pooler will not break.

PostgreSQL 16 §13.3.5. Avoid: application lock, mutex, named lock.

The two-step patterns

NOT VALID

The option that makes ADD CONSTRAINT skip its verification scan and commit immediately. It removes the scan, not the lock — ADD CHECK … NOT VALID still takes ACCESS EXCLUSIVE. It is safe because the lock is held briefly.

Avoid: deferred constraint (different thing), unvalidated constraint.
VALIDATE CONSTRAINT

The second step, verifying pre-existing rows under only SHARE UPDATE EXCLUSIVE, because “it knows that other transactions will be enforcing the constraint for rows that they insert or update”.

Avoid: validation, checking, confirming.
expand/contract

Reaching a target schema through individually-safe steps, at the cost of a period where both shapes are live. “A pattern to implement backward-incompatible changes to an interface in a safe manner, by breaking the change into three distinct phases: expand, migrate, and contract.” No vendor manual names or endorses it.

Danilo Sato, Parallel Change, 2014, crediting Kerievsky (2006). Avoid: zero-downtime migration, blue-green schema, safe rename.
contract phase

The deletion at the end, and the half practitioners skip: “If the contract phase is not executed you might end up in a worse state than you started, therefore you need discipline to finish the transition successfully.”

Sato, as above. Avoid: cleanup, tidy-up, phase three.

Alembic’s model

revision

One migration script, identified by a generated id, containing upgrade() and downgrade(). Ids may not contain @, - or + — those are reserved for the addressing syntax.

Avoid: migration file, version, changeset.
down_revision

The pointer to the revision that must run before this one. “This is how Alembic knows the correct order in which to apply migrations.” A down_revision of None marks a base.

Alembic Tutorial. Avoid: parent, previous, predecessor.
head

A revision nothing points down to — the end of a line. Plural when branches are unmerged, which is why alembic_version may hold more than one row.

Avoid: latest, tip, current.
merge point

A revision whose down_revision is a tuple of length ≥ 2. There is no merge type and no merge flag: return len(self._versioned_down_revisions) > 1. That is the entire definition.

alembic/script/revision.py:1702 (1.14.1). Avoid: merge migration, join, merge commit.
depends_on / dependencies

Revisions that must run before this one without being its lineage. They order the run; they do not define ancestry, do not make a revision a merge point, and never collapse rows in alembic_version.

Avoid: treating dependencies as parents, soft down_revision.
alembic_version

The one-column table holding the current head or heads. version_num VARCHAR(32) NOT NULL, primary key <table>_pkc. The column name is a documented contract; the width 32 is a bare literal with no named constant.

alembic/ddl/impl.py:161-172 (1.14.1). Avoid: migration log, schema_version.
compare-and-swap

UPDATE alembic_version SET version_num='<to>' WHERE version_num='<from>', followed by a rowcount assertion that exactly one row matched. The whole of Alembic’s concurrency control — and it runs after the DDL.

Avoid: lock, guard, mutex — it is none of those.
autogenerate

Comparing model metadata against a reflected database and emitting operations for the difference. Its detection surface is exactly nine comparator functions in one file, so anything outside them is invisible by construction.

Avoid: diffing, schema sync, introspection.
comparator

A function registered on the autogenerate dispatcher for schema, table or column. Nine exist in 1.14.1, and no dialect registers one — which is why the detection surface is the same on every backend.

Avoid: detector, checker, rule.
offline mode

--sql: the statement is compiled against the configured dialect and written to a buffer, never executed. A compiler, not an executor — it can tell you a migration renders, never that it works.

Avoid: dry run, preview, SQL export.
batch mode

The move-and-copy wrapper giving SQLite the ALTER TABLE forms it lacks: create new → copy → drop old → rename new into old. Exists because SQLite stores its schema as the original CREATE statement text.

Avoid: table recreate, SQLite mode, workaround.

The grades of evidence

documented guarantee

A claim quoted from a vendor manual for a named version. The only grade that may be stated without qualification — and even then, only for that version.

Avoid: the docs say, officially, canonically.
source-code fact

A claim read from Alembic 1.14.1 or SQLAlchemy 2.0.36 on disk because the documentation is silent or wrong. Weaker: it describes one released version and may change without a release note.

Avoid: internally, under the hood, actually.
maintainer statement

A first-party comment on the project’s own tracker. Authoritative about intent, carrying no versioned guarantee, and not covered by any test.

Avoid: the maintainers say, officially supported.
practitioner pattern

A named technique with an attributable author and no vendor owner. Expand/contract is the only one this topic teaches, and it is labelled every time.

Avoid: best practice, the standard approach, industry standard.
argument from absence

A claim that a source says nothing, established by exhaustive search with a working control group. Sound only when the search is shown.

Avoid: there’s nothing about it, undocumented (without showing the search).

Notes on usage

Distinctions worth keeping
  • Say “rewrite” or “scan”, never “slow”. A scan can be removed with NOT VALID; a rewrite cannot be removed at all.
  • Never say NOT VALID “avoids the lock”. It avoids the scan.
  • Say “blocks writes on both tables” about ADD FOREIGN KEY.
  • Never cite PostgreSQL for the convoy. Cite MySQL and say it is an analogy.
  • Distinguish “atomic” from “transactional”. MySQL’s own manual puts it in a Note box.
  • Say “compare-and-swap”, not “lock”, about alembic_version.
  • A migration that “passed in --sql mode” has been compiled, not tested.
