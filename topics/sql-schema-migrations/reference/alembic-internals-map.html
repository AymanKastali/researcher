Alembic has no mutual exclusion of any kind

grep -rniE "advisory|for_update|for update|lock" alembic/ → 35 hits. Excluding the English word “block” → 0. The published documentation search index returns 0 for advisori, concurr, mutex, lock and kubernet, against a control group that hits.

The compare-and-swap runs after the DDL, so it catches the bookkeeping race, never the DDL race. On PostgreSQL the loser’s error rolls its DDL back; on MySQL, SQLite and Oracle it does not.

Two gotchas

A missing down_revision target warns, then raises. util.warn(...) at revision.py:240-245 falls straight through to map_[downrev], so you see a bare KeyError instead of the message.

depends_on is not lineage. It orders the run; it does not make a merge point and never collapses rows in alembic_version.

The division of labour

Alembic writes the strings "ALTER TABLE" and "ADD COLUMN". SQLAlchemy writes everything about the column — name, type, DEFAULT, NOT NULL, GENERATED, identity, SERIAL.

One op.add_column() can emit several statements: the ALTER TABLE, one ADD CONSTRAINT per non-PK constraint, one CREATE INDEX per index, plus a COMMENT ON COLUMN where needed. Separate statements mean separate lock acquisitions.

PostgreSQL registers only four @compiles hooks — RenameTable, PostgresqlColumnType, ColumnComment, IdentityColumnDefault — and AddColumn is not one. op.alter_column() is the opposite: it branches per dialect.
