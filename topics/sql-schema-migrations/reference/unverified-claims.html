Reference

Unverified claims

The seven things in this topic that rest on something weaker than a vendor sentence, plus the questions nobody answers at all. Collected so the gaps are countable.

Everything else in this topic carries a quotation. These do not, and each is flagged in place as well as here. If a future version of these lessons quietly upgrades one of them to a confident assertion, that is a regression.

The seven

What is claimed, what it actually rests on, and where.
# Claim What it rests on Lesson
1 PostgreSQL DDL is transactional Inference. No affirmative sentence exists. The manual defines a transaction block without carving DDL out, then enumerates across a dozen pages the statements that cannot run inside one — an enumeration that would be pointless otherwise 1
2 What a failed statement leaves the session in A server error message, not documentation. current transaction is aborted, commands ignored until end of transaction block appears on no reference page. The nearest documented description is in the wire-protocol chapter 2
3 The lock-queue convoy — a waiting ACCESS EXCLUSIVE request blocks readers behind it Cited by analogy from MySQL. The single most consequential operational fact in the first half, and PostgreSQL never states it. MySQL documents the equivalent metadata-lock behaviour with a three-session worked example 5
4 Whether ADD COLUMN with identity or generated-stored rewrites Undocumented. PostgreSQL 16’s rewrite discussion covers volatile defaults and type changes and stops. The ledger marks the cell empty rather than guessing 4
5 Expand/contract as a pattern Practitioner writing. No vendor manual names or endorses it. Its mechanics are grounded — every step is a documented safe operation — but the pattern has no vendor owner 8
6 Every Alembic documentation quotation in this topic From a newer release. There is no published Alembic 1.14 documentation, so all quotations are from the current docs, checked against 1.14.1 source. Six disagreements recorded below 9–16
7 “Run migrations as a separate step, before rolling out instances” One maintainer comment. Not in Alembic’s documentation (proved by exhaustive search), not in SQLAlchemy’s or PostgreSQL’s. A discussion-tracker reply dated 7 March 2024 is its entire first-party basis 16

The two arguments from absence, and how they were made

Claims 3 and 7 are claims that a source says nothing. That is sound only if the search is exhaustive and a control group hits.

What nobody publishes at all

Timings

No primary source gives one. How long a rewrite, a scan, or a concurrent index build takes on a table of a given size is documented by no vendor.

No number appears anywhere in this topic, and none should be added. The honest answer to “how long will this migration take?” is: it depends on your hardware and your table, nobody has published a model, and the way to find out is to restore a copy and run it.

Deployment mechanics

Kubernetes init containers, Job-before-Deployment ordering, Helm pre-install hooks, and the rest of the folklore around running migrations in a pipeline are unverified practitioner consensus. No first-party source for any of it was found, and none is named here rather than cite one that was not read.

The same applies to the specific advisory-lock env.py recipes circulating on issue #633: those are user comments, not covered by Alembic’s test suite, and the maintainer explicitly declined to endorse them. One commenter there reports that advisory locking did not fully prevent concurrent-upgrade errors in their testing; that claim was not reproduced and is not repeated as fact.
