Lesson 0014

Offline mode is a compiler

--sql renders your migration; it does not run it. The distinction sounds pedantic until you see what a data migration does under it — which is to produce a plausible, wrong script and hand it to a DBA.

Offline mode has a clear documented purpose and a clear implementation: one branch, quoted in lesson 13. What it does not have is an enumerated list of what breaks under it — and the failure mode is nastier than the documentation’s one sentence implies.

Two consequences of one branch

Lesson 13 ended at the fork in DefaultImpl._exec: compiled = construct.compile(dialect=self.dialect, …), write the text, return None. Two things follow, and both matter more than the feature’s documentation suggests.

1. The statement is compiled, never executed

A construct that compiles cleanly but would fail at runtime produces a clean-looking script.

Offline mode cannot tell you that a migration works. It can only tell you that it renders. A migration that “passed in --sql mode” has been compiled, not tested — and describing it as checked implies an execution that never happened.

2. _exec returns None offline

Every rowcount-based safety check in Alembic is therefore inert under --sql. In lesson 16 this turns out to disable the only concurrency guard the tool has.

The connection is not real either

Python Quoted from alembic/runtime/migration.py:152-157 and 666-672 (1.14.1) 
if as_sql:
    self.connection = cast(
        Optional["Connection"], self._stdout_connection(connection)
    )
    assert self.connection is not None
    self._in_external_transaction = False

# ...and:

def _stdout_connection(
    self, connection: Optional[Connection]
) -> MockConnection:
    def dump(construct, *multiparams, **params):
        self.impl._exec(construct)

    return MockEngineStrategy.MockConnection(self.dialect, dump)

A SQLAlchemy MockConnection whose dump callable has no return statement. Everything you execute through it returns None.

What actually breaks, and the trap in how it breaks

The documentation’s entire statement of offline limitations is one paragraph:

“Will not work” undersells it. Consider a data migration that reads — op.get_bind().execute(select(...)).fetchall(). It fails with AttributeError: 'NoneType' object has no attribute 'fetchall', because execute() returned None. Fine: a loud failure.

But the SELECT is still in the script

The SELECT is written into the output, compiled and terminated like any DDL statement — because that is what _exec does with everything it is handed.

So the handoff script you give the DBA contains a stray SELECT that does nothing, sitting between statements that do. The script looks plausible and is wrong. If the Python failed after that line, the script is also incomplete — and nothing in it says so.

Source disagrees with documentation

Operations.get_bind documents the opposite, and the author flagged their own doubt in the docstring — alembic/operations/base.py:528-538:

“In a SQL script context, this value is None. [TODO: verify this]”

It is not None; it is a MockConnection. Prefer the source. The practical consequence is that the natural defensive idiom if op.get_bind() is not None: guards nothing offline — it is always true. MigrationContext.bind has the accurate wording: “this bind will be a ‘mock’ connection handler that cannot return results and is only appropriate for a very limited subset of commands.”

That last one is why op.bulk_insert() takes a different branch offline: it inlines each row as a literal, one INSERT per row, rather than issuing one executemany.

Correcting a widely-held belief about the start revision

It is commonly said that upgrade --sql requires an explicit start revision. It does not. Docs and source agree, and both disagree with the folklore.

In command.py::upgrade, starting_rev simply defaults to None and nothing raises when it stays there. downgrade is the one that insists:

Python Quoted from alembic/command.py:430-439 (1.14.1) 
starting_rev = None
if ":" in revision:
    if not sql:
        raise util.CommandError("Range revision not allowed")
    starting_rev, revision = revision.split(":", 2)
elif sql:
    raise util.CommandError(
        "downgrade with --sql requires <fromrev>:<torev>"
    )

So: upgrade --sql defaults to base; downgrade --sql hard-requires <from>:<to>; and a range passed without --sql raises Range revision not allowed from either command.

What the version table does in a handoff script

Reading these four behaviours precisely tells you what the DBA will actually receive:

  • _ensure_version_table() is skipped entirely — the guard at line 605 is if not self.as_sql and not heads and not dont_mutate:.
  • Instead, CREATE TABLE alembic_version is emitted inline at the first step, but only when the maintainer has no heads yet. Pass a start:end range and no CREATE TABLE appears — correct, since the DBA’s database already has one.
  • DROP TABLE alembic_version is emitted when the script ends with no heads, i.e. a full downgrade to base.
  • Offline gets a -- Running <step> comment per migration. Online does not.

The transaction wrapper is the backend’s, not Alembic’s

The documented contract promises literal BEGIN/COMMIT:

But read the first clause of the same docstring — “If is_transactional_ddl() is False, returns a ‘do nothing’ context manager” — and then lesson 10’s truth table. On a backend with transactional_ddl = False, the offline branch returns nullcontext() and no BEGIN or COMMIT is emitted at all.

What an offline script is wrapped in, by dialect. Read from the 1.14.1 tree.
Dialect transactional_ddl Terminator Batch separator Offline wrapper
default False ";" — none
postgresql True ";" — BEGIN; … COMMIT;
mssql True ";" "GO" BEGIN TRANSACTION; … COMMIT; + GO
mysql False ";" — none
sqlite False ";" — none
oracle False "" "/" none
Two entries carry their reasons in the source

SQLite’s: “SQLite supports transactional DDL, but pysqlite does not: see: http://bugs.python.org/issue10740” (alembic/ddl/sqlite.py:43-46). The flag is about the driver, not the engine.

Oracle’s command_terminator = "" with batch_separator = "/" is the SQL*Plus convention: statements get no trailing semicolon and a / line after each.

The practical reading

An offline script’s transactional semantics are the target backend’s, not Alembic’s.

Handing a DBA a PostgreSQL script means handing them something that rolls back as a unit. Handing them a MySQL script does not — and nothing in the script says so.

Check yourself

A data migration doing a SELECT is run with --sql. What do you get?

execute() returns None, so .fetchall() raises — but _exec has already compiled and written the SELECT to the output buffer, because it does that with everything. You get a partial script containing a statement that does nothing, and it looks like a valid handoff.

Check yourself

Does alembic upgrade --sql require a start revision?

starting_rev defaults to None in command.py::upgrade and nothing raises. It is downgrade that hard-requires <from>:<to> under --sql. And the third answer is impossible by construction — there is no connection to read anything from, which is the whole premise of offline mode.

The question this leaves open

Offline mode has no database to query. There is one Alembic feature whose entire method depends on reflecting the existing table — so the two are mutually exclusive by construction, and the feature exists for a reason SQLite itself explains better than anyone. Lesson 15.

Read next, from the source

Alembic documentation, “Generating SQL Scripts (a.k.a. ‘Offline Mode’)” — short, and worth reading with one question held in mind: what does this page not tell you? It is a good demonstration that complete-looking documentation can leave the most dangerous behaviour unstated.

Your agent is your teacher. Genuinely useful to work through: if you had to hand a DBA a script you could vouch for, what would you do in addition to --sql? The answer involves a real database somewhere, and constructing it is a better exercise than reading a recommendation.

On spacing

One sentence to retain: offline mode tells you a migration renders, never that it works. Everything else in this lesson is detail you can look up, and most of it lives in the internals map.
