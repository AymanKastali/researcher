Lesson 0015

Batch mode

Why SQLite’s ALTER TABLE is weak — SQLite’s own answer, which is more interesting than “it just is” — and what Alembic’s move-and-copy workaround silently drops on the way.

The usual framing is “SQLite has a weak ALTER TABLE”. True, and incurious. SQLite explains the cause itself, and the explanation turns a quirk into a design consequence — one that predicts exactly which operations are supported and which are not.

The cause, in SQLite’s own words

The limitation is architectural

Other engines edit a parsed structure. SQLite edits text — the literal CREATE TABLE statement you originally typed. An ALTER is a string-rewriting problem, which is why the supported set is so small and so oddly shaped.

Alembic’s own documentation agrees on the prognosis, calling these “philosophical and architectural concerns within SQLite, and they are unlikely to be changed”.

What SQLite supports is exactly four forms:

SQLite’s twelve-step procedure — and the ordering warning

For anything else, SQLite documents a procedure (§8): disable foreign keys, begin a transaction, record dependent objects, CREATE TABLE new_X, INSERT INTO new_X SELECT … FROM X, DROP TABLE X, ALTER TABLE new_X RENAME TO X, rebuild indexes, triggers and views, PRAGMA foreign_key_check, commit, re-enable foreign keys.

The part worth quoting is the Caution attached to it, because it is the reason Alembic’s step order is what it is rather than the more obvious alternative:

Two orderings that look equivalent. Only one is safe.
Correct Incorrect
Create new table Rename old table
Copy data Create new table
Drop old table Copy data
Rename new into old Drop old table

Alembic implements the left-hand column exactly:

Python Quoted from alembic/operations/batch.py:443-480, abridged (1.14.1) 
def _create(self, op_impl: DefaultImpl) -> None:
    self._transfer_elements_to_new_table()

    op_impl.prep_table_for_batch(self, self.table)
    assert self.new_table is not None
    op_impl.create_table(self.new_table)

    try:
        op_impl._exec(
            _insert_inline(self.new_table).from_select(...)
        )
        op_impl.drop_table(self.table)
    except:
        op_impl.drop_table(self.new_table)
        raise
    else:
        op_impl.rename_table(
            self.temp_table_name, self.table.name, schema=self.table.schema
        )
The bare except: is not decoration

On SQLite transactional_ddl is False (lesson 10), so a rollback cannot be relied on to clean up after a failed copy. The explicit op_impl.drop_table(self.new_table) is doing the work a transaction would do elsewhere.

Source disagrees with documentation — the temp table name

The documentation shows _alembic_batch_temp in its worked example, and a source comment repeats it. The actual name comes from ApplyBatchImpl._calc_temp_name, batch.py:244-245:

return ("_alembic_tmp_%s" % tablename)[0:50]

The real name is _alembic_tmp_<tablename>, truncated to 50 characters. Prefer the source — and note the consequence hiding in the truncation: two tables whose names share a long prefix can truncate to the same temp name.

The implementation is tracking the spec, not approximating it

Even an add_column escalates to a full recreate if its server default is a SQL expression, or if it is a persisted computed column. Those two escalations map precisely onto SQLite’s own stated ADD COLUMN restrictions: a column “may not have a default value of CURRENT_TIME, CURRENT_DATE, CURRENT_TIMESTAMP, or an expression in parentheses”, and “may not be GENERATED ALWAYS … STORED, though VIRTUAL columns are allowed” (§4).

Two asymmetries worth knowing:

  • DefaultImpl.requires_recreate_in_batch returns False (impl.py:187), so non-SQLite backends never auto-recreate. Batch mode on PostgreSQL is a no-op wrapper around ordinary ALTER TABLE unless you pass recreate="always".
  • drop_column forces a full recreate on SQLite even though SQLite has supported DROP COLUMN natively since 3.35.0. Alembic 1.14.1 does not take that shortcut.

What batch mode silently drops

_grab_table_elements sorts reflected constraints into buckets, and one of them is a hole:

An unnamed CHECK constraint on a reflected table is discarded when the table is recreated. The constraint was in your schema before the migration and is not in it afterwards, and nothing told you.

Version gap, stated precisely

The published documentation says: “Unnamed CHECK constraints continue to be omitted from the table recreate operation; up until version 1.20, this omission was silent. As of 1.20, it emits a warning.”

On 1.14.1 the omission is silent — the pass above has no util.warn anywhere near it. The documentation is describing a version you are not running.

A second staleness runs the other way. The batch_alter_table docstring at base.py:292-295 still carries pre-1.7 text: “The table copy operation will currently not copy CHECK constraints, and may not copy UNIQUE constraints that are unnamed.” That contradicts both the docs and the 1.14.1 code, which routes named CHECK constraints into self.named_constraints. Here the docstring is the stale one: named CHECK constraints do participate in 1.14.1; only unnamed ones vanish.

There is a second silent drop, this one undocumented anywhere — batch.py:345-346:

Where batch mode and offline mode collide

Batch mode’s whole method rests on reflecting the existing table. Lesson 14’s offline mode has no database to reflect from. The two are therefore mutually exclusive by construction, and BatchOperationsImpl.flush says so with an unusually long error (batch.py:127-140):

The documented escape is to hand Alembic the table definition it would otherwise reflect, via copy_from — and the documentation is candid that this is miserable: “The above use pattern is pretty tedious and quite far off from Alembic’s preferred style of working; however […] there’s not much alternative.” Autogenerate does not bridge the gap either; copy_from tables must be written by hand.

Batch on backends that do support ALTER

The documented reason to reach for recreate="always" elsewhere is lock avoidance:

Be clear-eyed about this, given lessons 3–5

Move-and-copy on PostgreSQL does not avoid the lock so much as relocate it. The DROP TABLE and RENAME at the end take ACCESS EXCLUSIVE anyway, and the copy window is one during which writes to the original table are lost unless you have arranged otherwise.

The documentation is candid about the unautomated parts too: “existing foreign key constraints which refer to the target table will need to be unconditionally dropped before the batch operation, and re-created to refer to the new table afterwards. Batch mode currently does not provide any automation for this.”

Check yourself

Why does SQLite have such a limited ALTER TABLE?

SQLite’s own §9: other engines store the schema parsed into system tables, so ALTER edits a structure; SQLite stores the original CREATE text, so ALTER must rewrite text. The third answer is also false on its face — SQLite does support transactional DDL; it is pysqlite that does not, which is why Alembic marks the dialect False.

Check yourself

On Alembic 1.14.1, what happens to an unnamed CHECK constraint during a batch recreate?

batch.py:272-275 is a bare pass with a TODO comment and no util.warn. The warning described in the current documentation arrived in 1.20 — the third answer is right about a later version. Named CHECK constraints are transferred on 1.14.1, which is where the batch_alter_table docstring is itself stale.

The question this leaves open

One question is left, and it is the one everybody asks first: what happens when two instances run alembic upgrade head at the same time? The answer is an absence, and establishing an absence takes more care than establishing a fact. Lesson 16.

Read next, from the source

SQLite, ALTER TABLE — specifically §8 and §9. It is some of the best technical writing in any database manual: it explains the design trade-off, admits the cost, gives a precise procedure, and warns you about the plausible wrong version of it. Read §9 even if you never touch SQLite.

Your agent is your teacher. Worth working through: given what lessons 3–5 said about locks, what would you actually have to build to make move-and-copy safe on PostgreSQL — around the lost-writes window and the dependent foreign keys? The answer is most of a replication system, and arriving at that yourself is the point.
