Lesson 0008

Expand and contract

The move you make when there is no safe form of the operation. Also the first thing in this topic with no vendor source at all — so this lesson is partly about how to teach something responsibly when the manuals are silent.

Lessons 6 and 7 both moved work out from under a strong lock. Some operations offer no such move. A table rewrite cannot be made cheap — no option anywhere removes it. A column rename is instant and cheap, and still breaks every running instance of your application the moment it commits. For these, the only remaining play is not to perform the operation.

First, the sourcing, because it is unusual

No vendor documents this pattern

Searched across every PostgreSQL 16 and MySQL 8.0 page consulted for this topic: zero hits for expand/contract, “parallel change”, or any equivalent rolling-upgrade schema language. No vendor documents, names, or endorses it.

What the manuals supply are its primitives — every one of which you have already met, each individually vendor-sourced: NOT VALID / VALIDATE CONSTRAINT, CREATE INDEX CONCURRENTLY plus ADD table_constraint_using_index, and the non-volatile-default fast path. The closest thing to vendor endorsement of a multi-step technique is the Note quoted in lesson 7, and it covers one constraint, not a protocol.

The pattern does have an attributable owner, and it is a practitioner source — held to a different evidential standard than everything in lessons 1–7, and labelled as such every time it appears:

Get the provenance right

The article’s own acknowledgements: the technique “was first documented as a refactoring strategy by Joshua Kerievsky in 2006 and presented in his talk The Limited Red Society presented at the Lean Software and Systems Conference in 2010.”

So the chain is Kerievsky (2006) → named and written up by Sato (2014). Not Martin Fowler, whose site hosts it — an attribution mistake made constantly, and an easy one to avoid.

The three phases, in the source’s words

Sato’s three phases, quoted, with what each means for a schema.
Phase The definition In a database
Expand “In the expand phase you augment the interface to support both the old and the new versions.” Add the new column. Write to both.
Migrate “During the migrate phase you update all clients using the old version to the new version.” Backfill in batches. Move reads across.
Contract “Once all usages have been migrated to the new version, you perform the contract phase to remove the old version.” Stop writing the old column. Drop it.

Why the pattern has to exist

The argument, in terms of lessons 1–7

Every operation in lesson 4’s table that is safe is safe because it is metadata-only or takes a weak lock. The ones that are unsafe — rewrites, and scans under ACCESS EXCLUSIVE — cannot be made safe by running them more carefully.

So the only way to avoid an unsafe operation is not to perform it: you reach the target schema through a sequence of individually-safe steps. The price is a period during which both shapes are live and the application must tolerate both.

Renaming a column is the canonical example, and it is worth being precise about why. The rename is not expensive — it is a catalog change. The problem is that no database offers a rename that is also compatible: at the instant it commits, every running application instance holding the old name starts failing. It is a deployment problem wearing a migration costume.

SQL Written for this lesson 
-- Instead of: ALTER TABLE users RENAME COLUMN email TO email_address;
--
-- Deploy 1 -- EXPAND
ALTER TABLE users ADD COLUMN email_address text;   -- metadata-only, no default
-- ...then ship application code that writes BOTH columns and reads the old one.

-- Deploy 2 -- MIGRATE
-- Backfill in bounded batches, so no single statement holds a long lock:
--   UPDATE users SET email_address = email
--    WHERE id IN (SELECT id FROM users WHERE email_address IS NULL LIMIT 1000);
-- ...then ship application code that reads the NEW column.

-- Deploy 3 -- CONTRACT
-- Ship application code that no longer writes the old column, then:
ALTER TABLE users DROP COLUMN email;               -- ACCESS EXCLUSIVE, instant

Five operations, each individually cheap, spread across at least three deploys. That count is the real cost of the pattern, and it is why it is reached for deliberately rather than by default. Notice also that the middle deploy contains no DDL at all — the backfill is ordinary DML, and it is batched for exactly the reason lesson 5 gave: a single enormous UPDATE is a long-held lock by another name.

The half that gets skipped

This is the failure mode in practice, and it is worth stating baldly: a half-finished expand/contract leaves you with two columns, dual-write code that nobody dares delete, and a schema that is harder to reason about than the one you started with. The first two deploys are interesting work and the third is not, so the third is the one that stays in the backlog. The pattern is three phases; two phases is not a partial success.

Check yourself

Why is expand/contract needed for a column rename, which is instant?

The rename is cheap — a catalog change — and on PostgreSQL it rolls back like any other DDL. The incompatibility is the problem: every deployed instance still using the old name fails at the instant of commit. Expand/contract is a response to a deployment constraint, which is why it is the one technique here with no vendor source: it is not about the database.

Check yourself

What kind of source is expand/contract, and who is it attributable to?

No vendor manual names it. It is practitioner writing with a clear chain: first documented by Joshua Kerievsky in 2006, named and written up by Danilo Sato in 2014 on martinfowler.com. Attributing it to Fowler — the site’s owner rather than the article’s author — is the common error, and “no single known author” is exactly the vagueness this topic exists to refuse.

End of the first half

That is the database. You can now read an operation and predict what it does, move work out from under strong locks two different ways, and recognise the case where neither move exists. None of it mentioned a migration tool, because none of it depends on one.

Read next, from the source

Danilo Sato, Parallel Change — it is one page and takes five minutes. Read it as an interface pattern rather than a database one, because that is how it is written: the database is one application among several, and seeing the general form makes the schema case obvious rather than memorable.

Your agent is your teacher. A genuinely useful exercise: name a schema change you would want to make and work out the expand/contract sequence for it together, deploy by deploy — then ask which individual steps are safe by lesson 4’s table and which need a lock_timeout. Doing it for a change you actually care about is worth far more than reading the rename example again.
