Lesson 0013

How op.add_column() becomes SQL

Follow one operation from your revision file to the wire. Alembic writes two strings; SQLAlchemy writes the rest. Knowing which is which tells you where to look when the emitted SQL is not what you expected.

op.add_column("orders", sa.Column("shipped_at", sa.DateTime())) produces ALTER TABLE orders ADD COLUMN shipped_at TIMESTAMP WITHOUT TIME ZONE. Between those two things are nine hops across six files, and the interesting discovery is how little of the final string Alembic is responsible for.

The chain

1. alembic.op is generated at import time

The module you import is this, in its entirety:

Python Quoted from alembic/op.py, complete file (1.14.1) 
from .operations.base import Operations

# create proxy functions for
# each method on the Operations class.
Operations.create_module_class_proxy(globals(), locals())

Every public method of Operations gets a proxy installed into the module namespace at import. And Operations.add_column is itself generated: @Operations.register_operation("add_column") builds the method source as a string and execs it (base.py:192), rewriting the op class’s (cls, operations) signature into (self).

Two familiar annoyances, explained

Why the type stubs live in a separate file. Because the real methods do not exist until runtime, the static signatures and documentation live in alembic/op.pyi — a 50 KB stub file maintained alongside the generator. That is what your editor is reading.

Why calling op.add_column outside a migration raises a NameError about a proxy. The proxy exists, but it has no Operations instance bound to it until a migration is running.

2. The first dialect-aware dispatch is invoke

Python Quoted from alembic/operations/base.py:438-441 (1.14.1) 
fn = self._to_impl.dispatch(
    operation, self.migration_context.impl.__dialect__
)
return fn(self, operation)

This looks up (op_class, dialect_name) and falls back to (op_class, "default"). For AddColumnOp no dialect registers an override, so every backend — PostgreSQL, MySQL, SQLite, Oracle, MSSQL — lands on the same toimpl.add_column.

3. One op.add_column() can emit several statements

Python Quoted from alembic/operations/toimpl.py:172-197, abridged (1.14.1) 
if column.table is not None:
    column = _copy(column)

t = operations.schema_obj.table(table_name, column, schema=schema)
operations.impl.add_column(table_name, column, schema=schema, **kw)

for constraint in t.constraints:
    if not isinstance(constraint, sa_schema.PrimaryKeyConstraint):
        operations.impl.add_constraint(constraint)
for index in t.indexes:
    operations.impl.create_index(index)

It fabricates a throwaway Table to host the column so that SQLAlchemy derives the implied constraints, emits the ALTER TABLE … ADD COLUMN, and then emits each non-primary-key constraint as its own ALTER TABLE … ADD CONSTRAINT, each index as its own CREATE INDEX, and — on a dialect with out-of-line comments — a separate COMMENT ON COLUMN.

This matters for lesson 3’s batching rule

A single op.add_column() with a unique constraint and an index on it is three separate statements, each taking its own lock in sequence — not one ALTER TABLE with several subcommands.

So the “strictest lock of the batch” rule from lesson 3 does not apply here: you get three lock acquisitions rather than one, which under lock_timeout means three chances to fail and three chances to queue. Worth knowing before you assume the tool batches for you.

The _copy on the first line is defensive: the Column is copied if it is already bound to a Table, so your model object is not mutated by generating a migration against it.

4. PostgreSQL does not override AddColumn at all

alembic/ddl/postgresql.py has exactly four @compiles registrations — RenameTable, PostgresqlColumnType, ColumnComment and IdentityColumnDefault — and AddColumn is not among them. Nor does any dialect override DefaultImpl.add_column. So the hand-off is a single line:

Python Quoted from alembic/ddl/base.py:328 (1.14.1) 
text = "ADD COLUMN %s" % compiler.get_column_specification(column, **kw)
The division of labour, exactly

Alembic writes the strings "ALTER TABLE" and "ADD COLUMN".

Everything about the column — its quoted name, its type, DEFAULT, NOT NULL, GENERATED, identity — is written by SQLAlchemy’s DDLCompiler, and on PostgreSQL by PGDDLCompiler.get_column_specification.

That is where SERIAL / BIGSERIAL / SMALLSERIAL are produced — and it requires column.table._autoincrement_column, which is exactly why the throwaway Table in toimpl.add_column has to exist.

The generalisation is worth holding onto, because it tells you where to debug: op.add_column() is dialect-neutral all the way down inside Alembic, and its PostgreSQL-specific text comes from SQLAlchemy. If the column definition is wrong, the bug is not in Alembic.

op.alter_column() is the opposite — there Alembic does branch per dialect, which is how postgresql_using= threads a USING clause into ALTER COLUMN … TYPE. The two operations are worth contrasting precisely because they sit on opposite sides of this line.

The fork at the bottom

Finally, every statement — this one and all the others — passes through one if in DefaultImpl._exec:

Python Quoted from alembic/ddl/impl.py:212-232, abridged (1.14.1) 
if self.as_sql:
    if multiparams is not None or params:
        raise TypeError("SQL parameters not allowed with as_sql")
    ...
    compiled = construct.compile(dialect=self.dialect, **compile_kw)
    self.static_output(
        str(compiled).replace("\t", "    ").strip()
        + self.command_terminator
    )
    return None

Offline compiles the construct against the configured dialect and writes the text plus a terminator to the output buffer, returning None. Online hands the construct to Connection.execute. That return None is small and it has consequences all over the package — lesson 14 is about them.

Check yourself

Who writes the type and NOT NULL in the emitted ADD COLUMN?

Alembic contributes the literal strings "ALTER TABLE" and "ADD COLUMN"; the entire column specification comes from compiler.get_column_specification(column). PostgreSQL registers only four @compiles hooks and AddColumn is not one of them — which is why an unexpected column definition is a SQLAlchemy question, not an Alembic one.

Check yourself

How many statements does one op.add_column() emit?

toimpl.add_column loops over the throwaway table’s constraints and indexes, emitting each separately — plus a COMMENT ON COLUMN where the dialect needs one. The third answer is the tempting one, and getting it wrong costs you: separate statements mean separate lock acquisitions rather than one batched ALTER TABLE.

The question this leaves open

That return None in the offline branch looks like an implementation detail. It is load-bearing: it is why a --sql script can contain statements that would fail, and why every rowcount-based safety check in Alembic is inert under it. Lesson 14.

Read next, from the source

alembic/ddl/base.py in the 1.14.1 tree — it is short, and it is where Alembic’s own DDL constructs and their @compiles hooks all live. Read visit_add_column and the add_column() helper together, then look at alembic/ddl/postgresql.py and count the four @compiles lines yourself. Seeing how small the dialect-specific surface is changes how you debug generated SQL.

Your agent is your teacher. A good follow-up: ask it to trace op.alter_column() the same way, and compare. It branches per dialect where add_column does not, and seeing the two side by side is the clearest way to understand what “dialect support” means in this codebase.

On spacing

Do not memorise the chain — it is lookup material and it lives in the internals map. Retain two things: Alembic writes two strings and SQLAlchemy writes the rest, and one op call can be several statements.
