Lesson 0002

What a half-failed migration leaves

Three answers, depending on where the failure happened: nothing, an index that charges you rent while doing no work, or a schema you have to repair by hand. Knowing which one you are in decides your next move.

A migration failed on statement four of five. What is in the database now? This is the question you actually ask at 3am, and it has three different answers on three different sets of circumstances — one of which is not PostgreSQL at all.

The ordinary case: nothing

If the whole migration ran inside one transaction and a statement raised, the block is left in the aborted state and every effect is discarded on rollback. The locks go with it:

This is the good outcome and it is the common one. Nothing to clean up, nothing to diagnose beyond the error itself.

A sourcing note worth having

The message everyone recognises from this situation — current transaction is aborted, commands ignored until end of transaction block — is a server error message, not documentation. It does not appear on the BEGIN, SAVEPOINT, ROLLBACK TO, transactions-tutorial, isolation or psql pages.

The documented description of the state is tucked into the wire protocol chapter: “the session will be left inside a failed regular transaction block, since the ROLLBACK is not reached after the divide-by-zero error. Another ROLLBACK will be needed to restore the session to a usable state.” §55.2.2.1. A string you have read a thousand times in a terminal is not a citation — and hunting for where the behaviour is actually written down is a habit worth keeping.

The interesting case: the statements outside the transaction

Everything on lesson 1’s exception list fails outside transactional protection, and CREATE INDEX CONCURRENTLY is the one you will actually meet. Here the leftover is not nothing, and — this is the part that surprises people — it is not inert either:

Read the two halves against each other. Ignored for queries, so no read gets faster. Still consumes update overhead, so every INSERT and UPDATE pays to maintain it. You are being charged rent on an index that does no work.

The worst of all three worlds

A failed concurrent unique index build leaves an index that is skipped by the planner, charged to every writer, and still rejecting duplicate rows.

From the application’s side this presents as: writes that used to succeed now fail with a uniqueness violation, against an index no query plan mentions. It is extremely easy to mistake for an application bug, and the migration that caused it may have failed days earlier.

The documented recovery is to drop the index and retry — the manual also offers REINDEX INDEX CONCURRENTLY as an alternative. Either way it is a deliberate action; nothing cleans this up for you.

A leftover that labels itself

REINDEX CONCURRENTLY leaves a better-signposted mess. Its leftover is suffixed _ccnew if the rebuild failed, and _ccold if the rebuild succeeded but the old index could not be dropped, with a numeric suffix added if needed to stay unique.

The suffix tells you which half of the swap failed, and therefore which index to drop. That is a genuinely thoughtful piece of design, and it is worth noticing precisely because CREATE INDEX CONCURRENTLY gives you no such hint.

The third case: a database that cannot roll DDL back at all

MySQL 8.0 introduced atomic DDL, and the feature is real. The announcement:

MySQL’s own documentation then puts the disclaimer in a Note box directly beneath it, which tells you how often the feature is misread:

Atomic DDL vs transactional DDL

Atomic DDL is crash atomicity for one statement: the dictionary write, the engine work and the binlog write all land or none do, even if the server dies mid-operation.

Transactional DDL is composition: several statements roll back together. MySQL does not have this, and cannot, because the second DDL statement implicitly commits the first.

The distinction is MySQL’s own, from the Note quoted above.

The practical consequence is the one every MySQL migration tool has to design around. A five-statement migration that fails on statement four leaves statements one through three committed and unrecoverable by rollback. The database cannot help you; only a hand-written compensating migration can.

And one carve-out makes it worse rather than better — a statement that does not implicitly commit, but also cannot be rolled back:

The three answers, side by side

Where the failure happened decides what you are cleaning up.
Situation What is left behind Your next move
PostgreSQL, statement inside the transaction Nothing. Effects discarded, locks released Fix the migration and run it again
PostgreSQL, CREATE INDEX CONCURRENTLY An invalid index: unused by queries, maintained by every writer, and still enforcing uniqueness if unique Find it, drop it, retry — nothing does this for you
MySQL, statement 4 of 5 Statements 1–3 committed. Each was atomic; together they were never a unit Write a compensating migration by hand
Check yourself

A CREATE INDEX CONCURRENTLY on a unique index failed overnight. What is true this morning?

CONCURRENTLY cannot run in a transaction block, so there is no rollback to save you. The manual states all three properties separately: ignored for querying, still consuming update overhead, and — if the failure was in the second scan — still enforcing uniqueness. The third answer is the comfortable misreading, and it is the reason this leftover gets missed.

Check yourself

What does MySQL 8.0’s atomic DDL guarantee about a five-statement migration?

Atomic DDL is crash atomicity per statement — dictionary, engine and binlog land together or not at all. It is not composition, and MySQL’s own Note says so directly: DDL “implicitly end[s] any transaction that is active in the current session”. The InnoDB restriction in the fourth answer is real but irrelevant to this question; it limits which engines get atomic DDL, not what atomic DDL means.

The question this leaves open

You now know what survives a failure. The much more common problem is a migration that does not fail at all — it simply holds a lock, and the application stops. To predict that, you need to know exactly what “holding a lock” excludes, and PostgreSQL’s answer is unusually crisp. That is lesson 3.

Read next, from the source

PostgreSQL 16, CREATE INDEX — “Building Indexes Concurrently” — read the whole subsection, not just the paragraph quoted here. It is about two pages, it is the most operationally dense writing in the PostgreSQL manual, and you will come back to it in lesson 7 with the lock vocabulary needed to read the rest of it.

Your agent is your teacher. A good thing to push on here: ask what the application-visible symptom of a leftover invalid unique index would be, and work out how you would tell it apart from a genuine application bug. Reasoning from the mechanism to the symptom is the skill this lesson is really for.
