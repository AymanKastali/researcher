Lesson 0017

Reading the evidence

Sixteen lessons rested on four different grades of evidence. This one makes the grading itself the object of study — because it is the part that survives PostgreSQL 17 and Alembic 1.20, and the rest is not.

Every claim in this topic carried a source, and those sources were not equivalent. A sentence in the PostgreSQL manual and a comment on a GitHub issue are both “first-party”, and believing them equally is a mistake. So is refusing to use the weaker one. Here is the grading, the places this topic had to use each grade, and the seven things that could not be verified at all.

The four grades

What each grade licenses you to say, and where it appeared.
Grade What it is What it licenses
Documented guarantee A sentence in a vendor manual for a named version — the ALTER TABLE lock rule, the NOT VALID rationale Stating it flatly. But only for that version: the ALTER TYPE pair in lesson 1 is the same page saying opposite things four releases apart
Source-code fact A line read from Alembic 1.14.1 on disk — the truth table, the nine comparators, the compare-and-swap Stating what this release does. Not what the project promises. It can change without a release note
Maintainer statement A first-party comment on the project’s own tracker — the two Mike Bayer quotations in lesson 16 Describing intent. Carries no versioned guarantee and no test coverage. Must be labelled every time
Practitioner pattern A named technique with an author and no vendor owner — expand/contract Naming the author and the date. Never “best practice”, never “the standard approach”
A fifth move, used twice

The argument from absence — establishing that a source says nothing, by exhaustive search with a working control group.

Used in lesson 5 (PostgreSQL never documents the convoy) and lesson 16 (Alembic’s documentation contains no concurrency material, its source no locking primitive). It is sound only when the search is shown, which is why both lessons print their counts rather than summarising them. Five zeroes with no control group is not evidence; it is a broken grep.

Where the documentation and the source disagreed

Six times in this topic, and each time the lesson preferred the source and said so. Collected here because the pattern is more useful than any individual case:

Why three of six are version gaps

There is no published Alembic 1.14 documentation: /en/rel_1_14/ is not published and /en/release-1.14.0/ returns 404. So every documentation quotation in this topic came from the current docs, and three “disagreements” are really the docs being correct about a release you are not running.

That is worth internalising as a habit rather than a fact: when a project’s documentation is unversioned or version-skewed, a disagreement with the source is more likely to be a version gap than an error — and the only way to tell is to read the source.

The seven things that could not be verified

Flagged in place throughout, and collected here so the gaps are countable:

  1. PostgreSQL never states that DDL is transactional. Established negatively in lesson 1, from the enumeration of statements that cannot run inside a transaction block. The inference is safe. It is still an inference.
  2. current transaction is aborted, commands ignored until end of transaction block is a server error message, not documentation. It describes the half-failed-migration behaviour exactly, and it is emitted by the server rather than written by a technical writer. No manual section states the rule it implies.
  3. PostgreSQL never documents the lock-queue convoy. The most consequential operational fact in the first half. Lesson 5 sources it from MySQL’s manual and says plainly that it is a citation by analogy.
  4. PostgreSQL 16 does not say whether ADD COLUMN with an identity or generated-stored specification rewrites the table. Lesson 4’s table marks the cell undocumented rather than guessing.
  5. Expand/contract appears in no vendor manual. Its mechanics are grounded — every step it prescribes is one of the safe operations in lesson 4 — but the pattern as a pattern has no vendor owner.
  6. There is no Alembic 1.14 documentation online. See the table above.
  7. “Run migrations as a separate step, before rolling out application instances” has no documented owner. Its only first-party support is one maintainer comment on a discussion tracker, dated 7 March 2024. Everything beyond that — init containers, Job ordering, Helm hooks — is unverified practitioner consensus, and none of it is named here rather than cite something that was not read.
And one thing nobody publishes

No primary source gives timings. How long a rewrite takes on a table of a given size is documented by no vendor, so no number appears anywhere in this topic.

If you find yourself wanting one — and you will, when someone asks “how long will this migration take?” — the honest answer is that it depends on your hardware and your table, that nobody has published a model, and that the way to find out is to restore a copy and run it.

How to check any of this yourself

The most transferable thing in this topic is not any fact in it. It is that all of it is checkable, cheaply:

Shell Written for this lesson 
# 1. Pin a version and read it. Every source claim here came from this.
uv pip install --target ./alembic-src "alembic==1.14.1" "SQLAlchemy==2.0.36"
grep -n '__version__' alembic-src/alembic/__init__.py

# 2. Check a claim about detection surface.
grep -rn 'comparators.dispatch_for' alembic-src/alembic/

# 3. Check a claim about absence -- always with a control group.
grep -rniE "advisory|for_update|lock" alembic-src/alembic/ | grep -viE "block" | wc -l

# 4. Check a documentation claim against the version you actually run.
#    PostgreSQL pages are the same URL with the version number changed:
#      /docs/16/sql-altertype.html   vs   /docs/11/sql-altertype.html
The habit, in one sentence

When a claim matters, find the sentence — and when there is no sentence, say so.

Most of what circulates about schema migrations is true, undated, and unattributed. The three properties are independent, and only the first one is the one people check.

Check yourself

What makes an argument from absence sound rather than lazy?

Zeroes are equally consistent with a working search and a broken one — only terms that do hit distinguish the cases. Lesson 16 searched the complete published index rather than selected pages, and printed four control terms alongside the five zeroes. Without that right-hand column the result would be worthless.

Check yourself

Alembic’s docs list a feature your installed version lacks. What is the likeliest explanation?

Alembic publishes documentation only for the current release — there is no 1.14 build at all — so any page you read describes a later version than a pinned install. Three of this topic’s six disagreements were exactly that, and each was identifiable because the docs carried an “Added in version” marker. Genuine errors exist too, but they are the rarer case.

You have finished the topic

Seventeen lessons: eight on what a database does under a migration, eight on what one tool does on top of that, and this one on how to tell which claims to trust. What you should be able to do now is on the MISSION.md beside these lessons, and the reference documents are what to come back to rather than these pages.

The most durable thing here is the smallest: a lock is its conflict set, a scan can be moved and a rewrite cannot, and a claim without a sentence behind it is folklore no matter who is repeating it.

Read next, from the source

Pick the one you will actually use. If you run PostgreSQL, it is the ALTER TABLE Notes section — two pages, and the source of more of this topic than anything else. If you run Alembic, it is alembic/runtime/migration.py in a pinned install. Both reward a second reading far more than any summary of them does.

Your agent is your teacher, and this is the point where that matters most. Bring it a claim about migrations you have read somewhere — a blog post, a linter rule, a team convention — and ask it to grade the evidence: documented guarantee, source-code fact, maintainer statement, practitioner pattern, or nothing. Doing that to three or four real claims will teach you more than re-reading any lesson here.

On spacing

Leave this a week, then come back and try to reconstruct, without notes: lesson 4’s three surprising rows, lesson 5’s three actors, lesson 6’s four steps, and lesson 16’s one-sentence summary of what the compare-and-swap does and does not catch. Whatever you cannot produce is what to re-read — and only that. What this topic could not establish is listed in unverified claims, and the vocabulary it settled on is in the glossary.
