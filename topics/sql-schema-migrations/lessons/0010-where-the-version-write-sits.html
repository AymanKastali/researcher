Lesson 0010

Where the version write sits

Is alembic_version updated inside the transaction that ran your migration? One line of source answers it, the answer is not configurable, and it is the reason a failed deploy on PostgreSQL is recoverable and on MySQL is not.

Lesson 9 ended with a question the documentation does not answer. The source answers it in one with block — and then hands you a second question, about where the transaction boundary actually is, which turns out to be a two-line truth table.

The ordering: always, and after

Python Quoted from alembic/runtime/migration.py:610-630 (1.14.1) 
assert self._migrations_fn is not None
for step in self._migrations_fn(heads, self):
    with self.begin_transaction(_per_migration=True):
        if self.as_sql and not head_maintainer.heads:
            # for offline mode, include a CREATE TABLE from
            # the base
            assert self.connection is not None
            self._version.create(self.connection)
        log.info("Running %s", step)
        if self.as_sql:
            self.impl.static_output(
                "-- Running %s" % (step.short_log,)
            )
        step.migration_fn(**kw)

        # previously, we wouldn't stamp per migration
        # if we were in a transaction, however given the more
        # complex model that involves any number of inserts
        # and row-targeted updates and deletes, it's simpler for now
        # just to run the operations on every version
        head_maintainer.update_to_step(step)
Two lines are the whole answer

step.migration_fn(**kw) — line 623 — is your revision script’s upgrade().

head_maintainer.update_to_step(step) — line 630 — is the alembic_version write.

They share one with block, and the body comes first. The version row is written after your DDL, in the same scope. This is not configurable.

The comment at lines 625–629 is worth reading as history: Alembic used to skip the per-migration stamp when the whole run was already inside a transaction, and now always emits it. Behaviour people rely on is often the residue of a simplification.

But which transaction?

The with block above settles the ordering. It does not settle the boundary, because begin_transaction may not open a real transaction at all. That decision is one line:

Python Quoted from alembic/runtime/migration.py:413-419 (1.14.1) 
if self._in_external_transaction:
    return nullcontext()

if self.impl.transactional_ddl:
    transaction_now = _per_migration == self._transaction_per_migration
else:
    transaction_now = _per_migration is True

begin_transaction is called from exactly two places: your env.py, with no arguments — so _per_migration=False — and run_migrations above, once per step, with _per_migration=True. Line 417 is an equality between two booleans, which makes the behaviour a truth table:

transaction_now on a transactional-DDL backend, by configuration and call site.
transaction_per_migration Outer call (env.py) Per-step call
False (the default) Real transaction nullcontext()
True nullcontext() Real transaction
Exactly one level opens a transaction

Never both, never neither. So on PostgreSQL with defaults, a single transaction wraps the entire alembic upgrade command — every migration body and every version-table write for the whole run commits or rolls back together.

Set transaction_per_migration=True and the unit becomes one revision script plus its own stamp. That is the only choice on offer, and it is a real one: ten revisions as one atom, or ten atoms.

Line 418 — the else branch — is the non-transactional-DDL case: MySQL, SQLite and Oracle always take the per-step path regardless of the setting. There is no point holding a run-wide transaction open around DDL the server has already committed behind your back, which is lesson 2’s implicit commit showing up in a tool’s control flow.

And line 413 is an escape hatch worth knowing about: if the Connection handed to configure() was already inside a transaction, Alembic opens and closes nothing — the embedding application owns the boundary. That is implementation detail, not a documented promise.

Which backends Alembic believes have transactional DDL

transactional_ddl is a class attribute on the dialect impl, overridable per-run via EnvironmentContext.configure(transactional_ddl=…):

Read directly from the 1.14.1 tree. Two of six are True.
Impl file:line Value
DefaultImpl alembic/ddl/impl.py:97 False
PostgresqlImpl alembic/ddl/postgresql.py:81 True
MSSQLImpl alembic/ddl/mssql.py:53 True
MySQLImpl alembic/ddl/mysql.py:44 False
SQLiteImpl alembic/ddl/sqlite.py:43 False
OracleImpl alembic/ddl/oracle.py:37 False

The default is False, so a third-party dialect that says nothing is assumed non-transactional — a conservative default, and the right one.

A claim about the backend, not a universal truth

PostgresqlImpl.transactional_ddl = True is a generalisation. Lesson 1 established that PostgreSQL has statements which cannot run inside a transaction block at all — which is precisely why Alembic also ships autocommit_block(), a context manager for stepping outside the run-wide transaction to issue a CREATE INDEX CONCURRENTLY.

Using it means that portion of your migration has no rollback, and leaves behind exactly the invalid index lesson 2 described.

What the documentation promises, and what it does not

Note what it does not say

Nothing in the published API promises that the version row is written after the body, or inside the same scope. That is behaviour of this tree, established by reading it.

It is entirely load-bearing — lesson 16 shows the whole concurrency story turns on this ordering — and it is undocumented. That combination is worth noticing whenever you find it.

Why the ordering matters

Same code, two outcomes, decided entirely by the backend.
Backend DDL and version write are… A failure leaves
PostgreSQL, MSSQL In one real transaction Nothing. Both roll back together — the schema and the version row stay consistent
MySQL, SQLite, Oracle Not in any transaction — the DDL committed itself on the way past A changed schema and a version row that does not describe it. Repair is manual
Check yourself

With Alembic’s defaults on PostgreSQL, what is the unit of rollback for alembic upgrade head across ten revisions?

With transaction_per_migration at its default of False, the outer call in env.py opens the real transaction and every per-step call returns nullcontext(). So one transaction wraps the whole command. The first answer describes what you get by setting that flag to True — a real option, just not the default.

Check yourself

Where is the alembic_version write relative to your upgrade()?

step.migration_fn(**kw) then head_maintainer.update_to_step(step), both inside one with self.begin_transaction(...). The last answer describes Alembic’s older behaviour, which the source comment at lines 625–629 explicitly records as having been removed in favour of always stamping.

The question this leaves open

Alembic runs “the revisions the database has not run”. Computing that set requires a graph — and once two people can add revisions independently, that graph has branches, merges and more than one end. What a merge actually is, in the source, is far simpler than the ceremony around it suggests: lesson 11.

The source itself. Install it — uv pip install --target ./alembic-src "alembic==1.14.1" "SQLAlchemy==2.0.36" — and read alembic/runtime/migration.py from run_migrations at line 592 to the end of HeadMaintainer. It is about 250 lines and it is the most consequential file in the package. Everything in lessons 10 and 16 is in it.

Your agent is your teacher. A good thing to work through together: what would break if the version write came before the migration body instead of after? The answer differs by backend, and reasoning it out is the best preparation for lesson 16 you can do.
