Lesson 0006

NOT VALID and VALIDATE

Splitting one long lock into a short lock plus a long weak one. The documented pattern, the reason it is sound, and the recipe the manual never quite assembles for you.

Adding a constraint has to check that existing rows satisfy it, and that check is a full scan under a strong lock — the exact combination lesson 5 showed is lethal. PostgreSQL’s answer is to separate the two things the single statement was doing, and the reasoning behind it is quoted in full below because it is the clearest paragraph on the whole ALTER TABLE page.

The pattern, as documented

Now the part that explains why this is sound rather than merely convenient. Read it twice — it is the load-bearing sentence:

Why the second step can afford a weak lock

Once the constraint exists — even unvalidated — it is already being enforced against every new write. So the set of rows that could possibly violate it is frozen at the moment of the ADD CONSTRAINT, and it can only shrink.

The validation scan is therefore checking a closed set, and needs no protection from concurrent writers. That is the entire argument, and it is why the pattern is a genuine result rather than a trick.

What each step actually costs

One expensive statement becomes two cheap ones — but not in the way most people assume.
Step Lock Duration Blocks
ADD CONSTRAINT … CHECK … NOT VALID ACCESS EXCLUSIVE Instant — no scan Everything, for a moment
ADD CONSTRAINT … FOREIGN KEY … NOT VALID SHARE ROW EXCLUSIVE, both tables Instant — no scan Writes, for a moment
VALIDATE CONSTRAINT SHARE UPDATE EXCLUSIVE Long — full scan Nothing you care about
The misconception this lesson exists to kill

NOT VALID removes the scan, not the lock. ADD CHECK … NOT VALID still takes ACCESS EXCLUSIVE — the strongest lock there is.

It is safe because the lock is held briefly. And because lesson 5 showed that a brief lock you have to wait for is still an outage, lock_timeout around step one is mandatory, not optional. Step two barely needs it.

The second use, which is easy to miss

The same paragraph ends with a purpose that has nothing to do with concurrency:

NOT VALID is the sanctioned way to adopt a constraint over dirty data. It freezes the violation set at the moment of the ALTER and lets you clean up behind it, with the guarantee that the mess cannot grow while you work. Most people meet this option as a performance trick and never learn it is also a data-quality tool.

The recipe the manual never assembles

SET NOT NULL is the operation people most want to make safe, and PostgreSQL documents every piece of the answer — on three different parts of the same page, without ever putting them together. Here are the pieces:

Put that beside the two quotations above, and the sequence assembles itself:

SQL Written for this lesson 
-- Step 1. Instant. ACCESS EXCLUSIVE, held momentarily -- needs lock_timeout.
ALTER TABLE orders
  ADD CONSTRAINT orders_shipped_at_not_null
  CHECK (shipped_at IS NOT NULL) NOT VALID;

-- Step 2. Long. SHARE UPDATE EXCLUSIVE -- reads and writes carry on.
ALTER TABLE orders VALIDATE CONSTRAINT orders_shipped_at_not_null;

-- Step 3. Instant. The scan is SKIPPED, because a valid CHECK proves no NULL.
ALTER TABLE orders ALTER COLUMN shipped_at SET NOT NULL;

-- Step 4. Optional. The CHECK is now redundant with the NOT NULL.
ALTER TABLE orders DROP CONSTRAINT orders_shipped_at_not_null;

Four statements, and the only long one runs under a lock that blocks nothing. Compare the naive version — a single SET NOT NULL that scans the whole table under ACCESS EXCLUSIVE, with the whole application queued behind it.

Two details that will bite you

Step 3 is not optional and not cosmetic. A CHECK (col IS NOT NULL) is not a NOT NULL constraint: the column is still nullable as far as the catalog, the planner, and every tool that reflects your schema is concerned. Stopping at step 2 leaves you with the enforcement but not the declaration.

“and is not dropped in the same command” — the parenthesis in the quotation is doing real work. Batching step 3 and step 4 into one ALTER TABLE defeats the optimisation and you get the full scan back, under ACCESS EXCLUSIVE. Run them separately.

Check yourself

What does NOT VALID change about ADD CONSTRAINT … CHECK?

The lock is unchanged — ACCESS EXCLUSIVE, the same as any ADD CHECK. What goes away is the verification scan, so the lock is held for an instant. And enforcement is immediate: the constraint applies to every new insert and update from the moment it exists, which is precisely why the later validation can use a weak lock.

Check yourself

Why can VALIDATE CONSTRAINT run under a weak lock?

The manual’s own reasoning: “it knows that other transactions will be enforcing the constraint for rows that they insert or update; only pre-existing rows need to be checked”. The set of possible violators is closed at the moment of the ADD CONSTRAINT and can only shrink, so the scan needs no protection from writers. It is a full scan, not a sample, and it is synchronous.

The question this leaves open

The two-step pattern gets scans out from under strong locks. Index creation has the same problem and a different answer — one with a much larger set of operational traps attached. Lesson 7.

Watching the four-step recipe assemble from three widely separated paragraphs is the actual lesson; recipes you assemble yourself are the ones you can regenerate later.

Your agent is your teacher. Good challenge to set it: ask what goes wrong if you run the four steps in one transaction, or if you merge steps 3 and 4 into a single ALTER TABLE. Both have real answers that follow from things you already know, and working them out beats being told.

On spacing

The four-step sequence is the single most reusable thing in this topic. Do not re-read it — tomorrow, write it out from memory and then check, including which lock each step takes.
