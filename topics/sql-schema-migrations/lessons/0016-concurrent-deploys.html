Lesson 0016

Concurrent deploys

What does Alembic do when two instances run alembic upgrade head at once? Nothing. Establishing that properly — as an absence, with evidence — is the whole lesson.

This is the question everyone asks first and the one with the shortest honest answer. But “the tool provides nothing” is a claim that has to be established rather than asserted, and the method for proving an absence is more transferable than the conclusion.

The documentation contains no concurrency material at all

Searching a few likely pages is not sufficient to prove an absence, so the whole published search index was searched instead — https://alembic.sqlalchemy.org/en/latest/searchindex.js, which covers every page including the full changelog. Stemmed token counts, run while writing this lesson:

Five zeroes prove nothing on their own — they are equally consistent with a broken search. The right-hand column establishes that the index and the method both work: terms that should be there are found.

There is no page, paragraph, or changelog entry in the Alembic documentation about running migrations concurrently, about mutual exclusion, about advisory locks, or about rolling deploys. The single deploy hit is a cookbook sentence about slow DDL, not concurrency.

The source contains no locking primitive

An exhaustive grep over the entire installed 1.14.1 package:

$ grep -rniE "advisory|for_update|for update|lock" alembic/ | wc -l
35
$ grep -rniE "advisory|for_update|for update|lock" alembic/ \

All 35 hits are the English word block — autocommit_block, prose about “transaction block”, test names, a comment reading “assert outside the block”. Zero hits for advisory, pg_advisory, FOR UPDATE, LOCK TABLE, threading.Lock, or any mutex of any kind.

Alembic 1.14.1 has no built-in mutual exclusion of any form. Nothing serialises two alembic upgrade head processes except the database’s own transaction semantics.

The read that starts every run is a bare SELECT

Python Quoted from alembic/runtime/migration.py:533-539 (1.14.1) 
assert self.connection is not None
return tuple(
    row[0]
    for row in self.connection.execute(
        _select(self._version.c.version_num)
    )
)

No .with_for_update(), no execution option. It compiles to SELECT alembic_version.version_num FROM alembic_version. Two processes starting together both read the same head and both compute the same list of migrations to run.

There is a second, narrower race on a virgin database. _ensure_version_table uses self._version.create(self.connection, checkfirst=True), and checkfirst=True is a read-then-write with no lock: two processes can both observe the table as absent and both attempt the CREATE. Because it is guarded by not heads, this window exists on first-ever deploy only — which is exactly when nobody is watching.

What it catches, and what it does not

The ordering from lesson 10 is the whole story

head_maintainer.update_to_step(step) runs at line 630, after step.migration_fn(**kw) at line 623. The CREATE TABLE and ALTER TABLE statements have already been issued before the version row is touched.

So the compare-and-swap catches the bookkeeping race — it will not let two processes both stamp — but it cannot prevent the DDL race, because the DDL has already happened by the time it runs.

The loser of the race, by backend. Same code, two very different outcomes.
Backend What happens to the loser
Transactional DDL — PostgreSQL, MSSQL The DDL and the version UPDATE are in one transaction, so the loser’s CommandError rolls the DDL back with it. An ugly failure, but a safe one
Non-transactional DDL — MySQL, SQLite, Oracle The DDL has already committed and cannot be rolled back. The loser leaves the schema half-changed and the version table inconsistent with it

Three further preconditions narrow the guard:

When the only guard is not in effect.
Situation Behaviour Evidence
Loser’s UPDATE matches 0 rows CommandError: Online migration expected to match one row when updating …; 0 found migration.py:806-817
Branch-create step (an INSERT) No check at all migration.py:759-767
Offline (--sql) Check disabled — not self.context.as_sql migration.py:806-811
Dialect without sane rowcount Check disabled migration.py:808

supports_sane_rowcount is True on all five major dialects in SQLAlchemy 2.0.36, so in practice only the offline and INSERT exclusions bite.

The defensible summary

The compare-and-swap serialises the bookkeeping, converting a concurrent run into a rolled-back CommandError on transactional-DDL backends — not into a correct queued migration, and not into anything at all on the backends that need it most.

The maintainer’s position

The absence is deliberate, and the project says so — on the issue tracker, which is authoritative about intent and carries no versioned guarantee:

And, asked directly about running migrations on every instance start:

“Run migrations as a separate step, before rolling out application instances” is the near-universal recommendation, and the quotation above is the only first-party support it has anywhere. It is not in the Alembic documentation — the search above proves that — nor in SQLAlchemy’s nor PostgreSQL’s.

Everything beyond it — Kubernetes init containers, Job-before-Deployment ordering, Helm pre-install hooks — is unverified practitioner consensus. It may well be right. It is not sourced, and this topic will not pretend otherwise.

If you must serialise it yourself

Since Alembic provides nothing, the exclusion has to come from the database, and env.py is the place to put it. PostgreSQL’s advisory locks are the fit:

The session/transaction distinction is the crux:

Python Written for this lesson — a sketch, not a recipe with an owner 
from sqlalchemy import text

# In env.py, inside run_migrations_online(), before context.run_migrations().
# The key is any constant you choose; every migrator must use the same one.
MIGRATION_LOCK_KEY = 0x4D494752  # "MIGR"

with connectable.connect() as connection:
    context.configure(connection=connection, target_metadata=target_metadata)

    with context.begin_transaction():
        got_it = connection.scalar(
            text("SELECT pg_try_advisory_xact_lock(:k)"), {"k": MIGRATION_LOCK_KEY}
        )
        if not got_it:
            # Someone else is migrating. Exit zero and let them finish,
            # rather than queueing behind them.
            return
        context.run_migrations()
    # Transaction-level lock is released automatically at transaction end.

pg_advisory_xact_lock(key) “obtains an exclusive transaction-level advisory lock, waiting if necessary”; pg_try_advisory_xact_lock(key) “will either obtain the lock immediately and return true, or return false without waiting” (9.27.10). The try_ forms are what you want in a deploy pipeline.

Two caveats, both sourced

The maintainer’s own suggestion has a known hole. The LOCK TABLE alembic_version IN ACCESS EXCLUSIVE MODE recipe in issue #633 cannot protect the case where the table does not exist yet — the virgin-database race above. An advisory lock does not depend on the table existing, which is why later commenters moved to pg_advisory_xact_lock. Those specific env.py recipes are user comments; the maintainer explicitly declined to endorse them.

Session-level advisory locks and connection poolers do not mix. PostgreSQL’s manual does not discuss pooling at all. The first-party statement comes from PgBouncer’s own feature matrix, which lists “Session-level advisory locks” as Yes under session pooling and Never under transaction pooling (PgBouncer Features). That is the concrete reason to prefer the _xact_ form — with the corresponding limitation that a transaction-scoped lock cannot span a multi-transaction run, so transaction_per_migration or an autocommit_block steps outside its protection.

A deploy gate that is documented

Separately from exclusion, the cookbook documents a read-only check that the database is at head, useful as a pipeline gate:

...

FAILED: Database is not on all head revisions
Note the version

--check-heads arrived in 1.17.1, so it is not available on 1.14.1. On the version you are learning, the same check has to be the hand-rolled recipe the cookbook also gives: compare ScriptDirectory.get_heads() against MigrationContext.get_current_heads().

And either way it is a gate, not a lock: it tells you whether to proceed, not whether anyone else is already proceeding.

Check yourself

Two instances run alembic upgrade head simultaneously against PostgreSQL. What happens?

Nothing serialises them: the opening read is a bare SELECT, so both compute the same work and both issue the DDL. The compare-and-swap runs after the body, so the loser matches zero rows and raises CommandError — and because PostgreSQL has transactional DDL, that rolls its schema changes back too. Ugly, but safe. On MySQL the loser’s DDL would already be committed.

Check yourself

Which advisory lock scope suits a migration running behind a connection pooler?

PgBouncer lists session-level advisory locks as Never supported under transaction pooling, which rules out both session-level answers however they are released. The transaction-level form — pg_try_advisory_xact_lock — is released at transaction end, so a pooler reassigning the connection cannot strand it, and the try_ prefix lets a second migrator exit zero rather than queue. A LOCK TABLE on alembic_version is the maintainer’s own suggestion and has the hole described above: it cannot protect a database where the table does not exist yet.

The question this leaves open

This lesson leaned on four different grades of evidence — a documented guarantee, source code, a maintainer comment, and an argument from absence — and the difference between them mattered every time. That is worth making explicit, because it is the part of this topic that survives the next release. Lesson 17.

sqlalchemy/alembic issue #633 — read the whole thread, 2019 to 2025. Watch the community converge on advisory locks while the maintainer declines to bless any of it.

Your agent is your teacher. Worth doing together: take the env.py sketch above and find its holes. What happens if the migration needs an autocommit_block? What if the second migrator exits zero but the first then fails? Neither has a documented answer, which is exactly why working it out matters.

On spacing

Two things to retain: Alembic provides no mutual exclusion at all, and the compare-and-swap runs after the DDL, not before. The second is what makes the first survivable on PostgreSQL and dangerous everywhere else. The exclusions are tabulated in the internals map, and the serialising recipe is in the safe migration recipes.
