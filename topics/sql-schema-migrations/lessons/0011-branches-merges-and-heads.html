Lesson 0011

Branches, merges and heads

A merge revision is a tuple. That is the entire definition, and once you have it, branch labels, multiple heads and upgrade head all reduce to set arithmetic on a graph.

Branching is where Alembic acquires a reputation for complexity. Most of that reputation belongs to the vocabulary rather than the mechanism — which is small enough to state in one property, one set difference, and one distinction that the documentation makes and almost nobody notices.

A merge revision is a tuple

There is no merge type, no merge flag, no marker in the file. A revision’s down_revision is normally a string; when it is a tuple of two or more, the revision is a merge point:

Python Quoted from alembic/script/revision.py:1698-1702 (1.14.1) 
@property
def is_merge_point(self) -> bool:
    """Return True if this :class:`.Script` is a merge point."""

    return len(self._versioned_down_revisions) > 1
That is the whole definition

alembic merge is not a special operation. It writes an ordinary revision file whose down_revision happens to be a tuple:

down_revision = ("4f2c1a9b8e30", "9c03ee41d7ab")

Everything that follows — the two heads collapsing into one, the version table going from two rows to one — is a consequence of that tuple, not of any merge machinery.

Three different meanings of “below me”

Lesson 9’s revision template had a fourth variable you have not used yet: depends_on. It sits alongside down_revision, and the split between them is what makes the rest of the module legible:

Three properties on Revision, alembic/script/revision.py:1625-1645. Each is used for exactly one thing.
Property Contents Used for
_versioned_down_revisions down_revision only The version table, and is_merge_point
_all_down_revisions down_revision + all resolved dependencies Cycle detection
_normalized_down_revisions down_revision + dependencies not already implied by an ancestor Traversal order
The consequence worth keeping

A revision with one down_revision and three depends_on entries is not a merge point and never collapses rows in alembic_version.

Dependencies order the run; they do not define lineage.

The source’s own docstring says exactly this:

How heads are computed

RevisionMap._revision_map builds the whole graph in one pass. The algorithm is optimistic-then-subtractive, which is a nice trick: assume everything is a head, then take away everything that something points at.

Python Quoted from alembic/script/revision.py:238-249 (1.14.1) 
for rev in map_.values():
    for downrev in rev._all_down_revisions:
        if downrev not in map_:
            util.warn(
                "Revision %s referenced from %s is not present"
                % (downrev, rev)
            )
        down_revision = map_[downrev]
        down_revision.add_nextrev(rev)
        if downrev in rev._versioned_down_revisions:
            heads.discard(down_revision)
        _real_heads.discard(down_revision)

The two discard lines are the distinction again, in executable form. A pure depends_on link removes the target from _real_heads but leaves it a versioned head — because the second discard is unconditional and the first is guarded.

A wart worth recognising in the wild

Look at the if downrev not in map_ branch. It calls util.warn(...) and then falls straight through to map_[downrev] — which raises KeyError on the very next line.

The warning never reaches you as a warning. If you delete a revision file that another file still points at, what you get is a bare KeyError, not the helpful message sitting right there in the source.

Addressing: head, heads, and the rest

Lesson 9 noted that revision ids may not contain @, - or +. Here is what those characters are reserved for. _resolve_revision_number decodes the symbols, and two details are easy to miss:

Symbolic targets, from alembic/script/revision.py:748-786.
You write It resolves to
base, or nothing The empty tuple — “before everything”
head The single head — raises MultipleHeads if there is more than one
heads _real_heads — dependency-aware
mybranch@heads filter_for_lineage(self.heads, …) — the versioned heads. An asymmetry, and undocumented
mybranch@head The one head on that labelled branch
abc123+2, head-1 Relative offsets. The regex requires the offset — absolute targets take a different path entirely

Partial revision ids work, with a hard four-character floor — if x and len(x) > 3 and x.startswith(resolved_id), revision.py:631. Three characters will not match, and the error tells you so.

Upgrade and downgrade are set arithmetic

After all that graph machinery, deciding what to run is one line:

Python Quoted from alembic/script/revision.py:1508 (1.14.1) 
needs = required_node_set.difference(current_node_set)
The sentence to keep

Upgrade set = ancestors(target) − ancestors(current).

Both sides are computed with _get_ancestor_nodes(..., include_dependencies=True) unioned with their targets. Downgrade is the mirror: collect the descendants of the roots being dropped, then intersect with what is currently active.

The resulting set is then topologically sorted. One detail explains an otherwise baffling line elsewhere in the codebase: the sort yields newest-first, so ScriptDirectory._upgrade_revs reverses it, because an upgrade must run oldest-first.

The errors, and why they say what they say

The error hierarchy in revision.py. All are converted to util.CommandError at the ScriptDirectory boundary by _catch_revision_errors.
Error Means
MultipleHeads “Multiple heads are present for given argument” — you said head and there are two. Merge, or say <branchname>@head
RangeNotAncestorError “Revision X is not an ancestor of revision Y” — you asked for a range across unrelated lines
ResolutionError The identifier matched nothing, or matched ambiguously
CycleDetected, DependencyCycleDetected, LoopDetected The pointers form a loop — detected using _all_down_revisions, so dependencies count here

That conversion is where the familiar advice to use '<branchname>@head' comes from — it is written into the error text, not into the documentation you were reading when you hit it.

Check yourself

What makes a revision a merge point?

return len(self._versioned_down_revisions) > 1, and _versioned_down_revisions is down_revision alone. Dependencies are explicitly excluded — that is the whole reason the three “below me” properties exist. And two rows in the version table are the situation a merge resolves, not what defines one.

Check yourself

You add depends_on to a revision. What changes in alembic_version?

The version table follows _versioned_down_revisions, which is down_revision only. In the heads loop, a pure dependency link hits the unconditional _real_heads.discard(...) but not the guarded heads.discard(...) — so the target stays a versioned head and keeps its row. Dependencies order the run and nothing else.

The question this leaves open

You now know how Alembic decides which revisions to run. The next question is where their contents come from when you do not write them yourself — and what a machine comparing your models to your database is structurally incapable of noticing. Lesson 12.

Alembic documentation, “Working with Branches” — the one Alembic doc page that is genuinely worth reading end to end. It works through creating a branch, labelling it, and merging it, with the version table printed at each step. Read it knowing that every diagram in it is a picture of a tuple.

Your agent is your teacher. Worth asking it to walk through: two developers each add a revision off the same parent, and both merge to main. What is in alembic_version before and after alembic merge, and what would alembic upgrade head do in between? Working the set arithmetic on a concrete case is what makes this stick.
