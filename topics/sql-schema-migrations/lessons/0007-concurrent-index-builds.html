Lesson 0007

Concurrent index builds

The other way to move work out from under a strong lock — and the one place in the PostgreSQL manual that blesses a multi-step recipe outright. Plus the waiting clause that quietly stalls the whole thing.

A plain CREATE INDEX takes SHARE, which blocks every write for as long as the build takes. CONCURRENTLY trades that for SHARE UPDATE EXCLUSIVE — blocking nothing — and the manual is unusually candid about what the trade costs.

What you get

What it costs, stated just as plainly

The operational trap is in the middle clause

“it must wait for all existing transactions that could potentially modify or use the index to terminate.”

A concurrent build cannot finish while any long-running transaction that predates it is still open. One forgotten idle in transaction session stalls the build indefinitely — and unlike lesson 5’s convoy, this stall is silent: nothing is blocked, nothing errors, the build simply never completes.

Worse, it does not end at completion. The manual: “in the worst case, it cannot be used as long as transactions exist that predate the start of the index build.” A finished index that no query plan will touch.

Concurrency restriction, narrower than usually quoted

“Regular index builds permit other regular index builds on the same table to occur simultaneously, but only one concurrent index build can occur on a table at a time.”

Two regular builds on one table may run together. Two concurrent builds may not. The restriction people repeat — “only one index build per table” — is wrong in the direction that costs you time.

And recall lesson 2: because CREATE INDEX CONCURRENTLY cannot run inside a transaction block, a failure leaves an invalid index behind — maintained by every writer, used by no query, and still enforcing uniqueness if it was unique. That is the price of stepping outside transactional protection, and it is why every concurrent build needs a follow-up check rather than just a success exit code.

The one recipe PostgreSQL blesses

The ALTER TABLE page contains something it contains nowhere else: an explicit endorsement of a multi-step technique, with the motivation stated in the same breath.

SQL Written for this lesson 
-- Step 1. Long, and blocks nothing. Cannot run inside a transaction block.
CREATE UNIQUE INDEX CONCURRENTLY orders_reference_key ON orders (reference);

-- Check it actually succeeded before going on -- a failure here is silent.
--   SELECT indisvalid FROM pg_index WHERE indexrelid = 'orders_reference_key'::regclass;

-- Step 2. Instant. Adopts the existing index instead of building a new one.
ALTER TABLE orders
  ADD CONSTRAINT orders_reference_key UNIQUE USING INDEX orders_reference_key;

The manual attaches restrictions that make the technique sound, and they are worth knowing before you reach for it: the index must be b-tree, in the default sort order, not on expressions, not partial, and not partitioned.

The same shape as lesson 6

Notice this is structurally identical to NOT VALID → VALIDATE: do the long work under a weak lock, then do the instant catalog change under a strong one.

That is the general form of every safe migration in PostgreSQL, and once you see it you will recognise it everywhere. There are only ever two moves — remove the work from under the lock, or avoid the operation entirely. Lesson 8 is the second move.

Check yourself

A CREATE INDEX CONCURRENTLY has been running for hours on a small table. Most likely cause?

The build “must wait for all existing transactions that could potentially modify or use the index to terminate”. On a small table the scans are quick, so a build measured in hours is almost always waiting on someone’s forgotten open transaction — idle_in_transaction_session_timeout is the systemic fix. A regular build would not block it: only another concurrent build on the same table would.

Check yourself

Why build the index first and adopt it as a constraint second?

Same shape as lesson 6: the scan moves under SHARE UPDATE EXCLUSIVE, leaving only an instant catalog change under the strong lock. Nothing is skipped — the uniqueness is fully checked during the concurrent build — and nothing is deferred to query time. The first answer states the motivation backwards: it is true that ADD CONSTRAINT has no CONCURRENTLY form, but the recipe is what you do about that, not why it helps.

The question this leaves open

Every technique so far moves work out from under a lock. But some operations have no safe form at all — a rewrite cannot be made cheap, and a rename cannot be made compatible. For those the only remaining move is not to perform the operation. Lesson 8 is the last lesson before the tool.

Pay attention to the paragraphs on what happens between the two scans; they explain why the wait for predating transactions is unavoidable rather than a shortcoming.
