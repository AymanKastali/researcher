Lesson 0001

DDL inside a transaction

The property every safe migration rests on, established the only way the manual allows — negatively. Plus the first lesson in sourcing: what to do when the sentence you want to quote does not exist.

Start with a negative result, because it shapes everything after it. “PostgreSQL has transactional DDL” is the first thing anyone says about migrations on PostgreSQL, and it is true. It is also not a sentence you can quote. The PostgreSQL 16 manual never affirmatively states it. Learning why, and what you can legitimately say instead, is worth more than the fact itself.

What the manual actually gives you

“All statements.” “Every SQL statement.” No exception is announced for CREATE TABLE or ALTER TABLE. That is the whole of the positive evidence, and on its own it is thin — an absence of exclusion is not an inclusion.

The property is established by its exceptions

What the manual does instead is enumerate, across a dozen separate reference pages, the specific statements that cannot run inside a transaction block. Each sentence below is from that statement’s own page.

Statements PostgreSQL 16 documents as forbidden inside a transaction block. Each restriction is quoted from that statement’s own reference page, linked in the first column.
Statement Documented restriction
CREATE INDEX CONCURRENTLY “a regular CREATE INDEX command can be performed within a transaction block, but CREATE INDEX CONCURRENTLY cannot”
DROP INDEX CONCURRENTLY “regular DROP INDEX commands can be performed within a transaction block, but DROP INDEX CONCURRENTLY cannot”
REINDEX CONCURRENTLY “a regular REINDEX TABLE or REINDEX INDEX command can be performed within a transaction block, but REINDEX CONCURRENTLY cannot”
CREATE DATABASE “CREATE DATABASE cannot be executed inside a transaction block.”
CREATE TABLESPACE “CREATE TABLESPACE cannot be executed inside a transaction block.”
VACUUM “VACUUM cannot be executed inside a transaction block.”
ALTER SYSTEM “since this command acts directly on the file system and cannot be rolled back, it is not allowed inside a transaction block or function”
ALTER TABLE … DETACH PARTITION CONCURRENTLY “CONCURRENTLY cannot be run in a transaction block”
The inference, stated as one

That enumeration would be pointless if DDL in general were not transactional. You do not carefully list the exceptions to a rule that does not exist.

So the inference is safe — and it is still an inference. The honest form of the claim is: “PostgreSQL documents which statements cannot run in a transaction block, and ALTER TABLE is not among them.” That sentence you can defend line by line.

Notice what the exceptions have in common. Every one of them either acts outside the database’s own storage (CREATE DATABASE, CREATE TABLESPACE, ALTER SYSTEM writing to the file system) or deliberately drops out of transactional protection in order to avoid blocking other sessions — which is what CONCURRENTLY means in every one of the four places it appears. That second group is the one you will actually meet, and lesson 2 is about what it costs.

Transactional does not mean MVCC-clean

One more thing to know before trusting a rewrite inside a transaction. Transactionality gets you rollback; it does not get you the isolation you might assume comes with it:

The same paragraph explains why this is usually invisible — a transaction that has already touched the table holds a lock that blocks the DDL outright, so it never gets to observe the inconsistency — and why it is not always invisible: the inconsistency shows up between the rewritten table and other tables. Hold onto the phrase “the table-rewriting forms of ALTER TABLE”. Which subforms those are is the subject of lesson 4, and it is the most useful list in this topic.

What this buys a migration

The payoff is composition. On a transactional backend you can put five schema changes in one transaction and know that either all five land or none do — so a migration that fails on the fourth statement leaves a database that looks exactly as it did before it started.

That guarantee is the reason migrations on PostgreSQL feel safe, and it is worth noticing now that it is a property of the engine, not of any migration tool. No tool can give it to you on a backend that does not have it, and lesson 2 shows what happens on a backend that does not.

Check yourself

How does the PostgreSQL 16 manual establish that DDL is transactional?

There is no affirmative sentence anywhere. The property is established negatively: BEGIN is defined over “all statements” without carving DDL out, and a dozen reference pages then enumerate the specific statements that cannot run inside a transaction block — an enumeration that would be pointless if the general rule did not hold. The MVCC chapter says the opposite of the fourth answer: it is where the caveat lives.

Check yourself

On PostgreSQL 16, what happens to ALTER TYPE … ADD VALUE inside a transaction?

The prohibition was relaxed in PostgreSQL 12; what survives is the narrower restriction that “the new value cannot be used until after the transaction has been committed”. The first answer is the PostgreSQL 11 wording, which is still what most circulating advice says — which is the point of teaching the two pages side by side.

The question this leaves open

If a migration inside a transaction either lands completely or not at all, then a failure leaves nothing behind — which sounds like the end of the story. It is not, for two reasons: the statements on the exception list above are not protected by any transaction, and not every database works this way at all. Lesson 2 is about the mess.

Read next, from the source

PostgreSQL 16, 3.4. Transactions — two pages, and the clearest statement of the implicit-transaction model you will find. Then skim BEGIN with one question in mind: notice that it never mentions DDL, and notice that you now know why that silence is the evidence rather than a gap.

Your agent is your teacher. The argument in this lesson is an inference rather than a quotation, which makes it exactly the kind of claim worth attacking — try to construct a reading of the manual in which DDL is not transactional and see what breaks. If you find a PostgreSQL page that states the property outright, that is a genuine correction and worth bringing back.

On spacing

Before opening lesson 2, close this page and try to say out loud what the two halves of the argument are — what BEGIN gives you, and what the exception list gives you. Getting it half right and then checking is worth more than reading this page again now. The list itself is lookup material and lives in the lock and rewrite ledger.
