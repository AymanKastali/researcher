Lesson 0009

What Alembic is

Orientation, from zero: a revision file, a pointer, and a table with one column. Four ideas, and everything in lessons 10–16 is a consequence of them.

The second half of this topic takes one tool apart. Before that can be interesting, the tool has to exist for you — so this lesson establishes the four things Alembic is made of and nothing else. If you have written migrations before, it is five minutes. If you have not, it is the lesson the rest depends on.

A caveat that applies to every Alembic quote in this topic

There is no published Alembic 1.14 documentation. /en/rel_1_14/ is not published and /en/release-1.14.0/ returns HTTP 404.

Every documentation quotation in lessons 9–16 is therefore from the current published docs, checked against 1.14.1 source read on disk. Where the two disagree — and they do, in five specific places — these lessons prefer the source and say so at the time. Lesson 17 collects the disagreements.

1. A revision is a file with two functions

Alembic generates migration scripts from a template. This is the real template shipped in 1.14.1 — not a paraphrase:

Python Quoted from alembic/templates/generic/script.py.mako (1.14.1) 
"""${message}

Revision ID: ${up_revision}
Revises: ${down_revision | comma,n}
Create Date: ${create_date}

"""
from typing import Sequence, Union

from alembic import op
import sqlalchemy as sa

# revision identifiers, used by Alembic.
revision: str = ${repr(up_revision)}
down_revision: Union[str, None] = ${repr(down_revision)}
branch_labels: Union[str, Sequence[str], None] = ${repr(branch_labels)}
depends_on: Union[str, Sequence[str], None] = ${repr(depends_on)}


def upgrade() -> None:
    ${upgrades if upgrades else "pass"}


def downgrade() -> None:
    ${downgrades if downgrades else "pass"}

Filled in, a real migration file is unremarkable — which is the point. It is a Python module with two functions and four module-level variables:

Python Written for this lesson 
"""add shipped_at to orders

Revision ID: 4f2c1a9b8e30
Revises: 7d81b0c5a112
Create Date: 2026-09-14 11:02:41.883617

"""
from alembic import op
import sqlalchemy as sa

revision: str = "4f2c1a9b8e30"
down_revision: Union[str, None] = "7d81b0c5a112"
branch_labels = None
depends_on = None


def upgrade() -> None:
    op.add_column("orders", sa.Column("shipped_at", sa.DateTime(timezone=True)))


def downgrade() -> None:
    op.drop_column("orders", "shipped_at")

The identifier is not meaningful — it is twelve hex characters, uuid.uuid4().hex[-12:] (alembic/util/langhelpers.py:232-233). And it may not contain @, - or +, because those three characters are reserved for an addressing syntax you will meet in lesson 11:

Python Quoted from alembic/script/revision.py:47-48 (1.14.1) 
_relative_destination = re.compile(r"(?:(.+?)@)?(\w+)?((?:\+|-)\d+)")
_revision_illegal_chars = ["@", "-", "+"]

2. down_revision is the whole ordering mechanism

A linked list, pointing backwards

Each file names its predecessor. There is no ordering file, no sequence number, no timestamp that decides anything — the order is reconstructed from the pointers every time Alembic runs.

A down_revision of None marks the first file, the base. A revision nothing points down to is a head. Those two words are the vocabulary of the whole second half.

3. alembic_version records where the database is

The structure is four lines of source. In 1.14.1 it moved behind a dialect hook, DefaultImpl.version_table_impl:

Python Quoted from alembic/ddl/impl.py:161-172 (1.14.1) 
vt = Table(
    version_table,
    MetaData(),
    Column("version_num", String(32), nullable=False),
    schema=version_table_schema,
)
if version_table_pk:
    vt.append_constraint(
        PrimaryKeyConstraint(
            "version_num", name=f"{version_table}_pkc"
        )
    )

So on PostgreSQL the table Alembic creates for you is exactly this:

SQL Written for this lesson, from the source above 
CREATE TABLE alembic_version (
    version_num VARCHAR(32) NOT NULL,
    CONSTRAINT alembic_version_pkc PRIMARY KEY (version_num)
)
Two details worth carrying forward

The row count is not always one. It is the number of current heads — one row per unmerged branch. That is why the column is not declared unique-to-one-row, and why get_current_revision() raises rather than guess when there is more than one.

The width is not a contract. The column name is — the hook’s own docstring requires a replacement table to contain “at least a single string-holding column named version_num”. But 32 is a bare literal with no named constant anywhere in the package, and generated ids use only 12 of those characters.

4. upgrade runs the ones that have not run

The commands referred to in the rest of this topic.
Command What it does
alembic upgrade head Run every revision the database has not yet run
alembic downgrade -1 Reverse one revision, using its downgrade()
alembic revision -m "…" Write a new empty revision file from the template above
alembic revision --autogenerate Write one with the body filled in by comparing your models to the database — lesson 12
alembic upgrade head --sql Print the SQL instead of running it — lesson 14
alembic current, alembic history Report where the database is, and what exists

That is the whole model

Files that point backwards, a table holding where you are, and a command that runs the difference. Everything from here on is a question about the gaps in that sentence — which difference, in what transaction, and what happens when two processes compute the same difference at once.

Check yourself

How does Alembic determine the order to apply migrations in?

down_revision is the entire mechanism — the graph is rebuilt from the pointers on every run. The header timestamp is a comment; filenames carry a slug rather than a sequence; and alembic_version holds only where the database currently is, not a history. This is why two people can add revisions on separate branches and produce two heads rather than a conflict.

Check yourself

How many rows can alembic_version hold?

The table holds the current heads — one row per unmerged branch. The primary key is on version_num, which prevents duplicate values rather than multiple rows. It is not a history: applied revisions leave no trace once superseded, which is exactly why downgrade needs the files rather than the table.

The question this leaves open

“It looks in this table for the current version” — and when does it write to it? Before your migration body or after? Inside the same transaction or outside it? The answer is not configurable, not documented, and decides what a failed deploy leaves behind. Lesson 10.
