Lesson 0004

The lock and rewrite table

Two independent costs — which lock, and how much work under it — and the three rows where everyone’s intuition is wrong. This is the table you will come back to.

Every ALTER TABLE subform has two properties that decide whether it is safe, and they are independent of each other. The lock decides who waits. The work — rewrite, scan, or neither — decides how long they wait. A statement can hold the strongest lock in the system and be perfectly safe because it holds it for a millisecond, and it is the pairing, never either half alone, that tells you what will happen.

The three grades of work

Metadata-only — the catalog changes, no row is touched. Duration independent of table size.

Scan — every row is read to verify something, but nothing is written. “Adding a CHECK or NOT NULL constraint requires scanning the table to verify that existing rows meet the constraint, but does not require a table rewrite.”

Rewrite — the entire table and all its indexes are written out again. The expensive one, and — unlike a scan — there is no option anywhere that removes it.

Quotation from PostgreSQL 16, ALTER TABLE, Notes.

One cell is honestly empty

PostgreSQL 16 does not state whether ADD COLUMN with an identity or GENERATED … STORED specification rewrites the table. The ALTER TABLE page’s rewrite discussion covers volatile defaults and type changes and stops there.

The cell is marked undocumented rather than guessed. If you need the answer, test it on a copy — and treat any blog post that states it confidently as unsourced until it shows you the sentence.

The three rows that surprise people

1. A default does not mean a rewrite — and the criterion is broader than “constant”

The word is “non-volatile”, not “constant”

Any IMMUTABLE or STABLE expression qualifies for the fast path — not only a literal. The PostgreSQL tutorial says “constant default value”, which is narrower than what the reference page promises.

When two pages of the same manual disagree in precision, the reference page is the one to trust. This fast path arrived in PostgreSQL 11; on 10 and earlier, every default rewrote.

So ADD COLUMN status text DEFAULT 'pending' is metadata-only, and so is a default calling an IMMUTABLE function. ADD COLUMN created_at timestamptz DEFAULT now() — now() being STABLE, not volatile — also takes the fast path. DEFAULT random() does not: it rewrites, because each row must get a different value.

2. ADD FOREIGN KEY takes a weaker lock, on a table you did not name

Two facts in one paragraph, and the second is the one that bites. Run the lock through lesson 3’s table: SHARE ROW EXCLUSIVE permits reads and blocks every INSERT, UPDATE and DELETE — on both tables.

The shape of the surprise

Adding a foreign key to a small child table blocks writes to the large parent table you never mentioned in the statement. Your migration touches order_line_items; your outage is on orders.

And it is self-exclusive, so two foreign keys pointing at the same parent serialise against each other — two “small” migrations deployed together take twice as long as either alone.

3. NOT VALID removes the scan, not the lock

Look at the table again. ADD FOREIGN KEY … NOT VALID takes SHARE ROW EXCLUSIVE — but that is because every ADD FOREIGN KEY does, valid or not. ADD CHECK … NOT VALID still takes ACCESS EXCLUSIVE: the strongest lock in the system.

Why it is safe anyway, and why that matters

ADD CHECK … NOT VALID is safe because the lock is held briefly — no scan happens under it — and not because the lock is weak.

That distinction is not pedantry. It decides whether lock_timeout is optional or mandatory around the statement, because a lock you only need for a millisecond is still a lock you might wait an hour to get. Lesson 5 is about that hour.

MySQL exposes the same decisions as a matrix

Worth one look, because seeing another vendor decompose the same problem differently sharpens what PostgreSQL’s two properties actually are. MySQL publishes five columns per operation:

Changing a column’s data type is the only common column operation that is negative in every column — MySQL’s equivalent of PostgreSQL’s ACCESS EXCLUSIVE rewrite. Note the asymmetry, though: PostgreSQL can skip the rewrite when the new type is binary coercible, while MySQL documents no such exception beyond the narrow “Extending VARCHAR column size” row.

One asterisk carries real weight, and it is a different kind of safety than it looks:

MySQL buys onlineness by skipping the verification. PostgreSQL’s NOT VALID defers it. Those are different safety properties wearing similar-looking table rows, and the difference is the whole subject of lesson 6.

The one thing MySQL has that PostgreSQL does not

“Specifying an ALGORITHM clause requires the operation to use the specified algorithm for clauses and storage engines that support it, or fail with an error otherwise.” 15.1.9 ALTER TABLE

ALGORITHM=INPLACE and LOCK=NONE are assertions, not requests: they turn a silent downgrade into a loud failure. PostgreSQL has nothing at statement level that does this. You approximate it with lock_timeout and NOWAIT, which is a strictly weaker tool — it bounds the waiting, not the work.

Check yourself

Which of these rewrites a large PostgreSQL 16 table?

A volatile default such as gen_random_uuid() needs a distinct value per row, so the table must be rewritten. A non-volatile default — a literal, or any IMMUTABLE or STABLE expression — is evaluated once and stored in metadata. The two constraint additions scan or skip the scan; neither rewrites, because “adding a CHECK or NOT NULL constraint […] does not require a table rewrite”.

Check yourself

You add a foreign key from a small table to a huge one. What is blocked?

ADD FOREIGN KEY takes SHARE ROW EXCLUSIVE on the altered table and on the referenced table. That mode conflicts with ROW EXCLUSIVE, so writes block on both; it does not conflict with ACCESS SHARE, so reads continue. The weak-lock fact in the last answer is real but incomplete — weak is not the same as harmless.

The question this leaves open

The table says ADD CHECK … NOT VALID holds ACCESS EXCLUSIVE for a millisecond. That sounds free. It is not, and the reason is the single most consequential fact in this topic — and the one PostgreSQL refuses to write down. Lesson 5.

Your agent is your teacher. Bring it a real ALTER TABLE and ask it to place the statement in this table — lock, rewrite, scan — and to name the sentence in the manual that puts it there. If it cannot name a sentence, that is the answer being marked undocumented, which is a legitimate outcome here.

On spacing

This is a reference-shaped lesson, and rereading tables does not build retention. Instead: tomorrow, before you open lesson 5, write down from memory the three rows that surprise people and what is surprising about each.
