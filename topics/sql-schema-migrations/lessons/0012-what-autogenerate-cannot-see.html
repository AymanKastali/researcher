Lesson 0012

What autogenerate cannot see

Not a list of limitations to memorise — a proof. Nine functions are the entire detection surface, and one of them shows why a column rename can never be detected, no matter how good the heuristics get.

alembic revision --autogenerate compares your model metadata against a reflected database and writes the difference into a revision file. The interesting question is not what it detects — the documentation has a list — but what it is structurally incapable of detecting, and whether that published list is accurate. On 1.14.1 it is wrong in both directions.

The complete detection surface

Autogenerate’s entire detection surface is nine functions registered on one dispatcher in one file. A grep for comparators.dispatch_for across the whole package returns these nine lines and nothing else:

Invisible by construction, not by accident

Anything not in that table is not detected — not because it was overlooked, but because there is no code path that could look at it. This is a much stronger statement than a documentation list, and it is one you can verify yourself in about ten seconds with grep.

Two structural facts frame everything else. First, the downgrade is not computed:

Python Quoted from alembic/autogenerate/compare.py:66 (1.14.1) 
upgrade_ops.reverse_into(downgrade_ops)

Your downgrade() is the mechanical reverse of your upgrade(). It has not been checked against anything, and it has never been run. Second, only the default schema is examined unless you pass include_schemas=True — schemas = {None}, compare.py:91.

The proof that renames cannot be detected

_compare_columns is three set operations, keyed on the column’s name:

Python Quoted from alembic/autogenerate/compare.py:366-436, abridged (1.14.1) 
for cname in metadata_col_names.difference(conn_col_names):
    ...  ops.AddColumnOp.from_column_and_tablename(...)

for colname in metadata_col_names.intersection(conn_col_names):
    ...  comparators.dispatch("column")(...)

for cname in set(conn_col_names).difference(metadata_col_names):
    ...  ops.DropColumnOp.from_column_and_tablename(...)
There is no fourth pass

In the model but not the database → add. In both → compare. In the database but not the model → drop. Three sets, and every column falls into exactly one of them.

There is no similarity heuristic, no type matching, no ordinal matching — nothing that could pair a dropped name with an added one. AlterColumnOp does have a modify_name field (it is how op.alter_column(..., new_column_name=...) is expressed), but no comparator ever assigns it.

So rename detection is not a limitation that better heuristics could tighten. Rename detection requires pairing, and there is no pairing step to improve. _compare_tables has the same shape at the table level, with the same consequence.

Autogenerate will therefore turn your column rename into a drop_column plus an add_column — which is to say, it will silently write you a migration that deletes the data. That is the single most expensive thing in this lesson, and it follows directly from three for loops.

Server defaults: off by default, and crude when on

MigrationContext._compare_server_default returns False immediately unless compare_server_default=True was passed. When it is on, the generic implementation is the whole of alembic/ddl/impl.py:600-607:

Python Quoted from alembic/ddl/impl.py:600-607 (1.14.1) 
def compare_server_default(
    self,
    inspector_column,
    metadata_column,
    rendered_metadata_default,
    rendered_inspector_default,
):
    return rendered_inspector_default != rendered_metadata_default

One string comparison between two rendered defaults. server_default="0" against a database that reflects '0'::integer is a false positive — a migration generated to change nothing.

PostgreSQL does better, and does it by asking the server:

Python Quoted from alembic/ddl/postgresql.py:142-149 (1.14.1) 
# run a real compare against the server
conn = self.connection
assert conn is not None
return not conn.scalar(
    sqla_compat._select(
        literal_column(conn_col_default) == metadata_default
    )
)

It executes SELECT <conn_default> = <metadata_default> and inverts the answer — one round trip per differing column. It also exempts SERIAL primary keys outright (postgresql.py:113-118, with the comment “don’t do defaults for SERIAL columns”), so a nextval(...) default on an autoincrement primary key is never reported.

Types: a token comparison with deliberate blind spots

compare_type is on by default, but it is a token comparison rather than a semantic one: the type is compiled to a string, regex-split, and compared — with explicit synonym tables that suppress real differences by design.

Python Quoted from alembic/ddl/impl.py:99 and postgresql.py:82-84 (1.14.1) 
type_synonyms: Tuple[Set[str], ...] = ({"NUMERIC", "DECIMAL"},)

# ...and on PostgreSQL:
type_synonyms = DefaultImpl.type_synonyms + (
    {"FLOAT", "DOUBLE PRECISION"},
)

And _column_args_match deliberately ignores one-sided parameters. Its docstring, impl.py:554-558: “if they both have collation, we want to make sure they are the same. However, if only one specifies it, dont flag it for being less specific.” A collation present only in your model is never reported.

Named things only — and one designed-in silent miss

The index and constraint comparator states its own assumptions in a comment, which is unusually honest:

Python Quoted from alembic/autogenerate/compare.py:619-625 (1.14.1) 
# assumptions:
# 1. a unique constraint or an index from the connection *always*
#    has a name.
# 2. an index on the metadata side *always* has a name.
# 3. a unique constraint on the metadata side *might* have a name.
# 4. The backend may double up indexes as unique constraints and
#    vice versa (e.g. MySQL, Postgresql)

Unnamed unique constraints get a by-column-signature rescue — but an add-only one: there is no corresponding removal pass. Anonymous constraints of any other kind have no rescue at all.

“Skip” means “considered equal”

ComparisonResult.Skip means “cannot be compared”, and its docstring is explicit about the consequence:

“the constraint cannot be compared for the provided reason(s). The message is logged, but the constraints will be otherwise considered equal, meaning that no migration command will be generated.” — alembic/ddl/_autogen.py:68-73

A thing Alembic cannot understand is treated as a thing that has not changed. That is a defensible default and it is the opposite of what most people assume the word “skip” means.

Where the published list and this version part company

Source disagrees with documentation

The current documentation — Auto Generating Migrations — lists CHECK-constraint detection under “Autogenerate can optionally detect”. That feature does not exist in 1.14.1. grep for CheckConstraint in compare.py returns zero hits, and the nine-comparator registry has no entry for it.

The docs page resolves the discrepancy itself: the subsection is marked “Added in version 1.19.0” and “Changed in version 1.19.2: This feature is no longer enabled by default.” So /en/latest/ is documenting a release five minor versions after the one you are reading about. On 1.14.1, CHECK constraints are simply undetectable.

The published “can not detect” list — table renames, column renames, anonymously named constraints, Enum on backends without a native ENUM — is also considerably shorter than what the source supports. Beyond it, the code shows that all of the following are outside the comparison entirely:

Not detected in 1.14.1, established from the comparator registry rather than from a documentation list.
Category Examples
Never reflected at all Views (get_view_names is never called anywhere in the package), triggers, stored procedures, functions, extensions, grants, RLS policies, partitions
No comparator exists CHECK constraints, free-standing PRIMARY KEY and EXCLUDE constraints, sequences, computed/identity changes
Excluded by configuration Non-default schemas without include_schemas; server defaults without compare_server_default

The practical rule

Autogenerate drafts; you review. Not as a matter of discipline but because the tool is a nine-function comparison that reverses your downgrade mechanically and treats what it cannot understand as unchanged.

The review that matters most is the one for renames, because that is the failure mode that costs data rather than time.

Check yourself

Why can autogenerate never detect a column rename?

_compare_columns is three set operations on names: added, common, removed. Detecting a rename would require pairing a removed name with an added one, and there is no such pass. The last answer is specifically false — AlterColumnOp does have modify_name; no comparator ever assigns it. That is what makes this a proof rather than a missing feature.

Check yourself

On Alembic 1.14.1, what happens to a CHECK constraint you add to a model?

grep CheckConstraint alembic/autogenerate/compare.py returns zero hits on 1.14.1. The documentation does list the feature — and marks it “Added in version 1.19.0”, which is the version gap this topic warns about at every Alembic quotation. The documentation is right about a release you are not running.

The question this leaves open

Whether you wrote the revision or autogenerate drafted it, the body is a call like op.add_column(...). What turns that into PostgreSQL-specific SQL, and how much of the resulting statement is actually Alembic’s? Less than you would think. Lesson 13.

Read next, from the source

Alembic documentation, “Auto Generating Migrations” — read the “what it can detect” and “what it can not detect” lists, then check each entry against the nine-comparator table above. Reading a documentation page against the source is the transferable skill here, and this page is an unusually good one to practise on because you already know where it is wrong.

Your agent is your teacher. Ask it to run the greps in this lesson against a real 1.14.1 install — grep -rn 'comparators.dispatch_for' alembic/ and grep -c CheckConstraint alembic/autogenerate/compare.py. Watching the second one return 0 is more convincing than being told, and it is the habit that lets you check any future version for yourself.

On spacing

One thing to retain: the three set operations, and what each does. Everything else here is lookup material. If you can say why a rename is structurally undetectable, you have the part of this lesson that will still be true in Alembic 2.0. The nine comparators are tabulated in the internals map.
