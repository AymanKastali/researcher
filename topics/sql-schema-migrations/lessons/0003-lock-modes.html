Lesson 0003

Lock modes

One sentence from the manual dissolves the whole subject: a lock mode is nothing but the set of modes it conflicts with. Learn to read the names as shorthand for “who waits”, and every later lesson becomes arithmetic.

Lock mode names are the worst-designed vocabulary in PostgreSQL, and the manual says so itself. SHARE ROW EXCLUSIVE contains three words that sound like they mean something and, read as English, they mislead. There is exactly one way to make this tractable, and the manual hands it to you in a single sentence.

The definition that matters

Read this as a definition, not a remark

A lock mode is its conflict set. It has no other content — no strength, no scope, no priority. “Stronger” is a convenient shorthand for “conflicts with more”, and nothing else.

So the only question ever worth asking about a lock is: who has to wait for it?

And the names genuinely are noise. The manual is blunt:

The two modes your application takes

Before the DDL modes, the two that ordinary traffic acquires — because these are the ones your migration will be blocking:

Reads take ACCESS SHARE. Writes take ROW EXCLUSIVE. Those are the two things that get blocked, so those are the two columns of the only table you need.

Work the first row yourself as a check. SHARE UPDATE EXCLUSIVE conflicts with SHARE UPDATE EXCLUSIVE, SHARE, SHARE ROW EXCLUSIVE, EXCLUSIVE and ACCESS EXCLUSIVE. Is ACCESS SHARE on that list? No — reads continue. Is ROW EXCLUSIVE? No — writes continue. That is the entire derivation, and it works the same way for every row.

Why this decides how you read the ALTER TABLE page

The ALTER TABLE reference page has one rule in its Description that governs everything on it:

Two things follow, and both are sourced rather than guessed.

Silence is an answer, not a gap

For any subform where the page names no lock, the documented answer is ACCESS EXCLUSIVE — because the default is stated. When you read the page and find nothing about locking under DROP COLUMN, you have your answer: it blocks everything.

Batching is a real trade-off, in both directions

“When multiple subcommands are given, the lock acquired will be the strictest one required by any subcommand.” Adding a cheap SHARE ROW EXCLUSIVE foreign key alongside an ACCESS EXCLUSIVE change upgrades the whole statement to ACCESS EXCLUSIVE.

But the page also gives the reason to batch anyway:

“The main reason for providing the option to specify multiple changes in a single ALTER TABLE is that multiple table scans or rewrites can thereby be combined into a single pass over the table.”

So: batch things that all scan or rewrite, and never batch a weak-lock operation with a strong-lock one.

The last piece: waiting is unbounded

By default, a migration that cannot get its lock does not fail. It waits, forever, and so does everything behind it. Hold that thought — it is half of lesson 5, which is the most consequential lesson in this topic.

Check yourself

What, according to the manual, distinguishes one lock mode from another?

“The only real difference between one lock mode and another is the set of lock modes with which each conflicts.” Duration is uniform — to end of transaction. Scope is uniform — every mode here is table-level, which is exactly what the “names are historical” note is warning you about. And the modes carry no priority.

Check yourself

A migration holds SHARE ROW EXCLUSIVE on a table. What happens to traffic?

SHARE ROW EXCLUSIVE lists ROW EXCLUSIVE among its conflicts, so INSERT, UPDATE, DELETE and MERGE wait. It does not list ACCESS SHARE, so SELECT proceeds — which the Tip states directly: only ACCESS EXCLUSIVE blocks a plain SELECT. You can derive this from the conflict lists without memorising anything.

The question this leaves open

You can now read any lock mode as a statement about who waits. What you cannot yet do is say which lock a given ALTER TABLE subform takes, or whether it rewrites the table underneath. That table — lesson 4 — is the reference you will come back to most.

Read next, from the source

PostgreSQL 16, 13.3. Explicit Locking — read §13.3.1 in full, and study Table 13.2, “Conflicting Lock Modes”, which is the matrix this lesson derived three rows of. Reading the table once while holding the question “who waits for me?” is worth more than memorising any of it.

Your agent is your teacher. A good exercise to ask for: name a pair of modes and have yourself say, without looking, whether they conflict — then check against Table 13.2. The pairs worth drilling are SHARE UPDATE EXCLUSIVE against ROW EXCLUSIVE, and SHARE ROW EXCLUSIVE against itself.

On spacing

This lesson is short on purpose — it is one definition and one derivation. Do not space it away from lesson 4; they work as a pair, and lesson 4 is where the definition starts paying. The longer pause belongs after lesson 5. The full conflict matrix is not worth memorising; it is in the lock and rewrite ledger.
