Lesson 0007

Choosing the flow

Twenty-five skills, five flows, and one measurement that settles most of the choice. This is the lesson the rest of the topic is arranged around.

The hard part of this set is not remembering what any one skill does — the tree is on disk and greppable. The hard part is standing at the start of a piece of work and picking. Everything from here is a worked answer to this lesson.

The one measurement

Almost the whole routing decision reduces to a single question, and it is not about lines of code, difficulty, or importance:

The floor

Does the work fit in one context window?

The branch is put this way in ask-matt/SKILL.md:22-24 and in the trigger tables of both docs/engineering/to-spec.md and docs/engineering/to-tickets.md.

And the docs page states the same branch as a table you can read off:

docs/engineering/to-spec.md:13-18, verbatim.

The sentence to keep

The question is never "is this big?" — it is "will this outlive one context window?"

A three-thousand-line mechanical rename can fit one window. A forty-line change touching an unfamiliar subsystem may not. Size and span are different measurements, and only one of them routes.

There is a floor below the floor

The set says this once, in a docs page, about over-decomposition — and it is the most useful sentence in the whole routing story:

And below that, nothing at all

This is synthesis, flagged as such, because no document in the set says it. The router routes by situation and every route lands on a skill. There is no route that terminates in "just do it".

For a typo, a config bump, a one-line fix — no skill is the right answer. The ceremony has a cost, the set never names the point at which the cost exceeds the benefit, and you have to supply that judgement yourself.

The three over-reaches

Routing wrongly upward is the expensive direction — you pay the ceremony and get nothing back. The set names three by hand.

1. Wayfinder on a well-scoped feature

2. Looping a cleared map straight into the build

The CHANGELOG calls these two "The two mistakes people most often make with the heaviest, most cognitively demanding flow."

3. Triaging your own tickets

Two things available inside every flow

Neither routes anywhere; both can be reached at any moment without leaving what you are doing.

  • /wait-what — for a message that did not land. Its entire body: "Wait — I don't understand where you've got to here. Re-pitch that: give me a little bit of context, talk in ASD-STE100 Simplified Technical English, and use the ubiquitous language from CONTEXT.md." Four lines of frontmatter and one sentence, and it is the most reusable thing in the set.
  • /ask-matt — the router itself, if you cannot remember any of this. But note what its own docs page says of it: it is "a secondary source over the skills it describes" and is hand-maintained, so where it and a SKILL.md disagree, the SKILL.md wins.
Check yourself

A rename touching 400 call sites, entirely mechanical, that you could finish in one sitting. Which flow?

Size is not the measurement — span is. Four hundred mechanical edits may well fit one window, in which case /implement is right and the spec is skipped. If they do not, this is the shape /to-tickets calls a wide refactor, which gets its own sequencing in lesson 14. The honest answer is that you measure first.

Check yourself

Your /wayfinder map has cleared. What do you feed /to-spec?

The trigger table says /to-spec #<map_issue>. The map is an index pointing at the tickets that hold the detail, and /to-spec's job is to collapse those linked decisions into one buildable plan. Going straight to /implement is named as one of the two most common mistakes with this flow.

What this sets up

Five branches, five worked answers. Start with the one you will run most often and which has the fewest moving parts: lesson 8.

Read next, from the source

skills/engineering/ask-matt/SKILL.md — all 89 lines. It is the only document in the set that describes the whole thing at once, and it is short enough to reread whenever routing feels uncertain. Read it knowing it is hand-maintained and lags the skills, which is exactly the caveat its own docs page attaches to it.

Your agent is your teacher. The best exercise for this lesson: describe three pieces of work you actually have waiting, and ask it to route each one — and to say which row of the table it matched and what would have to change for the answer to move. The boundary cases are where routing is learned.

On spacing

This is the hinge of the topic, so it is worth a pause and a return. Before going on, state the one measurement in a sentence, and name the two things below the floor. The routing table is the reference document to come back to; this lesson is the argument for why it is shaped the way it is.
