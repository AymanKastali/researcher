Lesson 0005

Domain modelling

The skill that runs alongside grilling and writes things down. It has one prohibition about what its file may contain, and a three-part test that stops it writing anything most of the time.

This is the difference between /grill-me and /grill-with-docs: the same interview, with a second skill running inline capturing what gets settled. It produces two artifacts, and the rules for each are short and strict.

It runs inline, and it never batches

Which means a correctly-running /grill-with-docs session has an edited CONTEXT.md in the working tree partway through, not at the end. A session that produces one big glossary write as it closes has been doing something else.

The five moves it makes during a session

domain-modeling/SKILL.md:44-72, as section headings.
MoveLooks like
Challenge against the glossary "Your glossary defines 'cancellation' as X, but you seem to mean Y — which is it?"
Sharpen fuzzy language "You're saying 'account' — do you mean the Customer or the User? Those are different things."
Discuss concrete scenarios Inventing edge cases that force precision about where one concept stops
Cross-reference with code "Your code cancels entire Orders, but you just said partial cancellation is possible — which is right?"
Update CONTEXT.md inline Writing the resolved term the moment it resolves

The fourth is the one that earns its place. An agent that checks a stated belief against the code and surfaces the contradiction is doing something a conversation alone cannot.

The prohibition

And a second filter, on which words qualify at all:

The sentence to keep

A glossary and nothing else — and only the words this project invented.

Two tests, and most candidate entries fail one of them. "Retry policy" fails the second. "How we handle retries" fails both.

The entry format is three lines, and the third line is the opinionated one:

Markdown CONTEXT-FORMAT.md, the shipped example 
**Customer**:
A person or organization that places orders.
_Avoid_: Client, buyer, account

"Be opinionated. When multiple words exist for the same concept, pick the best one and list the others under _Avoid_." The avoid-list is what makes it a decision rather than a definition — it says which words this project has agreed to stop using.

The three gates for an ADR

The second artifact is a decision record, and it is offered sparingly. All three conditions, or none:

Why three gates and not one

Each one alone admits far too much. Hard to reverse: every schema change qualifies. Surprising: every clever line of code qualifies. A real trade-off: every library choice qualifies. It is the conjunction that makes the bar high enough that most sessions produce no ADR at all — which is the intended outcome.

And the artifact is deliberately tiny:

A worked example: the ADR in this repository

docs/adr/0001-shared-stylesheet-across-independent-topics.md is worth testing against the three gates, because it passes all of them visibly — and the second one in a way that is easy to miss.

One real ADR against the three gates.
GateWhy it passes
Hard to reverse Every page hard-codes its depth to the root, so the decision is written into every page ever produced
Surprising without context It contradicts what /teach specifies — assets at the repo root rather than inside each workspace
A real trade-off It carries a Considered options section with two rejected alternatives

The middle row is the instructive one. "Surprising" does not mean clever — it means a future reader will find it strange and be right to. Deliberately departing from a documented convention is the clearest case there is.

Reaching it on its own

domain-modeling is model-invoked, so unlike most of what this topic covers you can simply describe the situation and it may fire. Its trigger string:

YAML domain-modeling/SKILL.md, frontmatter 
description: Build and sharpen a project's domain model. Use when
  discussing codebase terminology, writing or editing a CONTEXT.md, or
  recording or editing an ADR.

The router describes it as one of two vocabulary layers that run beneath the other skills — "Reach for them directly when the words, not the process, are the problem" (ask-matt/SKILL.md:56). Arguing about what to call something is exactly that situation.

Check yourself

Which of these belongs in CONTEXT.md?

Only the second is a word this business invented and would have to define for a newcomer. The first and fourth are general programming concepts, excluded even if used constantly. The third is an implementation decision — plausibly an ADR, never a glossary entry, because the file is "a glossary and nothing else".

Check yourself

You picked Postgres over MySQL because the team knows it. Does this earn an ADR?

Gates one and three pass, and that is exactly the trap. Gate two fails: no future reader wonders why a team chose the database it already knew. All three or none — and the discipline is in being willing to lose a decision that passed two of them.

What this sets up

You now have the interview and the record it leaves. The last primitive is not a skill at all — it is the decision about what to do with a context window when a phase ends, and it is the one the set calls the fuzziest in the whole map: lesson 6.

Read next, from the source

skills/engineering/domain-modeling/CONTEXT-FORMAT.md, then this repository's own CONTEXT.md beside it. Reading a format specification and a real file written to it, together, is worth more than either alone — and this one is short enough to read whole in a few minutes.

Your agent is your teacher. Worth trying: pick three words your current project uses loosely and ask it to challenge each against the CONTEXT-FORMAT.md rules — is this specific to this context, and what should the _Avoid_ list say? The ones that turn out not to qualify teach the filter faster than the ones that do.

On spacing

Before moving on, recite the three ADR gates from memory, then find a decision from your own recent work that passes two and fails one. That is the useful exercise — anyone can recognise a decision that passes all three.
