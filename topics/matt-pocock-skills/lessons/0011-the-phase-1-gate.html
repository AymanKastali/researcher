The Phase 1 gate

One skill in this set refuses to think about your bug until it can make the bug fail on demand. That refusal is the whole skill — everything after it, by its own account, is mechanical.

Trigger: something is broken, throwing, failing, or slow — and it resisted a first glance. The router reserves this for the hard ones: the intermittent flake, the regression that crept in between two known-good states.

Step 0 — only if someone else filed it

There are two entry points into a bug fix, and which one you take depends on who wrote the report:

/triage's relevant step is verification: "Before any grilling, check that the claim holds up. For a bug, reproduce it from the reporter's steps." It produces an agent brief written to survive the codebase changing underneath it — "Don't reference file paths — they go stale" — and every comment it posts must carry the disclaimer > *This was generated by AI during triage.*

Expect to do the verification twice

The docs page is candid: "Triage's step 3 is essentially a shallow, bounded instance of diagnosing-bugs Phase 1–2, but neither file mentions the other." Triage confirms the bug is real. Phase 1 builds something you can run a hundred times. They are not the same artifact.

The claim the skill makes about itself

Read that as a resource-allocation instruction. Most debugging effort goes into thinking about the cause. This skill says to spend it instead on building the instrument, and claims the cause then follows.

The tenth ships with the skill as scripts/hitl-loop.template.sh. Its point is that even when a person has to be in the loop, the loop is still structured — the human is driven by the script, and their output feeds back in.

Tighten it — the loop is a product

For a flake, the target is not a clean repro

"The goal is not a clean repro but a higher reproduction rate."

Loop the trigger 100×, parallelise, add stress, narrow timing windows, inject sleeps. "A 50%-flake bug is debuggable; 1% is not — keep raising the rate until it's debuggable." You are not trying to make it deterministic. You are trying to make it frequent.

What to watch for as the human

The gate is enforced by the agent on itself, which means it can be skipped silently. The tell is a session that starts explaining the bug — "this is probably the cache invalidation" — without ever having shown you a command and its red output.

One question recovers it: "what command goes red on this, and have you run it?"

Check yourself

You have a script that boots the service and exits zero. Does it pass the Phase 1 gate?

The skill anticipates exactly this: red-capable means it "asserts the user's exact symptom… Not 'runs without erroring'". A loop that cannot go red on this specific bug satisfies three criteria and fails the one that matters.

Your agent is your teacher. The single most useful habit from this lesson: on the next real bug, before anything else, ask "what command goes red on this, and have you run it?" Ask it every time until you stop needing to.
