Lesson 0019

When the set has misfired

Every flow in this topic has a way of looking like it worked when it did not. This lesson is the tells, the four things you must always do yourself, and the one judgement nothing in the set will make for you.

This is the lesson that makes the other eighteen safe to rely on. A flow that fails loudly costs you an afternoon; a flow that reports success having skipped its own gate costs you the thing you were trying to build.

The judgement nothing will make for you

Lesson 7 ended here and it is worth ending the topic here too. The router routes by situation, and every route lands on a skill. There is no branch that terminates in "do it yourself".

The set's own floor is the context window — "if the whole change fits in one context window, you don't need this skill at all". Below that floor, for a typo or a config bump, the honest answer is no skill, and no document in the set says so.

The sentence to keep

Deciding whether a change is worth the ceremony is yours, and always will be.

That is not a defect in the set. A router cannot know what a change is worth; it can only know what shape it is. The judgement was always going to be the human's, and knowing that it is missing — rather than looking for it — is the last thing this topic has to teach.

What this topic could not tell you

One honest limit, stated plainly because it applies to every page you have read. None of these flows was run. Every lesson describes what a skill's text instructs, and separately quotes what the repo's own docs pages report that users observed. Neither is a report of the flow working.

So treat this topic as a map of the territory drawn from the survey documents, not from walking it. The first real /to-tickets or /wayfinder session you run is worth writing down — it is the evidence these pages do not have.

Check yourself

You want the agent to stop over-triggering diagnosing-bugs. Where does that instruction go?

The plugin install is read-only and an update overwrites edits, so the SKILL.md is out. Setup explicitly declines to hold preferences — "Config is death". What survives an update is a prompt-level adaptation: your own CLAUDE.md, or saying it when you invoke.

Check yourself

Which omission halts a build while everything still looks fine?

The frontier is defined as tickets whose blockers are closed, so an unclosed ticket leaves everything downstream reading as blocked with no error anywhere. The label omission fails loudly, the branch omission leaves a visible bad commit, and the review omission produces an obviously empty report.

Where to go from here

Back to lesson 7, which is the one worth rereading — everything else in this topic is a branch of it. The routing table, flow chains and manual patches are built for keeping open while you work; the skill index answers "can the agent fire this, and what is its exact trigger".

Read next, from the source

docs/engineering/ and docs/productivity/ in your own install — all twenty pages, one per promoted skill, each a list of problems real users hit. Read the page for whichever skill you are about to use for the first time. It is the cheapest hour in this whole topic, and it is the half of the truth the SKILL.md files do not carry.

Your agent is your teacher — and for this topic, it is also the subject. The most useful question you can ask from here on is mid-flow rather than about it: "which skill are you running right now, and which step are you on?" A confident answer that does not match what you have read here is exactly the misfire this lesson is about.

On spacing

This is the end of the topic, so space the review rather than the reading. In a week, try to reconstruct: the invocation axis, the one routing measurement, the Phase 1 gate, and the four manual patches. The ones that come back slowly are the lessons to reread — and they will not be the ones you expect.
