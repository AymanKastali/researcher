TDD and the seam gate

The one place a build stops and hands control back to you — plus the three bad tests the skill names, and the step its own description promises that it does not contain.

Trigger: reached automatically by /implement, or typed directly when you want one behaviour built test-first without a spec. It is model-invoked, so a request phrased around building something test-first can fire it on its own.

What the skill actually is

Note what it does not claim to be: a procedure. The loop is assumed known. What the file contains is the set of judgements that make the loop worth running.

The gate

Seam

The public boundary you test at: the interface where you observe behavior without reaching inside. Tests live at seams, never against internals.

skills/engineering/tdd/SKILL.md:20.
The sentence to keep

No test is written at an unconfirmed seam.

This is the only hard stop in the small-feature flow. When /implement pauses to ask you about interfaces, this is why — and answering it carelessly is the cheapest way to get a suite you will later delete.

In the full chain, this gate fires earlier

Running the big-feature flow, the seams are agreed during /to-spec step 2 rather than in each /implement run — which is how one negotiation covers a whole feature instead of recurring per ticket.

The three anti-patterns

skills/engineering/tdd/SKILL.md:30-32.
Anti-patternWhat it isThe tell
Implementation-coupled Mocks internal collaborators, tests private methods, or verifies through a side channel — querying the database instead of using the interface The test breaks when you refactor but behavior hasn't changed
Tautological The assertion recomputes the expected value the way the code does, so it passes by construction It can never disagree with the code
Horizontal slicing Writing all tests first, then all implementation Bulk tests verify imagined behavior — the shape of things, not user-facing behaviour

The tautological one is worth dwelling on, because it is the one an agent produces most naturally. The skill gives the fix in one clause: "Expected values must come from an independent source of truth — a known-good literal, a worked example, the spec."

Python Written for this lesson 
# Tautological: the assertion recomputes the value the way the code does.
# It passes by construction and can never disagree with the implementation.
def test_prorated_refund_tautological():
    assert prorated_refund(1200, 9, 30) == 1200 * 9 // 30

# Independent: the expected value comes from a worked example in the spec,
# so the test can disagree with the code -- which is the only reason to have it.
def test_prorated_refund():
    # Spec, section 4.2: "a 1200-unit annual plan cancelled with 9 of 30
    # days remaining in the final month refunds 360 units."
    assert prorated_refund(1200, 9, 30) == 360

And on mocking, the rule is three words long (tdd/mocking.md:10-14): "Don't mock: Your own classes/modules · Internal collaborators · Anything you control."

The gap: it never asks whether to test at all

The row in question was: "Config, wiring, glue, type annotations, straight CRUD delegation". For that kind of change the honest answer is no test, and the skill will not reach it — "that judgement is yours or your CLAUDE.md's".

Check yourself

/implement asks "which seams should we test?" — what happens if you shrug?

The rule is absolute: "No test is written at an unconfirmed seam." It is the only hard stop in the flow, and it exists so testing effort lands on critical paths rather than every edge case — a choice the skill explicitly will not make for you.

Check yourself

Where does refactoring happen, if not in the loop?

The rule names its destination: "It belongs to the review stage (see the code-review skill)". The removal was deliberate — agents essentially never did it in the loop, and separating implementation from review was judged to work better. The description still says "red-green-refactor" only because that phrase fires the skill.

Read next, from the source

skills/engineering/tdd/mocking.md — the shortest of the three tdd files and the most opinionated. It is where the implementation-coupled anti-pattern stops being an abstraction and becomes a list of things not to do.

Your agent is your teacher. Worth trying on real code: hand it a test you already have and ask which of the three anti-patterns it exhibits, and why. The tautological one is the most instructive to find in your own work, because it always looked fine when it was written.

On spacing

Before moving on, name the three anti-patterns and give the tell for each — the observable symptom, not the definition. The tells are what you will actually use; the definitions are in the glossary.
