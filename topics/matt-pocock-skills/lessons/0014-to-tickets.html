To-tickets

Cutting a spec into slices that each land green, declaring what blocks what — and a quiz step that exists because this skill gets it wrong in two specific, predictable ways.

Trigger: a spec exists, or a plan is in the conversation, and it will not fit one context window. Run it in the same window as /to-spec.

The third rule is the one that ties this lesson to lesson 7. A slice is sized to fit one fresh context window — the same measurement that decided whether you needed this skill at all, now applied to each piece.

Blocking edges

"Give each ticket its blocking edges — the other tickets that must complete before it can start. A ticket with no blockers can start immediately." And the edges are what make the frontier computable:

Two senses of "frontier", and they rhyme

In grilling the frontier is every question whose prerequisites are settled. Here it is every ticket whose blockers are done. Same idea — the set of things actionable now — applied to questions in one case and work in the other.

How the edges are stored depends entirely on what /setup-matt-pocock-skills configured, which is why lesson 3 called this flow a hard dependency:

Prefactoring

Step 2 carries an instruction that is easy to skim past and changes the shape of the whole breakdown: "Look for opportunities to prefactor the code to make the implementation easier. 'Make the change easy, then make the easy change.'" Prefactoring tickets come first and block the rest.

The exception: a wide refactor

One shape of work cannot be cut into vertical slices, and the skill handles it explicitly rather than pretending otherwise:

   pkg-a           pkg-b           pkg-c

#5 CONTRACT  delete the old form   (blocked by #2, #3, #4)

And the fallback when even the batches cannot stay green alone: keep the sequence, but let them share an integration branch that all block a final integrate-and-verify ticket — "green is promised only there."

The quiz step is yours to use

Those three questions exist because the skill fails in two known ways, and the quiz is where you catch both.

Failure one — over-decomposition

Failure two — horizontal slices, despite the rule

The one question to ask at the quiz

"What can I demo when this ticket is done?"

Ask it of every ticket. A ticket with no answer is a horizontal slice, and you have caught it at the only cheap moment there is.

Check yourself

A ticket reads "add the database columns for the new billing fields". What is wrong?

It is a horizontal slice — one layer, no path through the others. Apply the demo question and there is no answer, which is the tell. The fix at the quiz step is to merge it into the vertical slice that needs those columns, so the ticket delivers behaviour rather than a layer.

Check yourself

Renaming a type used in 900 files. How should this be sequenced?

This is the wide-refactor exception: blast radius means no vertical slice can land green. Add the new form beside the old, migrate call sites in batches each blocked by the expand — CI stays green throughout because the old form still exists — then delete the old form in a ticket blocked by every batch.

What this sets up

The tickets are published and the frontier is defined. Working it is mostly mechanical — except for one step nothing in the set performs, which stops the frontier advancing at all: lesson 15.

Read next, from the source

skills/engineering/to-tickets/SKILL.md — and specifically the two templates at the bottom, for a local file and for a tracker issue. Reading the fields a ticket is expected to carry (Parent, What to build, Acceptance criteria, Blocked by) tells you what a good one looks like faster than the prose does.

Your agent is your teacher. At the quiz step, do not just answer the three questions — ask it the demo question back, once per ticket, and make it answer in one concrete sentence each time. The tickets where the answer comes out vague are the ones to merge.

On spacing

Before moving on, draw the expand–migrate–contract graph from memory and say which ticket blocks which. Then state the demo question. Those two things are most of what this skill asks you to bring.
