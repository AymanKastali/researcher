Lesson 0006

Phase boundaries

Five things you can do with a context window, one ordered tree for picking between them, and one reason the option most people reach for first sits at the bottom.

This is not a skill — it is a supporting document inside the router, and it governs every flow in the set. The router calls the decision "the fuzziest decision in this whole map", which is unusually candid and exactly right.

A phase, and its boundary

The timing rule, first

Make this decision at a boundary. Mid-phase there is no decision to make.

Compacting because the window is filling up, in the middle of the implementation, is the move this rule exists to prevent.

The five options

The tree, in order

"Work top to bottom at the boundary. The first yes wins." The order is the whole content — the options are obvious, the sequence is not.

Text Written for this lesson 
1. Can you continue in this session?              -> Continue
2. Is the context irrelevant to what comes next?  -> /clear
3. Do you need to hand off?                       -> /handoff
4. Can the task be done AFK?                      -> Subagent
5. Otherwise                                      -> /compact

1 — Continue, and why it is ruled out first

That example is the one to remember, because it is the boundary you will meet most often. After a grilling session, stay put. The build wants the argument as it happened.

2 — Clear, the cheapest move with a one-way cost

3 — Handoff, and the closed list

/handoff is narrower than it sounds. Four situations, and the document says so plainly: "That list is the whole clause."

  • Swapping to a new harness (Claude → Codex)
  • Moving to a new directory or repo
  • Sending the work to a colleague
  • Forking a side task you found mid-phase

"What /handoff buys is portability — a file that travels. If nothing is travelling, you don't need it." Note the fourth entry is the one exception to the timing rule: forking a side task is explicitly a mid-phase move.

4 — Subagent, when you are not needed

"Automated review is the standard case: the agent reads the diff and reports, and you aren't needed while it does." The test is whether the task is scoped tightly enough to run with no steering.

5 — Compact, at the bottom on purpose

And when you do land here, pass it an instruction — /compact we're going to QA this area — so the summary keeps what the next phase needs.

Two senses of "primary source" in this workspace

This repository uses primary source for the authority a claim is quoted from — a specification, a manual, a file on disk. The phase boundary document uses it for the session as it happened, before anyone summarised it.

The analogy is exact and the referents are different. The glossary keeps both entries and says which is which.

The rule that governs the main flow

The router turns all of this into one instruction for the spec-and-tickets chain, and it is the single most consequential application of the tree:

Grill, spec, split: one window. Then /clear before every ticket — question 2 answering yes, because a self-contained ticket makes the previous ticket's context genuinely disposable.

The budget you are spending

The limit on "one unbroken window" is the smart zone — about 150k tokens, "the window within which the model still reasons sharply". If a session approaches it before /to-tickets, the router is explicit: "don't push on degraded — /compact at the nearest phase boundary and carry on".

Check yourself

A long grilling session has just ended and you are about to build. What does the tree say?

The document names this exact boundary as the standard yes to question one: "the implementation wants the reasoning verbatim, not a summary of it". The glossary holds the resolved terms, never the argument that resolved them — so clearing here loses the why while looking like it kept everything.

Check yourself

Why does /compact sit at the bottom of the tree rather than the top?

Quoted directly: "It sits at the bottom because the four questions above it are all cheaper or more precise." It is still the default — the tree lands there often — but reaching for it first produces "a fresh session that is confidently wrong about a decision the summary flattened".

What this sets up

Read next, from the source

skills/engineering/ask-matt/PHASE-BOUNDARIES.md — 55 lines, and the last section is the one to read slowly: "These are judgement calls." It admits the questions are not objective and that the same boundary can go two ways on two days. The value it claims is only in asking them in order, which is a modest and believable claim.

Your agent is your teacher. Worth asking at the end of any real session: "we are at a phase boundary — walk the five questions in order and tell me where it lands, and why it did not land higher." Getting the reasoning for the rejected branches is where the tree actually gets learned.

On spacing

This is the end of the foundations. Before going on, try to write the five questions out in order from memory, then state the one-sentence cost that explains the ordering. Lessons 1–6 are the model; lesson 7 is where it starts paying.
