Lesson 0003

What setup writes

One skill runs once per repository and configures the three things the rest assume. Skipping it does not produce an error — it produces a confident wrong answer, and that is the more expensive failure.

/setup-matt-pocock-skills was five of the six inoperative instructions in lesson 2. Every one of those lines is a skill telling you, through the agent, that it needs something you have not given it. This lesson is what that something is.

What it configures

Its own frontmatter carries the sequencing rule, and it is the last clause of the description: "Run once before first use of the other engineering skills."

What actually breaks if you skip it

Not everything. The set has thought about this precisely enough to have written a decision record about it, and the answer has two grades:

Which flows need setup, and which merely prefer it.
Flow Without setup
Small feature — grill, implement, review Works. Output is less sharp
Bug fix — /diagnosing-bugs Works. Output is less sharp
Big feature — /to-spec, /to-tickets Wrong, not fuzzy
Greenfield — /wayfinder Wrong, not fuzzy
Incoming issues — /triage Wrong, not fuzzy

"Wrong, not fuzzy" — the actual failure

This is the part worth committing to memory, because the symptom is silence. /wayfinder states its own fallback in the open:

The silent wrong default

A repository with a live GitHub issue tracker, but no docs/agents/issue-tracker.md, gets markdown files written into .scratch/.

No error. No warning. The flow completes and reports success. Your tickets exist — just not anywhere your team is looking, and with plain text where the native blocking links should have been. The frontier that lesson 14 depends on is not computable from text.

What it writes

Four artifacts. The first is a block injected into your CLAUDE.md or AGENTS.md, and it is the load-bearing one:

Markdown setup-matt-pocock-skills/SKILL.md:86-100, verbatim 
## Agent skills

### Issue tracker

[one-line summary of where issues are tracked]. See `docs/agents/issue-tracker.md`.

### Triage labels

[one-line summary of the label vocabulary]. See `docs/agents/triage-labels.md`.

### Domain docs

[one-line summary of layout -- "single-context" or "multi-context"]. See `docs/agents/domain.md`.

Notice what that block is: three pointers and no content. It is an indirection layer, and skills are supposed to resolve the tracker through it rather than hard-coding a path. The set learned this the hard way:

Then three files under docs/agents/:

The three documents, and what each carries.
FileCarries
issue-tracker.md CLI conventions, what "publish to the issue tracker" and "fetch the relevant ticket" mean here, a PRs-as-requests flag defaulting to no, and a Wayfinding operations section
triage-labels.md A two-column table mapping the five canonical triage roles onto this tracker's label strings. Written only if triage is installed
domain.md Where CONTEXT.md and ADRs live, and the instruction to read them before exploring

Why a freshly set-up repo looks empty

Setup does not create CONTEXT.md and does not create any ADRs, and it instructs every skill not to complain about that:

The sentence to keep

Setup writes where things live. It never writes what is in them.

The glossary and the decision records are grown by /domain-modeling during real conversations, one term at a time. An empty CONTEXT.md after setup is not an unfinished step.

A worked example: this repository

The repository you are reading this in has been through setup. Its CLAUDE.md carries the block, filled in:

And its docs/agents/triage-labels.md is an identity table — every canonical role mapped to a label of the same name. That looks like a step someone forgot to finish, and it is not:

Three things it will not do for you

  • It does not create labels. The mapping file is a mapping — it never runs gh label create. On a fresh GitHub repository the labels genuinely do not exist, and gh issue create --label <missing> fails outright rather than creating it. This is the first of the four manual patches, and it is the one that stops lesson 16 dead.
  • It does not hold your preferences. "Config is death." Standing instructions — how you want grilling paced, whether to diagnose or just answer — belong in your own CLAUDE.md as plain prose.
  • There is no user-level mode. Every repository carries its own docs/agents/. Running the skills across ten repos means running setup ten times.
There is no verify mode either, and that is deliberate

The intended way to check an existing setup is to run the skill again and tell it what you want: "don't rewrite anything, just check my existing files against the current seed templates and report drift". Because the skill is prompt-driven rather than a script, scoping it in the invocation works.

Check yourself

You run /to-tickets in a GitHub repo that never had setup run. What happens?

The documented fallback is the local-markdown tracker, and it is taken silently. The skill cannot stop and run setup for you — setup is user-invoked — and nothing in it infers a tracker from git remote. You get a complete-looking result in the wrong place, with text where the blocking links should be.

Check yourself

After a successful setup run, CONTEXT.md does not exist. What should you do?

Setup writes where the domain docs live, never their contents. domain.md instructs every consumer to proceed silently when they are absent, because /domain-modeling creates them lazily when a term actually gets resolved. An empty glossary is the correct state of a repo that has not yet argued about a word.

What this sets up

The configuration is in place. Now the primitives the flows are built from — and the first of them is the one five different skills run internally: lesson 4.

Read next, from the source

skills/engineering/setup-matt-pocock-skills/issue-tracker-github.md — the seed template, which is what your docs/agents/issue-tracker.md is a copy of. Reading the template and your own copy side by side shows you exactly which decisions were made on your behalf, including the PRs-as-a-request-surface flag that was left at its default.

Your agent is your teacher. Worth asking: have it run setup in verification mode against this repository — "don't rewrite anything, report drift against the current seed templates". It is the only supported way to check an existing configuration, and seeing it work teaches something about prompt-driven skills that no amount of reading will.

On spacing

Before moving on, try to state the difference between a hard and a soft dependency, and give one flow on each side. Then name the failure mode in one sentence — the word to reach for is silent, not broken.
