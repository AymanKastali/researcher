Lesson 0013

To-spec

A skill whose first instruction is to not ask you anything — and which quietly contains the step where the whole feature's test seams get agreed.

Trigger: you have decided what to build and the work spans more than one context window. That is the floor from lesson 7, crossed.

Why the document exists

The most useful sentence about this skill is not in the skill. It is in its docs page, and it explains the entire design:

The sentence to keep

The spec is a decision record, not a design document.

It is the grilling session, made portable. That is also the acceptance test for reading one back: anything in it you do not recognise from the conversation is a defect, not a helpful addition.

The defining constraint

Which is the reason step 2 of the main flow has to happen before this one. /to-spec has no discovery mechanism at all — if the thinking has not happened, it will synthesise a spec out of a thin conversation and it will look complete.

The three steps, and the middle one matters most

This is where the seam gate is really satisfied

Lesson 9 established that /tdd writes no test at an unconfirmed seam. In the full chain, that confirmation happens here — once, for the whole feature — rather than in the first exchange of every /implement run.

Which is why this step deserves your attention even though it looks like a formality. You are agreeing the test strategy for a multi-session build in one answer.

Note the direction of the advice: fewer, higher. "The ideal number is one" is an unusual thing for a testing instruction to say, and it follows from the same reasoning as /tdd's — you cannot test everything, so the effort should land at as few places as possible, as far from the internals as possible.

The template is fixed

The seven sections of <spec-template>, to-spec/SKILL.md:21+.

User Stories "A LONG, numbered list", "extremely extensive" — as an actor, I want a feature, so that a benefit
Implementation Decisions Modules, interfaces, schema changes, API contracts, architectural decisions
Testing Decisions The seams agreed in step 2
Out of ScopeWhat was deliberately refused
Further NotesEverything else

The one prohibition

The same rule appears in /to-tickets and in /triage's agent brief. It is the set's most consistent instruction: a document that outlives a context window must not name a file path, because the path will move and the document will not.

Publishing, and the trap it sets

The spec is published as an issue carrying ready-for-agent. That label is what makes tickets grabbable — and the spec now wears it too:

A parent spec labelled agent-ready

An unattended agent polling for ready-for-agent will find the parent spec and try to build the entire feature in one run.

The docs page's fix: "exclude the parent spec explicitly in your AFK agent's prompt, or strip the label once /to-tickets has run." Only relevant if you run agents unattended — but total if you do.

Do not clear before the next step

Lesson 6's rule applies with force here — grill, spec and split stay in one window. The reason is specific to this skill: a very large spec can outgrow what a tracker serves back cleanly, and "there is no local copy to fall back on". Run /to-tickets in the same window and the spec is never re-fetched.

Check yourself

You invoke /to-spec after a two-message conversation. What do you get?

"Do NOT interview the user — just synthesize what you already know." With little to synthesise, it fills the fixed template anyway. By the docs page's own standard — "anything the spec asserts that you never actually said is a defect" — the result is mostly defect, and it will not look like one.

Check yourself

Why are file paths banned from the spec?

"They may end up being outdated very quickly." The same rule governs /to-tickets and /triage's agent briefs, for the same reason: a ticket may sit for weeks while files are renamed and moved. Describe interfaces and contracts, which survive; not paths, which do not.

What this sets up

The spec is published and still in the window. Splitting it is the step with the most reported friction in the whole set: lesson 14.

Read next, from the source

skills/engineering/to-spec/SKILL.md — and specifically the <spec-template> block, read as a checklist. The sections you find hardest to fill honestly from your last grilling session are the parts of that session that were not finished.

Your agent is your teacher. Worth doing on your first real spec: ask it to go through the finished document line by line and mark every claim with where in the conversation it came from. Anything it cannot place is exactly what the docs page calls a defect, and catching one is the fastest way to learn what this skill is for.

On spacing

Before moving on, answer this in one sentence: what is a spec for? If the answer involves planning or design, reread the first excerpt — the answer this set gives is narrower and more useful than either.
