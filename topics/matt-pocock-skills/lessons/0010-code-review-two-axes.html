Lesson 0010

Code review's two axes

Two sub-agents that must never see each other's findings, a report you are forbidden to merge, and a loop that will never come back clean.

Trigger: you want a branch, a PR, or the work since a fixed point reviewed. It is model-invoked, so describing that situation can fire it — and it is the last step of every flow in this topic.

The two axes, and why they are two

The justification is a two-line argument at the bottom of the file:

The fixed point

Three dots, and committed work only

<fixed-point>...HEAD compares against the merge-base, so work that landed on main after you branched is excluded — which is what you want.

It also means staged and working-tree changes are invisible. This is the collision from lesson 8: commit first, then review.

What it looks for when your repo documents nothing

The Standards axis reads whatever the repo has — CODING_STANDARDS.md, CONTRIBUTING.md — and on top of that always carries a fixed baseline of twelve code smells from Fowler's Refactoring, chapter 3. Two rules bind it:

The twelve, abbreviated from SKILL.md:45-56. Each entry in the skill reads what it is → how to fix.

Mysterious NameA name that doesn't reveal what it does or holds

Data ClumpsThe same fields travelling together — a type wanting to be born

The aggregation rule

The sentence to keep

Two reports, two worst issues, no overall verdict.

A review that hands you one ranked list has undone the entire design. The separation is the product.

No spec is a legitimate outcome

The skill looks for the originating spec in a fixed order — issue references in commit messages, then a path you passed, then a file under docs/, specs/ or .scratch/, then it asks you. And then: "If they say there isn't one, the Spec sub-agent will skip and report 'no spec available'." (SKILL.md:32)

Which is what happens after a bug fix with no originating issue. It is a reported result, not a failure.

Three things to know before you run it unattended

It never converges

Its sub-agents can rediscover it and fan out

There are two skills called code-review

They do different jobs — use both

Bugs in the diff, versus spec compliance and repo standards. These are not competing implementations of one idea; they are two reviews, and a branch can want both. The mattpocock-skills: prefix is what lets you name which one you mean.

Check yourself

The review returns four Standards findings and one Spec finding. What should the summary line say?

"Don't pick a single winner across axes — that's the reranking the separation exists to prevent." The whole design is that one axis must not be able to mask the other, and a cross-axis ranking is exactly the masking mechanism.

Check yourself

You have fixed everything the review found. Should you rerun it until it is clean?

Fixes create new surface, and half the Standards axis is judgement-based and non-deterministic between runs. The guidance is to treat a pass as a list of leads, act on the ones with a cited rule behind them, and stop. Looping burns tokens for an outcome that cannot arrive.

skills/engineering/code-review/SKILL.md, section 3 — the twelve smells with their fixes, each in one line. It is a compressed reading of Fowler's chapter 3 and it is useful well beyond this skill; if you only ever read one section of one SKILL.md in this set for its own sake, this is the one.

Your agent is your teacher. Worth asking on a real branch: run the review, then ask it which findings had a cited rule behind them and which were baseline judgement calls. That distinction is what makes a pass actionable, and the skill's own text insists on it.
