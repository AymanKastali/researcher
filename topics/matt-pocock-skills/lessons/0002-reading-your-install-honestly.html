Lesson 0002

Reading your install honestly

Three things are true about the tree on your disk that no blog post about these skills will tell you: half of them are invisible to the agent, six instructions inside them cannot execute, and the version number identifies nothing.

All three follow from lesson 1's one axis, plus one fact about how the plugin is shipped. None of them is a fault in your installation, and each one produces a symptom you would otherwise misread.

One: half the set looks uninstalled

A user-invoked skill is hidden from the model. That hiding is done by the harness, and the harness hides it by leaving it out of the skill list it shows the agent. The agent then reads that list as complete.

The symptom, and the wrong conclusion

You ask for the spec-and-tickets flow. The agent tells you those skills are not installed and helpfully offers /grilling and /tdd instead. Nothing is wrong.

The wrong move is to reinstall the plugin, which changes nothing. The right move is to type /to-spec anyway. It is there.

This lesson can confirm the mechanism first-hand rather than quoting it. The session that wrote these pages was shown a skill listing containing exactly eleven entries under a mattpocock-skills: prefix — grilling, domain-modeling, codebase-design, tdd, diagnosing-bugs, code-review, prototype, research, resolving-merge-conflicts, wizard, writing-for-agents. That is precisely the model-invoked set from lesson 1, and the fourteen user-invoked skills were absent.

How strong is that evidence

It is an observation of one harness in one session, not a documented guarantee. The tree describes the mechanism and this session matched it exactly — but if your own harness ever shows all twenty-five, believe your harness and treat this paragraph as out of date rather than explaining the difference away.

Two: six instructions in the set cannot execute

Apply the invariant to the tree itself and something awkward turns up. Skills in 1.2.3 contain instructions telling the agent to run user-invoked skills — which lesson 1 established is impossible. Here is one, quoted whole:

setup-matt-pocock-skills carries disable-model-invocation: true. No skill can reach it. That sentence is sitting inside a skill, addressed to an agent, describing an action the agent cannot take. Grep the tree and there are seven such lines:

That names the skill without telling anyone to run it, so it is perfectly fine. Six lines are instructions the agent cannot carry out; the seventh merely mentions a skill.

The sentence to keep

Any instruction inside a skill that tells the agent to run a user-invoked skill is addressed to you.

Read it as a note in the margin, not a step in the process. Nothing will happen at that line unless you make it happen.

Three: the version number identifies nothing

This is the one that will bite you when you read anything written about these skills elsewhere. Your install says it is 1.2.3. The public repository's main also says it is 1.2.3. They are 34 commits apart.

The first of those is not cosmetic. The changeset that makes the change says why, and in doing so admits a weakness in the version you are running:

What to do about all three

Bash Written for this lesson 
P=~/.claude/plugins/cache/claude-plugins-official/mattpocock-skills

# Which version directory is actually installed, and what commit is it?
ls "$P" && git -C "$P"/*/ rev-parse --short HEAD

# The authority on what is present -- not the agent's skill listing.
python3 -c "import json,sys;print(len(json.load(open(sys.argv[1]))['skills']))" \
  "$P"/*/.claude-plugin/plugin.json
  • When the agent says a skill is missing — type it anyway, and check plugin.json rather than asking the agent again.
  • When a skill's text tells the agent to run another skill — check whether the named skill is user-invoked. If it is, the line is for you.
  • When something you read elsewhere does not match — the file on your disk is what runs. Open it. The version string will not settle the disagreement.
Check yourself

The agent reports that /to-tickets is not installed. What has actually happened?

to-tickets is user-invoked, so the harness leaves it out of the list it injects into the agent's context, and the agent reads that list as exhaustive. It is installed. The third answer is a real phenomenon for other names — to-plan and to-issues really were merged into to-tickets in 1.1.0 — but it is not what is happening here.

Check yourself

Why can two trees both correctly report version 1.2.3 while differing by 34 commits?

The marketplace listing carries a pinned sha, so work lands on main continuously while installed users move only when that pin advances. The version is bumped by a release, not by every commit — so a month of unreleased work sits on main under the same number.

What this sets up

Five of the six inoperative instructions name the same skill, and it is the one you are supposed to run before any engineering flow at all. What it writes, and what silently goes wrong if you never do: lesson 3.

Read next, from the source

.claude-plugin/plugin.json in your own install. It is the authority on what is present — the docs page above says so explicitly — and reading the twenty-five names in one list is the fastest cure for believing an agent that tells you something is missing.

Your agent is your teacher. Worth pushing on: ask it to grep the tree for every line that names setup-matt-pocock-skills, then ask it which of those lines it could actually act on. The answer is none of them, and getting it to reach that conclusion itself is a good test of whether lesson 1 landed.

On spacing

This is a good place to stop for a day. Lessons 1 and 2 are the model of the machine; everything after them is what to do with it. Before moving on, try to name the three consequences with no notes — invisible skills, inoperative instructions, meaningless version — and say which one would have cost you the most time if you had not known it.
