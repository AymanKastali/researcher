Lesson 0008

The small feature loop

Three skills, one context window, and two steps you have to insert yourself because nothing in the set does them for you.

Trigger: you have decided what to build, and the work fits one context window. That is the whole entry condition — the floor from lesson 7 — and if it is met, the spec is skipped entirely.

The chain

Text Written for this lesson 
/setup-matt-pocock-skills           (once per repo, ever)
  -> /grill-with-docs               sharpen it; CONTEXT.md grows
  -> [ stay in the window ]         phase-boundary question 1: continue
  -> [ check your branch ]          YOU. nothing does this
  -> /implement                     drives /tdd, then commits
  -> [ commit exists now ]          YOU, if implement did not
  -> /code-review <branch-point>    two axes, reported separately

The two bracketed lines with YOU on them are the subject of half this lesson. They are not optional and no skill performs them.

Step 1 — /grill-with-docs

This is lesson 4 and lesson 5 in practice. Expect terms appended to CONTEXT.md as they resolve, and expect zero ADRs — a small feature rarely clears all three gates, and that is the correct outcome rather than a skipped step.

Step 2 — do not clear

The phase-boundary tree lands on Continue here, and the router states it as a rule rather than a preference:

Step 3 — check your branch [synthesis]

implement's final line is "Commit your work to the current branch", and the skill contains no step that creates one. The docs page states the consequence flatly:

The default case is the bad one

If you have not branched, you are on main, and /implement will commit a feature onto it without comment.

This is manual patch two of four, and it is the one with the shortest fix and the worst consequence.

Step 4 — /implement, which is nine lines long

It is worth seeing the whole skill, because its brevity explains most of its behaviour:

Markdown skills/engineering/implement/SKILL.md:7-15, complete body 
Implement the work described by the user in the spec or tickets.

Use /tdd where possible, at pre-agreed seams.

Run typechecking regularly, single test files regularly, and the full test suite once at the end.

Once done, use /code-review to review the work.

Commit your work to the current branch.
Say where the plan is

The first line says "the spec or tickets", and in this flow there is neither — the plan is in the conversation. The docs page names the failure: "which nudges the model to go hunting for a file that doesn't exist. If the plan lives only in the thread, say so when you invoke it."

Step 5 — the seam gate fires inside step 4

/implement drives /tdd, and /tdd will stop and ask you something before it writes anything. That gate is lesson 9, and it is the one place in this flow the agent hands control back mid-build.

Step 6 — commit first, then review [synthesis]

Here is a genuine collision between two skills in the set, reported by multiple users and unfixed on both sides:

The sentence to keep

The review step inside /implement reviews an empty diff.

It runs. It reports. It finds nothing, because there is nothing in <fixed-point>...HEAD yet. A clean review here is not evidence of anything.

There is a second, independent reason to run the review yourself:

So the working order is: let /implement build and commit, then invoke /code-review yourself against the point you branched from. Lesson 10 is what it does when you do.

What this flow will not do

Three limits, each from docs/engineering/implement.md.
It does notSo
Create a branch Check before you start
Open a PR — "no configuration flag and no PR mode" Push and open it yourself
Run more than one ticket per invocation Matters in lesson 15, not here
Check yourself

/implement finishes and reports that its review found no issues. What do you conclude?

implement runs the review before committing, and code-review compares <fixed-point>...HEAD, which excludes staged and working-tree changes. Unless an interim commit already existed, it reviewed nothing and correctly found nothing. Commit, then review against your branch point.

Check yourself

Why does this flow skip /to-spec entirely?

The docs page puts it exactly this way: "The spec exists because context windows end." When the build happens in the same window as the grilling, nothing is being lost, so there is nothing for a spec to preserve. The spec is a decision record for a conversation that is about to be cleared — and here it is not.

What this sets up

One step inside /implement stops and waits for you, and it is the only gate in the flow: lesson 9.

Read next, from the source

docs/engineering/implement.md — the question-and-answer page for the thinnest skill in the set. It is the clearest example in the whole tree of the gap between what a skill's nine lines say and what people actually run into, and reading the two together is the best training available for reading any of the others.

Your agent is your teacher. Worth asking before your first real run: "what branch am I on, and does this repo expect a PR?" It is the step the flow omits, and asking for it out loud is the cheapest way to build the habit until it is automatic.

On spacing

Before moving on, say the chain out loud and name the two steps that are yours. If you can only remember one, remember the branch check — the review-ordering problem produces a misleading result, but the branch problem produces commits on main.
