Lesson 0002

What HTTP actually promises

One of the mission’s success criteria is stating from memory why PUT and DELETE are idempotent but POST is not — and why “returns the same response” is the wrong definition. This lesson is that criterion.

RFC 9110 is the current definition of HTTP semantics — an Internet Standard (STD 97, June 2022) that obsoletes RFC 7231 among others. Almost every vendor’s idempotency documentation is quoting or paraphrasing one sentence of it, so it is worth reading that sentence in the original.

Two axes, not one

HTTP classifies methods along two separate axes, and conflating them is the first mistake. Safety first:

safe

Request methods are considered “safe” if their defined semantics are essentially read-only; i.e., the client does not request, and does not expect, any state change on the origin server as a result of applying a safe method to a target resource. Likewise, reasonable use of a safe method is not expected to cause any harm, loss of property, or unusual burden on the origin server.

[…] Of the request methods defined by this specification, the GET, HEAD, OPTIONS, and TRACE methods are defined to be safe.

RFC 9110 §9.2.1, IETF, STD 97, June 2022.

And then the definition this entire topic rests on:

idempotent

A request method is considered “idempotent” if the intended effect on the server of multiple identical requests with that method is the same as the effect for a single such request. Of the request methods defined by this specification, PUT, DELETE, and safe request methods are idempotent.

RFC 9110 §9.2.2, IETF, STD 97, June 2022.
The two axes are independent. Safe is a strict subset of idempotent.
Method Safe Idempotent
GET yes yes
HEAD yes yes
OPTIONS yes yes
TRACE yes yes
PUT no yes
DELETE no yes
POST no no
PATCH no no

Every safe method is idempotent, because a method that changes nothing trivially changes nothing twice over. The converse fails: DELETE is idempotent and emphatically not safe. Written as a relation, safe ⊂ idempotent. Note also that PATCH is not defined in RFC 9110 at all — it comes from RFC 5789 — and that both POST and PATCH appear in the table as “no” because §9.2.2 simply does not list them.

The caveat that matters most

Read the definition again and notice what it is about: the intended effect on the server. It is not about the response the client receives. The specification is explicit that the response may legitimately differ between the first request and the retry:

The demonstration to remember

DELETE /orders/7 returns 204 No Content the first time and 404 Not Found the second. The responses differ. The intended effect on the server — that order 7 not exist — is identical. The method is idempotent.

Anyone who defines idempotence as “returns the same response” will conclude, wrongly, that DELETE is not idempotent. This is the single most common error in the whole subject, and you now have the counterexample that settles it in one line.

So an idempotent PUT that writes two audit-log rows on two attempts has not violated anything. Idempotence is a promise about the requested effect, and only that.

Check yourself

A DELETE returns 204, then 404 on retry. What does RFC 9110 say about this?

The definition is about the intended effect on the server, not the response, and §9.2.2 says outright that “the response might differ”. The intended effect — that the order not exist — is identical after one call and after two. No key is involved, and changing state on the first call is exactly what a non-safe idempotent method is expected to do.

The clause that justifies the whole topic

“unless it has some means to know that the request semantics are actually idempotent, regardless of the method”.

That subordinate clause, buried in a SHOULD NOT, is the entire specification-level justification for the Idempotency-Key header. The header is the means. Everything in the remaining lessons is an elaboration of how to build it.

Why POST is not idempotent

Not because of anything about bodies, tunnels, or creation semantics. It is because the specification declines to constrain what POST does at all:

The semantics are the resource’s, not the method’s. Because HTTP does not know what a given POST means, it cannot promise that doing it twice equals doing it once. And the mirror image explains the other two:

The promise tracks whether the method names an absolute state.
Method What it names Promise possible?
PUT A destination state — replace the resource with this Yes. Absolute, so repeating lands in the same place.
DELETE An absence — this resource should not exist Yes. Absolute, and absence is absence.
POST Nothing. The resource decides. No. HTTP cannot promise what it does not define.

This is the same destination-versus-delta split from lesson 1, now showing up at the protocol level rather than in a function.

Check yourself

Why does RFC 9110 decline to call POST idempotent?

§9.3.3 hands the semantics to the resource: a POST does whatever that particular resource says it does. HTTP cannot promise a property of an operation it has not defined. Note that “always creates a resource” is simply false — plenty of POST endpoints create nothing — and neither bodies nor caching enter into the definition of idempotence.

Where this leaves you

Suppose you now obey RFC 9110 perfectly: you choose idempotent methods wherever the operation permits it, and you never auto-retry a POST. You still have a serious problem, and it is not a problem about HTTP at all. It is a problem about distributed systems, and it was described precisely in 1983 — lesson 3.

Read next, from the source

RFC 9110 §9.2, “Common Method Properties” — sections 9.2.1 and 9.2.2 together run to roughly a page and a half. This is the highest-trust document in the entire topic, it is readable prose rather than grammar, and everything the vendors say later is downstream of it. If you read one primary source from this workspace, read this one.

Your agent is your teacher. A good question to bring back: is a PATCH that sets fields to absolute values idempotent? The answer is genuinely interesting and the specification’s “regardless of the method” clause is what settles it.
