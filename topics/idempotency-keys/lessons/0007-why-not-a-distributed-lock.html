Lesson 0007

Why not a distributed lock

A mission success criterion: argue why a conditional insert in the store that holds the effect beats an external lock — using the fencing-token argument on both sides. The dispute is the lesson, not a detour from it.

The third design occurs to almost everyone: before doing anything, grab a lock named after the idempotency key from Redis, ZooKeeper or etcd; do the work; release it. It is intuitive, it is popular, and it has a failure mode that a famous argument makes unanswerable.

Where the two actually converge

This is the useful conclusion, and it is easy to miss while watching two experts disagree.

They agree on the requirement and differ only on its strength.
Voice Says the resource must Strength required
Kleppmann “take an active role in checking tokens” Monotonic — also handles a late write from a stale holder
antirez “operate the read-modify-write only if the token is still the same when we write” Unique identity — handles duplicates but not ordering

Both are saying the same structural thing: the resource that holds the effect must itself check something before applying the write. Not the lock service. The resource.

The synthesis

The answer to “how do high-scale companies do this?”

They do not take a lock. They make the key’s creation itself the atomic operation, in the same store that holds the effect, so that winning the race and recording the effect are the same commit.

This is strictly better than an external lock for four reasons:

  1. No lease to expire. A unique-constraint violation or a ConditionalCheckFailedException is a decision made by the storage engine at write time, not a promise made to a client earlier that may have gone stale. Kleppmann’s entire GC-pause argument is about the gap between being told you hold the lock and performing the write — and a conditional write has no such gap, because the two are one operation.
  2. No second system to be partitioned from. An external lock service can be unreachable while the database is fine, and vice versa. Adyen documents what that costs: “In the unlikely event that this data store should become unavailable, the API returns an HTTP 503 – Service Unavailable status with the error code 703”.
  3. It is a fencing token, for free, in the only place that matters. The key record is the token, and the store that holds the effect is the store that checks it — exactly what both Kleppmann and antirez say the resource must do.
  4. It composes with the commit of the effect. Step (5) requires the effect and the key record to become durable together. Same store: one transaction. External lock service: impossible.

The external lock keeps a legitimate but narrower role — as an efficiency optimisation in Kleppmann’s sense, avoiding wasted duplicate work before you reach the database. Layered on top of the conditional write, never instead of it.

What the vendors actually do when two identical keys collide

Every vendor documents this case, and no two of them answer it the same way.

Vendor Status Retryable?

The single most important row is the one that isn’t there

Nobody blocks. Not one vendor documents holding the second request open until the first finishes and then replaying its response — which is exactly what a naive “just take a lock and wait” design would do. Every one of them fails fast and tells the client to retry.

That is the practical consequence of everything above: waiting means holding a lease, and a lease you hold is a lease that can expire under you.

One subtlety worth carrying forward. Stripe deliberately does not store the concurrent-conflict response as the idempotent result:

If the 409 were stored, the key would be permanently poisoned: every subsequent retry would replay a 409 and the client could never learn the real outcome. The rule that only results from requests which actually began executing get stored is what keeps the key usable — and lesson 8 generalises it.

Check yourself

A lock holder pauses for 40s in GC; its lease was 30s. What follows?

The paused holder has no way to learn its lease expired, and checking just before the write does not help because the pause can land between the check and the write. Nothing revokes it, because revocation only works if the resource checks something at write time. And a shorter lease makes the problem more likely, not less.

Check yourself

What do Kleppmann and antirez actually agree about?

Kleppmann wants the storage server to “take an active role in checking tokens”; antirez wants a read-modify-write that proceeds “only if the token is still the same when we write”. Same structure. They disagree precisely on whether the checked value must be monotonic or merely unique — which is the second and third options, both of which antirez contests.

Next

The mechanism is now complete and correct. What remains are the edges — and one of them will silently re-execute your operation while both sides believe everything worked. Lesson 8.

Read next, from the source

Kleppmann, “How to do distributed locking”, and then antirez, “Is Redlock safe?” — in that order, back to back, in one sitting. Neither is a specification and neither is the last word; the value is in watching two serious people disagree carefully about something that looks simple. Read them as a pair or not at all.

Your agent is your teacher. Genuinely worth arguing about: is antirez’s first point — that if you can resolve the race another way you did not need a strong lock — a fair objection or a dodge? There is a defensible case either way, and constructing it is the best possible test of whether this lesson landed.
