Lesson 0008

The edges that bite

The last two mission criteria live here: naming the mechanism’s most dangerous property, and recognising that a key buys effectively-once effect and never exactly-once execution.

The mechanism is complete and correct. What is left is where it fails anyway — and the first of these is the only failure mode in the whole subject that is invisible from both sides at once.

1. Retention: the silent re-execution

No authority agrees with any other, and the specifications explicitly decline to choose:

Documented retention windows. The spread is four orders of magnitude.
Source Window
AWS DynamoDB TransactWriteItems 10 minutes
AWS Lambda Powertools 1 hour by default, configurable with no upper limit
Stripe 24 hours — but see the discrepancy below
Brandur (practitioner) ~72 hours, to survive a bad Friday deploy into Monday
Adyen “valid for a period of 7 to 14 days after first submission”
Birrell & Nelson, 1983 “say, after five minutes”
PayPal, Square, AWS EC2 not documented
Stripe’s two pages do not say the same thing

The API reference says keys “can [be removed] from the system automatically after they’re at least 24 hours old” — a floor on when pruning may begin. The error-handling page says “keys expire out of the system after 24 hours” — a ceiling on validity. These are different statements, and this workspace quotes both rather than reconciling them.

The rule that generates all of those numbers is one sentence:

The rule

Retention must exceed the client’s maximum retry horizon.

If a client’s retry policy can fire a final attempt 36 hours after the first, and the server prunes at 24, the final retry finds no record and executes the operation a second time.

Stripe states the consequence outright:

The most dangerous property of the whole mechanism

An expired key is not an error. It is indistinguishable from a key never seen, and therefore silently executes.

The failure is invisible from both sides: the client believes it retried idempotently, the server believes it received a new request, and a second charge exists. Nothing logs an error. Nothing alerts.

Worse, the retention window and the client’s retry schedule are one design — and they are usually owned by two different teams who never discuss it.

Adyen’s 7–14 days is interesting precisely because it is a range: the guarantee is a floor of 7 days, with actual pruning somewhere up to 14. A client should always plan against the floor.

2. Same key, different payload

This is what the idempotency fingerprint exists to catch. The draft’s answer is 422:

AWS uses one consistent error name across two services:

The authorities disagree on the status code

The IETF draft says 422. AWS returns HTTP 400. Stripe describes the error without pinning a code to it on its idempotency page. Square hedges: “this behavior might vary depending on the API.” If you are writing a client, do not assume 422.

Why detect it at all? Because both alternatives are worse. Replay on key alone, and a client with a key-reuse bug silently receives someone else’s answer — the $5 charge response for a $500 request. Ignore the key and execute, and you have no idempotency. Failing loudly is the only option that surfaces the client’s bug.

A trap inside the fingerprint

draft-07 §2.4 permits fingerprinting either the entire payload or selected elements, and the choice has teeth. Whole-payload checksums are brittle: a client that re-serialises its JSON with different key ordering, adds a client_timestamp, or upgrades a library that changes float formatting will produce a different fingerprint for a semantically identical retry — and receive a 422 on a request that should have replayed.

Fingerprinting only the semantically significant fields is more forgiving, at the cost of missing changes to the fields you excluded. The specification takes no position. This is a real decision, and it is yours.

3. Scoping: a key is never global

draft-07 §5 makes this a security requirement rather than mere hygiene:

Concretely: if keys are global and a client sends Idempotency-Key: 1, it receives whatever response the previous sender of 1 got. That is a cross-tenant data disclosure reachable by guessing.

The observed scopes differ substantially.
Scope Who
Per user account Brandur: UNIQUE (user_id, idempotency_key)
Per company account Adyen
Per region Adyen, and AWS EC2 (“regional idempotency”)
Per availability zone AWS EC2 (“zonal idempotency”)
Per API call type PayPal — authorize and capture are different keys
Per function + payload hash AWS Lambda Powertools, by default
Regional scoping breaks region failover

AWS says it outright, and so does Adyen: a request with the same token “can complete only once within a Region”. A client with region failover in its retry policy can duplicate an operation while following every documented rule correctly.

Note also the Powertools default: the key is derived from the payload hash rather than supplied by the client. That is a genuinely different design. It deduplicates identical payloads automatically, but it cannot distinguish “the same request retried” from “two legitimately identical requests” — which is precisely the distinction a client-supplied key exists to express. A reasonable default for event processing; a poor one for payments.

4. Which failures to store, and which free the key

This is the most contested design point in the subject. Stripe stores nearly everything:

That final clause is the justification, and it is a good one: a 500 means the outcome is indeterminate, so re-running under a new key risks a second effect from an operation that may have half-succeeded.

The operative principle

It is not “cache successes, free failures”. It is:

Store the outcome of anything that may have had an effect. Free the key for anything that provably did not.

A validation rejection, an auth failure, a rate-limit and a concurrency conflict all happen before the handler runs — so nothing happened, so the key stays available. A 500 from inside the handler might have done anything, so it is recorded.

Stripe warns that the boundary is genuinely fuzzy:

Because a status code alone does not carry enough information, two vendors invented headers for it — Adyen’s transient-error, and Stripe’s Stripe-Should-Retry, whose three-valued design is worth noticing because it admits ignorance: set to true, retry; set to false, don’t; not set, “the API can’t determine whether or not it can retry the request.” Neither header is in the IETF draft, which is itself a comment on the draft’s completeness.

5. The crashed holder

If the server dies after claiming the key and before completing, the record sits in IN_FLIGHT forever and the key is bricked — every retry gets a 409 and the operation can never complete. So the in-flight state needs a lease, and every real implementation has one.

This is lesson 7’s hazard, in your own database

It does not disappear because the lease is local. If the original holder was merely paused rather than dead, it can wake after the lease expires and complete its work alongside the second attempt.

What makes it tolerable here is that the commit in step (5) is itself conditional: the awakened holder’s write targets a record whose state it no longer owns, and a conditional update (UPDATE ... WHERE state = 'IN_FLIGHT' AND lease_id = ?) rejects it.

The lease is an optimisation for liveness; the conditional write is what provides safety. Get those two backwards and the lease becomes the safety mechanism — which is exactly the mistake Kleppmann was warning about.

Nobody documents how long “in flight” may last. Powertools ties it to the Lambda timeout and Brandur uses a constant; Stripe, Adyen, PayPal and Square state no figure. This is a genuine gap in the public record, not an omission here.

That third category is the hard one, and it is the end-to-end argument from lesson 4 biting from the other direction. If a downstream service offers no key, no amount of care upstream makes the composite operation idempotent. The honest options are to make the call observable — query downstream for whether your operation happened, using a correlation ID you chose — or to accept at-least-once and reconcile afterwards.

7. The conceptual payoff

State this flatly

A key gives you effectively-once effect, never exactly-once execution.

The handler may run more than once. That is not a bug to be engineered away; it is forced by the ambiguous failure. The client cannot distinguish a lost request from a lost response, so it must retry, and a retry may arrive after a crashed first attempt left partial work behind. Van Steen’s six orderings show there is no protocol that avoids it.

What the key buys is that the externally observable effect occurs once. The charge row exists once. The email is sent once — if the email provider honours a key. The instance is launched once, within its region.

The distinction is not pedantic. It dictates three things:

  • Handlers must tolerate partial re-execution, because they will get it. Anything done before a crash must be either rolled back by the transaction or made idempotent in its own right.
  • “Exactly-once” in vendor marketing means this, not what it says. Kafka’s documentation is the model of honesty: “it is important to read the fine print”.
  • The composite is only as idempotent as its weakest foreign call.

8. When not to use one

Worth stating because it is the most common misuse. A key is unnecessary where the method already carries the guarantee:

Both Stripe and Adyen are appealing directly to RFC 9110 §9.2.2 here. A key on a PUT adds a row, a lookup and a failure mode in exchange for a guarantee the method already makes.

The genuinely marginal case is PATCH, which is not idempotent in general but often is in practice: a PATCH that sets fields to absolute values behaves like a scoped PUT; one that increments does not. RFC 9110 §9.2.2’s clause — “unless it has some means to know that the request semantics are actually idempotent, regardless of the method” — is what licenses treating such a PATCH as safe to retry, and a key is how you would establish that for the ones that are not.

Check yourself

A retry arrives after the key record was pruned. What happens?

An expired record is deleted, so the atomic claim succeeds and the request looks brand new. There is no expired-key error because there is nothing left to report on, and nothing to replay. This is the mechanism’s most dangerous property: both sides believe everything worked.

Check yourself

Why does Stripe store the result of a 500 but not of a 409?

The concurrency conflict happens before the endpoint begins executing, so provably nothing happened and the key stays usable. A 500 from inside the handler is indeterminate, so it is recorded. Storing the 409 would poison the key permanently — every later retry would replay it and the client could never learn the real outcome.

Check yourself

What exactly does an idempotency key guarantee?

Effectively-once effect, never exactly-once execution. The handler may well run twice — after a crash, after a lease expiry — which is why it must tolerate partial re-execution. The request certainly arrives more than once; that is the premise. And responses may legitimately differ, as PayPal’s return-current-state design shows.
