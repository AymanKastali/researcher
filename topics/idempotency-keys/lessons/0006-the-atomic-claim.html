Lesson 0006

The atomic claim

Step (3) of the lifecycle, alone. It is the step that decides whether the whole design is correct, and the mission asks you to be able to say what breaks when it is not atomic.

Step (3) looks innocuous right up until you write it as two operations. Then it is a textbook time-of-check-to-time-of-use bug, wearing the costume of a safety mechanism.

The race, precisely

Two things this is not

It is not fixed by narrowing the window. Moving t₂ closer to t₀ shrinks the probability and removes nothing. A bug that happens rarely on a payments endpoint is still a bug that happens.

It is not fixable in the process. The two requests may be handled by different processes on different machines, so a mutex, a language-level lock, or a per-process cache cannot help. There is no shared memory to guard.

This is not exotic. A double-clicked submit button, two load-balanced retries landing on different application servers, or a client retrying on timeout while the original still runs will all produce it.

The requirement, stated once

The check and the claim must be a single indivisible operation in a store that both requests can see.

There are three families of answer. Two are good. One is popular and worse — and it gets lesson 7 to itself.

Mechanism A — the atomic conditional insert

Collapse check-and-claim into one statement, and let the storage engine’s own uniqueness machinery arbitrate. Exactly one request wins; the loser is told it lost. This is the recommended answer, and every major store offers the primitive.

PostgreSQL

A UNIQUE index on the key column makes a second insert fail. The documentation states the guarantee for the upsert form outright:

“Even under high concurrency” is the phrase doing the work. INSERT ... ON CONFLICT DO NOTHING combined with RETURNING tells you in a single round trip whether you claimed the key or somebody else already had it.

A caveat worth recording

The SET page makes no explicit atomicity claim. This is widely misquoted. The guarantee has to be sourced from the transactions page instead: “All the commands in a transaction are serialized and executed sequentially. A request sent by another client will never be served in the middle of the execution of a Redis Transaction.” (Redis, “Transactions”.)

Mechanism A in the wild: AWS Lambda Powertools

AWS ships a first-party implementation of exactly this design, and it is worth looking at because the reasoning is documented alongside the code:

The condition expression itself is a three-way “claim if nobody holds this, or the holder’s claim has gone stale”. The comments are the library authors’:

Python 
# Conditions to successfully save a record:

# The idempotency key does not exist:
#    - first time that this invocation key is used
#    - previous invocation with the same key was deleted due to TTL
idempotency_key_not_exist = "attribute_not_exists(#id)"

# The idempotency record exists but it's expired:
idempotency_expiry_expired = "#expiry < :now"

# The status of the record is "INPROGRESS", there is an in-progress expiry timestamp, but it's expired
inprogress_expiry_expired = " AND ".join(
    [
        "#status = :inprogress",
        "attribute_exists(#in_progress_expiry)",
        "#in_progress_expiry < :now_in_millis",
    ],
)

condition_expression = (
    f"{idempotency_key_not_exist} OR {idempotency_expiry_expired} OR ({inprogress_expiry_expired})"
)

Quoted from aws_lambda_powertools/utilities/idempotency/persistence/dynamodb.py. This is the library’s source, not code written for this lesson.

Both mechanisms are correct. They differ in what does the arbitrating.
Mechanism Arbitrated by The loser learns via
A — conditional insert A uniqueness constraint or condition expression Constraint violation, ConditionalCheckFailedException, or a null reply
B — serialisable transaction The isolation level’s conflict detection A serialisation failure aborting the transaction
Check yourself

Why can’t an in-process mutex protect the claim step?

A mutex guards shared memory, and two load-balanced requests carrying the same key have none. The arbitration has to happen in the one place both requests can see — the store. Note that runtimes do not silently release mutexes, and keying a lock table by string is trivial; neither is the real objection.

Check yourself

Which single property makes INSERT ... ON CONFLICT the right tool here?

Postgres guarantees “an atomic INSERT or UPDATE outcome … even under high concurrency”, which is precisely the indivisibility the race requires. Saving a round trip is a genuine but incidental benefit, and holding a lock for the request duration is the thing the next lesson argues against.

Read next, from the source

PostgreSQL 17, INSERT — the “ON CONFLICT Clause” section — read for the atomicity guarantee and for what it carefully does not promise. Then compare it with DynamoDB’s PutItem: two entirely different databases arriving at the same primitive is the strongest evidence you will get that this is the right shape.
