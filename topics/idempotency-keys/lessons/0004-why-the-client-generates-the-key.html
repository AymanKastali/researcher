Lesson 0004

Why the client generates the key

The mission is the reasoning, and this is the step most people skip: not what the key is, but why it can only come from the client and from nowhere else in the stack.

Deduplication at the receiver needs an identifier. The obvious question is why that identifier is the application’s problem — surely the network, the framework, or the load balancer could suppress duplicates on your behalf. The answer is one of the most-cited arguments in systems design, and it settles the matter.

The sentence that explains the whole design

TCP already deduplicates segments. It cannot deduplicate intentions.

Only the client knows that the POST /charges it is sending now is a retry of the one it sent thirty seconds ago rather than a genuine second charge. The two are byte-identical, and no layer beneath the application has any way to tell them apart. So the client must say so — and the way it says so is by attaching a stable identifier it chose before the first attempt.

Notice that the argument cuts both ways. It is not just that lower layers need not suppress duplicates; it is that they cannot, for the class of duplicate that matters most. A retry the application generated is, to the network, a new message that happens to look like an old one.

Five names, one mechanism

Birrell & Nelson’s call identifier, Kafka’s producer ID + sequence number, Stripe’s Idempotency-Key, AWS’s ClientRequestToken, PayPal’s PayPal-Request-Id and Google’s request_id. The mechanism has not changed since 1983 — a client-chosen identifier, a table at the receiver, and an expiry.

The header itself

Only now, with the reasoning in place, is the syntax worth looking at. The header is being standardised but is not yet an RFC. The current revision is draft-ietf-httpapi-idempotency-key-header-07, Jena & Dalal, IETF HTTPAPI Working Group, dated 15 October 2025. Its own boilerplate insists on how it may be cited:

idempotency key

An idempotency key is a unique value generated by the client which the resource uses to recognize subsequent retries of the same request. The Idempotency-Key HTTP request header field carries this value.

draft-ietf-httpapi-idempotency-key-header-07 §2. Work in progress, not an RFC.

The draft describes where the WG wants to go

Almost no production deployment quotes the value. Stripe’s own documented example is Idempotency-Key: KG5LxwFBepaKHyUD — unquoted. Every real deployment is older than the draft, and this is one of several places where the two diverge. Do not read the draft as a description of current practice.

Random UUIDv4 Collisions are effectively impossible, and two genuine requests never share a key. A UUID held only in the retrying process’s memory is lost if that process dies.
Derived from a cart ID Reconstructible by any process, so it survives a restart — nothing has to be remembered. The same cart legitimately checked out twice collides, and the second checkout silently replays the first.

The mistake that silently disables the whole mechanism

There is one error here that is worth more attention than everything else in this lesson, because it produces a system that looks correct, passes review, and provides no protection whatsoever.

Python Written for this lesson 
# WRONG. A fresh key per attempt means every attempt is a new operation,
# and the server has no way to connect them. This has no idempotency at all.
for attempt in range(3):
    post("/charges", key=uuid4(), body=body)

# RIGHT. The key is bound to the intent, generated once, before the first
# attempt, and reused unchanged by every retry.
key = uuid4()
for attempt in range(3):
    post("/charges", key=key, body=body)

The key must be bound to the user’s intent — one checkout, one key — rather than to an attempt. And if the client can restart, the key has to survive the restart, which is precisely the argument for deriving it from something durable rather than generating it in memory.

Check yourself

Why can’t the network layer suppress duplicate requests for you?

Saltzer, Reed and Clark put it exactly this way: “These application level duplications look like different messages to the communication system, so it cannot suppress them.” TCP does deduplicate its own segments perfectly well — that is not the gap. The gap is that a retry your code decided to issue is a genuinely new message, and only your code knows it represents the same intent.

Check yourself

Where in a retry loop should the idempotency key be generated?

The key identifies the intent, not the attempt, so it is generated once and reused unchanged. Generating inside the loop is the classic silent failure: every attempt carries a different key, so the server sees several unrelated first-time requests. Sending it only on retries fails because there is then no record from the first attempt to match against, and a server-issued key cannot work at all — the client needs it before it makes the request whose response it may never see.
