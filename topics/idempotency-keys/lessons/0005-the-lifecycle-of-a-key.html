Lesson 0005

The lifecycle of a key

A mission success criterion: draw the eleven-step lifecycle from memory, and name which two steps must be atomic and what breaks if either is not. This lesson builds the drawing.

Here is the case the entire mechanism exists for. The operation succeeds. The response is lost. The client retries. The server replays. Nothing goes wrong anywhere, and without a key the customer is charged twice.

Fix the vocabulary first

Three of these terms are Brandur Leach’s — practitioner vocabulary, not normative, but widely borrowed and worth using.
Term Meaning Weight
Idempotency key The client-generated value the resource uses to recognise retries. Specification (draft-07 §2)
Idempotency fingerprint A checksum or field match over the payload, generated by the resource. Specification (draft-07 §2.4)
Key record The server-side row holding key, fingerprint, state and the stored response. Implied by draft-07 §2.6; schema from Brandur
Foreign state mutation “Calling out and manipulating data on another system” — a side effect you cannot roll back. Practitioner
Atomic phase “A set of local state mutations that occur in transactions between foreign state mutations.” Practitioner
Recovery point A checkpoint reached after an atomic phase or foreign state mutation succeeds. Practitioner
Keep two of these apart

The idempotency key is the client’s value. The key record is the server’s row. The client never sees the record, and the server never invents the key. Conflating them makes the lifecycle impossible to describe.

The steps that carry weight

(2) The server computes the fingerprint

This is done by the resource, never by the client, and the draft deliberately leaves the algorithm open:

Because it may be “selected element(s)” rather than the whole payload, two conforming implementations can legitimately disagree about whether a given retry is “the same request”. That is a real consequence, and lesson 8 returns to it.

(3) The atomic claim

Conceptually: insert a record for this key in the IN_FLIGHT state, but only if no record for this key exists, and do the existence check and the insert as one indivisible operation. Win and you proceed; lose and you are a duplicate.

The step the whole design lives or dies on

“Check whether it exists” and “create it” must be one operation, not two. A read followed by a write is a race, and it loses in a way that produces exactly the double charge the key was added to prevent. Lesson 6 is entirely about this one step.

(5) Persist the response atomically with the effect

The effect — the charge row — and the key record’s transition to COMPLETE with its stored status and body must commit together. If they commit separately there is a window in which the effect exists but the key record does not say so, and a retry landing in that window executes the effect a second time.

(7) The client retries — same key, same body, after backoff

Why jitter matters more here than usual

Idempotency-key retries are correlated by construction: every client that lost a response to the same incident will retry on the same schedule. Without jitter, the recovery is itself a synchronised stampede.

The key record as a state machine

And the read path — what happens to a request whose atomic claim failed because a record already exists:

The three-way branch, which draft-07 §2.6 sets out and the vendors then disagree about.
Existing state Fingerprint Server does Status
IN_FLIGHT not checked refuse; tell the client to retry later 409 (draft-07, Stripe)
COMPLETE matches replay the stored status and body; do not run the handler the stored status
COMPLETE differs refuse; the client has a key-reuse bug 422 (draft-07) / 400 (AWS)
“Expired” is not a fourth case

An expired record is deleted. So the atomic claim in step (3) succeeds and the operation runs again as if the key had never been seen. This is the most dangerous property of the entire mechanism and it gets its own section in lesson 8.

The IN_FLIGHT state is the whole reason this is hard. If operations were instantaneous it would not exist, and an idempotency key would be nothing more than a cache lookup.

The whole thing, in one sketch

Python Written for this lesson 
import hashlib
import json

CONFLICT = "another request with this key is in flight"
MISMATCH = "this key was used with a different payload"


def fingerprint(body: dict) -> str:
    """The resource computes this; the client never sends it.
    draft-07 §2.4 permits a checksum over the whole payload."""
    canonical = json.dumps(body, sort_keys=True, separators=(",", ":"))
    return hashlib.sha256(canonical.encode()).hexdigest()


def handle(db, account_id, key, body, operation):
    scope = (account_id, key)          # keys are scoped, never global
    fp = fingerprint(body)

    # --- Step 3: the atomic claim. -----------------------------------------
    # One statement. The existence check and the insert cannot be separated,
    # or two concurrent requests can both observe "absent" and both proceed.
    claimed = db.insert_if_absent(
        scope, {"fingerprint": fp, "state": "IN_FLIGHT"}
    )

    if not claimed:
        record = db.get(scope)

        if record["fingerprint"] != fp:
            return 422, {"error": MISMATCH}          # draft-07 §2.7

        if record["state"] == "IN_FLIGHT":
            return 409, {"error": CONFLICT}          # draft-07 §2.7

        # Replay. The handler is NOT invoked.
        return record["status"], record["body"]

    # --- Steps 4 and 5: execute, then commit effect and record TOGETHER. ---
    # If these two commits can be separated, a retry landing in the gap
    # executes the operation a second time.
    with db.transaction() as tx:
        status, response = operation(tx, body)
        tx.update(scope, {
            "state": "COMPLETE", "status": status, "body": response,
        })

    return status, response

This omits error handling, transaction retry, observability and expiry. Everything genuinely interesting is in two places: insert_if_absent, and the single with db.transaction() block.

Check yourself

Why must the effect and the key record commit in one transaction?

Separate commits leave a window where the charge exists but the key record does not yet say COMPLETE. A retry arriving in that window finds nothing to replay and runs the handler again. Note that the draft does not require one transaction — it says nothing about storage at all — and performance is beside the point.

Check yourself

Who computes the idempotency fingerprint, and from what?

draft-07 §2.4: the fingerprint “is generated from request payload data by the resource”. The client never sends it and never computes it — which matters, because a client-supplied fingerprint could be forged to make a different payload look like the original.
