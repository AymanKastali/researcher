Lesson 0001

What “idempotent” actually means

The mission is to own the reasoning, not the header. Everything later rests on one distinction made in this lesson: idempotence of a function is checkable, idempotence of an effect has to be engineered.

The word is a century older than computing, and it did not originally describe functions at all. Starting where it started is worth ten minutes, because the modern misuses of the word are all recoverable from the original definition.

The algebraic origin

It was coined by Benjamin Peirce, Perkins Professor of Astronomy and Mathematics at Harvard, to name a class of expressions in a hypercomplex algebra.

idempotent

25. When an expression raised to the square or any higher power vanishes, it may be called nilpotent; but when, raised to a square or higher power, it gives itself as the result, it may be called idempotent.

The defining equation of nilpotent and idempotent expressions are respectively An = 0, and An = A; but with reference to idempotent expressions, it will always be assumed that they are of the form A² = A, unless it be otherwise distinctly stated.

Benjamin Peirce, Linear Associative Algebra, §25, p. 8. Lithographed and privately circulated 1870; quoted here from the 1882 D. Van Nostrand printing, scanned at the Internet Archive.

Transposed to functions

Notice what Peirce is not saying. He defines a property of an element under multiplication — A² = A — not a property of a function. The form programmers recite is the same idea moved to function composition:

notation 
f(f(x)) = f(x)

Applying f to an already-f’d value changes nothing further. That is a property you can check by reading the function.

Python Written for this lesson 
abs(abs(-5)) == abs(-5)                 # idempotent
sorted(sorted([3, 1])) == sorted([3, 1])  # idempotent
max(max(2, 5), 5) == max(2, 5)            # idempotent — clamping to a floor
set(set("aab")) == set("aab")             # idempotent

total = 0
total += 1        # NOT idempotent: each application moves the value
items = []
items.append("x") # NOT idempotent: each application grows the list

The pattern separating the two groups: the idempotent operations name a destination, and the others name a delta. “Make this non-negative” has a fixed answer you can arrive at twice. “Add one” does not.

Check yourself

Which of these functions is idempotent under f(f(x)) = f(x)?

Rounding down to the nearest ten is idempotent: 41 becomes 40, and 40 is already a whole ten, so it stays 40. The other three each move the value further every time they are applied — they name a delta rather than a destination. Note how narrow the property is: rounding up to the next ten in the strict sense, where 50 becomes 60, would not be idempotent. Idempotence lives in the exact definition, never in the general shape of the operation.

The distinction the rest of the topic turns on

Everything above is idempotence of a function: a property of a pure mapping from input to output. It is checkable by inspection, it holds for all time, and no world outside the function is involved.

What you actually need from an API is a different thing wearing the same word. Idempotence of an effect over a network is a property of a system’s state after a message is processed, possibly more than once, by a remote party, across a channel that can lose, delay, duplicate and reorder. Nothing about it is checkable by inspection. It is a property you have to engineer.

The load-bearing sentence

A function is idempotent or it is not, and you can tell by looking. An effect is idempotent only because somebody built the machinery that makes it so. The rest of this topic is about that machinery.

Three objects, and only one of them is interesting

Analogies are not definitions — the definitions are quoted above and in the next lesson — but these three fix the shape of the problem.

The same word covering three genuinely different situations.
Object Idempotent? Why
Light switch Yes, inherently “Set the switch to on” leaves the room lit whether you do it once or ten times. The operation names a destination state, so repeating it is free.
Doorbell No Each press produces another ring. The operation is a delta. “Charge this card $20” is a doorbell.
Elevator call button Yes, but only by construction Physically a doorbell — you can press it repeatedly. The controller keeps a record that a call for this floor in this direction is already outstanding, and drops the duplicate.

The most common misconception

An idempotency key does not make a non-idempotent operation idempotent. It adds a deduplication record in front of the operation. The record is what makes the observable effect idempotent, while the underlying operation stays exactly as non-idempotent as it always was. Charging a card is a doorbell before and after you add a key.

That record — the elevator controller’s note that this floor is already called — is the idempotency key. You now know what it is for before knowing anything about its syntax, which is the right order.

Check yourself

What does adding an idempotency key to a “charge this card” endpoint actually change?

The operation is unchanged — it is still a delta, still a doorbell, and running it twice still produces two charges. What the key adds is a deduplication record consulted before the operation runs, so the second request never reaches it. The client is very much still allowed to send the second request; in fact the whole design assumes it will.

Where this is going

You now have the distinction and the shape of the fix. What you do not yet have is a reason to believe the fix is necessary — after all, if PUT is idempotent, why not simply choose idempotent methods and be done? That is lesson 2, and the answer turns out to be that HTTP’s promise is both narrower and stranger than it first looks.

Read next, from the source

Benjamin Peirce, Linear Associative Algebra — §25 is on page 8, and it is four lines long. Read the preface too (it is the paragraph quoted above). Ten minutes with a 140-year-old algebra text is a surprisingly good way to make a definition stick, because you will remember where you got it.

Your agent is your teacher. If the function-versus-effect distinction feels like a word game rather than a real difference, say so — that reaction is common and worth taking apart before moving on, because every later lesson leans on it.
