Vendor comparison

Where the implementations actually differ. No two vendors answer the concurrent case the same way, and the retention windows span four orders of magnitude — so this is the page to check before assuming anything about someone else’s API.

Read this first

Every disagreement below is real and load-bearing. A client written against one vendor’s behaviour and pointed at another’s will be wrong in ways that do not surface until a failure — which is exactly when you were relying on it.

Field name and length budget

Vendor / spec Field Max length
IETF draft-07 Idempotency-Key — Structured Field String, quoted on the wire not specified
Stripe Idempotency-Key 255
Adyen idempotency-key 64
Square idempotency_key — a body field 45
PayPal PayPal-Request-Id 38 single-byte characters
AWS EC2 ClientToken 64 ASCII characters
AWS DynamoDB ClientRequestToken 36
Google AIP-155 request_id — a proto field “Restricted to 36 ASCII characters” — in the illustrative proto comment only, not a normative bullet
Why UUIDv4 is the universal recommendation

A bare UUIDv4 is 36 characters, which fits inside every budget above — including DynamoDB’s 36 and PayPal’s 38. That is not a coincidence; it is the reason the recommendation is universal.

Square adds a caveat nobody else does: “the number of allowed characters might be less than the stated maximum, if multi-byte characters are used.”

Concurrent request — a retry while the first is still in flight

Vendor Status Retryable?
IETF draft-07 409 yes — “with the exception of 409 where no correction is required”
Stripe 409 Conflict yes, explicitly
Adyen 422 or 409, error code 704 yes — transient-error: true header
PayPal not stated — “might fail the second request” not stated
AWS Lambda Powertools IdempotencyAlreadyInProgressError yes — “you can safely retry the operation”
Square nothing documented —
AWS EC2 nothing documented —
Nobody blocks

Not one vendor documents holding the second request open until the first finishes and then replaying its response — which is what a naive “take a lock and wait” design would do. Every one of them fails fast and tells the client to retry. Waiting means holding a lease, and a lease you hold is a lease that can expire under you.

Same key, different payload

Vendor Behaviour
IETF draft-07 422 Unprocessable Content
AWS (EC2, DynamoDB) IdempotentParameterMismatch, HTTP 400
Stripe Errors, “indicating that the new request didn’t match the original”; no code pinned on the idempotency page
Square An error, hedged: “this behavior might vary depending on the API”

The authorities disagree on the status code. If you are writing a client, do not assume 422.

Retention window

Both specifications explicitly decline to choose. AIP-155: “APIs may choose any reasonable timeframe.”
Source Documented window
AWS DynamoDB TransactWriteItems 10 minutes, stated on two pages
AWS Lambda Powertools 1 hour default; “no limit on how long” it can be set to
Stripe (API reference) “can remove keys … after they’re at least 24 hours old” — a floor on pruning
Stripe (error handling) “keys expire out of the system after 24 hours” — a ceiling on validity
Brandur (practitioner) ~72 hours, to carry a bad Friday deploy through to Monday
Adyen “valid for a period of 7 to 14 days after first submission”
Birrell & Nelson, 1983 “say, after five minutes”
AWS EC2 / PayPal / Square not documented
The rule behind every number above

Retention must exceed the client’s maximum retry horizon. An expired key is indistinguishable from a key never seen, so it silently executes — invisibly from both sides. Adyen’s 7–14 days is a range, not a number: plan against the floor.

What gets replayed

A genuine, citable fork in the design space — and not a cosmetic one.

Approach Who Consequence
Replay the stored original response Stripe (“saving the resulting status code and body of the first request”), Square The client sees exactly what it would have seen, however stale.
Return current state AIP-155, and PayPal explicitly: “PayPal provides the status of a request at the current time and not the status of the original request.” A client assuming the first approach will misread a subsequently-modified resource as the original outcome.

Key scoping

Scope Who
Per user account Brandur: UNIQUE (user_id, idempotency_key)
Per company account Adyen
Per region Adyen; AWS EC2 “regional idempotency”
Per availability zone AWS EC2 “zonal idempotency”
Per API call type PayPal — authorize and capture are separate keys
Per function + payload hash AWS Lambda Powertools, by default
Regional scoping breaks region failover

AWS and Adyen both say it: a key is checked only within its region. A client whose retry policy fails over to another region can duplicate an operation while following every documented rule correctly.

Vendor-specific headers, none of them standardised

Header Vendor Meaning
Idempotent-Replayed: true Stripe This response was replayed, not executed. The only way a client can tell. Documented on the error-handling page only.
Stripe-Should-Retry Stripe Three-valued: true retry, false don’t, absent means the API cannot determine it.
transient-error: true Adyen Safe to retry with the same key. Absent or false means do not retry.

None of these three appears in the IETF draft — which is itself a comment on the draft’s completeness, since a status code alone does not carry enough information to decide whether to retry.

What is not documented anywhere

Gaps in the public record, recorded rather than guessed at.

  • How long “in flight” may last before a claim is stale. Powertools ties it to the Lambda timeout, Brandur uses a constant; Stripe, Adyen, PayPal and Square state no figure.
  • The EC2 client-token retention window. Any circulating figure is unsourced. DynamoDB’s 10 minutes is documented.
  • Square’s concurrent-case behaviour and retention window, and its exact error code for a payload mismatch.
