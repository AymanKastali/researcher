Key record lifecycle

The eleven steps, the state machine, the read-path decision table, and the one-statement atomic claim idiom in each major store. Built for looking things up, not for reading through.

The eleven steps

# Step The thing to get right
0 Client generates the key Before the first attempt, bound to the intent. Must survive a client restart.
1 Request carries the key in a header Request header. Not the body, not the URL, not on the resource.
2 Server computes the fingerprint By the resource, over the payload. The client never sends it.
3 Atomic claim Check and insert as one operation. A read then a write is a race.
4 Execute the operation The only slow step, so the only one a duplicate can land during.
5 Commit effect + key record together One transaction. Separate commits leave a window that re-executes.
6 Response is lost Everything was correct. The client still does not know.
7 Client retries Same key, same body, exponential backoff with jitter.
8–9 Lookup, then fingerprint check Match → replay. Mismatch → refuse.
10 Replay the stored response The handler does not run. No second effect.
11 Expiry Record deleted. After this the key is indistinguishable from new.
The two steps that must be atomic

Step 3 — or two concurrent requests both observe “absent” and both execute.

Step 5 — or a retry arriving between the effect’s commit and the record’s commit executes the effect a second time.

State machine

Read path: the claim failed, a record exists

State Fingerprint Do Status
IN_FLIGHT not checked refuse; client retries later 409 (draft-07, Stripe) / 422 or 409 (Adyen)
COMPLETE matches replay stored status and body; do not run the handler the stored status
COMPLETE differs refuse; the client has a key-reuse bug 422 (draft-07) / 400 (AWS)

The atomic claim, per store

One statement each. The loser is told it lost by the mechanism in the last column.
Store Idiom Loser learns via
PostgreSQL INSERT ... ON CONFLICT DO NOTHING RETURNING, over a UNIQUE index Empty RETURNING result
PostgreSQL (alt.) SERIALIZABLE transaction Serialisation failure, transaction aborted
DynamoDB PutItem with attribute_not_exists(<partition key>) ConditionalCheckFailedException
Redis SET key value NX Null reply
Sourcing note on Redis

The SET page makes no explicit atomicity claim — this is widely misquoted. The guarantee comes from the transactions page: commands “are serialized and executed sequentially”, and another client “will never be served in the middle”.

The design rule

Prefer a compare-and-set in the store that holds the effect

Do not take a lock. Make the key’s creation itself the atomic operation, in the same store that holds the effect, so that winning the race and recording the effect are the same commit.

No lease to expire · no second system to be partitioned from · it is a fencing token for free, in the only place that matters · it composes with the commit of the effect.

Reference implementation sketch

Python Written for this workspace 
import hashlib
import json

CONFLICT = "another request with this key is in flight"
MISMATCH = "this key was used with a different payload"


def fingerprint(body: dict) -> str:
    """The resource computes this; the client never sends it."""
    canonical = json.dumps(body, sort_keys=True, separators=(",", ":"))
    return hashlib.sha256(canonical.encode()).hexdigest()


def handle(db, account_id, key, body, operation):
    scope = (account_id, key)          # keys are scoped, never global
    fp = fingerprint(body)

    # Step 3: the atomic claim. One statement — the existence check and the
    # insert cannot be separated, or two requests both observe "absent".
    claimed = db.insert_if_absent(
        scope, {"fingerprint": fp, "state": "IN_FLIGHT"}
    )

    if not claimed:
        record = db.get(scope)

        if record["fingerprint"] != fp:
            return 422, {"error": MISMATCH}

        if record["state"] == "IN_FLIGHT":
            return 409, {"error": CONFLICT}

        # Replay. The handler is NOT invoked.
        return record["status"], record["body"]

    # Steps 4 and 5: execute, then commit effect and record TOGETHER.
    with db.transaction() as tx:
        status, response = operation(tx, body)
        tx.update(scope, {
            "state": "COMPLETE", "status": status, "body": response,
        })

    return status, response

Omits error handling, transaction retry, observability, leases and expiry. Its only job is to make the atomicity of steps 3 and 5 concrete.

Checklist

  • Key generated before the first attempt, not inside the retry loop.
  • Key scoped by account — never a global namespace.
  • Claim is one statement, in the store that holds the effect.
  • Effect and key record commit in one transaction.
  • Fingerprint computed server-side; mismatch refused, not replayed.
  • In-flight claims carry a lease, and the final commit is conditional.
  • Retention window exceeds the client’s maximum retry horizon.
  • Outcomes stored only for requests that began executing; pre-handler failures free the key.
  • Replays marked, so a client can tell them apart.
