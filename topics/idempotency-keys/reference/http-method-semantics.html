HTTP method semantics

What RFC 9110 promises, in the order you will want to check it: the two definitions, the method table, the retry rules, and the three consequences people most often get wrong.

All quotations from RFC 9110, HTTP Semantics — Fielding, Nottingham & Reschke (eds.), IETF, STD 97, June 2022. Obsoletes RFC 7231.

The two definitions

safe — §9.2.1

Request methods are considered “safe” if their defined semantics are essentially read-only; i.e., the client does not request, and does not expect, any state change on the origin server as a result of applying a safe method to a target resource.

RFC 9110 §9.2.1
idempotent — §9.2.2

A request method is considered “idempotent” if the intended effect on the server of multiple identical requests with that method is the same as the effect for a single such request. Of the request methods defined by this specification, PUT, DELETE, and safe request methods are idempotent.

RFC 9110 §9.2.2

The table

safe ⊂ idempotent. Every safe method is idempotent.
Method Safe Idempotent Defined in
GET yes yes §9.2.1, §9.2.2
HEAD yes yes §9.2.1, §9.2.2
OPTIONS yes yes §9.2.1, §9.2.2
TRACE yes yes §9.2.1, §9.2.2
PUT no yes §9.2.2
DELETE no yes §9.2.2
POST no no not listed in §9.2.2
PATCH no no RFC 5789; not listed in §9.2.2

Three consequences

(a) Safety and idempotence are different axes

A method that changes nothing trivially changes nothing twice over, so safe implies idempotent. The converse fails: DELETE is idempotent and emphatically not safe.

(b) It is about the effect, not the response

The one-line settler

DELETE /orders/7 → 204, then 404. Responses differ; intended effect is identical; the method is idempotent. Anyone defining idempotence as “returns the same response” concludes wrongly here.

(c) Idempotence is what licenses automatic retry

Why the header exists at all

“unless it has some means to know that the request semantics are actually idempotent, regardless of the method” — that clause is the specification-level justification for Idempotency-Key. The header is the means.

Why POST is not idempotent

The promise tracks whether the method names an absolute state.
Method What it names
PUT A destination state — replace the resource with this.
DELETE An absence — this resource should not exist.
POST Nothing. The resource decides, so HTTP cannot promise.

Status codes the idempotency draft leans on

409 Conflict — §15.5.10

The 409 (Conflict) status code indicates that the request could not be completed due to a conflict with the current state of the target resource. This code is used in situations where the user might be able to resolve the conflict and resubmit the request.

RFC 9110 §15.5.10. A good fit for “wait, then retry the same key”.
422 Unprocessable Content — §15.5.21

The 422 (Unprocessable Content) status code indicates that the server understands the content type of the request content […] and the syntax of the request content is correct, but it was unable to process the contained instructions.

RFC 9110 §15.5.21. A fingerprint mismatch is exactly this.

Two errata in the idempotency draft

Verified against the source documents, and a useful reminder that a draft is a draft.

  1. It omits TRACE. draft-07 §1 says “Per [RFC9110], the methods OPTIONS, HEAD, GET, PUT and DELETE are idempotent”. RFC 9110 §9.2.2 says “PUT, DELETE, and safe request methods”, and §9.2.1 lists the safe methods as “GET, HEAD, OPTIONS, and TRACE”.
  2. Its normative references are stale. It cites RFC 8941 for Structured Fields, obsoleted by RFC 9651 in September 2024; and RFC 7231 for “resource” and IMF-fixdate, obsoleted by RFC 9110 in June 2022 — the very document it cites elsewhere.
When not to add a key

A key on a GET, PUT or DELETE adds a row, a lookup and a failure mode in exchange for a guarantee the method already makes. Stripe: “Don’t send idempotency keys in GET and DELETE requests because it has no effect. These requests are idempotent by definition.”
