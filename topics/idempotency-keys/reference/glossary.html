Glossary

The vocabulary of retry-safe APIs. Where a term has a quoted definition in a specification, that quotation is the authority and the entry here is its compression.

Canonical source: GLOSSARY.md in this topic. The two are kept in step; this page is the readable rendering.

The property

idempotent

Of a request method, one whose intended effect on the server after several identical requests is the same as after one.

Defined by RFC 9110 §9.2.2. Avoid: repeatable, retry-safe, “returns the same response”.
safe

Of a request method, one whose defined semantics are essentially read-only. Every safe method is idempotent; the converse fails, which is why DELETE is idempotent and not safe.

RFC 9110 §9.2.1. Avoid: read-only, harmless, non-mutating.
idempotence of an effect

A property of a system’s state after a message is processed, possibly more than once, across a channel that can lose, delay, duplicate and reorder. Engineered, never checkable by inspection — as distinct from idempotence of a function, which is a property of a pure mapping.

Avoid: real idempotency, practical idempotency.
effectively-once

The guarantee an idempotency key actually delivers: the externally observable effect occurs once, while the handler may run more than once.

Avoid: exactly-once, once-only, deduplicated delivery.

The failure

ambiguous failure

The state a client is left in when a request produces no response: the operation was performed either once or not at all, and the client is not told which.

Named in Birrell & Nelson, 1983. Avoid: timeout, network error, unknown state.
at-least-once

A delivery policy under which the client retries on ambiguity, so work is never lost but may be applied twice.

Avoid: guaranteed delivery, reliable delivery.
at-most-once

A delivery policy under which the client never retries, so work is never applied twice but is silently dropped whenever a response is lost.

Avoid: fire-and-forget, best effort.
exactly-once

Not a selectable delivery policy. Where it is achieved it is always at-least-once delivery plus deduplication at the receiver, and vendor claims to the contrary warrant reading the fine print.

Use the term only to name the thing that does not exist as advertised.

The machinery

idempotency key

“A unique value generated by the client which the resource uses to recognize subsequent retries of the same request.” It identifies a request, never a resource.

draft-07 §2, work in progress. Avoid: request ID, token, nonce, dedupe key.
idempotency fingerprint

A checksum or field match computed by the resource over the request payload, used to detect the same idempotency key arriving with a different request. The client never sends it.

draft-07 §2.4. Avoid: request hash, payload checksum, body signature.
key record

The server-side row holding the idempotency key, the idempotency fingerprint, the state, and the stored response. The thing the atomic claim creates.

Avoid: lock row, cache entry, dedupe record.
atomic claim

The single indivisible operation that creates a key record only if none exists, deciding in one step whether this request owns the idempotency key or is a duplicate. A read followed by a write is not one of these.

Avoid: lock acquisition, check-and-insert, reservation.
replay

Returning a key record’s stored status and body without invoking the handler. The step at which the second request produces no second effect.

Avoid: cache hit, re-serve, idempotent response.
retention window

How long a key record survives before it is deleted. Must exceed the client’s maximum retry horizon, because an expired key record is indistinguishable from one never seen.

Avoid: TTL, expiry, cache lifetime.
lease

A time bound on an in-flight claim, so a key is not bricked forever when its holder dies. An optimisation for liveness; never the safety mechanism.

Avoid: lock timeout, deadline, in-progress expiry.
fencing token

A number that strictly increases each time a lock is acquired, sent with every write so the storage layer can reject a write whose token has gone backwards.

Kleppmann, 2016. Avoid: version number, sequence, epoch.

Where the effect lives

foreign state mutation

“Calling out and manipulating data on another system” — a side effect that no local transaction can roll back, and therefore the point at which the effect and the key record can no longer commit together.

Brandur Leach, practitioner writing. Avoid: external call, side effect, third-party write.
atomic phase

“A set of local state mutations that occur in transactions between foreign state mutations.”

Brandur Leach, practitioner writing. Avoid: step, stage, unit of work.
recovery point

A named checkpoint reached after an atomic phase or a foreign state mutation completes, so a retry can resume from just before the last failure rather than from the beginning.

Brandur Leach, practitioner writing. Avoid: checkpoint, resume marker, saga step.

Notes on usage

Key versus record

The idempotency key names the client’s value; the key record names the server’s row. Conflating them makes the lifecycle impossible to describe, because the whole mechanism is about what the server does with a row the client never sees.

State names in this workspace

A key record’s states are IN_FLIGHT and COMPLETE throughout. Real implementations disagree on spelling — AWS Lambda Powertools uses INPROGRESS, COMPLETED and EXPIRED in its source constants while its own documentation page writes COMPLETE and IN_PROGRESS elsewhere. Vendor spellings appear here only inside quotations.

“Expired” is not a third state

An expired key record is deleted, so the atomic claim succeeds and the operation runs again as if the key had never been seen.
