# Network Idempotency Glossary

The vocabulary of retry-safe APIs: what "idempotent" means, the failure that
makes keys necessary, and the parts of the machinery that delivers them. Where a
term has a quoted definition in a specification, that quotation is the authority
and this entry is the compression of it.

## The property

**Idempotent**:
Of a request method, one whose intended effect on the server after several
identical requests is the same as after one. Defined by
[RFC 9110 §9.2.2](https://www.rfc-editor.org/rfc/rfc9110.html#section-9.2.2).
_Avoid_: Repeatable, retry-safe, "returns the same response"

**Safe**:
Of a request method, one whose defined semantics are essentially read-only. Every
safe method is idempotent; the converse fails, which is why `DELETE` is
idempotent and not safe.
_Avoid_: Read-only, harmless, non-mutating

**Idempotence of an effect**:
A property of a system's state after a message is processed, possibly more than
once, across a channel that can lose, delay, duplicate and reorder. Engineered,
never checkable by inspection — as distinct from idempotence of a function, which
is a property of a pure mapping.
_Avoid_: Real idempotency, practical idempotency

**Effectively-once**:
The guarantee an idempotency key actually delivers: the externally observable
effect occurs once, while the handler may run more than once.
_Avoid_: Exactly-once, once-only, deduplicated delivery

## The failure

**Ambiguous failure**:
The state a client is left in when a request produces no response: the operation
was performed either once or not at all, and the client is not told which. Named
in [Birrell & Nelson
1983](http://www.bitsavers.org/pdf/xerox/parc/techReports/CSL-83-7_Implementing_Remote_Procedure_Calls.pdf).
_Avoid_: Timeout, network error, unknown state

**At-least-once**:
A delivery policy under which the client retries on ambiguity, so work is never
lost but may be applied twice.
_Avoid_: Guaranteed delivery, reliable delivery

**At-most-once**:
A delivery policy under which the client never retries, so work is never applied
twice but is silently dropped whenever a response is lost.
_Avoid_: Fire-and-forget, best effort

**Exactly-once**:
Not a selectable delivery policy. Where it is achieved it is always at-least-once
delivery plus deduplication at the receiver, and vendor claims to the contrary
warrant reading the fine print.
_Avoid_: (use the term only to name the thing that does not exist as advertised)

## The machinery

**Idempotency key**:
"A unique value generated by the client which the resource uses to recognize
subsequent retries of the same request"
([draft-07 §2](https://datatracker.ietf.org/doc/html/draft-ietf-httpapi-idempotency-key-header-07#section-2)).
It identifies a request, never a resource.
_Avoid_: Request ID, token, nonce, dedupe key

**Idempotency fingerprint**:
A checksum or field match computed **by the resource** over the request payload,
used to detect the same idempotency key arriving with a different request. The
client never sends it.
_Avoid_: Request hash, payload checksum, body signature

**Key record**:
The server-side row holding the idempotency key, the idempotency fingerprint, the
state, and the stored response. The thing the atomic claim creates.
_Avoid_: Lock row, cache entry, dedupe record

**Atomic claim**:
The single indivisible operation that creates a key record only if none exists,
deciding in one step whether this request owns the idempotency key or is a
duplicate. A read followed by a write is not one of these.
_Avoid_: Lock acquisition, check-and-insert, reservation

**Replay**:
Returning a key record's stored status and body without invoking the handler.
The step at which the second request produces no second effect.
_Avoid_: Cache hit, re-serve, idempotent response

**Retention window**:
How long a key record survives before it is deleted. Must exceed the client's
maximum retry horizon, because an expired key record is indistinguishable from
one never seen.
_Avoid_: TTL, expiry, cache lifetime

**Lease**:
A time bound on an in-flight claim, so a key is not bricked forever when its
holder dies. An optimisation for liveness; never the safety mechanism.
_Avoid_: Lock timeout, deadline, in-progress expiry

**Fencing token**:
A number that strictly increases each time a lock is acquired, sent with every
write so the storage layer can reject a write whose token has gone backwards.
Kleppmann's answer to a lease expiring under a holder that is merely paused.
_Avoid_: Version number, sequence, epoch

## Where the effect lives

**Foreign state mutation**:
"Calling out and manipulating data on another system" — a side effect that no
local transaction can roll back, and therefore the point at which the effect and
the key record can no longer commit together.
_Avoid_: External call, side effect, third-party write

**Atomic phase**:
"A set of local state mutations that occur in transactions between foreign state
mutations."
_Avoid_: Step, stage, unit of work

**Recovery point**:
A named checkpoint reached after an atomic phase or a foreign state mutation
completes, so a retry can resume from just before the last failure rather than
from the beginning.
_Avoid_: Checkpoint, resume marker, saga step

## Notes on usage

- **"Idempotency key" names the client's value; "key record" names the server's
  row.** Conflating them makes the lifecycle impossible to describe, because the
  whole mechanism is about what the server does with a row the client never sees.
- **Say "effectively-once" and never "exactly-once"** when describing what a key
  delivers, except when naming the marketing claim in order to reject it.
- **A key record's states are `IN_FLIGHT` and `COMPLETE`** in this workspace.
  Real implementations disagree on spelling — AWS Lambda Powertools uses
  `INPROGRESS`, `COMPLETED` and `EXPIRED` in its source constants while its own
  documentation page writes `COMPLETE` and `IN_PROGRESS` elsewhere. The
  workspace's two names are used throughout, and the vendor spellings appear only
  inside quotations.
- **"Expired" is not a third state.** An expired key record is deleted, so the
  atomic claim succeeds and the operation runs again as if the key had never been
  seen.
