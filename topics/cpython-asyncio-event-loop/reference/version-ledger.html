Two entries deserve a note. task_step_handle_result_impl is the 3.12 split of the monolithic task_step_impl into “advance the coroutine” and “interpret what it yielded” — the second half being the _asyncio_future_blocking dispatch — and the split exists so the eager-start path can reuse it. asyncio_running_loop is the 3.13 move of the running-loop pointer from a threading.local into a field on _PyThreadStateImpl, the free-threading-friendly equivalent.

What actually changed inside _run_once

Two changes in three releases, both cosmetic.
Window Change Effect
3.11 → 3.12 event_list = None added after _process_events, commented “Needed to break cycles when an exception occurs”. Reference-cycle hygiene. No behaviour change in the ordinary path.
3.12 → 3.13 timeout = min(max(0, when - self.time()), MAXIMUM_SELECT_TIMEOUT) became the four-line if/elif. Semantically identical; removes two builtin calls per iteration.
3.13.0 → 3.13.11 Nothing. Byte-identical.
What the stability implies

Three releases of active asyncio development — structured concurrency, eager tasks, a free-threading port — and the scheduling core moved twice, for reference-cycle hygiene and two builtin calls. The parts of this topic most likely to be wrong in a future release are the ones above the loop: task semantics, cancellation, the registries.

The counterpart warning: a file can be reformatted without any behaviour changing, and every line citation in this topic would break. Stability of behaviour is not stability of line numbers.

Free-threading, in three concrete places

What Py_MOD_GIL_NOT_USED costs _asynciomodule.c.
Accommodation Detail Line
FutureIter free-list compiled out #ifndef Py_GIL_DISABLED guards the field, the allocation and the deallocation. Under free-threading every await on a Future allocates a fresh iterator. 74–77, 1534–1550, 1755–1764
Atomic task-name counter _Py_atomic_add_uint64 instead of ++. The Python side solves the same problem with itertools.count(1).__next__, citing bpo-11866. 2089–2093; tasks.py:31-34
swap_current_task critical section The only Py_BEGIN_CRITICAL_SECTION in the module. Needed because the swap is a compound read-then-write; enter_task and leave_task each manage with a single dict operation. 2024–2028

Not protected: the WeakSet task registry. PEP 703's per-object lock stops it corrupting, but list(_scheduled_tasks) in all_tasks is still a compound operation over a mutating collection — which is why it retries up to 1000 times.

And the loop gains nothing. BaseEventLoop is pure Python and unchanged. N loops in N threads do not contend on a GIL; a single loop is still one thread running one callback at a time. None of this was executed — no free-threaded interpreter was available.

When a new release lands

  1. Re-diff _run_once against the new tag. If it is unchanged, lessons 1–6 and 11–12 stand.
  2. Re-check every line number. The most fragile citation in this topic. A reformat breaks all of them without changing behaviour.
  3. Grep Modules/_asynciomodule.c for the symbol table above. New entries date the release's C-side work faster than the release notes do.
  4. Read What's New for what it omits. The 3.13 § Optimizations section contains no asyncio entry at all — which is the finding.
  5. Re-check the five disagreements. A documentation fix would retire one, and that is worth knowing rather than assuming.
