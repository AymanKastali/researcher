Thread safety

What may and may not be touched from a thread other than the loop's, what happens when you get it wrong, and the self-pipe that makes the one safe operation safe. Against CPython tag v3.13.11, selector loops only.

Reach for this page when reviewing code that mixes a loop with threads — concurrent.futures callbacks, GUI toolkit handlers, and library callbacks that “just call set_result” are the three that come up. Nothing here applies to ProactorEventLoop, which was not read.

The one-line rule

The table

Every loop-touching operation, graded.
Operation Status Evidence
loop.call_soon_threadsafe(cb) Safe. [guaranteed] PEP 3156 § Thread interaction; Doc/library/asyncio-eventloop.rst:235-249
asyncio.run_coroutine_threadsafe(coro, loop) Safe. [guaranteed] Doc/library/asyncio-dev.rst:85-87; implemented as loop.call_soon_threadsafe(callback) at tasks.py:1003
loop.call_soon / call_later / call_at Not safe. [guaranteed] that it isn't; [impl detail] that it appears to work, with unbounded latency Doc/library/asyncio-eventloop.rst:233: “Unlike call_soon_threadsafe(), this method is not thread-safe.” Measured below.
fut.set_result / fut.cancel / task.cancel Not safe. Use call_soon_threadsafe(fut.cancel) Doc/library/asyncio-dev.rst:77-83; the Future docstring, futures.py:35 — “This class is not thread-safe.”
loop.stop() Undocumented, and does not wake the loop. [impl detail] base_events.py:727-733 sets a flag and nothing else; runners.py:155 works around it
loop.close() Not safe, and refuses while running base_events.py:743-744
loop._write_to_self() Safe by construction, but private selector_events.py:141-149 — written to tolerate concurrent teardown
asyncio.all_tasks(loop) Races, and retries up to 1000 times tasks.py:44-68, citing issues 34970 and 36607
loop.add_signal_handler Main thread only, enforced unix_events.py:103-109 — signal.set_wakeup_fd raises off the main thread, and is called early on purpose

The two differences that matter

call_soon versus call_soon_threadsafe. Both funnel into the same _call_soon.
call_soon call_soon_threadsafe
Builds a Handle, copies the context, appends Yes Yes
_check_thread() Yes — but only if self._debug No
_write_to_self() No Yes, unconditionally

call_soon can skip the wakeup because the loop thread can only be calling it from inside the drain or from outside run_forever — never from inside select(). A send() per call_soon would be a wasted syscall on the hottest path in asyncio.

What getting it wrong actually costs

Text 
call_soon_threadsafe:     callback ran 0.000s after scheduling
call_soon (other thread): callback ran 2.803s after scheduling

Measured for the research document on CPython 3.13.11: a loop parked in await asyncio.sleep(3.0), a worker thread scheduling 0.2 s in. Single machine, one run.

The failure mode

Not a crash, and not a lost callback — deque.append is atomic, so the handle is safely in _ready. It is an unbounded latency determined by whatever else the loop happens to have scheduled. On a genuinely idle loop (timeout = None, epoll_wait(-1)) the callback never runs at all.

Which is why it survives development, where something is always happening, and fails in production, where nothing is.

_check_thread, and why it is quiet

  1. Debug mode only. call_soon and call_at both guard it with if self._debug:. In production there is no thread check at all. [guaranteed] as a debug feature — Doc/library/asyncio-dev.rst:47-51.
  2. Silent when the loop is not running. if self._thread_id is None: return. That is what lets the common “build the loop here, hand it to a thread there” setup work without a diagnostic.
  3. Advisory. Its own docstring says the non-thread-safe methods “will likely behave incorrectly”. Nothing enforces it.

The self-pipe

The self-pipe's four moving parts.
Part What it is Where
_make_self_pipe socket.socketpair() — not os.pipe(), because Windows' select() takes only sockets. Created in __init__, so every selector loop has one from birth. selector_events.py:118-124
_write_to_self _csock.send(b'\0'), with the socket copied to a local before the None check and OSError swallowed — callable from any thread at any time, including during teardown. selector_events.py:141-157
_read_from_self Drains everything available and discards it. The wakeup is the payload. selector_events.py:129-139
_process_self_data pass on the base class. On Unix, demultiplexes signal numbers — b'\0' is the wakeup byte because signal 0 does not exist. selector_events.py:126-127; unix_events.py:83-88

Waking a parked loop by hand

Python 
    def _on_sigint(self, signum, frame, main_task):
        self._interrupt_count += 1
        if self._interrupt_count == 1 and not main_task.done():
            main_task.cancel()
            # wakeup loop if it is blocked by select() with long timeout
            self._loop.call_soon_threadsafe(lambda: None)
            return
        raise KeyboardInterrupt()

Lib/asyncio/runners.py:150-157 — Runner._on_sigint(). call_soon_threadsafe(lambda: None) is not a callback; it is a hand-written selector wakeup, and it is in CPython because no public API does only that. [impl detail] — and worth stealing.

Reentrancy

Three independent refusals to run a loop inside a loop.
Guard Refuses Where
_check_running A second run_forever on this loop, or any run_forever while another loop runs in this thread. base_events.py:635-640
_enter_task / _leave_task A task step inside a task step, on the same loop. tasks.py:1057-1070
Runner.run / asyncio.run “asyncio.run() cannot be called from a running event loop”, with a short traceback on purpose. runners.py:189-192

call_soon_threadsafe is the exception and is documented as reentrancy-safe: “safe to be called from a reentrant context or signal handler, however, it is not safe or fruitful to use the returned handle in such contexts” (Doc/library/asyncio-eventloop.rst:241-242). That contradicts PEP 3156, and the unverified-claims page resolves it.

There is no per-loop task registry

_scheduled_tasks is one module-level weakref.WeakSet shared by every loop in the process, and all_tasks(loop) filters it by futures._get_loop(t) is loop. In the C build it is created once in the module's per-interpreter state, so the registry is per-interpreter — not per-loop, not per-thread. Twenty loops in twenty threads share one WeakSet, and all_tasks linearises the whole thing on every call. [impl detail], and undocumented.
