Unverified claims

Everything this topic does not know, and everywhere its sources contradict each other. Reach for this page when a claim about asyncio needs grading, or when something taught here stops matching what you see.

A page that names its own gaps is more useful than one that does not. Every entry below is either a source conflict resolved with both texts on the page, or a plainly stated limit on what was checked.

The two markers

The distinction every page in this topic carries.
Marker Means Source
[guaranteed] You may rely on it. If CPython breaks it, that is a bug in CPython. A PEP, the language reference, or docs.python.org for 3.13.
[impl detail] True of CPython 3.13.11 because that is how the code is written. Promised nowhere. A different loop, a different version, or a refactor may change it without notice. The source at tag v3.13.11, and nothing else.

Most of what is interesting in this topic is [impl detail]. The six steps, the ntodo snapshot, the _asyncio_future_blocking protocol, the compaction constants, the self-pipe and the C/Python division are none of them promised anywhere.

Five source conflicts

Where PEP, documentation and source disagree, and which wins.
# Conflict Verdict
1 PEP 3156 says call_soon_threadsafe is not signal-safe “(since it may use locks)”. The 3.13 docs say it is. Prefer the docs and the source. The path is _check_closed → Handle() → copy_context() → deque.append → socket.send. No lock anywhere. The PEP describes an implementation that no longer exists. The caveat about the returned handle is real: Handle.cancel() mutates three attributes unsynchronised.
2 PEP 3156 intends stop() to “stop short of polling for I/O”. The 3.13 docs say the loop polls once with a zero timeout. The 3.13 docs are precisely right. It depends when you call it: stop() before run_forever means _stopping is already true at base_events.py:2001-2003, so the loop polls with timeout = 0 and drains. stop() during the drain means no further poll, as the PEP intends. The PEP's “not to run any callbacks scheduled in the future” is also slightly strong — a due timer will fire.
3 The clock-resolution fudge is documented twice; the cancelled-timer compaction beside it is documented nowhere. Not a contradiction — the clearest illustration of the line. Documentation commits to the observable (“may run up to one clock-resolution early”) and stays silent about the mechanism. Relying on a mechanism rather than an observable puts you in [impl detail] whether or not anything said so.
4 asyncio.isfuture's documentation describes a weaker test than base_futures.py:20-21 performs. Prefer the source. Two omitted conditions: the attribute must be on the class, and its value must not be None. A class opts out with a class-level None while its instances opt back in with False — and test_isfuture asserts exactly that pair. Following the documentation literally gets both backwards.
5 What's New in 3.13 says three create_task entry points gained **kwargs. One did. Prefer the source and the reference pages. At v3.13.11, only BaseEventLoop.create_task (base_events.py:461) has it; asyncio.create_task (tasks.py:402) and TaskGroup.create_task (taskgroups.py:181) do not. The entry describes the 3.13.3 state; two signatures were reverted in 3.13.4 and it was never updated. Release notes are the least maintained grade.

Ten things that could not be verified

  1. asyncio.free_running_loop does not exist, in 3.13 or anywhere findable. It was on the research brief as a “verify, don't assume” item. grep -rn free_running_loop over a full asyncio/ install returns nothing; hasattr(asyncio, 'free_running_loop') is False; the string does not appear in Doc/whatsnew/3.13.rst or any of the four relevant library pages at tag v3.13.11. No such API is described anywhere in this workspace.

  2. The origin of the ntodo idiom was not traced. Lesson 3 is argued from the in-source comment, from test__run_once_schedule_handle, from the documented run_forever behaviour, and from the collections.deque guarantee. The comment says “Use an idiom that is thread-safe without using locks”; the commit or Tulip-era issue that first wrote it was not found, so the historical motivation is inferred from the comment rather than sourced from a discussion.

  3. The _timer_cancelled_count staleness is an observation, not a known issue. A cancelled timer buried behind a live one is popped by step 5 without decrementing the counter, so the counter is an upper bound rather than a count. The behaviour is certain — the code path is short and the reproduction in lesson 12 is deterministic. Whether it is considered a defect or an accepted approximation is not certain: a semantic search of python/cpython issues found nothing describing it. It is presented as an observation, not a bug report.

  4. No free-threaded interpreter was available. sys._is_gil_enabled() returned True on the install used, so every claim about the Py_GIL_DISABLED build is read from #ifdef branches, PEP 703 and the free-threading how-to. None of it was executed. In particular, “N loops in N threads do not contend on a GIL” is a reading of Py_mod_gil, not a measurement.

  5. ProactorEventLoop (Windows) is not covered. Everything in BaseEventLoop applies to it, because it inherits the same _run_once — so lessons 1–3, 6, 11 and 12 hold. Everything about the selector, the await round trip and the self-pipe does not: IOCP is a completion model, not a readiness model, and proactor_events.py and windows_events.py were not read. No claim here should be transferred to Windows without checking.

  6. sslproto.py, streams.py and subprocess.py were not read. The transport trace in lesson 8 stops at _SelectorSocketTransport. How StreamReader turns data_received callbacks back into awaitable Futures is one layer further up and is not described.

  7. The benchmark numbers are single-machine, best-of-three. They establish orders of magnitude — “the C accelerator is worth tens of percent, not an order of magnitude”, “eager tasks are worth several times” — and nothing finer. No CPU pinning, no pyperf, no isolation from an otherwise-busy desktop. They are reported because they falsify plausible assumptions, not because they characterise performance.

  8. The two _run_once changes between 3.12 and 3.13 have no cited issue numbers. They were found by diffing the file across tags, which establishes that and when they changed but not why or by whom. The _run_forever_setup split has a motivation only because its docstring states one; the timeout un-inlining does not, and none is asserted.

  9. PEP 3156's Status: Final was taken at face value. Conflicts 1 and 2 above are reported as PEP-versus-implementation drift. No search of python-dev or the issue tracker was made for a discussion formally superseding either passage, so it is possible one was consciously amended somewhere unexamined rather than silently outgrown.

  10. “BaseEventLoop has no C implementation” is scoped to CPython. It is true of the source tree at v3.13.11 — no loop type in Modules/_asynciomodule.c, no accelerator import in base_events.py. Third-party loops, uvloop in particular, replace exactly this layer, and nothing in lessons 1–5 or 11–13 should be assumed to hold under one.

Four questions to ask of any claim

  1. Which grade is it? Traceable to a PEP, to docs.python.org for a named version, or only to a line of source? If only to source, it is [impl detail].
  2. Observable, or mechanism? Documentation commits to observables. A claim about how rather than what will never be confirmed by reading the docs.
  3. Does a test pin it? A behaviour Lib/test/test_asyncio/ asserts is not promised, but it is deliberate and changing it would break CI. That is the strongest evidence available for the drain semantics and the compaction constants.
  4. Which version, and which loop? Everything here is CPython 3.13.11 with a selector loop. Name both, every time.
The reason this page exists

A confident sentence with nothing behind it is the one failure this topic cannot absorb. Every claim in the fifteen lessons is either quoted from a source that is linked, labelled as a measurement, or listed here as something that could not be established. If you find a fourth kind, it is a defect.
