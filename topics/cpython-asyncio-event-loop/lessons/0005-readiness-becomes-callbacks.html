Lesson 0005

Readiness becomes callbacks

Step 4, which is twelve lines, and the seam it sits on. The whole of asyncio's I/O dispatch is one loop over a list of ready descriptors — and knowing that it runs no user code is what makes the rest of the topic predictable.

The poll has returned. Somewhere in the process a socket has data. What happens next is much less than most people assume, and the fact that it is less is the design.

All of it

Python 
    def _process_events(self, event_list):
        for key, mask in event_list:
            fileobj, (reader, writer) = key.fileobj, key.data
            if mask & selectors.EVENT_READ and reader is not None:
                if reader._cancelled:
                    self._remove_reader(fileobj)
                else:
                    self._add_callback(reader)
            if mask & selectors.EVENT_WRITE and writer is not None:
                if writer._cancelled:
                    self._remove_writer(fileobj)
                else:
                    self._add_callback(writer)

Lib/asyncio/selector_events.py:740-752 — BaseSelectorEventLoop._process_events().

That is the entirety of asyncio's I/O dispatch. Three things are worth naming.

key.data is always a two-tuple

The selectors module lets a registration carry an opaque payload. asyncio's payload is invariably (reader_handle, writer_handle), either element possibly None. There is at most one reader and at most one writer per descriptor, and lesson 8 shows what happens when you register a second one.

“Ready” becomes “queued”, not “run”

Python 
    def _add_callback(self, handle):
        """Add a Handle to _ready."""
        if not handle._cancelled:
            self._ready.append(handle)

Lib/asyncio/base_events.py:1955-1958 — BaseEventLoop._add_callback().

No user code runs in step 4. _process_events moves handles between data structures and returns. This is what makes lesson 2's claim exact rather than approximate: the drain really is the only place callbacks are called, and the I/O path is no exception to it.

A cancelled handle deregisters the descriptor

Note the asymmetry with the drain. In step 6, a cancelled handle is skipped and forgotten. Here, a cancelled reader causes _remove_reader(fileobj) — because a readiness registration is a standing subscription with the kernel, and leaving it in place would make the loop spin on an event nobody wants.

The seam

On the abstract base class, this method does not exist:

Python 
    def _write_to_self(self):
        """Write a byte to self-pipe, to wake up the event loop.

        This may be called from a different thread.

        The subclass is responsible for implementing the self-pipe.
        """
        raise NotImplementedError

    def _process_events(self, event_list):
        """Process selector events."""
        raise NotImplementedError

Lib/asyncio/base_events.py:541-552 — the two stubs that mark the boundary of the “event loop proper”.

Two NotImplementedErrors is a very small interface, and it is the entire contract between the scheduling half of the loop and the I/O half. Everything above that line — _ready, _scheduled, call_soon, Handle, the clock, _run_once itself — is portable scheduling that has never heard of a file descriptor. Everything below it is BaseSelectorEventLoop (Unix, and Windows' SelectorEventLoop) or ProactorEventLoop (Windows IOCP).

This split is not an accident of the implementation. It is the first paragraph of the design document, which the module docstring repeats almost verbatim:

Why the seam is worth remembering

It tells you which of these lessons are about asyncio and which are about CPython's selector loop. Lessons 1–3, 6, 11 and 12 are above the line and hold for any loop built on BaseEventLoop. Lessons 4, 5, 8 and 13 are below it, and nothing in them should be transferred to Windows IOCP — a completion model, not a readiness model — or to uvloop, which replaces the whole stack.

What the loop refuses to know

Notice what is not in _process_events: no buffering, no protocols, no partial reads, no error handling beyond the cancelled check. It does not call recv. It does not know whether the handle it queued belongs to a transport, a sock_recv Future, or the self-pipe. Those distinctions live entirely in the callback that was registered, and the loop treats all three identically.

That indifference is what lets the self-pipe work at all. The mechanism by which another thread wakes a parked loop (lesson 13) is nothing more than a socket registered here like any other, whose callback throws the bytes away.

Check yourself

What does _process_events do when a descriptor is ready for reading?

It appends, and nothing more. The recv happens inside the callback, in step 6; resolving a Future happens inside that; and running a handle in its context is Handle._run, which is lesson 6. Keeping step 4 free of user code is what makes the drain the single place anything can happen.

Check yourself

Which two methods does BaseEventLoop leave unimplemented for its I/O subclasses?

Exactly those two, at base_events.py:541-552: turn events into callbacks, and wake me up from another thread. Everything else about I/O is defined further down the hierarchy, and everything about scheduling is defined above it. Two stubs is the whole seam.

Where this is going

The handle is in _ready, the drain has reached it, and it is about to be run. Lesson 6 is the eighteen lines that do the running — which turn out to decide how context variables propagate and which exceptions can kill a loop.

Four of the six steps are now open. The _run_once reference carries the whole table, so you can see which two are left and where each step lives, without re-reading the lessons that opened them.

That closes the first arc. Lessons 1–6 describe a callback machine with no coroutines in it at all, which is exactly what PEP 3156 says asyncio fundamentally is:

PEP 3156 — Asynchronous IO Support Rebooted: the “asyncio” Module, Guido van Rossum, 2012 — read the first three sections and § Coroutines and the Scheduler. It is the design document for everything you have read so far, it is readable in an evening, and it is the source lesson 15 will eventually argue against in two specific places. Knowing it well is what makes that argument legible.

Your agent is your teacher. Worth asking now: “which of the first five lessons would still be true under uvloop?” The answer is a good test of whether the seam has landed, and getting it wrong is informative.

On spacing

This is a natural long pause. Lessons 1–5 are one complete idea — a callback machine — and lesson 6 finishes it. Before going on, try to describe the whole of one iteration to someone else, out loud, without notes. Explaining it is a harder retrieval than recalling it, and harder retrieval is the point.
