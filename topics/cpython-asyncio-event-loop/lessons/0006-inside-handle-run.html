Lesson 0006

Inside Handle._run

The last piece of the callback machine. Eighteen lines that decide how context variables propagate, which exceptions a loop survives, and which two can kill it.

The drain has popped a handle and is about to call it. This is the call — and it is not self._callback(*self._args), for three separate reasons that each show up somewhere else in your programs.

The method

Python 
    def _run(self):
        try:
            self._context.run(self._callback, *self._args)
        except (SystemExit, KeyboardInterrupt):
            raise
        except BaseException as exc:
            cb = format_helpers._format_callback_source(
                self._callback, self._args,
                debug=self._loop.get_debug())
            msg = f'Exception in callback {cb}'
            context = {
                'message': msg,
                'exception': exc,
                'handle': self,
            }
            if self._source_traceback:
                context['source_traceback'] = self._source_traceback
            self._loop.call_exception_handler(context)
        self = None  # Needed to break cycles when an exception occurs.

Lib/asyncio/events.py:87-105 — Handle._run().

One: the callback runs inside a context, never bare

The context is captured when the Handle is constructed, not when it runs:

Python 
    def __init__(self, callback, args, loop, context=None):
        if context is None:
            context = contextvars.copy_context()
        self._context = context

Lib/asyncio/events.py:36-39 — Handle.__init__().

Since call_soon builds the Handle synchronously, the effect is that a callback runs in the context of whoever scheduled it — not of whoever happened to be running when the loop got round to it. That is the behaviour PEP 567 makes normative:

A small divergence, with no observable effect

PEP 567's own sketch puts the copy_context() inside call_soon rather than inside Handle.__init__ (PEP 567 § asyncio). CPython does it one level down. Because call_soon constructs the handle synchronously (base_events.py:852-857), the two are indistinguishable from outside — a reminder that a PEP's example code is illustrative and its Backwards Compatibility section is the normative part.

This is also why lesson 8's _add_reader passes context=None: an I/O callback inherits the context of whoever registered interest in the descriptor, not of whoever's data happens to arrive.

Two: exceptions are swallowed into the exception handler

A callback that raises does not propagate out of _run_once, and does not stop the loop. It is packaged into a context dict and handed to call_exception_handler, which is what produces the familiar log line:

Text 
Exception in callback <...>

The message is assembled at events.py:96. The 'handle' key in the context dict is why the log line can name the callback that failed, and 'source_traceback' — present only in debug mode — is why it can also name the line that scheduled it.

This is the right default for a loop that must keep serving every other connection, and it is also why an unhandled error in an asyncio program can be invisible until you look at the log. If you want failures to be loud, replacing the exception handler is the supported way (loop.set_exception_handler), and it is one of the few pieces of loop configuration worth doing in every service.

Three: two exceptions are re-raised, and they escape

Python 
        except (SystemExit, KeyboardInterrupt):
            raise

SystemExit and KeyboardInterrupt are let through. They escape _run_once, unwind run_forever, and hit the finally: that runs _run_forever_cleanup() — which is how a Ctrl-C gets the loop's asyncgen hooks and thread id restored rather than left dangling.

The asymmetry is deliberate and it recurs all through asyncio, always in exactly this shape. Two other instances, so the pattern is recognisable rather than surprising:

Why these two specifically

Both are BaseException, not Exception — deliberately outside the ordinary error hierarchy, because both mean “this process is trying to end” rather than “this operation failed”. Routing them into an exception handler that logs and continues would make a program unkillable, and Ctrl-C would look like it had simply been ignored.

And the last line, again

self = None closes the method, with the same comment you saw in lesson 3: if _run raises, its frame is captured in the traceback, and a local naming the handle that names the loop that names the frame is a cycle only the cyclic collector can break. Four places in asyncio do this, and now you have seen two of them.

Check yourself

Whose contextvars context does a call_soon callback run in?

Handle.__init__ calls contextvars.copy_context() at construction time, and call_soon constructs the handle synchronously — so the captured context is the caller's. PEP 567 states this as a compatibility guarantee, and it is why a request id set before scheduling is still visible inside the callback.

Check yourself

A callback raises ValueError. What happens to the loop?

Handle._run catches every BaseException except SystemExit and KeyboardInterrupt, and passes a context dict to loop.call_exception_handler. It is not silent — the default handler logs it — but it is easy to miss, which is the practical reason to install your own.

Where this is going

That completes the callback machine. Lessons 1–6 describe a system that polls descriptors, keeps two queues, and runs functions inside captured contexts — with no coroutine anywhere in it.
