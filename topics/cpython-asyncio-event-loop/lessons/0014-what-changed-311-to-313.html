Lesson 0014

What changed, 3.11 → 3.13

The headline is that _run_once barely moved. Everything interesting happened one layer up — and the one change that is a genuine semantic break is opt-in, for a reason the documentation is unusually blunt about.

Three releases, and the eighty lines you learned in lesson 2 changed twice, cosmetically. That stability is itself worth knowing: it tells you which parts of this topic will survive Python 3.14 and which will not.

3.11: four features that are one design

TaskGroup, timeout(), Runner and the cancellation count landed together and are not four independent additions. The problem they solve is that CancelledError carries no identity: if a task is cancelled while already being cancelled by someone else, whoever catches it cannot tell whose cancellation it is. cancelling() / uncancel() add that identity as a counter.

Python 
    def uncancel(self):
        """Decrement the task's count of cancellation requests.

        This should be called by the party that called `cancel()` on the task
        beforehand.

        Returns the remaining number of cancellation requests.
        """
        if self._num_cancels_requested > 0:
            self._num_cancels_requested -= 1
            if self._num_cancels_requested == 0:
                self._must_cancel = False
        return self._num_cancels_requested

Lib/asyncio/tasks.py:248-260 — Task.uncancel().

The if self._num_cancels_requested == 0: self._must_cancel = False clause is the 3.13 addition, and the release note describing it is unusually revealing:

asyncio.timeout uses the counter exactly as lesson 12 showed — timeouts.py:93 snapshots self._task.cancelling() on entry, and timeouts.py:112 compares against it on exit to decide whether the CancelledError it is looking at is its own. TaskGroup uses it to keep the count stable across its own internal cancel/uncancel dance (taskgroups.py:144-149).

The reason to know this

If you ever write a construct that cancels a task and then wants to swallow the resulting CancelledError, you must snapshot cancelling() before and call uncancel() after — otherwise you will swallow somebody else's cancellation and produce a task that refuses to die. The 3.11 API exists precisely so that timeout and TaskGroup can nest without doing that to each other.

3.12: the eager task factory, and a semantic change

This is the largest behavioural change in the window. Normally, creating a Task schedules its first step:

Python 
        if eager_start and self._loop.is_running():
            self.__eager_start()
        else:
            self._loop.call_soon(self.__step, context=self._context)
            _register_task(self)

Lib/asyncio/tasks.py:124-128 — Task.__init__().

With eager_start=True and a running loop, the first step happens inline, in the constructor:

Python 
    def __eager_start(self):
        prev_task = _swap_current_task(self._loop, self)
        try:
            _register_eager_task(self)
            try:
                self._context.run(self.__step_run_and_handle_result, None)
            finally:
                _unregister_eager_task(self)
        finally:
            try:
                curtask = _swap_current_task(self._loop, prev_task)
                assert curtask is self
            finally:
                if self.done():
                    self._coro = None
                    self = None  # Needed to break cycles when an exception occurs.
                else:
                    _register_task(self)

Lib/asyncio/tasks.py:262-279 — Task.__eager_start().

Read the finally carefully. If the coroutine finished during that first step, the task is never registered in _scheduled_tasks and never touches _ready. If it blocked, it graduates — _register_task(self) — and from that point behaves like any other task. The two registries exist for exactly this:

Python 
# Collectively these two sets hold references to the complete set of active
# tasks. Eagerly executed tasks use a faster regular set as an optimization
# but may graduate to a WeakSet if the task blocks on IO.
_scheduled_tasks = weakref.WeakSet()
_eager_tasks = set()

Lib/asyncio/tasks.py:1036-1040. It is also why all_tasks snapshots _eager_tasks first: reading the eager set before the scheduled set means a task graduating between the two reads is seen twice, not zero times.

What it is worth

Text 
lazy  100k create_task(noop): 0.367s
eager 100k create_task(noop): 0.079s   -> 4.64x faster

Measured for the research document on CPython 3.13.11, best of three. Single machine, no CPU pinning. It lands inside the range the release notes claim — “making some use-cases 2x to 5x faster”, Doc/whatsnew/3.12.rst:650-653 — which is the only reason it is quoted here.

And it is a semantic change, not an optimisation

The documentation is unusually blunt about this:

It is opt-in precisely because of that, and nothing in CPython sets it by default in 3.13. If your code relies on create_task returning before the coroutine body starts — and a surprising amount of code does, usually accidentally — the eager factory will break it.

3.13: free-threading, and what it means for the loop

The free-threaded build is experimental in 3.13 and requires a separate interpreter binary, usually python3.13t (Doc/whatsnew/3.13.rst:316-331). _asyncio declares itself ready for it:

C 
static struct PyModuleDef_Slot module_slots[] = {
    {Py_mod_exec, module_exec},
    {Py_mod_multiple_interpreters, Py_MOD_PER_INTERPRETER_GIL_SUPPORTED},
    {Py_mod_gil, Py_MOD_GIL_NOT_USED},
    {0, NULL},
};

Modules/_asynciomodule.c:3754-3759 at tag v3.13.11. Py_MOD_GIL_NOT_USED means importing asyncio on a free-threaded build does not re-enable the GIL.

What that declaration costs, concretely, is three things:

  1. The FutureIter free-list is compiled out. #ifndef Py_GIL_DISABLED guards the struct field, the allocation and the deallocation. A shared, unlocked free-list cannot be made safe cheaply, so under free-threading every await on a Future allocates a fresh iterator.
  2. The task-name counter becomes atomic — _Py_atomic_add_uint64 instead of ++ (_asynciomodule.c:2089-2093). The pure-Python side has the same concern and solves it differently, with itertools.count(1).__next__ and a comment citing bpo-11866.
  3. swap_current_task takes a critical section — the only place in the whole module that does, because it is a compound read-then-write that must be atomic as a unit. enter_task gets away with a single PyDict_SetDefaultRef; swap cannot.
What is not protected

The task registry is a weakref.WeakSet — a pure-Python object. Under PEP 703 its internal set gets a per-object lock, so it will not corrupt; but the compound operation list(_scheduled_tasks) in all_tasks is still a loop over a mutating collection, which is exactly why all_tasks retries up to 1000 times (lesson 13). PEP 703 is explicit that per-object locking does not make compound operations atomic.

And the event loop itself gains nothing. BaseEventLoop is pure Python and unchanged for free-threading. The _ready deque idiom from lesson 3 relies on deque.append/popleft being individually atomic, which PEP 703 preserves via the per-object lock — but the free-threading how-to is careful to label that as description, not promise:

The practical position in 3.13: you may run N loops in N threads on a free-threaded build without contending on a GIL, but a single loop is no more parallel than before — one thread, one callback at a time — and every cross-loop shared structure (_scheduled_tasks, _current_tasks) is a genuine contention point. Nothing in the documentation promises asyncio is free-threading-safe; the only evidence is the Py_mod_gil declaration above.

No free-threaded interpreter was available while writing the research this topic is built from. Every claim here is read from #ifdef branches, PEP 703 and the free-threading how-to. The claim that N loops in N threads do not contend on a GIL is a reading of Py_mod_gil, not a measurement.

What actually changed inside _run_once

Two changes in three releases, both cosmetic.

3.11 → 3.12: cycle-breaking on event_list. These two lines are absent at v3.11.0 and present from v3.12.0:

Python 
        self._process_events(event_list)
        # Needed to break cycles when an exception occurs.
        event_list = None

3.12 → 3.13: the timeout computation was un-inlined. At v3.11.0 and v3.12.0 it read timeout = min(max(0, when - self.time()), MAXIMUM_SELECT_TIMEOUT); from v3.13.0 it is the four-line if/elif you learned in lesson 4. Semantically identical; it removes two builtin calls per iteration from the hottest loop in the module.

_run_once is otherwise byte-identical between v3.13.0 and v3.13.11.

The lesson inside the lesson

Three releases of active asyncio development — structured concurrency, eager tasks, a free-threading port — and the scheduling core moved twice, for reference-cycle hygiene and two builtin calls. The parts of this topic most likely to be wrong in 3.15 are the ones above the loop: task semantics, cancellation, the registries. The six steps are the durable part.

Which is also a warning: _run_once being stable is exactly what makes a line citation feel safer than it is. A file can be reformatted without any behaviour changing, and every anchor in this topic would break.

Check yourself

Under the eager task factory, a coroutine that returns immediately — what does the loop see?

__eager_start runs the first step in the constructor, and its finally only calls _register_task if the task is not done. A coroutine that returns or raises in its first step never touches _ready and never enters _scheduled_tasks — which is exactly why the documentation calls this a semantic change rather than an optimisation.

Check yourself

What did the free-threaded build change about BaseEventLoop?

The three free-threading accommodations are all in Modules/_asynciomodule.c — the free-list, the name counter and swap_current_task. The loop is untouched, and one loop is still one thread running one callback at a time. The deque's atomic append and popleft come from PEP 703's per-object locks, which the free-threading how-to explicitly declines to promise.

Reading a release note for what it omits is a skill, and this pair is a good exercise in it: the largest performance change in the window (eager tasks) shipped in 3.12 and is not repeated, and nothing in the loop got faster in 3.13.

Your agent is your teacher. Worth asking: “should I turn on the eager task factory?” The right answer depends on whether anything in your code assumes create_task returns before the body runs, and finding out is a concrete, useful audit.
