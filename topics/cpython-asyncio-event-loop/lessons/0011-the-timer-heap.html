Lesson 0011

The timer heap

Step 5, and the clock it depends on. Why TimerHandle's ordering is a preorder rather than a total order, why the loop fires timers slightly early on purpose, and which of all this you are entitled to rely on.

The second of the loop's two queues. Everything with a deadline in asyncio — sleep, timeout, wait_for, keepalives, retry backoff — is a TimerHandle in one min-heap, and the whole of step 5 is six lines of popping it.

TimerHandle

Python 
class TimerHandle(Handle):
    """Object returned by timed callback registration methods."""

    __slots__ = ['_scheduled', '_when']

    def __init__(self, when, callback, args, loop, context=None):
        super().__init__(callback, args, loop, context)
        if self._source_traceback:
            del self._source_traceback[-1]
        self._when = when
        self._scheduled = False

Lib/asyncio/events.py:108-118 — TimerHandle.

Two fields on top of Handle: an absolute deadline, and a flag recording whether this handle is currently sitting in the heap. Both Handle and TimerHandle are __slots__-ed, because one is allocated per callback and their size shows up in real workloads.

The ordering is a preorder, not a total order

The comparison methods order on _when alone:

Python 
    def __lt__(self, other):
        if isinstance(other, TimerHandle):
            return self._when < other._when
        return NotImplemented

Lib/asyncio/events.py:129-132. __le__, __gt__ and __ge__ follow the same shape.

But __eq__ does not:

Python 
    def __eq__(self, other):
        if isinstance(other, TimerHandle):
            return (self._when == other._when and
                    self._callback == other._callback and
                    self._args == other._args and
                    self._cancelled == other._cancelled)
        return NotImplemented

Lib/asyncio/events.py:149-155 — TimerHandle.__eq__(). __hash__ is hash(self._when), consistent with __eq__ being a refinement of deadline equality.

So two TimerHandles with the same deadline but different callbacks are neither < nor > nor == each other. heapq never needs more than __lt__, so this is harmless in practice — but it is also exactly why the ordering of same-deadline timers is left undefined, which is the one part of this that is promised:

A cheap way to be bitten

If two timers must fire in a known order, do not give them the same deadline and hope. Nothing in the heap, the comparison methods, or the documentation will keep them ordered — and unlike most undefined behaviour, this one will be stable in your tests and unstable in production, because it depends on heap shape rather than on time.

call_at is the primitive; call_later is sugar

Python 
    def call_at(self, when, callback, *args, context=None):
        """Like call_later(), but uses an absolute time.

        Absolute time corresponds to the event loop's time() method.
        """
        if when is None:
            raise TypeError("when cannot be None")
        self._check_closed()
        if self._debug:
            self._check_thread()
            self._check_callback(callback, 'call_at')
        timer = events.TimerHandle(when, callback, args, self, context)
        if timer._source_traceback:
            del timer._source_traceback[-1]
        heapq.heappush(self._scheduled, timer)
        timer._scheduled = True
        return timer

Lib/asyncio/base_events.py:805-821 — BaseEventLoop.call_at(). call_later is one line: self.call_at(self.time() + delay, callback, *args, context=context) at base_events.py:799-800.

This is PEP 3156's stated equivalence, implemented literally:

The practical consequence of call_later snapshotting self.time() at scheduling time is worth stating: a delay is relative to when you scheduled it, not to when the previous iteration ended. There is no drift accumulation from the loop itself — only from however long the callback is delayed by a busy queue once it is due.

The clock

Source Says Grade

Step 5, and the fudge

Python 
        # Handle 'later' callbacks that are ready.
        end_time = self.time() + self._clock_resolution
        while self._scheduled:
            handle = self._scheduled[0]
            if handle._when >= end_time:
                break
            handle = heapq.heappop(self._scheduled)
            handle._scheduled = False
            self._ready.append(handle)

Lib/asyncio/base_events.py:2017-2025 — step 5 of _run_once(). self._clock_resolution is time.get_clock_info('monotonic').resolution, captured once at base_events.py:430 and used in this one place.

A timer is considered due if _when < now + resolution, not _when <= now. The loop deliberately fires timers up to one clock tick early, rather than burning an entire extra iteration — another select(), another syscall — on a timer that is within the clock's own measurement error of being due.

This is one of very few pieces of _run_once internals that made it into the reference documentation, and it is stated as a note on both call_later and call_at:

Two roundings, pulling opposite ways

Lesson 4 showed EpollSelector.select rounding the poll timeout up to the next whole millisecond, so the sleep is never short. Step 5 treats a timer as due one resolution early. The two pull in opposite directions and roughly cancel.

On Linux, time.get_clock_info('monotonic').resolution is typically 1 ns, so the fudge is negligible and the epoll rounding dominates. On a platform with a coarse monotonic clock, the fudge is what stops timers being late by a full tick. Two mechanisms, each load-bearing on a different platform.

Check yourself

Two timers are scheduled for exactly the same deadline. In what order do their callbacks run?

Both the 3.13 reference and PEP 3156 state it as undefined, and the mechanism is visible in the source: TimerHandle orders on _when alone, so equal deadlines make the two handles incomparable and the outcome depends on heap shape. It will look stable in a small test and will not be.

Check yourself

Why does step 5 compare against now + _clock_resolution rather than against now?

A timer within one clock tick of being due is fired now rather than costing another select() syscall — the documentation calls it out as “for performance”, and the effect is that callbacks may run up to one clock-resolution early. It is the opposite of the first answer, and it happens to partly offset the epoll rounding from lesson 4 rather than being designed around it.

Where this is going

Timers go into the heap easily. Getting them out when they are cancelled is the awkward part, because you cannot cheaply remove from the middle of a heap. Lesson 12 is step 1 — the two strategies, the two undocumented constants, and one observation about the counter that no CPython issue appears to describe.
