Lesson 0013

Threads and the self-pipe

The most operationally useful lesson here. What call_soon from a worker thread actually does — not “it breaks”, but the precise failure — the one socket that makes call_soon_threadsafe work, and why loop.stop() from another thread quietly does not.

Everything so far has been single-threaded. The moment a second thread exists, one question matters more than all the others: how does it get the attention of a loop parked in epoll_wait(-1)?

The two methods, side by side

Python 
    def call_soon(self, callback, *args, context=None):
        """Arrange for a callback to be called as soon as possible.

        This operates as a FIFO queue: callbacks are called in the
        order in which they are registered.  Each callback will be
        called exactly once.

        Any positional arguments after the callback will be passed to
        the callback when it is called.
        """
        self._check_closed()
        if self._debug:
            self._check_thread()
            self._check_callback(callback, 'call_soon')
        handle = self._call_soon(callback, args, context)
        if handle._source_traceback:
            del handle._source_traceback[-1]
        return handle

Lib/asyncio/base_events.py:823-840 — BaseEventLoop.call_soon().

Python 
    def call_soon_threadsafe(self, callback, *args, context=None):
        """Like call_soon(), but thread-safe."""
        self._check_closed()
        if self._debug:
            self._check_callback(callback, 'call_soon_threadsafe')
        handle = self._call_soon(callback, args, context)
        if handle._source_traceback:
            del handle._source_traceback[-1]
        self._write_to_self()
        return handle

Lib/asyncio/base_events.py:876-885 — BaseEventLoop.call_soon_threadsafe(). Both funnel into the same three-line _call_soon at base_events.py:852-857, which builds a Handle and appends it.

There are exactly two differences

call_soon calls _check_thread() — and only in debug mode. call_soon_threadsafe calls _write_to_self() — unconditionally. That is all. The Handle construction, the context copy and the _ready.append are identical.

The thread check is advisory, and only in debug mode

Python 
    def _check_thread(self):
        """Check that the current thread is the thread running the event loop.

        Non-thread-safe methods of this class make this assumption and will
        likely behave incorrectly when the assumption is violated.

        Should only be called when (self._debug == True).  The caller is
        responsible for checking this condition for performance reasons.
        """
        if self._thread_id is None:
            return
        thread_id = threading.get_ident()
        if thread_id != self._thread_id:
            raise RuntimeError(
                "Non-thread-safe operation invoked on an event loop other "
                "than the current one")

Lib/asyncio/base_events.py:859-874 — BaseEventLoop._check_thread().

Three things to take from it, all of them uncomfortable.

  1. It only runs in debug mode. call_soon guards the call with if self._debug:, as does call_at. In production there is no thread check at all. The documentation is explicit that this is a debug feature: “Many non-threadsafe asyncio APIs (such as loop.call_soon() and loop.call_at() methods) raise an exception if they are called from a wrong thread” (Debug Mode, Doc/library/asyncio-dev.rst:47-51). [guaranteed]
  2. It returns silently when the loop is not running. self._thread_id is None means run_forever has not been entered — the attribute from lesson 1. So calling call_soon from an arbitrary thread on a not-yet-running loop is never diagnosed, even in debug mode. That is what makes the common “build the loop here, hand it to a thread there” setup work.
  3. It is advisory, not protective. The docstring says the non-thread-safe methods “will likely behave incorrectly”. Nothing enforces it.

So what actually happens?

Read the code and the answer is uncomfortable: the Handle is constructed and self._ready.append(handle) runs. deque.append is atomic, so the queue is not corrupted and the callback is not lost. The callback will run. It just will not run until something else wakes the selector.

Text 
call_soon_threadsafe:     callback ran 0.000s after scheduling
call_soon (other thread): callback ran 2.803s after scheduling

Measured for the research document on CPython 3.13.11: a loop parked in await asyncio.sleep(3.0), and a worker thread scheduling a callback 0.2 s in. The second callback sat in _ready untouched for 2.8 seconds, until the sleep(3.0) timer expired and step 3 returned of its own accord. Single machine, one run.

The failure mode, stated precisely

Not a crash. Not a lost callback. An unbounded latency that depends entirely on what else the loop happens to have scheduled. Here it was 2.8 seconds because a sleep(3.0) happened to be pending. Had the loop been idle — timeout = None, epoll_wait(-1), as in lesson 4 — the callback would never have run at all.

This is why the bug is nasty: it works in development, where something is always happening, and stops working in production at 3 a.m., where nothing is.

The honest two-part statement:

  • [impl detail] — call_soon from another thread does not corrupt the queue in CPython 3.13.11, because _ready is a deque. Nothing about that guarantee is part of the call_soon contract.
  • [guaranteed] — it is nonetheless wrong: “Unlike call_soon_threadsafe(), this method is not thread-safe” (Doc/library/asyncio-eventloop.rst:233).

The self-pipe

Python 
    def _make_self_pipe(self):
        # A self-socket, really. :-)
        self._ssock, self._csock = socket.socketpair()
        self._ssock.setblocking(False)
        self._csock.setblocking(False)
        self._internal_fds += 1
        self._add_reader(self._ssock.fileno(), self._read_from_self)

Lib/asyncio/selector_events.py:118-124 — BaseSelectorEventLoop._make_self_pipe(), called from __init__ at selector_events.py:66 — every selector loop owns one from birth.

Despite the name it is a socket.socketpair(), not an os.pipe() — the comment says as much — because Windows' select() only accepts sockets. _ssock is registered with the selector as a reader; _csock is the end that gets written to.

The write side is built to survive anything

Python 
    def _write_to_self(self):
        # This may be called from a different thread, possibly after
        # _close_self_pipe() has been called or even while it is
        # running.  Guard for self._csock being None or closed.  When
        # a socket is closed, send() raises OSError (with errno set to
        # EBADF, but let's not rely on the exact error code).
        csock = self._csock
        if csock is None:
            return

        try:
            csock.send(b'\0')
        except OSError:
            if self._debug:
                logger.debug("Fail to write a null byte into the "
                             "self-pipe socket",
                             exc_info=True)

Lib/asyncio/selector_events.py:141-157 — _write_to_self().

csock = self._csock is copied into a local before the None check — that local read is the guard against another thread setting self._csock = None in _close_self_pipe between the check and the send. The except OSError then swallows the case where the socket was closed after the local was taken. This function is written to be callable from any thread, at any time, including during loop teardown. Very few functions in CPython are.

The read side throws the bytes away

Python 
    def _read_from_self(self):
        while True:
            try:
                data = self._ssock.recv(4096)
                if not data:
                    break
                self._process_self_data(data)
            except InterruptedError:
                continue
            except BlockingIOError:
                break

Lib/asyncio/selector_events.py:129-139. On the base class, _process_self_data is pass (selector_events.py:126-127).

The bytes are irrelevant. The wakeup is the payload. recv returning is proof that select() returned, which is proof that the loop is out of step 3 and on its way to step 6, where it will drain whatever the other thread appended.

End to end

Note the one-iteration lag. The self-pipe wakeup arrives as an event, whose handler goes into _ready. If your handle was appended before the loop woke, both are in _ready and both run in the same drain. If it raced in afterwards, it runs next iteration. Either way the loop is awake and _ready is non-empty, so step 2 computes timeout = 0 and it spins straight through.

The same socket carries signals

            signal.set_wakeup_fd(self._csock.fileno())

Lib/asyncio/unix_events.py:102-109 — _UnixSelectorEventLoop.add_signal_handler().

On Unix, add_signal_handler points CPython's signal-wakeup fd at the same _csock. So the kernel writing a signal number both wakes the loop and delivers the number. The loop then demultiplexes the two uses of one socket:

Python 
    def _process_self_data(self, data):
        for signum in data:
            if not signum:
                # ignore null bytes written by _write_to_self()
                continue
            self._handle_signal(signum)

Lib/asyncio/unix_events.py:83-88.

b'\0' is the chosen wakeup byte precisely because signal number 0 does not exist. One socket, two protocols, disambiguated by a gap in the POSIX signal numbering. [impl detail], and a neat one.

Why one writes and the other need not

call_soon is only ever legitimately called from the loop thread. The loop thread can only be executing call_soon if it is inside step 6 — running a callback — or outside run_forever entirely. In neither case is it blocked in select(). A wakeup would be a wasted send() syscall on every single call_soon, which is the hottest path in asyncio: every Task step goes through it.

call_soon_threadsafe has no such guarantee, so the send() is mandatory. PEP 3156 specifies exactly this:

stop() is the sharpest illustration

It sets a flag and does not write to the self-pipe (lesson 1). So loop.stop() from another thread will not wake a parked loop, and the loop keeps sleeping until something else does. CPython's own Runner knows this and works around it explicitly:

Python 
    def _on_sigint(self, signum, frame, main_task):
        self._interrupt_count += 1
        if self._interrupt_count == 1 and not main_task.done():
            main_task.cancel()
            # wakeup loop if it is blocked by select() with long timeout
            self._loop.call_soon_threadsafe(lambda: None)
            return
        raise KeyboardInterrupt()

Lib/asyncio/runners.py:150-157 — Runner._on_sigint().

call_soon_threadsafe(lambda: None) scheduling a no-op is not a callback at all. It is a hand-written selector wakeup, and it is in CPython because there is no public API that does only that. [impl detail] — and a technique worth stealing when you need one.

all_tasks deserves its own look

It is the one place in asyncio where a cross-thread race is handled by retrying:

Python 
    scheduled_tasks = None
    i = 0
    while True:
        try:
            scheduled_tasks = list(_scheduled_tasks)
        except RuntimeError:
            i += 1
            if i >= 1000:
                raise
        else:
            break
    return {t for t in itertools.chain(scheduled_tasks, eager_tasks)
            if futures._get_loop(t) is loop and not t.done()}

Lib/asyncio/tasks.py:56-68 — all_tasks(). The comment cites CPython issues 34970 and 36607.

What that code reveals

There is no per-loop task registry. _scheduled_tasks is one module-level WeakSet shared by every loop in the process, and all_tasks(loop) filters it by futures._get_loop(t) is loop. In the C build it is the same object, created once in the module's per-interpreter state — so the registry is per-interpreter, not per-loop and not per-thread.

Running twenty loops in twenty threads puts all their tasks in one WeakSet, and all_tasks linearises the whole thing on every call. That is a real cost in a multi-loop process, and it is not documented anywhere.

Reentrancy

_run_once is not reentrant, and three separate things enforce it:

  • _check_running refuses a second run_forever on the same loop, and any run_forever while another loop is running in this thread (base_events.py:635-640).
  • _enter_task / _leave_task refuse a second task step inside a task step on the same loop (tasks.py:1057-1070, quoted in lesson 8).
  • Runner.run and asyncio.run fail fast: “asyncio.run() cannot be called from a running event loop” (runners.py:189-192).

There is no nested-loop facility and none is planned; nest_asyncio-style third-party patches work by monkeypatching around _check_running, not through any supported hook.

call_soon_threadsafe is the one unusual case — it is documented as reentrancy-safe:

Check yourself

A worker thread calls loop.call_soon(cb) on an idle loop with no timers. What happens to cb?

The append succeeds and the handle is safely in _ready — but the loop is parked in epoll_wait(-1) with no deadline, and nothing has written to the self-pipe. It stays there until some unrelated fd becomes ready. The RuntimeError only happens in debug mode, and only once the loop is actually running.

Check yourself

Why does Runner._on_sigint schedule lambda: None through call_soon_threadsafe?

The comment in the source says it: “wakeup loop if it is blocked by select() with long timeout”. main_task.cancel() on the previous line only sets state; it does not touch the self-pipe. The no-op callback is irrelevant — the _write_to_self() inside call_soon_threadsafe is the entire point.

Where this is going

Developing with asyncio, Python 3.13 documentation — the whole page, and § Concurrency and Multithreading in particular. Read it now, with the mechanism in hand, and you will notice how much of it is consequence rather than rule.

Your agent is your teacher. The highest-value question in the whole topic: “look at my code and tell me where it touches loop state from a thread.” concurrent.futures callbacks, GUI toolkit handlers, and library callbacks that “just call set_result” are the usual three.
