Lesson 0010

The C accelerator

Half of what you read in lessons 7–9 is not the code that runs. This lesson is about which half, how it is swapped in, what it buys — much less than you would guess — and the reason the loop itself can never join it.

asyncio.Task in your process is a C type. So is asyncio.Future, and current_task, and get_running_loop. BaseEventLoop is not, and the reason it is not is a design constraint rather than an unfinished job.

How the swap works

Three modules do the same trick at the bottom of the file. futures.py:

Python 
try:
    import _asyncio
except ImportError:
    pass
else:
    # _CFuture is needed for tests.
    Future = _CFuture = _asyncio.Future

Lib/asyncio/futures.py:419-425 — the accelerator import. tasks.py:390-399 does the same for Task/_CTask, having first bound _PyTask = Task.

And events.py, which attaches its rationale:

Python 
try:
    # get_event_loop() is one of the most frequently called
    # functions in asyncio.  Pure Python implementation is
    # about 4 times slower than C-accelerated.
    from _asyncio import (_get_running_loop, _set_running_loop,
                          get_running_loop, get_event_loop)
except ImportError:
    pass
else:
    # Alias C implementations for testing purposes.
    _c__get_running_loop = _get_running_loop
    _c__set_running_loop = _set_running_loop
    _c_get_running_loop = get_running_loop
    _c_get_event_loop = get_event_loop

Lib/asyncio/events.py:858-871 — the running-loop accessors.

The pattern is always the same: define the pure-Python version, alias it to _Py*, rebind the public name to the C version, alias that to _C*. Both implementations stay importable, which is the whole point — and is why lesson 9's class statement reads class Task(futures._PyFuture) rather than class Task(Future).

What the C version actually accelerates

Reading Modules/_asynciomodule.c, the wins are structural rather than algorithmic. Seven of them, the first two being the ones that matter:

1. Struct fields instead of instance dicts

C 
#define FutureObj_HEAD(prefix)                                              \
    PyObject_HEAD                                                           \
    PyObject *prefix##_loop;                                                \
    PyObject *prefix##_callback0;                                           \
    PyObject *prefix##_context0;                                            \
    PyObject *prefix##_callbacks;                                           \
    PyObject *prefix##_exception;                                           \
    PyObject *prefix##_exception_tb;                                        \
    PyObject *prefix##_result;                                              \
    PyObject *prefix##_source_tb;                                           \
    PyObject *prefix##_cancel_msg;                                          \
    PyObject *prefix##_cancelled_exc;                                       \
    fut_state prefix##_state;                                               \
    /* These bitfields need to be at the end of the struct
       so that these and bitfields from TaskObj are contiguous.
    */                                                                      \
    unsigned prefix##_log_tb: 1;                                            \
    unsigned prefix##_blocking: 1;

Modules/_asynciomodule.c:113-130 at tag v3.13.11. This file is not shipped with a binary install; it was fetched from the tag.

_asyncio_future_blocking — a Python attribute lookup in the pure-Python path — is fut_blocking, a one-bit bitfield, here. Task reuses the header macro so that the Future and Task bitfields pack contiguously, which is the comment's whole subject.

2. A fast path that skips the attribute lookup entirely

That is lesson 7's dispatch, compiled. But note: the generic path is still there, sixty lines further down, doing the full PyObject_GetOptionalAttr(result, &_Py_ID(_asyncio_future_blocking), &o) and PyObject_SetAttr(… Py_False) for third-party Future-likes. The C version implements both the fast structural path and the documented duck-typed protocol, and they must agree.

How much is it worth? Less than you would guess

Text 
_CTask   200k bare-yield steps: 0.286s
_PyTask  200k bare-yield steps: 0.319s      ratio 1.12x
C Task+Future    100k awaits:   0.278s
Py Task+Future   100k awaits:   0.411s      ratio 1.48x

Measured for the research document on CPython 3.13.11, Linux 6.8, GIL enabled, EpollSelector. Three repetitions, best of each. Single machine, no CPU pinning, no pyperf — these establish an order of magnitude and nothing finer, and are reported because they falsify a plausible assumption rather than because they characterise performance.

A 1.1×–1.5× improvement, not 10×. The reason is the instructive part.

Why the accelerator hits a floor

Every step of a Task still goes through loop.call_soon → events.Handle.__init__ → contextvars.copy_context() → _ready.append → Handle._run → Context.run. That is six pure-Python operations per step, and the accelerator touches none of them.

The C module makes Task and Future cheap. The loop remains the floor.

Why there is no C event loop

This is not an omission. The C Task schedules itself by calling the Python loop.call_soon through the ordinary attribute-lookup path:

C 
static int
call_soon(asyncio_state *state, PyObject *loop, PyObject *func, PyObject *arg,
          PyObject *ctx)
{
    PyObject *handle;

    if (ctx == NULL) {
        PyObject *stack[] = {loop, func, arg};
        size_t nargsf = 3 | PY_VECTORCALL_ARGUMENTS_OFFSET;
        handle = PyObject_VectorcallMethod(&_Py_ID(call_soon), stack, nargsf, NULL);
    }

Modules/_asynciomodule.c:288-298 at tag v3.13.11.

That is PEP 3156's “using only the public interface of the event loop” constraint — the same clause that produced _asyncio_future_blocking in lesson 7 — enforced in C. The accelerator cannot reach into _ready, because doing so would break third-party loops. So _ready, _scheduled, _run_once, call_soon, Handle and TimerHandle are pure Python in every CPython build, always.

The parity requirement

Because both implementations are live, they are tested against each other in a matrix. test_tasks.py instantiates the same BaseTaskTests body six ways:

Python 
@unittest.skipUnless(hasattr(futures, '_CFuture') and
                     hasattr(tasks, '_CTask'),
                     'requires the C _asyncio module')
class CTask_CFuture_Tests(BaseTaskTests, SetMethodsTest,
                          test_utils.TestCase):

    Task = getattr(tasks, '_CTask', None)
    Future = getattr(futures, '_CFuture', None)

Lib/test/test_asyncio/test_tasks.py:2821-2828 — the parity matrix, which also contains CTask_PyFuture_Tests, PyTask_CFuture_Tests, PyTask_PyFuture_Tests and two subclass variants.

And a decorator injects an extra assertion into the subclass variants, which is the interesting one:

Python 
        self.assertEqual(
            dict(task.calls),
            {'add_done_callback': 1})

Lib/test/test_asyncio/test_tasks.py:2745-2747, against a CommonFuture mixin that counts method calls (2710-2724).

That is not a performance test. It asserts that a C Task awaiting a Python Future — and every other cross combination — calls add_done_callback exactly once: that the C fast path and the generic duck-typed path produce identical observable call sequences. The commented-out lines in Task.cancel from lesson 9 carry the same requirement as a note to a future maintainer.

One place parity is not exact

The Python _get_running_loop carries a PID guard (events.py:747-776) — it stores (loop, pid) and returns the loop only if the pid still matches. The C one reads ts->asyncio_running_loop with no PID check at all. The gap is closed by a fork hook that applies to both (events.py:874-882, registered with os.register_at_fork), so behaviour is equivalent on any platform that has one — but it is not the same code. Check yourself

Which of these is not replaced by the C _asyncio module?

Handle belongs to the loop, and the loop is pure Python in every build — there is no loop type in Modules/_asynciomodule.c and base_events.py has no accelerator import. The other three are all rebound at import time. current_task gained its C implementation in 3.12.

Check yourself

Why is the C Task only about 1.1× to 1.5× faster than the Python one?

call_soon, Handle.__init__, copy_context, deque.append, Handle._run and Context.run are six pure-Python operations per task step, and the accelerator touches none of them — by design, because PEP 3156 forbids the scheduler from reaching past the loop's public API. The fast path is real, but the floor underneath it is Python.

Where this is going

That closes the coroutine arc. The remaining machinery is the half of _run_once the round trip did not use: lesson 11 takes step 5 and the clock, and lesson 12 takes step 1 and asyncio.sleep.

Which symbols _asynciomodule.c exports, and how that set has moved across releases, is tracked in the version ledger. That is the page to re-check first when a new Python lands, because it is the part of this lesson most likely to have gone stale.

Seeing the same logic twice, in two languages, kept in step by a test matrix, is the clearest possible demonstration of what “parity requirement” costs.

Your agent is your teacher. Worth asking: “what would break if the C Task appended to loop._ready directly instead of calling call_soon?” The answer is not “nothing, it would be faster”, and working out why is the whole lesson.
