Lesson 0003

The ntodo snapshot

The hinge of the topic. Four lines of step 6 solve fairness and thread-safety at the same time, and they explain a documented behaviour, an undocumented one, and a class of bug you will otherwise spend an afternoon on.

This is a short lesson about a small piece of code, and it is the one to over-learn. If you understand why the drain counts before it pops, you can predict what asyncio will do in most of the situations where people find it surprising.

The code, and the obvious alternative

Python 
        # This is the only place where callbacks are actually *called*.
        # All other places just add them to ready.
        # Note: We run all currently scheduled callbacks, but not any
        # callbacks scheduled by callbacks run this time around --
        # they will be run the next time (after another I/O poll).
        # Use an idiom that is thread-safe without using locks.
        ntodo = len(self._ready)
        for i in range(ntodo):
            handle = self._ready.popleft()

Lib/asyncio/base_events.py:2027-2035 — inside BaseEventLoop._run_once().

The obvious alternative is shorter and would look better in review:

Python Written for this lesson 
# Not what CPython does. This version is wrong, twice over.
while self._ready:
    handle = self._ready.popleft()
    handle._run()

The source comment names both reasons it is wrong, in the order they were presumably discovered. Take them one at a time.

Reason one: fairness

Callbacks run during the drain routinely schedule more callbacks. That is not an edge case — it is the entire mechanism by which a Task advances, as lesson 8 shows. A while loop would run those too, in the same iteration, and then their children, and so on.

Consider a coroutine that does while True: await asyncio.sleep(0). That is a bare yield, which re-schedules the task with call_soon (tasks.py:691-707 and tasks.py:355-357; lesson 12 takes it apart). Under a while self._ready drain it would keep _ready permanently non-empty, the loop would never return to step 3, and every socket in the process would stall — not slowly, but completely, forever.

With the snapshot, that coroutine gets exactly one step per iteration and step 3 runs in between. The comment states the rule as a property of the design:

CPython's own test suite pins it

This is [impl detail] — nothing in the reference documentation describes the drain. But a behaviour a test asserts is meaningfully different from one that merely happens, and there is a test:

Python 
    def test__run_once_schedule_handle(self):
        handle = None
        processed = False

        def cb(loop):
            nonlocal processed, handle
            processed = True
            handle = loop.call_soon(lambda: True)

        h = asyncio.TimerHandle(time.monotonic() - 1, cb, (self.loop,),
                                self.loop, None)

        self.loop._process_events = mock.Mock()
        self.loop._scheduled.append(h)
        self.loop._run_once()

        self.assertTrue(processed)
        self.assertEqual([handle], list(self.loop._ready))

Lib/test/test_asyncio/test_base_events.py:405-422 — test__run_once_schedule_handle.

Read the last assertion. After one complete _run_once(), the callback that cb scheduled is still sitting in _ready, unrun. That is the rule, asserted.

Reason two: thread safety, without a lock

call_soon_threadsafe appends to _ready from an arbitrary OS thread while the loop thread is popping from the left. There is no mutex anywhere near this. The snapshot is what makes that safe, in three parts:

  • deque.append and deque.popleft are individually atomic. The documentation says so, and this guarantee is load-bearing for the whole design:
  • ntodo is read once, before any popping. A concurrent append can therefore only make the real length larger than ntodo, never smaller. The drain never pops more than it counted, so it can never hit an IndexError.
  • Nothing else pops from _ready. close() calls self._ready.clear() (base_events.py:750) but refuses to run while the loop is running (base_events.py:743-744).
The while version fails differently here

while self._ready would also be memory-safe — the deque guarantee covers it. But it would add a livelock to the starvation problem: a producer thread appending faster than the loop drains would pin the loop inside step 6 indefinitely, and the loop would never poll again. The snapshot bounds the drain by a number decided before any other thread could influence it.

Two consequences that catch people out

A cancelled handle still consumes a slot

Python 
            handle = self._ready.popleft()
            if handle._cancelled:
                continue

Lib/asyncio/base_events.py:2035-2037 — inside the drain.

Cancelling a call_soon handle does not remove it from _ready. It is still popped, and for i in range(ntodo) has already budgeted a slot for it; the drain just steps over it. Cancellation here is a flag read at run time, not a removal. [impl detail]

Debug mode is checked per handle, not per iteration

if self._debug: sits inside the for loop (line 2038), so a set_debug() taking effect mid-drain is observable. In debug mode each callback is timed and anything slower than self.slow_callback_duration (default 0.1) is logged:

Given lesson 2's corollary — a slow callback blocks the poll — this log line is the single most useful diagnostic asyncio emits, and it costs one call to loop.set_debug(True).

One more oddity in the same eighty lines

handle = None at line 2051 and event_list = None at line 2015 are not tidiness. Both carry the comment “Needed to break cycles when an exception occurs”: if _run_once raises, its frame is captured in the traceback, and a live local referring to a handle that refers to a task that refers to the frame is a reference cycle only the cyclic collector can free. The same idiom appears at events.py:105, tasks.py:296 and tasks.py:371. [impl detail]

Check yourself

Why does the drain snapshot ntodo rather than looping while self._ready?

Fairness and lock-free thread safety — the two reasons the source comment names. Bounding the batch guarantees the loop returns to the poll; reading the length once guarantees a concurrent call_soon_threadsafe append can only grow the queue beyond what the drain will touch. Ordering is FIFO either way, the debug timer is per handle, and cancelled handles are stepped over rather than removed.

Check yourself

A callback running in step 6 calls loop.call_soon(f). When does f run?

ntodo was fixed before the drain began, so f sits in _ready until the next _run_once — which is exactly what test__run_once_schedule_handle asserts. Note that the loop will not be idle in between: step 2 sees a non-empty _ready and picks a zero timeout, so the poll returns at once.

Where this is going

You now know what bounds the drain. The next question is what bounds the wait — how long the loop is prepared to sit in step 3, and what “blocking” costs when it gets that wrong. Lesson 4 takes the timeout computation and the syscall underneath it.

The four rules the drain obeys are collected, without the argument that got us here, in the _run_once reference — the page to reach for when you want the rule rather than the reasoning.

On spacing

Leave a day if you can, and before lesson 4 try to state both reasons the snapshot exists without looking. Most people retrieve the fairness reason and lose the thread-safety one, because it is the one with no visible symptom — which is precisely why it is worth the deliberate recall.
