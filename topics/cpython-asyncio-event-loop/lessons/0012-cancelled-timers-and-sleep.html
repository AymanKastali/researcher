Lesson 0012

Cancelled timers, and sleep

Step 1 — the step people forget when reciting the six. Two strategies for a problem heaps are bad at, two constants that exist nowhere in the documentation, one reproducible oddity, and the coroutine that makes the whole mechanism necessary.

You cannot cheaply remove an element from the middle of a binary heap. A server with ten thousand outstanding timeouts that mostly never fire has ten thousand cancellations to deal with, and step 1 is asyncio's answer.

Cancelling a timer does not remove it

Python 
    def cancel(self):
        if not self._cancelled:
            self._loop._timer_handle_cancelled(self)
        super().cancel()

Lib/asyncio/events.py:157-160 — TimerHandle.cancel().

Python 
    def _timer_handle_cancelled(self, handle):
        """Notification that a TimerHandle has been cancelled."""
        if handle._scheduled:
            self._timer_cancelled_count += 1

Lib/asyncio/base_events.py:1965-1968 — BaseEventLoop._timer_handle_cancelled().

It sets a flag and tells the loop. _timer_cancelled_count is a running estimate of how much dead weight the heap is carrying, and step 1 uses it to choose between two strategies.

The two strategies

Python 
# Minimum number of _scheduled timer handles before cleanup of
# cancelled handles is performed.
_MIN_SCHEDULED_TIMER_HANDLES = 100

# Minimum fraction of _scheduled timer handles that are cancelled
# before cleanup of cancelled handles is performed.
_MIN_CANCELLED_TIMER_HANDLES_FRACTION = 0.5

Lib/asyncio/base_events.py:56-62 — the two constants. Both, and the whole mechanism, are [impl detail]. Neither appears anywhere on docs.python.org.

Step 1 picks one of these on every iteration.
Strategy When What it does Cost
Cheap path (the else branch) Always, unless the compaction condition holds. While the head of the heap is cancelled, pop it and decrement the counter. Cancelled handles buried behind live ones stay put. O(log n) per removal, touching nothing else.
Compaction (the if branch) More than 100 scheduled timers and more than half of them believed cancelled. Walk the whole list, keep the live ones, heapq.heapify the survivors, reset the counter to zero. O(n), and it is why the counter exists at all.
Undocumented, but not incidental

Nothing about this mechanism is promised. But CPython's own test suite imports both constants by name and computes its fixtures from them:

An observation about the counter

This part is presented as an observation, not as a bug report, and the distinction is deliberate.

_timer_cancelled_count is decremented in exactly one place — the head-pop loop at base_events.py:1996-1999 — and reset in exactly one other, the compaction branch at base_events.py:1993. Step 5, which also removes handles from _scheduled, does not touch it and does not test _cancelled:

Python 
        while self._scheduled:
            handle = self._scheduled[0]
            if handle._when >= end_time:
                break
            handle = heapq.heappop(self._scheduled)
            handle._scheduled = False
            self._ready.append(handle)

Lib/asyncio/base_events.py:2019-2025 — step 5, again. There is no _cancelled test here.

So a cancelled timer that is not at the head during step 1 (because a live timer with an earlier deadline sits in front of it) but is due during step 5 gets popped into _ready and skipped at the drain — while _timer_cancelled_count keeps counting it. That is reproducible:

Python Written for this lesson 
import asyncio

loop = asyncio.new_event_loop()
def cb(): pass
now = loop.time()
loop.call_at(now - 1.0, cb)                  # due, live, sorts first
h = loop.call_at(now - 0.5, cb); h.cancel()  # due, cancelled, sorts behind it
print(loop._timer_cancelled_count, len(loop._scheduled))   # -> 1 2
loop._run_once()
print(loop._timer_cancelled_count, len(loop._scheduled))   # -> 1 0
loop.close()

Reproduced from the research document, run on CPython 3.13.11. It prints 1 2 then 1 0: the heap is empty, and the loop still believes one cancelled timer is in it.

Why this is benign, and why it is still worth knowing

The consequence is bounded. An inflated _timer_cancelled_count inflates the ratio count / sched_count, so compaction can fire earlier than the 50% rule suggests — and compaction is correct regardless of the counter, because it resets it. Nothing goes wrong.

But it does mean the counter is an upper bound on cancelled scheduled handles, not a count of them. If you ever read that attribute — in a metric, in a test, in a custom loop subclass — that is the difference between a correct dashboard and a confusing one.

No CPython issue describing this was found. A semantic search of python/cpython issues returned nothing matching. The behaviour is certain; whether it is considered a defect or an accepted approximation is not, and this page does not claim to know.

asyncio.sleep, the canonical timer user

Python 
async def sleep(delay, result=None):
    """Coroutine that completes after a given time (in seconds)."""
    if delay <= 0:
        await __sleep0()
        return result

    if math.isnan(delay):
        raise ValueError("Invalid delay: NaN (not a number)")

    loop = events.get_running_loop()
    future = loop.create_future()
    h = loop.call_later(delay,
                        futures._set_result_unless_cancelled,
                        future, result)
    try:
        return await future
    finally:
        h.cancel()

Lib/asyncio/tasks.py:703-720 — asyncio.sleep().

A Future plus a call_later that resolves it — which is lesson 8's round trip with a TimerHandle where the selector registration was. And, critically, h.cancel() in the finally, so a cancelled sleep does not leave a dead TimerHandle in the heap forever.

That cancel() is what makes step 1 necessary. A server with ten thousand asyncio.wait_for-style timeouts that mostly don't fire is precisely the workload compaction exists for: every successful operation cancels its own timeout, and every cancellation is a dead handle somewhere in the heap.

sleep(0) takes a different path entirely

Python 
@types.coroutine
def __sleep0():
    """Skip one event loop run cycle.

    This is a private helper for 'asyncio.sleep()', used
    when the 'delay' is set to 0.  It uses a bare 'yield'
    expression (which Task.__step knows how to handle)
    instead of creating a Future object.
    """
    yield

Lib/asyncio/tasks.py:691-700 — __sleep0().

A bare yield produces result is None in __step_run_and_handle_result — the last branch of the table in lesson 7 — which hits elif result is None: at tasks.py:355-357 and simply call_soons the next step.

So await asyncio.sleep(0) is the idiom for “yield to the loop exactly once”, and it costs one Handle, no Future, no timer. [impl detail] — the documentation says only that “setting the delay to 0 provides an optimized path to allow other tasks to run”, without specifying the mechanism.

That counter is a 3.11 addition, and lesson 14 is where it comes from.

Check yourself

When does the loop rebuild the whole timer heap to drop cancelled handles?

Both conditions must hold — _MIN_SCHEDULED_TIMER_HANDLES is 100 and _MIN_CANCELLED_TIMER_HANDLES_FRACTION is 0.5. The third answer describes the cheap path, which runs on every other iteration and only touches the head. Both constants are implementation detail, and both are imported by name in CPython's test suite.

Check yourself

What does await asyncio.sleep(0) allocate?

sleep(0) routes to __sleep0, a bare yield. The Task sees result is None and calls call_soon(self.__step) — one Handle, no Future, no heap entry. The coroutine does suspend; it just suspends for exactly one iteration, which is the whole point of the idiom.

Where this is going

Every step of _run_once has now been opened. What remains is the world outside it: other threads, signals, and the one socket that lets any of them get the loop's attention. Lesson 13 is the most operationally useful lesson in the topic.

Both constants introduced here, with their values and their evidence grades, sit in the constants table of the _run_once reference — alongside the others the loop depends on, which is the useful way to see them.
