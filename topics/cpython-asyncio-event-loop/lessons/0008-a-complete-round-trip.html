Lesson 0008

A complete round trip

One await, followed all the way to epoll_wait and back. Everything in lessons 1–7 appears here in sequence — including the two places where a whole extra loop iteration is spent, and the case where the coroutine never suspends at all.

The path traced is await loop.sock_recv(sock, n): the shortest complete journey from a coroutine to the kernel and back that fits in one lesson. At the end, the transport path is shown as a contrast, because its most surprising property is only visible against this one.

The whole trip, in one picture

Stage 0: the fast path nobody mentions

Python 
    async def sock_recv(self, sock, n):
        """Receive data from the socket.

        The return value is a bytes object representing the data received.
        The maximum amount of data to be received at once is specified by
        nbytes.
        """
        base_events._check_ssl_socket(sock)
        if self._debug and sock.gettimeout() != 0:
            raise ValueError("the socket must be non-blocking")
        try:
            return sock.recv(n)
        except (BlockingIOError, InterruptedError):
            pass
        fut = self.create_future()
        fd = sock.fileno()
        self._ensure_fd_no_transport(fd)
        handle = self._add_reader(fd, self._sock_recv, fut, sock, n)
        fut.add_done_callback(
            functools.partial(self._sock_read_done, fd, handle=handle))
        return await fut

Lib/asyncio/selector_events.py:364-384 — BaseSelectorEventLoop.sock_recv().

Read lines 374–377 again

If the socket already has data buffered, sock.recv(n) returns it and the coroutine returns without ever suspending. No Future, no selector registration, no trip through the loop, no yield. await loop.sock_recv(...) is then just a function call that happens to be spelled with await.

[impl detail] — the documentation for loop.sock_recv says only “Receive up to nbytes from sock” and promises nothing about suspension. The write side has the same optimisation, commented “Optimization: try to send now” at selector_events.py:1064-1067.

Stage 1: registering with the selector

Python 
    def _add_reader(self, fd, callback, *args):
        self._check_closed()
        handle = events.Handle(callback, args, self, None)
        key = self._selector.get_map().get(fd)
        if key is None:
            self._selector.register(fd, selectors.EVENT_READ,
                                    (handle, None))
        else:
            mask, (reader, writer) = key.events, key.data
            self._selector.modify(fd, mask | selectors.EVENT_READ,
                                  (handle, writer))
            if reader is not None:
                reader.cancel()
        return handle

Lib/asyncio/selector_events.py:274-287 — BaseSelectorEventLoop._add_reader().

  • register versus modify. The selector holds one registration per descriptor with a combined read/write mask. First interest is a register (epoll_ctl(EPOLL_CTL_ADD)); adding the other direction is a modify (EPOLL_CTL_MOD) that ORs the bit in. _remove_reader reverses it, and calls unregister only when the mask goes empty.
  • One reader per descriptor, and the old one is silently cancelled — if reader is not None: reader.cancel(). This one is documented: “Any preexisting callback registered for fd is cancelled and replaced by callback” (loop.add_reader, Doc/library/asyncio-eventloop.rst:1010-1011). [guaranteed]
  • context=None at registration, so Handle.__init__ copies the current context — the I/O callback inherits the context of whoever registered interest, not of whoever's data arrives. That is lesson 6 paying off.
  • The private method returns the Handle; the public one throws it away. add_reader is four lines and returns nothing, exactly as specified: “Note that add_reader(), add_writer() and add_signal_handler() do not return Handles” (PEP 3156 § Handles). [guaranteed] The internal one returns it because sock_recv needs to know, later, whether the reader it installed is still the live one.

Stage 2: the data arrives

Step 4 queues the reader handle, step 6 runs it, and the callback is:

Python 
    def _sock_recv(self, fut, sock, n):
        # _sock_recv() can add itself as an I/O callback if the operation can't
        # be done immediately. Don't use it directly, call sock_recv().
        if fut.done():
            return
        try:
            data = sock.recv(n)
        except (BlockingIOError, InterruptedError):
            return  # try again next time
        except (SystemExit, KeyboardInterrupt):
            raise
        except BaseException as exc:
            fut.set_exception(exc)
        else:
            fut.set_result(data)

Lib/asyncio/selector_events.py:390-404 — BaseSelectorEventLoop._sock_recv(). Note the two-tier except from lesson 6, again.

fut.done() is checked first because the Future may have been cancelled between registration and readiness, and a spurious wakeup (BlockingIOError) is treated as “no data yet, stay registered”.

Stage 3: the resolution that costs an iteration

Python 
    def __schedule_callbacks(self):
        """Internal: Ask the event loop to call all callbacks.

        The callbacks are scheduled to be called as soon as possible. Also
        clears the callback list.
        """
        callbacks = self._callbacks[:]
        if not callbacks:
            return

        self._callbacks[:] = []
        for callback, ctx in callbacks:
            self._loop.call_soon(callback, self, context=ctx)

Lib/asyncio/futures.py:158-170 — Future.__schedule_callbacks(), called by set_result at futures.py:248-258.

The callbacks are never called inline. set_result returns having only enqueued them. This is a guarantee, and PEP 3156 is explicit that it is a deliberate divergence from the older concurrent-futures design:

Count the iterations

_sock_recv runs in iteration N's drain and calls call_soon(__wakeup). The ntodo snapshot (lesson 3) means __wakeup cannot run until iteration N+1. So there is a full extra loop iteration between “the bytes arrived” and “your coroutine sees them”.

That is latency, bought deliberately, in exchange for the strict serialisation PEP 3156 calls out as “an important guarantee: when two or more callbacks use or modify shared state, each callback is guaranteed that while it is running, the shared state isn't changed by another callback” (§ Basic Callbacks). It is the reason you have never needed a lock inside a coroutine.

Stage 4: waking up

Python 
    def __wakeup(self, future):
        try:
            future.result()
        except BaseException as exc:
            # This may also be a cancellation.
            self.__step(exc)
        else:
            # Don't pass the value of `future.result()` explicitly,
            # as `Future.__iter__` and `Future.__await__` don't need it.
            # If we call `_step(value, None)` instead of `_step()`,
            # Python eval loop would use `.send(value)` method call,
            # instead of `__next__()`, which is slower for futures
            # that return non-generator iterators from their `__iter__`.
            self.__step()
        self = None  # Needed to break cycles when an exception occurs.

Lib/asyncio/tasks.py:373-387 — Task.__wakeup().

__wakeup calls future.result() purely to turn a stored exception — or a cancellation — into a live raise, then forwards it into the coroutine via coro.throw. On success the value is deliberately discarded and re-fetched by Future.__await__ resuming past its yield. The comment gives the performance reason, and it is worth noticing that the team wrote it down rather than leaving it as a puzzle.

Stage 5: back into the coroutine

Python 
    def __step(self, exc=None):
        if self.done():
            raise exceptions.InvalidStateError(
                f'_step(): already done: {self!r}, {exc!r}')
        if self._must_cancel:
            if not isinstance(exc, exceptions.CancelledError):
                exc = self._make_cancelled_error()
            self._must_cancel = False
        self._fut_waiter = None

        _enter_task(self._loop, self)
        try:
            self.__step_run_and_handle_result(exc)
        finally:
            _leave_task(self._loop, self)
            self = None  # Needed to break cycles when an exception occurs.

Lib/asyncio/tasks.py:281-296 — Task.__step(); the actual resumption is result = coro.send(None) at tasks.py:304.

The transport path, for contrast

sock_recv is the low-level API, and it registers a reader per read. A transport registers its reader once, at construction:

Python 
        self._loop.call_soon(self._protocol.connection_made, self)
        # only start reading when connection_made() has been called
        self._loop.call_soon(self._add_reader,
                             self._sock_fd, self._read_ready)
        if waiter is not None:
            # only wake up the waiter when connection_made() has been called
            self._loop.call_soon(futures._set_result_unless_cancelled,
                                 waiter, None)

Lib/asyncio/selector_events.py:944-951 — _SelectorSocketTransport.__init__().

Even _add_reader is deferred through call_soon — that is how connection_made is guaranteed to have run before any data_received. Ordering by queue position, not by locking.

The thing to notice

There is no Future anywhere in the transport read path. _read_ready__data_received calls sock.recv and hands the bytes straight to self._protocol.data_received(data) (selector_events.py:1001-1019). It is a plain callback. The Future only reappears one layer up, in StreamReader, when somebody awaits.

That is PEP 3156's layering made visible: the callback API is the primitive, and “usage of coroutines is optional” (§ Coroutines and the Scheduler). The extra iteration you counted in stage 3 is the price of the coroutine layer, and the transport path does not pay it.

Check yourself

await loop.sock_recv(s, n) on a socket that already has buffered data. How many loop iterations does it cost?

sock_recv tries sock.recv(n) before doing anything else, and returns its result directly if it succeeds. No Future is created, nothing is registered, and no yield happens — so the await is a plain call. Two and three are the costs of the slow path, which is what the rest of the lesson traces.

Check yourself

Why does fut.set_result(data) not resume the waiting coroutine immediately?

__schedule_callbacks enqueues every done-callback with call_soon, and PEP 3156 makes that a guarantee: “the callback is never called immediately”. Combined with the ntodo snapshot, that costs one whole extra iteration — and buys the serialisation guarantee that means no callback ever observes shared state changing underneath it.

Where this is going

Five objects took part in that trip — the loop, the selector, a Handle, a Future and a Task — and it is worth being precise about which of them owns what. Lesson 9 draws the boundaries, and explains the one attribute that makes a Task more than a Future.
