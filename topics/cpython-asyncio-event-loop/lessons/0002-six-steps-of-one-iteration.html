Lesson 0002

Six steps of one iteration

The mission is to reason from the machinery. This is the machinery: one method, eighty lines, six steps. Every later lesson in this topic is a magnification of one of them.

Lesson 1 left run_forever calling _run_once() in a loop. This lesson is the map of _run_once(). The single win to take away is being able to recite the six steps in order — because once you can, questions like “why did my callback not run until the next socket event?” stop needing to be asked.

The shape

The method, uncut

The rest of this topic is commentary on the following, so it is worth having seen it whole once, even if most of it does not land yet.

Python 
    def _run_once(self):
        """Run one full iteration of the event loop.

        This calls all currently ready callbacks, polls for I/O,
        schedules the resulting callbacks, and finally schedules
        'call_later' callbacks.
        """

        sched_count = len(self._scheduled)
        if (sched_count > _MIN_SCHEDULED_TIMER_HANDLES and
            self._timer_cancelled_count / sched_count >
                _MIN_CANCELLED_TIMER_HANDLES_FRACTION):
            # Remove delayed calls that were cancelled if their number
            # is too high
            new_scheduled = []
            for handle in self._scheduled:
                if handle._cancelled:
                    handle._scheduled = False
                else:
                    new_scheduled.append(handle)

            heapq.heapify(new_scheduled)
            self._scheduled = new_scheduled
            self._timer_cancelled_count = 0
        else:
            # Remove delayed calls that were cancelled from head of queue.
            while self._scheduled and self._scheduled[0]._cancelled:
                self._timer_cancelled_count -= 1
                handle = heapq.heappop(self._scheduled)
                handle._scheduled = False

        timeout = None
        if self._ready or self._stopping:
            timeout = 0
        elif self._scheduled:
            # Compute the desired timeout.
            timeout = self._scheduled[0]._when - self.time()
            if timeout > MAXIMUM_SELECT_TIMEOUT:
                timeout = MAXIMUM_SELECT_TIMEOUT
            elif timeout < 0:
                timeout = 0

        event_list = self._selector.select(timeout)
        self._process_events(event_list)
        # Needed to break cycles when an exception occurs.
        event_list = None

        # Handle 'later' callbacks that are ready.
        end_time = self.time() + self._clock_resolution
        while self._scheduled:
            handle = self._scheduled[0]
            if handle._when >= end_time:
                break
            handle = heapq.heappop(self._scheduled)
            handle._scheduled = False
            self._ready.append(handle)

        # This is the only place where callbacks are actually *called*.
        # All other places just add them to ready.
        # Note: We run all currently scheduled callbacks, but not any
        # callbacks scheduled by callbacks run this time around --
        # they will be run the next time (after another I/O poll).
        # Use an idiom that is thread-safe without using locks.
        ntodo = len(self._ready)
        for i in range(ntodo):
            handle = self._ready.popleft()
            if handle._cancelled:
                continue
            if self._debug:
                try:
                    self._current_handle = handle
                    t0 = self.time()
                    handle._run()
                    dt = self.time() - t0
                    if dt >= self.slow_callback_duration:
                        logger.warning('Executing %s took %.3f seconds',
                                       _format_handle(handle), dt)
                finally:
                    self._current_handle = None
            else:
                handle._run()
        handle = None  # Needed to break cycles when an exception occurs.

Three things the shape tells you immediately

Polling happens before running, every time

Step 3 comes before step 6. An iteration always asks the kernel what is ready first, and only then runs callbacks. This is why the documented behaviour of stop() before run_forever() is “poll once with a zero timeout, then exit” rather than “exit”: step 2 sees _stopping and chooses a zero timeout, but step 3 still runs. Lesson 15 shows PEP 3156 expecting the opposite.

Nothing user-written runs outside step 6

Steps 1, 2, 4 and 5 only move objects between a heap, a deque and a selector. The source comment says it in as many words:

That is a stronger statement than it looks. When a socket becomes readable, your data_received does not run at step 4; a Handle is appended and the loop continues to step 5. When a Future is resolved, its done-callbacks do not run inline; they are appended. The whole system is one queue and one place that empties it.

Exactly one step can block

Steps 1, 2, 4, 5 are bounded by the work already queued. Step 6 is bounded by however long your callbacks take. Step 3 is the only place the process voluntarily waits, and lesson 4 is about it.

The operational corollary

Because step 3 of iteration N+1 cannot begin until step 6 of iteration N has finished, a slow callback does not merely delay itself — it delays the poll. No file descriptor in the process is even looked at while it runs. The documentation states the consequence without the mechanism: “if a function performs a CPU-intensive calculation for 1 second, all concurrent asyncio Tasks and IO operations would be delayed by 1 second” (Running Blocking Code, Doc/library/asyncio-dev.rst:122-125). Check yourself

A readable socket's callback is appended to _ready at step 4. When does it actually run?

Step 4 appends, step 6 drains, and both happen in the same call to _run_once — so an I/O callback runs in the iteration that polled for it. What waits until the next iteration is anything scheduled by a callback running in step 6, because ntodo was snapshotted before the drain began. That is lesson 3.

Check yourself

Which single step of _run_once can block for a meaningful duration?

self._selector.select(timeout) is the only call that waits on the kernel. Step 6 can certainly take a long time, but only because your own callbacks do — the loop is not waiting there, it is running your code. Steps 1 and 5 are bounded by the size of the heap.

Where this is going

Six steps, one of which blocks, and one of which runs anything. The next three lessons take the last three steps in reverse order of subtlety: lesson 3 on the four lines of step 6 that quietly solve two different problems at once, then lesson 4 on the timeout, then lesson 5 on the conversion from events to callbacks.

The six steps, as a bare table with the source line for each, are in the _run_once reference. Recall them from memory first; that page is for checking yourself, not for learning them from.

Your agent is your teacher. A good question to put to it now: “what would break if steps 5 and 6 were swapped?” Working out the answer from the code is worth more than reading the next lesson.

On spacing

This is the lesson to over-learn: almost everything later leans on it. Before lesson 3, try to name the six steps in order from memory, out loud, and then check. Recalling five and missing one teaches you more than re-reading the diagram, and the one you miss is usually step 1 — which is exactly why it gets its own lesson later.
