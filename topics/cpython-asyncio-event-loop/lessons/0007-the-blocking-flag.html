Lesson 0007

The blocking flag

The second hinge. One attribute name joins every coroutine you have ever written to the callback machine of lessons 1–6 — and the reason it is a duck-typed attribute rather than a method is a constraint written down in 2012.

_asyncio_future_blocking. It is the single most important identifier in asyncio and it appears exactly once in the published documentation. This lesson teaches the protocol cold, on its own; lesson 8 then watches it work.

Start with the declaration

The comment above it is the clearest single statement of design in the whole codebase, so read it before the code:

Python 
    # This field is used for a dual purpose:
    # - Its presence is a marker to declare that a class implements
    #   the Future protocol (i.e. is intended to be duck-type compatible).
    #   The value must also be not-None, to enable a subclass to declare
    #   that it is not compatible by setting this to None.
    # - It is set by __iter__() below so that Task._step() can tell
    #   the difference between
    #   `await Future()` or`yield from Future()` (correct) vs.
    #   `yield Future()` (incorrect).
    _asyncio_future_blocking = False

Lib/asyncio/futures.py:59-68 — a class attribute on Future.

The awaiting side

Python 
    def __await__(self):
        if not self.done():
            self._asyncio_future_blocking = True
            yield self  # This tells Task to wait for completion.
        if not self.done():
            raise RuntimeError("await wasn't used with future")
        return self.result()  # May raise too.

    __iter__ = __await__  # make compatible with 'yield from'.

Lib/asyncio/futures.py:283-291 — Future.__await__().

Six lines, and they are the bottom of every await chain you have ever written. That is not a metaphor; PEP 492 makes it a mechanism:

Whatever depth of await you write, the object that finally comes out of coro.send(None) is a Future, and the flag on it is True. You can watch that happen:

Python Written for this lesson 
import asyncio

f = asyncio.Future(loop=asyncio.new_event_loop())
f._asyncio_future_blocking          # -> False
it = f.__await__()
next(it) is f                       # -> True   (the future yields *itself*)
f._asyncio_future_blocking          # -> True

Reproduced from the research document's measurements, run against CPython 3.13.11. The three results are the whole protocol as seen from outside.

A direction PEP 492 got backwards, harmlessly

PEP 492 prescribed “to enable Future objects in await statements, the only change is to add __await__ = __iter__ line to asyncio.Future class” (§ Await Expression). CPython defines __await__ and aliases __iter__ to it — the opposite. From outside the two are indistinguishable, which is why it has never mattered.

The receiving side

This is the block that turns a yielded object into a scheduling decision. It is the single most important piece of code in asyncio:

Python 
        else:
            blocking = getattr(result, '_asyncio_future_blocking', None)
            if blocking is not None:
                # Yielded Future must come from Future.__iter__().
                if futures._get_loop(result) is not self._loop:
                    new_exc = RuntimeError(
                        f'Task {self!r} got Future '
                        f'{result!r} attached to a different loop')
                    self._loop.call_soon(
                        self.__step, new_exc, context=self._context)
                elif blocking:
                    if result is self:
                        new_exc = RuntimeError(
                            f'Task cannot await on itself: {self!r}')
                        self._loop.call_soon(
                            self.__step, new_exc, context=self._context)
                    else:
                        result._asyncio_future_blocking = False
                        result.add_done_callback(
                            self.__wakeup, context=self._context)
                        self._fut_waiter = result
                        if self._must_cancel:
                            if self._fut_waiter.cancel(
                                    msg=self._cancel_message):
                                self._must_cancel = False
                else:
                    new_exc = RuntimeError(
                        f'yield was used instead of yield from '
                        f'in task {self!r} with {result!r}')
                    self._loop.call_soon(
                        self.__step, new_exc, context=self._context)

            elif result is None:
                # Bare yield relinquishes control for one event loop iteration.
                self._loop.call_soon(self.__step, context=self._context)

Lib/asyncio/tasks.py:323-357 — inside Task.__step_run_and_handle_result(). Two further branches follow, for a yielded generator and for anything else; both raise.

Read it as a three-valued signal

The attribute is doing three jobs at once, and the design only becomes legible when you stop reading it as a boolean:

getattr(result, '_asyncio_future_blocking', None) and what the Task does about it.
Value Meaning The Task's response
None — absent, or explicitly None Not a Future at all. Fall through: a bare yield re-schedules the step; a generator or anything else raises.
False Is a Future, but it was yielded rather than awaited. RuntimeError('yield was used instead of yield from …')
True Is a Future and it suspended properly. Clear the flag, subscribe __wakeup, record it in _fut_waiter, return.

The None case is a deliberate opt-out

Python 
def isfuture(obj):
    """Check for a Future.

    This returns True when obj is a Future instance or is advertising
    itself as duck-type compatible by setting _asyncio_future_blocking.
    See comment in Future for more details.
    """
    return (hasattr(obj.__class__, '_asyncio_future_blocking') and
            obj._asyncio_future_blocking is not None)

Lib/asyncio/base_futures.py:13-21 — isfuture(). The documentation for asyncio.isfuture describes a weaker test than this one performs — see lesson 15.

The False case catches a classic mistake

yield fut inside a coroutine hands the Future to the Task without going through Future.__await__, so the flag was never set to True. The Task refuses rather than mis-scheduling.

The flag is a one-shot token

__await__ mints it — self._asyncio_future_blocking = True, at futures.py:285. __step burns it immediately — result._asyncio_future_blocking = False, at tasks.py:340, before doing anything else with the Future. A second yield of the same Future without a second __await__ is rejected, because the token has already been spent.

And the other end of the same token is checked back in __await__:

Python 
        if not self.done():
            raise RuntimeError("await wasn't used with future")

Lib/asyncio/futures.py:287-288. If control returns to __await__ and the Future is still pending, somebody resumed the coroutine without resolving it — the Task's side of the contract was broken.

The C implementation encodes the same check as a bitfield read:

C 
    if (fut->fut_state == STATE_PENDING) {
        if (!fut->fut_blocking) {
            fut->fut_blocking = 1;
            *result = Py_NewRef(fut);
            return PYGEN_NEXT;
        }
        PyErr_SetString(PyExc_RuntimeError,
                        "await wasn't used with future");
        return PYGEN_ERROR;
    }

Why an attribute, of all things

This is the part worth understanding rather than memorising. The whole protocol is [impl detail] — no PEP specifies the attribute, and the only place it surfaces in the documentation is the definition of asyncio.isfuture. But PEP 3156 describes the layering that forced it:

Read that as a constraint and the design becomes forced. The scheduler may use only call_soon, create_future and time. So when a coroutine yields an object, the Task cannot ask the loop “is this a Future of yours?” — there is no such public method, and adding one would break the promise that third-party loops work unchanged. The Task has to interrogate the yielded object itself.

A duck-typed attribute is the only tool available. Not isinstance, because that would exclude third-party Future-likes. Not a method call, because calling an arbitrary object's method during scheduling is a liability. An attribute read, with a three-valued convention, is what is left.

Check yourself

A coroutine does yield fut instead of await fut. What does the Task do?

The flag is False, because only Future.__await__ sets it to True. That is the middle row of the table: “is a Future, yielded wrongly”, answered with RuntimeError('yield was used instead of yield from …') scheduled via call_soon(self.__step, new_exc). Note that even the error is delivered through the ready queue rather than raised inline.

Check yourself

Why does the Task inspect an attribute rather than ask the loop whether the object is one of its Futures?

PEP 3156 makes the scheduler's use of the loop's public interface a design promise, so that third-party loops work without modification. There is no public “is this mine?” method and adding one would break that promise, so the Task must interrogate the object. Speed is a real consideration in the C path, but it is a consequence rather than the reason.

Where this is going

You now have both halves: a callback machine, and the handshake that hands a suspended coroutine to it. Lesson 8 puts them together and follows a single await all the way down to epoll_wait and back — counting, on the way, how many loop iterations the trip actually costs.

The three-valued table is the thing to keep. It is reproduced, with the response each value provokes, under the _asyncio_future_blocking signal in the _run_once reference.

Read next, from the source

Lib/asyncio/futures.py, the Future class header at tag v3.13.11 — the docstring, the state constants and the _asyncio_future_blocking comment in their original context. Ninety lines, and it is the closest thing asyncio has to a specification of its own core object.

Your agent is your teacher. The best question here is a construction one: “write me the smallest class that a Task will happily await, without inheriting from Future.” Building one, and then breaking it by setting the attribute to None, is the fastest way to make this protocol permanent.
