Lesson 0009

Who owns what

Three objects took part in the round trip. Drawing the boundaries between them — and finding the single attribute that makes a Task more than a Future — is what turns the trace into a model you can reason with.

The loop, the Future and the Task each know a strikingly small amount about the others. That separation is not tidiness; it is what lets a third-party loop work, what lets half of this be reimplemented in C, and what makes cancellation as complicated as it is.

The three-way split

What each object owns, and — more usefully — what it does not.
Owns Does not own
BaseEventLoop _ready, _scheduled, the selector, the clock, the thread identity, the exception handler, the executor. Calls callbacks. Anything about coroutines. It has never heard of await.
Future One result-or-exception slot, a state enum, a list of done-callbacks, and a reference to its loop. Turns set_result into loop.call_soon. Any knowledge of who is waiting, or why.
Task A coroutine object, a contextvars.Context, cancellation bookkeeping (_must_cancel, _num_cancels_requested, _cancel_message), and _fut_waiter. Drives coro.send / coro.throw. The ready queue, the selector, time.

A Task is a Future, by inheritance, and the class statement says why with unusual candour:

Python 
class Task(futures._PyFuture):  # Inherit Python Task implementation
                                # from a Python Future implementation.

Lib/asyncio/tasks.py:71-72 — the class statement. The _PyFuture spelling matters, and lesson 10 explains it.

The Task's own state machine, in its own words

Task publishes its invariant as a comment. It is the precise contract between all three parties, and it is worth reading slowly:

Python 
    # An important invariant maintained while a Task not done:
    # _fut_waiter is either None or a Future.  The Future
    # can be either done() or not done().
    # The task can be in any of 3 states:
    #
    # - 1: _fut_waiter is not None and not _fut_waiter.done():
    #      __step() is *not* scheduled and the Task is waiting for _fut_waiter.
    # - 2: (_fut_waiter is None or _fut_waiter.done()) and __step() is scheduled:
    #       the Task is waiting for __step() to be executed.
    # - 3:  _fut_waiter is None and __step() is *not* scheduled:
    #       the Task is currently executing (in __step()).
    #
    # * In state 1, one of the callbacks of __fut_waiter must be __wakeup().
    # * The transition from 1 to 2 happens when _fut_waiter becomes done(),
    #   as it schedules __wakeup() to be called (which calls __step() so
    #   we way that __step() is scheduled).
    # * It transitions from 2 to 3 when __step() is executed, and it clears
    #   _fut_waiter to None.

Lib/asyncio/tasks.py:76-93 — the Task state invariant. [impl detail] — nothing in the documentation describes these states, and the typo in the last bullet is in the source.

Map that onto lesson 8 and the trip reads as three transitions: the task was in state 3 while executing, moved to state 1 when it recorded _fut_waiter and returned, moved to state 2 when set_result scheduled __wakeup, and returned to state 3 when __step ran and cleared _fut_waiter.

_fut_waiter exists for exactly one reason

It is the only structural difference between a Task and a plain Future, and it exists because cancellation has to propagate inward:

Python 
        if self._fut_waiter is not None:
            if self._fut_waiter.cancel(msg=msg):
                # Leave self._fut_waiter; it may be a Task that
                # catches and ignores the cancellation so we may have
                # to cancel it again later.
                return True
        # It must be the case that self.__step is already scheduled.
        self._must_cancel = True
        self._cancel_message = msg
        return True

Lib/asyncio/tasks.py:229-238 — Task.cancel().

What task.cancel() does depends on which state the task is in.
State Situation What cancel() does
1 Blocked on a pending Future. Cancels that Future. Resolving it schedules __wakeup, which raises CancelledError into the coroutine.
2 or 3 Scheduled to step, or currently stepping. There is nothing to cancel. Sets _must_cancel = True. The next __step converts it into a throw (tasks.py:285-288).
Why cancellation is never immediate

In neither case does cancel() raise anything at the point of call. It either cancels an inner Future — whose resolution goes through call_soon, costing an iteration — or it sets a flag for the next step. task.cancel() is a request, delivered through the ready queue like everything else in this system. That is why the method returns a boolean and why catching CancelledError and continuing is possible at all.

Lib/asyncio/tasks.py:223-228 — Task.cancel(). The linked discussion is PR #31394, and reading it is the best available evidence of how hard this corner of the design is.

Two things in six lines. Commented-out code kept in the tree because removing it would lose the argument, and “also remember that this is duplicated in _asynciomodule.c” — the parity requirement showing through in a source comment. That is lesson 10.

What the loop refuses to know

Worth restating now that the Task is in view. Everything in the left-hand column of the ownership table is available to the Task only through call_soon, create_future and time. The Task never touches _ready, never looks at _scheduled, never sees the selector. It is a state machine that drives a coroutine and posts messages to a queue it cannot read.

That restriction is the PEP 3156 clause quoted in lesson 7, and holding both in mind at once is what makes the whole design click: the Task is deliberately a client of the loop rather than a part of it, and every awkwardness in this lesson — the three-valued flag, the state invariant, the two-path cancel — is the cost of that.

Check yourself

What is the only structural difference between a Task and the Future it inherits from?

_fut_waiter, and it exists so that cancelling a Task can reach the Future it is blocked on. A plain Future already has a loop reference and a callback list; a Task never touches the selector at all. Coroutine, context and cancel bookkeeping are also Task-only, but _fut_waiter is the one that changes the object's shape in the state machine.

Check yourself

A task is in state 2 — its __step is already scheduled — and you call task.cancel(). What happens?

There is no Future to cancel, so cancel() sets _must_cancel = True and returns True. When __step runs it converts that flag into a CancelledError thrown into the coroutine (tasks.py:285-288). Nothing is removed from _ready — cancellation in this system is always a flag read later, never a removal.

Where this is going

Half of what you have just read does not run as Python at all. The Task and Future in your process are C objects, swapped in at import time — while the loop underneath them is not, and cannot be. Lesson 10 is about that division, and about how much less it is worth than you would guess.

The three-state invariant is the one thing here worth being able to recite. It is stated on its own, with the source comment it comes from, under the Task's three states in the _run_once reference.

Read next, from the source

Lib/asyncio/tasks.py, lines 198–296 at tag v3.13.11 — cancel, cancelling, uncancel, __eager_start and __step in one block. It is a hundred lines and it is the hardest hundred lines in asyncio; reading it now, with the three states in hand, is much easier than reading it cold.

Your agent is your teacher. A good exercise to ask for: “given a task blocked in await asyncio.sleep(10), walk the objects from task.cancel() to the CancelledError appearing inside the coroutine, naming each one.” There are five hops and every one of them has appeared in a lesson.

On spacing

Before lesson 10, try to write the three-row ownership table from memory — and in particular the right-hand column, which is the one that does the work. Knowing that the loop has never heard of await is worth more than knowing that it owns a deque.
