Lesson 0001

Four lines, two queues

The mission is to reason about asyncio from the machinery rather than from the tutorial. This lesson establishes how small the machinery actually is — the whole event loop is a while statement, and the whole of its scheduling state is two attributes.

Before anything about coroutines, futures or await, it is worth seeing the loop with nothing on top of it. It is much smaller than its reputation, and almost every surprising thing asyncio does in production is a consequence of the two data structures introduced below.

The loop, in full

Here is run_forever. Not a summary of it — the method.

Python 
    def run_forever(self):
        """Run until stop() is called."""
        self._run_forever_setup()
        try:
            while True:
                self._run_once()
                if self._stopping:
                    break
        finally:
            self._run_forever_cleanup()

Lib/asyncio/base_events.py:678-687 — BaseEventLoop.run_forever(), CPython tag v3.13.11. Every line citation in this topic is against that tag.

That is the whole event loop. Everything else in asyncio — tasks, futures, transports, streams, task groups, timeouts — is scaffolding around _run_once(), which lesson 2 opens up.

Read the while carefully

The _stopping check happens after _run_once() returns. So the iteration in progress always finishes: the poll it already performed, the events it already collected, and the entire batch of callbacks it already committed to. There is no mechanism anywhere in asyncio for abandoning an iteration part-way.

stop() does not stop anything

Python 
    def stop(self):
        """Stop running the event loop.

        Every callback already scheduled will still run.  This simply informs
        run_forever to stop looping after a complete iteration.
        """
        self._stopping = True

Lib/asyncio/base_events.py:727-733 — BaseEventLoop.stop().

One assignment. It sets a flag and returns; it does not interrupt the loop, does not wake it, and does not cancel anything. That last point matters enormously later — lesson 13 shows CPython's own SIGINT handler working around it — but for now the useful thing is the docstring's promise, which is repeated in the reference documentation as a guarantee:

“The current batch” is a precise thing with a name in the source, and lesson 3 is entirely about it.

Claiming the thread

_run_forever_setup() is where the loop takes ownership of the thread it is about to run on:

            finalizer=self._asyncgen_finalizer_hook

Lib/asyncio/base_events.py:649-660 — BaseEventLoop._run_forever_setup().

self._thread_id is set here and cleared in _run_forever_cleanup(). It is also, in its entirety, the implementation of is_running():

Python 
    def is_running(self):
        """Returns True if the event loop is running."""
        return (self._thread_id is not None)

Lib/asyncio/base_events.py:768-770 — BaseEventLoop.is_running().

“Is this loop running” and “which thread owns this loop” are the same question, answered by the same attribute. Keep that in mind for lesson 13: the debug-mode thread check has to return silently when _thread_id is None, because at that point there is no correct thread to compare against.

Why the setup is a separate method at all

_run_forever_setup and _run_forever_cleanup were split out of run_forever in 3.13 so that a subclass integrating a GUI event loop can reuse the setup without reusing the while True. The docstring at base_events.py:645-647 says so explicitly. [impl detail] — lesson 14 dates it.

The entire scheduling state

Now the part worth memorising. Everything the loop knows about what to do next is two attributes, both initialised in the constructor:

Python 
        self._timer_cancelled_count = 0
        self._closed = False
        self._stopping = False
        self._ready = collections.deque()
        self._scheduled = []

Lib/asyncio/base_events.py:420-424 — BaseEventLoop.__init__().

The loop's two queues, and nothing else.
Attribute Structure Holds Discipline
_ready collections.deque Handle objects due now FIFO. call_soon appends on the right, the drain pops from the left.
_scheduled A plain list, used as a min-heap via heapq TimerHandle objects with absolute deadlines Ordered by fire time. The head is always the next timer to come due.

Every single thing the loop can be asked to do eventually turns into put a Handle in _ready or push a TimerHandle onto _scheduled. There is no third queue.

I/O readiness looks like a third source, and it is — but it is converted into the first. When a socket becomes readable, nothing runs; a Handle is appended to _ready and the loop carries on. Lesson 5 is that conversion, and it is twelve lines long.

The sentence to carry forward

The event loop has no idea what a coroutine is. It schedules callbacks and it waits on file descriptors. Everything you think of as “asyncio” — tasks advancing, await resuming, timeouts firing — is built out of those two operations by code that only ever touches the loop's public interface. That constraint is written down in PEP 3156, and lesson 7 shows the strange piece of design it forced.

Check yourself

What does BaseEventLoop.stop() do in CPython 3.13.11?

self._stopping = True is the entire body. It does not cancel, does not wake the selector, and does not close anything — run_forever notices the flag only after the current iteration has finished. The queues are cleared by close(), which refuses to run while the loop is running.

Check yourself

The loop's complete scheduling state is which two attributes?

A FIFO deque of things due now and a heapq min-heap of things due later. The selector is real, but it is the multiplexer rather than scheduling state — its output is converted into _ready entries before anything runs. There is no task registry on the loop at all; the one that exists is module-level and shared, which lesson 13 returns to.

Where this is going

You now know the loop is a while statement over _run_once(), and that its state is a deque and a heap. Lesson 2 opens _run_once() and walks its six steps, one of which — exactly one — can block.

The names introduced here — _ready, _scheduled, Handle — are used with these exact meanings for the rest of the topic. The glossary holds them, each with the source line it comes from and the misreading it invites.

Read next, from the source

Lib/asyncio/base_events.py, lines 620–790 at tag v3.13.11 — the run/stop/close block in one sitting. It is under two hundred lines and it is the whole lifecycle. Read it before lesson 2 and the six steps will land as a refinement of something you have already seen rather than as new material.

Your agent is your teacher. If “the loop has no idea what a coroutine is” sounds wrong — it certainly runs your coroutines — say so. That objection is exactly right in spirit and exactly wrong in mechanism, and taking it apart now will make lesson 7 much easier.

On spacing

The goal is retention in a year, not comprehension today, and retention is built by recalling things once you have started to forget them. Before opening lesson 2, try to write out run_forever from memory. It is ten lines; getting seven of them right is the point, not getting ten.
