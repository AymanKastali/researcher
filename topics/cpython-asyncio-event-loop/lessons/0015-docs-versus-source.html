Lesson 0015

Where the docs and the source disagree

The last lesson, and the one that outlasts every version number. Five places where a PEP, a documentation page and the 3.13.11 source contradict each other — each argued in full, each decided, and the deciding turned into a method.

Fourteen lessons have carried two markers, [guaranteed] and [impl detail], without ever making the distinction the object of study. This lesson does. The facts above will change; how to check them will not.

The three grades, and their standing

What each kind of source is the authority for.
Source Authority for Not authority for
A PEP What was intended and promised at the time it was written. What today's code does. PEP 3156 is dated 2012 and marked Status: Final — final means closed, not current.
docs.python.org for 3.13 What a user is entitled to rely on. This is what [guaranteed] means. Completeness. It is a contract, and contracts are deliberately narrower than behaviour.
CPython source at a tag What the implementation actually does, on that version, on that day. What it will do next release, and what any other loop does. This is what [impl detail] means.

When they conflict, the source is the authority for behaviour and the documentation is the authority for entitlement. Those are different questions, and most confusion about internals comes from asking one and answering the other.

Disagreement 1: is call_soon_threadsafe signal-safe?

PEP 3156 says no:

The 3.13 reference says yes:

The source supports the docs. The whole path is _check_closed → events.Handle(...) → contextvars.copy_context() → deque.append → socket.send(b'\0'). You have read every one of those in lesson 13. There is no threading.Lock anywhere in it.

PEP 3156's parenthetical “(since it may use locks)” describes an implementation that no longer exists. And the caveat about the returned handle is the honest residue: Handle.cancel() mutates _cancelled, _callback and _args with no synchronisation, so cancelling from a signal handler a handle the loop is about to run is genuinely racy.

Verdict: prefer the docs and the source. The PEP is normative about intent, not about the 3.13 code.

Disagreement 2: does stop() poll for I/O?

PEP 3156 intends not:

The 3.13 reference says it does:

The source says: it depends on when you call it — and the deciding line is one you already know, from lesson 4:

Python 
        timeout = None
        if self._ready or self._stopping:
            timeout = 0

Lib/asyncio/base_events.py:2001-2003. _stopping sharing a branch with _ready is the whole mechanism.

  • stop() before run_forever(): _stopping is already true when the first _run_once computes its timeout, so it polls with timeout = 0, runs _process_events, runs due timers, drains the ready queue, and exits. Exactly as the docs say, and not “short of polling for I/O”.
  • stop() during the drain: select() for this iteration already happened before the callback ran, and run_forever breaks immediately after _run_once returns. No further poll. As the PEP intends.

The PEP's “not to run any callbacks scheduled in the future” is also slightly strong: if a timer is already due when stop() is called before run_forever, step 5 moves it into _ready and step 6 runs it.

Verdict: the 3.13 docs are precisely right; the PEP describes intent for one of the two cases.

Disagreement 3: what the timer documentation does and does not cover

Not strictly a contradiction, but the sharpest illustration of where the line actually sits. Contrast two pieces of the same method:

Two mechanisms inside _run_once, one documented and one not.
Mechanism Where Documented?
The clock-resolution fudge — timers may run one tick early base_events.py:2018 Yes, twice — Doc/library/asyncio-eventloop.rst:301-305 and 327–331.
The cancelled-timer compaction, its two constants, and the counter staleness base_events.py:1978-1999 Nowhere at all.
The pattern to generalise

The observable timing skew is promised. The entire data-structure hygiene mechanism behind it is not. That is how the line is drawn throughout CPython: documentation commits to what you can observe and must tolerate, and stays silent about how. When you find yourself relying on a mechanism rather than on an observable, you have crossed into [impl detail] whether or not anything said so.

Disagreement 4: isfuture performs a stricter test than it documents

The docs:

The source, from lesson 7:

Python 
    return (hasattr(obj.__class__, '_asyncio_future_blocking') and
            obj._asyncio_future_blocking is not None)

Lib/asyncio/base_futures.py:20-21.

Two conditions the documentation omits:

  1. The attribute must be on the class. An instance-only attribute does not count.
  2. Its value must not be None. This is not an accident — it is the opt-out documented in the source: “The value must also be not-None, to enable a subclass to declare that it is not compatible by setting this to None” (futures.py:62-64).

And CPython's test suite asserts exactly the inverted case:

Python 
    def test_isfuture(self):
        class MyFuture:
            _asyncio_future_blocking = None

            def __init__(self):
                self._asyncio_future_blocking = False

        self.assertFalse(asyncio.isfuture(MyFuture))
        self.assertTrue(asyncio.isfuture(MyFuture()))

Lib/test/test_asyncio/test_futures.py:138-146 — test_isfuture.

A class sets _asyncio_future_blocking = None at class level to opt out, while its instances set False to opt back in. Following the documentation literally would get both of those backwards.

Verdict: prefer the source. The documented rule is a simplification that is wrong at the edges — and the edges are the whole reason the attribute is three-valued.

Disagreement 5: a What's New entry that outran the code

What's New in 3.13 says three methods gained **kwargs:

The source at 3.13.11 says one did:

The three signatures, as they actually stand at tag v3.13.11.
Where Signature Has **kwargs?
base_events.py:461 def create_task(self, coro, *, name=None, context=None, **kwargs) Yes
tasks.py:402 def create_task(coro, *, name=None, context=None) No
taskgroups.py:181 def create_task(self, coro, *, name=None, context=None) No

The two reference pages agree with the source, not with What's New: Doc/library/asyncio-task.rst:241 and :333 both document the plain signature, and only Doc/library/asyncio-eventloop.rst:370 shows the **kwargs. For completeness, the change is a patch-release event rather than a 3.13.0 one: at tag v3.13.0, even BaseEventLoop.create_task has no **kwargs.

Verdict: prefer the source and the reference pages. The What's New entry describes the 3.13.3 state of all three signatures; two of them were reverted in 3.13.4 and the entry was not fully updated.

The general point about release notes

A What's New entry is written once, at feature-freeze, and is rarely revisited during a release's five-year patch life. It is the least reliable of the three grades and it is the one most often quoted second-hand. When a release note and a reference page disagree, the reference page is maintained and the release note is not.

Four questions to ask of any claim

This is what to take away when everything above has gone out of date. Given any statement about how asyncio behaves:

  1. Which grade is it? Can it be traced to a PEP, to docs.python.org for a named version, or only to a line of source? If only to source, it is [impl detail] — say so, and expect it to change.
  2. Is it an observable, or a mechanism? Documentation commits to observables. If your claim is about how rather than what, no amount of reading the docs will confirm it.
  3. Does a test pin it? A behaviour that Lib/test/test_asyncio/ asserts is not promised, but it is deliberate, and changing it would break CI. That is a real, if weaker, form of stability — and it is the strongest evidence available for most of lessons 3, 12 and 15.
  4. Which version, and which loop? Every claim in this topic is scoped to CPython 3.13.11 with a selector loop. uvloop replaces the whole of lessons 1–5 and 11–13. ProactorEventLoop replaces lessons 4, 5, 8 and 13. Neither was read.
And the honest fifth question

What could not be verified? The unverified-claims reference lists everything this topic does not know: the _timer_cancelled_count observation that no CPython issue appears to describe, the historical origin of the ntodo idiom, the free-threading claims that were never executed, and the API that turned out not to exist. A page that names its own gaps is more useful than one that does not — and it is the first place to look when something here stops matching what you see.

Check yourself

PEP 3156 and the 3.13 documentation contradict each other. Which do you follow?

A PEP marked Status: Final is closed, not current — it records intent at the time of writing, and PEP 3156 is from 2012. The 3.13 documentation is what you are entitled to rely on, and the source at a tag is what actually happens. Release notes are the least reliable grade, as disagreement 5 shows.

Check yourself

A class sets _asyncio_future_blocking = None at class level. What does asyncio.isfuture say about it?

A class-level None is the documented-in-source opt-out, so the class itself fails the test — but an instance that sets the attribute to False passes, because the hasattr check is on the class and the value check is on the object. test_isfuture asserts exactly this pair, and the published documentation describes neither condition.

The end, and what to keep

Fifteen lessons. The mechanism — six steps, two queues, one blocking call, one three-valued attribute — is durable enough to survive several releases, as lesson 14 showed. The line numbers are not.

What is worth revisiting lives in the five reference documents rather than here: the run-once reference, the thread-safety table, the version ledger, the unverified claims, and the glossary. Lessons are read once; those are the pages designed to be come back to.

Read next, from the source

uvloop — not documentation, and the sharpest available test of whether this topic landed. It replaces exactly the layer you have spent fifteen lessons inside. Reading its loop implementation against base_events.py will tell you, faster than any quiz, which of these lessons describe asyncio and which describe CPython's event loop.

Your agent is your teacher, and this is where that matters most. The best use of it now is adversarial: give it a claim about asyncio you half-remember from somewhere and ask it to grade the claim rather than answer it. Which source would settle this? Does one exist? If the answer is “only the source”, you have found an [impl detail], and you now know what that costs.

On spacing

The most valuable thing you can do a week from now is not re-read these pages. Try instead to write out the six steps, the two differences between call_soon and call_soon_threadsafe, and the three-valued table from lesson 7 — on paper, from memory, badly. Then come back and check. The gap between what you produce and what is here is the only reliable measure of what has actually stuck.
