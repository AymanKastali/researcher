Lesson 0002

Inside a leaf page

Pricing the internal-identity job means counting bytes in a B-tree leaf. This lesson builds that count from quoted constants — and then checks it against a real page the manual prints, because a model you cannot validate is folklore with arithmetic on top.

Three figures appear in nearly every blog post on this subject: that a uuid is 16 bytes, that an index entry cannot exceed 2704 bytes, and that ascending inserts get special treatment. None of the three is in the PostgreSQL manual. Knowing where they actually come from is the first real skill in this topic.

Three grades of evidence

From here on, every number on every page of this topic is one of three things, and the page always says which:

The grading used throughout this topic.
Grade Where it comes from How much weight it carries
Documented guarantee The manual, an RFC, a vendor specification. May be stated flatly. The project has committed to it and will announce a change.
Source-code fact A REL_18_STABLE header, README, or commit, used only where the manual is silent. Weaker. It is true today and could change without a release note. A #define is not a promise.
Derived arithmetic Computed from quoted constants. Only as good as its inputs and its assumptions, both of which must be stated. Checkable, and checked below.

The manual itself authorises the second grade, and points at exactly where to look:

Note what is missing

The manual calls a uuid a “128-bit quantity” and never gives a byte count. It says an index entry “cannot exceed approximately one-third of a page” and never says 2704. Both of those numbers are real, but they are grade two.

The same three facts, from source

C 
/* src/include/utils/uuid.h */
#define UUID_LEN 16

/* src/include/access/itup.h — IndexTupleData */
ItemPointerData  t_tid;      /* 6 bytes */
unsigned short   t_info;     /* 2 bytes */
                             /* = 8 bytes of index tuple header */

/* src/include/access/nbtree.h */
BTMaxItemSize    /* evaluates to 2704 at 8 kB pages */

Read from REL_18_STABLE. Grade two: true today, and able to change without a release note.

One more platform fact, which the manual mentions only obliquely. MAXALIGN is 8 on 64-bit platforms; the manual never states the value, saying only that t_hoff “must always be a multiple of the MAXALIGN distance for the platform”. Treat it as a platform fact rather than a documented constant, and state the assumption every time you use it — as this lesson does.

The arithmetic

Grade three from here to the end of the section

Everything below is computed, not quoted. Assumptions: 8 kB pages, MAXALIGN 8, a single-column NOT NULL key, no INCLUDE columns, ASCII text.

A B-tree leaf page starts with 8192 bytes, loses the 24-byte page header, and loses 16 more to BTPageOpaqueData at the end of the page. That leaves 8152 bytes to share between line pointers and entries.

Python Written for this lesson 
PAGE = 8192
USABLE = PAGE - 24 - 16      # page header, BTPageOpaqueData  -> 8152
TUPLE_HEADER = 8             # IndexTupleData, from itup.h
LINE_POINTER = 4             # ItemIdData, from the manual
MAXALIGN = 8                 # 64-bit platform assumption


def per_entry(key_bytes: int) -> int:
    """Bytes one index entry costs, including its line pointer."""
    body = TUPLE_HEADER + key_bytes
    padded = -(-body // MAXALIGN) * MAXALIGN      # round up to MAXALIGN
    return padded + LINE_POINTER


def entries_per_leaf(key_bytes: int, fillfactor: int = 100) -> int:
    return (USABLE * fillfactor // 100) // per_entry(key_bytes)


for name, width in [("bigint", 8), ("uuid", 16), ("text, 26 chars", 1 + 26)]:
    print(name, per_entry(width), entries_per_leaf(width),
          entries_per_leaf(width, 90))

Checking the model against two real pages

This is the part that separates the arithmetic above from the arithmetic in a blog post. The pageinspect documentation prints real output from two different real indexes, and the model predicts both to the byte.

An oid is 4 bytes. So 8 + 4 = 12, rounded up to MAXALIGN 16 — the same item size as a bigint, and exactly the avg_item_size the manual prints for both. Now run the model forward:

Python Written for this lesson 
>>> per_entry(4)              # oid: 8 + 4 = 12 -> MAXALIGN 16, + 4 line ptr
20

# pg_proc_oid_index, a full page: live_items 367
>>> USABLE - 367 * 20         # 8152 - 7340
812
# PageGetFreeSpace withholds one further line pointer, so 812 - 4 = 808,
# which is the free_size the manual prints. Exact.

# pg_cast_oid_index, a page barely half full: live_items 224
>>> USABLE - 224 * 20         # 8152 - 4480
3672
# 3672 - 4 = 3668, again exactly what the manual prints.

>>> 367 / entries_per_leaf(4)  # how full is the pg_proc page?
0.9017...                      # the documented fillfactor, arriving on its own
Why this check is worth the space

The free-space prediction lands to the byte on two different indexes — one packed at ~90%, one barely half full at ~55% — so the model is not fitted to a single lucky case. And on the packed page the documented fillfactor of 90 falls out on its own, to within a fifth of a percent, from numbers that were never used to build the model.

That is what licenses the uuid and text rows, which no manual page prints. An unvalidated model of this kind would be exactly as trustworthy as the folklore it is meant to replace.

The headline consequence, stated as derived:

A uuid primary-key index needs roughly 1.4× the leaf pages of a bigint one; a 26-character text key roughly 2.2×.

Check yourself

Where does the claim “a uuid is 16 bytes in PostgreSQL” actually come from?

#define UUID_LEN 16 lives in src/include/utils/uuid.h. The manual's §8.12 says only “128-bit quantity” and never converts it to bytes — which is a real distinction, because 128 bits is a fact about the format while 16 bytes is a fact about this implementation's storage. RFC 9562 specifies the format, not PostgreSQL's layout.

One trap on text keys, pre-empted by the manual

So varchar(26) buys nothing over text. If you store an identifier as a string — and lessons 8 and 9 will argue you usually should not — store it as text with a CHECK constraint, and know from the table above that you have roughly halved how many keys fit in a page.

Check yourself

Why does an 8-byte bigint key cost 20 bytes per index entry rather than 8?

Each entry carries an 8-byte IndexTupleData header — a 6-byte heap pointer and 2 bytes of flags — giving 16 after MAXALIGN, and each item on a page also needs a 4-byte ItemIdData line pointer in the page's slot array. The page header is 24 bytes and is paid once per page, not per entry; nothing here is compressed or duplicated.

Where this is going

A 1.4× difference in index size sounds like it should show up as a deeper tree and slower lookups. Lesson 3 shows that it does not — depth barely moves — and that the number everyone is reaching for when they say “UUIDs are slow” is a completely different one, produced by a mechanism that has nothing to do with width.

Read next, from the source

PostgreSQL 18 manual, §66.6 “Database Page Layout” — Tables 66.1 and 66.2 are the whole basis of this lesson, and the page is short. Read it with the arithmetic above beside you and confirm that every input came from there. Then open §F.23.3 and find the free_size | 808 line yourself.

Your agent is your teacher. If you have a database to hand, ask for the pageinspect queries that reproduce the manual's output against one of your own indexes — seeing your own numbers land where the model predicts is worth more than reading this lesson twice. Note that pageinspect is superuser-only.

On spacing

Before opening lesson 3, try to reconstruct the 20-byte figure from scratch: page size, what comes off the top, what each entry carries. If you can rebuild it rather than recall it, the rest of the topic will cost you much less effort.
