Lesson 0014

The decision ladder

The payoff. Everything priced in lessons 2 to 13 turns into four rungs and one sentence that survives all of them — but first, a claim this topic has been quietly relying on that turns out not to be documented at all.

Lesson 13 argued that narrow join keys are worth having. It is worth checking whether the documentation supports that, and the honest answer is: not in the form it is usually stated.

Does a wider join key actually cost anything?

The claim, graded

The PostgreSQL documentation makes no claim that join-key width affects join performance. The EXPLAIN page reports row width= estimates but never connects key width to join cost or plan choice. Any “16-byte keys join more slowly than 8-byte keys” assertion is undocumented, and this topic will not make it.

What is documented is a chain you can reason from:

Hash joins build an in-memory table bounded by work_mem × hash_mem_multiplier; exceeding it produces multiple batches, which involve disk. Wider keys make each entry larger, so the bound is reached with fewer rows.

That is a coherent argument and probably true, but it is inference, not documentation — and note its shape: the effect is a step function at the spill threshold, not a smooth tax on every join. A schema well under the threshold pays nothing at all.

The defensible version of the claim

It is lesson 2's, and it needs no claim about join algorithms at all: narrower keys make indexes smaller, so more of the working set fits in shared_buffers. That is a cache-residency argument, it is grounded in quoted constants, and it is the form in which lesson 13's “~28% reduction across every child index” should always be stated.

Check yourself

How should the benefit of narrow foreign keys be argued?

The cache-residency argument rests entirely on quoted constants from lesson 2 and requires no claim the docs do not make. Join speed is undocumented — the plausible version is a step function at the work_mem spill threshold, not a per-row tax. Depth barely moves (lesson 3), and nothing suggests the planner has a preference for narrow columns as such.

What the decoupling buys at the API boundary

Three concrete benefits of separating the two jobs.
Benefit Why it follows
Renumbering becomes possible Merging two databases, resharding, or backfilling from a legacy system can renumber id freely as long as public_id travels with the row. External references — links customers bookmarked, ids in partners' systems, values in your own webhook history — stay valid.
JSON stays safe By lesson 9, a 64-bit integer does not survive JavaScript's 53-bit number type. A uuid serialises as a string and cannot be corrupted this way. If you ever do expose id, serialise it as a string.
Enumeration stops being trivial With lesson 11's caveat firmly attached: this is defence in depth behind an authorisation check, never a substitute for one. RFC 9562 §8 is normative on that point.

If you want TypeID's ergonomics (lesson 9), this is exactly where to add them: public_id stays uuid in the database, and the serialisation layer renders it as order_2x4y6z8a0b1c2d3e4f5g6h7j8k. The prefix is a property of the table, so storing it per row buys nothing.

When not to do this

The pattern earns its cost when identifiers are exposed to parties you do not control, or when the internal id might have to change. Below that threshold it is two columns and a lookup where one column would do — and the discipline cost from lesson 13 is still charged in full.

The ladder

A reasonable default ladder. Climb only as far as your situation requires.
# Situation Choice What you are accepting
1 Single-node application, ids not publicly meaningful. bigint GENERATED ALWAYS AS IDENTITY Narrowest, fastest, simplest. Serialise it as a string. No offline generation, and it leaks order if exposed.
2 Ids appear in URLs or in third parties' hands. Dual-identifier: bigint internal + uuidv7() external Lesson 13's four costs, of which the discipline cost is permanent.
3 Client-side or offline generation is required. A single uuid primary key holding a v7 8 more bytes per row and per child index entry, in exchange for generation without a round trip. For many distributed systems this is simply the right trade.
4 The id is a security-relevant surface. UUIDv4 for the external id Lesson 3's index behaviour on that one index, on RFC 9562 §8's own advice.
What survives every rung

Key on something you control, never update it, and put a unique constraint on anything that must be unique — including the identifier your framework already thinks is unique.

Each clause has a lesson behind it: “something you control” is lesson 10, “never update it” is lesson 5, and “put a unique constraint on it” is lesson 7's warning that an identity column does not guarantee uniqueness on its own.

Check yourself

Your mobile app must create records while offline and sync them later. Which rung applies?

Offline creation means the device must mint the id before any database has seen the row, which no sequence can do at any price (lesson 12). A single uuid primary key holding a v7 pays 8 extra bytes per row and per child index entry and buys exactly that capability. Rung two would not help, since the internal bigint still needs the database; rung four's v4 would additionally forfeit the index locality for no security requirement that was stated.

Read next, from the source

PostgreSQL 18 manual, §14.1 “Using EXPLAIN” — read it looking for a claim about key width, and notice that there is not one. Reading a document for an absence is a genuinely different skill from reading it for a fact, and it is the skill lesson 15 is built around.

Your agent is your teacher. This is the point to bring a real schema. Ask which rung it is on, and — more useful — which rung it was designed for versus which one it is now actually operating at. Systems commonly climb a rung without anyone deciding to.
