Lesson 0003

The rightmost page

This is the hinge of the whole topic. The real difference between a random key and a time-ordered one in PostgreSQL is not the eight extra bytes — it is a special case in the page-split code, and it is not in the manual.

Lesson 2 ended with a uuid index needing about 1.4× the leaf pages of a bigint one. The obvious next thought is that the tree must therefore be deeper and lookups slower. That thought is wrong, and disposing of it properly is what makes room for the fact that actually matters.

Depth barely moves

Tree depth is logarithmic in fan-out. Taking the fan-out figures derived in lesson 2 — about 366, 262 and 166 entries per leaf at fillfactor 90:

Rows bigint uuid text(26)
10⁶ 3 levels 3 3
10⁸ 4 4 4
10¹⁰ 4 5 5

A 28% reduction in fan-out usually buys zero extra levels, and occasionally one — at ten billion rows.

A claim to stop repeating

“UUID keys cost you a tree level” is arithmetic nobody did. Key width is a size problem, not a depth problem.

What does follow from the size difference is cache pressure. The same working set occupies 1.4× the pages, competing for a shared_buffers whose default is “typically 128 megabytes” and whose recommended starting point is “25% of the memory in your system” (§20.4.1). That is a real cost, and it is the honest version of the width argument.

What a page split is

Split a full page down the middle and you get two half-full pages. Do that everywhere, forever, and the tree settles at about 50% density. That is the default behaviour, and it is what a key with no ordering gets.

The special case

The manual's only nod to ordered inserts is a clause buried inside the fillfactor description — easy to read past, and the thread worth pulling:

The mechanism behind that clause is in the source, and it is the single most important quotation in this topic:

C comment 
If the page is the rightmost page on its level, we instead try to
arrange to leave the left split page fillfactor% full.  In this way,
when we are inserting successively increasing keys (consider sequences,
timestamps, etc) we will end up with a tree whose pages are about
fillfactor% full, instead of the 50% full result that we'd get without
this special case.

src/backend/access/nbtree/nbtsplitloc.c, _bt_findsplitloc(), REL_18_STABLE. Grade two: a source-code fact, not a documented guarantee.

And a second, separate optimisation for the same access pattern:

README 
We optimize for a common case of insertion of increasing index key
values by caching the last page to which this backend inserted the last
value, if this page was the rightmost leaf page.  For the next insert,
we can then quickly check if the cached page is still the rightmost leaf
page and also the correct place to hold the current value.  We can avoid
the cost of walking down the tree in such common cases.

src/backend/access/nbtree/README, “Fastpath For Index Insertion”, REL_18_STABLE. Grade two.

The mechanism, in one paragraph

An ordered key — a bigint sequence, UUIDv7, ULID, Snowflake — always inserts at the right edge. Splits there leave the left page ~90% full instead of 50%, so the tree settles at about 90% density, and the target page is cached so the insert skips the descent entirely. A random key — UUIDv4 — inserts everywhere. Those are ordinary 50/50 splits, the tree tends toward 50% density, and every insert touches a different, probably cold, leaf page.

Against a bigint sequence's ~366, a randomly-ordered uuid index at ~145 entries per leaf is the genuine ~2.5× gap — and note where it comes from:

The sentence to remember from this topic

Most of the cost of a random key is the split behaviour, not the eight extra bytes. Width takes you from 366 to 262. Insert ordering takes you from 262 to 145. This is precisely why UUIDv7 recovers most of the difference without narrowing the column by a single byte.

The README makes the same point about unique indexes directly:

README 
a primary key on an identity column will usually only have leaf page
splits caused by the insertion of new logical rows within the rightmost
leaf page.  If there is a split of a non-rightmost leaf page, then the
split must have been triggered by inserts associated with UPDATEs of
existing logical rows.

src/backend/access/nbtree/README, “Deduplication in unique indexes”, REL_18_STABLE. Grade two.

Check yourself

A UUIDv4 primary-key index holds roughly 40% as many entries per leaf page as a bigint one. What accounts for most of that gap?

Width takes you from ~366 entries to ~262 — real, but the smaller half. Random insert positions mean ordinary 50/50 splits rather than right-edge splits, taking ~262 down to ~145, which is the larger half. There is no extra tree level at realistic sizes, and the page header is 24 bytes regardless of what the index is on.

Check yourself

Where is the rightmost-page split behaviour documented?

A full-text search of the manual's B-tree page for “fastpath”, “rightmost”, “ascending” and “monotonic” returns zero hits. The manual gestures at the behaviour once, inside the fillfactor description on the CREATE INDEX page, and then sends you to src/backend/access/nbtree/README. So the most important mechanism in this topic is grade-two evidence, and could change without a release note.

Where this is going

You now have the mechanism and the magnitude. The next question is how far the damage spreads: does a random key scatter your rows as well as your index entries?

In InnoDB and SQL Server the answer is yes, and most of the writing on this subject was produced by people who learned it there. Lesson 4 shows why the answer in PostgreSQL is no, and why that one fact invalidates a great deal of imported advice.

Read next, from the source

src/backend/access/nbtree/README, REL_18_STABLE — the manual explicitly sends you here, and the sections “Fastpath For Index Insertion” and “Deduplication in unique indexes” are the two quoted above. It is a long file written for contributors; read those two sections and skim the rest. Seeing how differently it speaks from the manual is itself the lesson in evidence grading.

Your agent is your teacher. The step most worth challenging here is “~50% density” — it is a tendency the split rule produces over many random inserts, not a guarantee, and the source comment states it as the thing being avoided rather than as a measured figure. Ask about what would make the real number differ.

On spacing

This is the lesson to over-learn. Before lesson 4, try to say out loud — without looking — what happens when a rightmost page splits, what happens when any other page splits, and which of those two facts explains most of the gap between a v4 and a v7.
