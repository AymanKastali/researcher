Lesson 0010

Natural keys and the issuing authority

The last candidate, and the only one whose failure mode is scheduled by somebody else. The synthesis at the end of this lesson is the one piece of advice in the topic that survives every other choice you make.

A natural key uses data that already means something — an email address, an ISBN, a country code, an order number from the warehouse system. The appeal is genuine, and it is worth stating properly before taking it apart.

The case for

  • One less column. No surrogate to carry, generate, or explain.
  • No join to read the meaningful value. The child row already contains the email address, the ISBN, the country code.
  • The uniqueness constraint expresses a real business rule. “Two users cannot share an email address” is a fact about the domain, and putting it in the schema is correct.

Recall from lesson 1 that Codd's own worked example of a primary key — part number — is a natural key. This is not a fringe position, and it is not what the relational model argues against.

It is the strongest lock PostgreSQL has: nothing else may read or write the table, not even a SELECT. So the bill for a natural key's format change is a full rewrite of the table and all its indexes, needing up to double the disk space, with the table completely unavailable throughout — repeated for every table that references it. And the date was chosen by the ISBN agency.

Check yourself

What makes a natural key a structural risk rather than a style preference?

Width and insert ordering are real costs and are usually modest. The structural risk is that the issuing authority can widen or restructure the key on a date it chooses, and your migration — a full table and index rewrite under ACCESS EXCLUSIVE, propagated to every referencing table — is then scheduled by them rather than by you. The ISBN change of 1 January 2007 is the documented case.

The synthesis

Not “never use natural keys”

A natural key's uniqueness is a genuine business rule and belongs in the schema — as a UNIQUE constraint, which by lesson 1 is “functionally almost the same thing” as a primary key.

What it should not be is the target of your foreign keys. Declare UNIQUE (email); key on something you control.

SQL Written for this lesson 
CREATE TABLE users (
    id     bigint GENERATED ALWAYS AS IDENTITY PRIMARY KEY,
    email  text NOT NULL,

    -- The business rule, enforced. Not the foreign-key target.
    CONSTRAINT users_email_key UNIQUE (email)
);

CREATE TABLE orders (
    id       bigint GENERATED ALWAYS AS IDENTITY PRIMARY KEY,
    user_id  bigint NOT NULL REFERENCES users (id)
    -- Changing an email now rewrites exactly one row.
);

Because id is GENERATED ALWAYS it can never be updated at all (lesson 7), so the ON UPDATE cascade scan the docs describe simply cannot occur for it. The failure mode is not mitigated — it is structurally excluded.

One PostgreSQL-specific subtlety

If you do put a UNIQUE constraint on nullable natural-key data, know that by default “two null values are not considered equal”, so a nullable column permits any number of rows that are null in it. Check yourself

Where does a natural key's uniqueness rule belong in the schema?

The rule is real and the database should enforce it, so a UNIQUE constraint is right — and by lesson 1 that is “functionally almost the same thing” as a primary key, carrying the same B-tree index. What you avoid is making it the foreign-key target, because that is what turns one changed value into a cascade across every child table. A CHECK cannot express uniqueness at all.

Where this is going

PostgreSQL 18 manual, ALTER TABLE — specifically the “Notes” section and the table of lock levels. It is dry, and it is the document that tells you what a schema change will actually cost you in downtime. Reading it once, properly, changes how you design tables.

Your agent is your teacher. Worth raising: composite natural keys, which this lesson does not cover. A two- or three-column key inherits every problem above and adds width to every child index, but there are genuine cases — join tables, time-series partitions — where it is right. Ask for the trade-off in your own schema rather than generalising from here.
