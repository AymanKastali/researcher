Lesson 0012

Collisions, and generating away from the database

Two things at once: a question every primary source deliberately refuses to answer, and the capability that is the honest reason to accept a 128-bit key at all. The refusal is as instructive as the capability.

“A billion a second for a century” is the figure everyone reaches for when asked about UUID collisions. It is worth knowing where that number is not from.

What the specifications refuse to say

Neither specification states a numeric collision probability

RFC 9562 never mentions the birthday problem — a full-text search of the canonical text returns zero hits for “birthday”, and “probability” appears four times, never attached to a figure. The ULID spec gives no probability either.

Why the refusal is the right call

A collision probability is meaningless without a generation rate, a time horizon, a number of generators, and — above all — an impact class. The RFC substitutes a question you can actually answer (what does a collision cost me?) for one you cannot answer generically. That is a deliberate editorial choice, not an oversight, and it is the same instinct that keeps benchmark numbers out of this whole topic.

What can be stated honestly

The bit counts are quoted facts, so the entropy each format carries can be stated flatly:

Quoted, not derived.
Format Bits not determined by time or format Source
UUIDv4 122, once RFC 9562 §5.4: “122 bits total”
UUIDv7 74, per millisecond RFC 9562 §5.7: “the remaining 74 bits”
ULID 80, per millisecond ULID spec: “Randomness — 80 bits”

The per-millisecond framing is the structural reason a v7 can be safe with fewer random bits than a v4: the timestamp partitions the space, so only ids born in the same millisecond can possibly collide. ULID advertises this as “1.21e+24 unique ULIDs per millisecond”, which is 2⁸⁰.

The practical mitigation is the same regardless, and it is lesson 7's:

The only thing that actually guarantees uniqueness

A unique index. Not the format, not the bit count, not the RNG. And recall the manual's warning from lesson 7 — even an identity column does not give you uniqueness: “a PRIMARY KEY or UNIQUE constraint is needed for that.”

Check yourself

Why can a UUIDv7 be safe with 74 random bits when a UUIDv4 uses 122?

Two v7 values born in different milliseconds cannot collide at all, because their leading 48 bits differ. So the 74 bits only have to separate values generated within the same millisecond, where a v4's 122 bits have to separate every value ever generated. Version and variant bits are fixed and carry no entropy, and nothing checks the index before the value is returned.

The capability a sequence cannot offer

This is the thing a bigint identity column cannot do at any price, and it is the honest reason to reach for a 128-bit id. A client, a mobile app offline, or three services writing to different shards can each mint an identifier with no round trip and no coordination. nextval() cannot: it is a call into one database.

Two concrete consequences worth designing around:

What offline generation actually buys.
Capability How it works
Retry without duplication If the client generates the id, a retried INSERT hits a unique violation instead of creating a second row. The identifier is the deduplication mechanism, because the client chose it before the first attempt.
Batch construction An object graph — order, line items, shipment — can be built entirely in memory with all foreign keys already wired, then inserted in one round trip, because the parent id existed before the parent row did.

The RFC's guidance is narrower than folklore

That last sentence is a trust statement, not a technical one

If browsers or mobile devices mint your ids, you have accepted every one of those devices' RNGs into your uniqueness argument. And since the value arrives over the wire, you must treat it as hostile input and constrain it exactly as you would any other client-supplied field — lesson 11's fork caveat is one way this goes wrong, and a malicious client simply sending a chosen value is another.

Against which the RFC sets a preference cutting the other way for a single database, quoted in lesson 8: “Applications using a monolithic database may find using database-generated UUIDs […] provides the best UUID monotonicity.” And per lesson 6, even server-side generation in PostgreSQL orders strictly only within one backend.

Check yourself

What does RFC 9562 §6.4 require of an application whose clients generate their own UUIDs?

“Distributed applications generating UUIDs at a variety of hosts MUST be willing to rely on the random number source at all hosts” — a trust statement about machines you may not control. Central registries are explicitly NOT RECOMMENDED, an embedded node id is only a SHOULD for the case where extra collision resistance is needed, and rejecting values seen before is duplicate detection rather than a uniqueness argument — it tells you nothing about the values you have not seen.

Where this is going

Every candidate and every criterion is now on the table, and lesson 1's problem is still unsolved: one column, two jobs, and no way to satisfy both.

Read next, from the source

RFC 9562 §6.4 through §6.9 — five short subsections covering multi-node generation, collision impact, global uniqueness and the CSPRNG requirement. Read them together. The thing to notice is how consistently the document declines to give you a number and instead tells you what question to ask — which is unusual, and deliberate.

Your agent is your teacher. If you want the collision arithmetic anyway — and it is a reasonable thing to want — ask for it explicitly, with the generation rate and horizon stated as inputs. What you must not do is quote the result as though a specification said it.

On spacing

Before lesson 13, try to state the two things offline generation buys you, and the one thing it costs you. The cost is the sentence about trusting every host's RNG.
