Lesson 0013

The dual-identifier pattern

Lesson 1 said the two jobs conflict and you must choose which to sacrifice. This is the pattern that refuses — and unlike most write-ups of it, this lesson prints the bill before recommending anything.

Give the row two identifiers, each doing exactly one of lesson 1's jobs. The idea is not subtle. What is worth the lesson is the set of documented facts that make it work, and the four costs most descriptions leave out.

The pattern

SQL Written for this lesson 
CREATE TABLE orders (
    id          bigint GENERATED ALWAYS AS IDENTITY PRIMARY KEY,
    public_id   uuid   NOT NULL DEFAULT uuidv7(),
    -- ... domain columns ...
    created_at  timestamptz NOT NULL DEFAULT now(),

    CONSTRAINT orders_public_id_key UNIQUE (public_id)
);

CREATE TABLE order_lines (
    id        bigint GENERATED ALWAYS AS IDENTITY PRIMARY KEY,
    order_id  bigint NOT NULL REFERENCES orders (id),
    -- ...
);

CREATE INDEX ON order_lines (order_id);   -- see below; not automatic
The two rules that make it work

id is never serialised. public_id never appears in a foreign key.

Every internal join runs on 8-byte integers with the best possible index behaviour (lesson 3), and every external reference is an opaque 128-bit value revealing only a creation timestamp.

uuidv7() requires PostgreSQL 18. On 13–17 the equivalent is pg_uuidv7's uuid_generate_v7() where your platform allows it (lesson 6), gen_random_uuid() if you would rather have a v4 than a dependency, or application-side generation.

What it costs, stated plainly

This pattern is not free, and most write-ups skip the bill.

Four costs. The last one is the one that actually bites.
Cost Size of it
An extra 16-byte column On every row of the parent table. Real, and small.
An extra unique B-tree index About 28 bytes per entry by lesson 2, and — being on a v7 value — it benefits from the rightmost fastpath, so it settles near 90% density.
An extra lookup on every external request A URL carries public_id; the query needs id. One index probe before the real work starts. The only genuinely negotiable cost, and the section below is about negotiating it.
Two ways to name the same row A permanent invitation to leak the wrong one. This is a discipline cost, it never goes away, and it is the one that actually bites.

The UNIQUE constraint suffices. It is also the exact mistake this whole pattern exists to avoid: it puts 16 bytes in every child row and 16-byte keys in every child index, discarding the benefit and keeping all of the cost. Reference id.

Where the pattern quietly pays off a second time

You will create that index on order_lines (order_id) regardless. Making it 8 bytes wide rather than 16 is a ~28% reduction in its entry size by lesson 2 — replicated across every child table in the schema. In a schema with many many-to-one relationships, this compounds far more than the single extra index on the parent costs.

And note that an ALWAYS identity primary key can never be updated (lesson 7), so the ON UPDATE scan the docs describe simply cannot occur for it. Lesson 10's natural-key failure mode is structurally excluded, not merely avoided.

Check yourself

A colleague writes REFERENCES orders (public_id) because the UNIQUE constraint makes it legal. What is wrong with it?

It is perfectly legal — a unique constraint is enough, as the manual says. The problem is that it defeats the purpose: 16-byte keys land in every child row and every child index, so you pay for the extra column and the extra index on the parent and get none of the narrow-join benefit. The fastpath is unaffected, since a v7 is time-ordered wherever it sits.

Making the extra lookup cheap

The public_id → id resolution can in principle be served entirely from the index, without touching the heap:

SQL Written for this lesson 
CREATE UNIQUE INDEX orders_public_id_idx
    ON orders (public_id) INCLUDE (id);

There are three caveats, all documented, and all worth knowing first.

Why this optimisation is usually premature.
Caveat What it means here
It depends on the visibility map An index-only scan checks the visibility map for each candidate's heap page; if the all-visible bit is not set it must visit the heap anyway. The docs say index-only scans are most beneficial “when a large fraction of heap pages have their all-visible bits set” — i.e. on slowly-changing data. A hot, frequently-updated orders table will not get the benefit reliably.
It disables deduplication on that index Per lesson 5: “INCLUDE indexes can never use deduplication.” A unique index has no logical duplicates, so the direct cost is nil — but you also lose the documented secondary use, absorbing version churn to postpone page splits. On an update-heavy table that is a real trade, not a free win.
It only helps if the query touches nothing else SELECT id FROM orders WHERE public_id = $1 qualifies. SELECT * FROM orders WHERE public_id = $1 does not — and that is what most application code actually issues, in which case the plain UNIQUE (public_id) index is all you need and the INCLUDE buys nothing.
The honest recommendation

Measure before adding it. For most applications a unique index probe on 16 bytes is already fast enough that this optimisation is premature — and the third caveat means the code you actually wrote probably cannot use it anyway.

Check yourself

Why does INCLUDE (id) usually fail to help real application code?

An index-only scan is only possible when the query needs nothing but what the index carries. SELECT id FROM orders WHERE public_id = $1 qualifies; SELECT * does not, and SELECT * is what most code issues. There are two further costs — the visibility-map dependency, and losing deduplication on that index — but this is the one that most often makes the whole thing moot.

Where this is going

You have the pattern and its price. Lesson 14 asks whether the narrow-join benefit is even real — the answer is more careful than you might expect — then covers what the decoupling buys at the API boundary, when not to do any of this, and the ladder that turns the whole topic into a decision.

Read next, from the source

PostgreSQL 18 manual, §5.5.5 “Foreign Keys” — read the whole section, which is short. The paragraph about not auto-creating an index on the referencing side is the one people miss, and missing it is one of the most common real performance faults in production schemas — quite independent of which key type you chose.

Your agent is your teacher. The discipline cost is the one worth discussing concretely: ask how to make leaking id structurally hard in your stack rather than a rule people remember — serialiser-level exclusion, a distinct type, a test that greps responses. A rule that lives only in someone's head is the cost, not the mitigation.

On spacing

Before lesson 14, try to draw the two-table schema from memory, including which column the foreign key references and why, and then name all four costs. The fourth is the one people forget, which is fitting, because it is the one that bites.
