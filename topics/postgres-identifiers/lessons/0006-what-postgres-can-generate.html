Lesson 0006

What PostgreSQL can generate

Half of this decision is availability, not performance. This lesson establishes what the engine can mint natively, when each capability arrived, and — the part most summaries drop — exactly how far the UUIDv7 ordering guarantee extends.

Most advice on this subject was written before PostgreSQL 18, and a good deal of it before 13. Two release notes have quietly retired the arguments behind a generation of blog posts, so the first thing to get straight is what shipped when.

The monotonicity guarantee, read carefully

“Temporally sortable” is doing a lot of work in that note. The commit that added the function is precise about what is actually promised:

The sentence summaries drop

A PostgreSQL backend is one connection's server process. The guarantee does not extend across connections in a pool, across two application instances, or across servers. Two rows inserted in the same millisecond on two different connections have no defined order.

So be precise about what you have:

Two properties routinely conflated into one.
Property What uuidv7() gives you Good enough for
Index locality Millisecond-granular approximate ordering, globally. Inserts land near the right edge. Yes. The B-tree only needs inserts near the right edge, not in perfect sequence (lesson 3).
“Sort by id for creation order” Strict ordering along a single connection only. No. Through a connection pool, same-millisecond rows have no defined order.

The construction is RFC 9562 §6.2 Method 3, “Replace Leftmost Random Bits with Increased Clock Precision”, though the commit message does not name it. The commit cites “RFC 9652”; that is a typo in the commit itself — the uuid type page and the function docs both correctly say RFC 9562.

Check yourself

Your application uses a connection pool. Two rows are inserted in the same millisecond with uuidv7() defaults. What is guaranteed about their relative order?

The counter lives in rand_a and is per backend, so two connections generating inside the same millisecond produce values whose order is decided by random-ish bits rather than by time. This is fine for the index — both still land near the right edge — and not fine for any query that sorts by id expecting creation order. That is the whole distinction, and it is the one the release note's “temporally sortable” obscures.

What the uuid type is actually for

Two things worth extracting

The stated rationale is uniqueness without coordination. It is not unguessability, and it is not security. The project's own documentation never argues for UUIDs on security grounds — lesson 11 sources that argument to RFC 9562 instead, which is where the normative language actually lives.

The type is a container, not a validator. “Any UUID, regardless of the origin and the UUID version” is what makes it possible to store a ULID, a Snowflake, or a TypeID's suffix in a uuid column. Lesson 9 depends on this, and so does one of its traps.

What is left of the case for extensions

pgcrypto — its UUID function is now a shim:

Installing pgcrypto for UUID generation has been pointless since 13. It remains the source of gen_random_bytes(count integer) — “cryptographically strong random bytes”, at most 1024 per call.

uuid-ossp — still the only in-tree source of v1, v3 and v5, and its own page now says: “This module is only necessary for special requirements beyond what is available in core PostgreSQL.” Its uuid_generate_v1() entry carries a warning lesson 11 will build on:

pg_uuidv7 (third-party, MPL-2.0) — its own README now narrows its remit: “As of Postgres 18, there is a built in uuidv7() function, however it does not include all of the functionality below.” The one function with no core equivalent is the range-boundary constructor:

That is how you turn a time range into a WHERE id >= … AND id < … predicate against the primary key index, with no secondary index on created_at at all. It is genuinely useful, and PG18 core documents no equivalent.

Availability usually decides this, not performance

From first-party vendor documentation: AWS RDS and Aurora list uuid-ossp (1.1) and pgcrypto; pg_uuidv7 does not appear in the supported-extensions list for any major version. Neon lists pg_uuidv7 at 1.6 for PG14–18. Supabase does not enumerate its extensions, so nothing can be concluded either way — and this topic claims nothing either way.

A schema that depends on uuid_timestamptz_to_v7() is not portable to RDS. That is a sharper constraint than any performance argument in this topic.

Check yourself

You are on PostgreSQL 15 and want UUIDv4 primary keys. What do you need to install?

gen_random_uuid() moved into core in PostgreSQL 13, and pgcrypto's version has been an explicitly “obsolete” shim calling it ever since. The advice to install an extension for v4 generation was correct before 2020 and has been wrong since — which is a good illustration of why every claim in this topic is dated to a release.

Where this is going

You now know what the engine can supply. Lesson 7 takes the first candidate seriously: the bigint identity column, which is the narrowest and best-behaved key available, and whose two real limits are both worth being able to state exactly.

Read next, from the source

Commit 78c5e141e, “Add UUID version 7 generation function” — read the commit message in full, then look at the diff. It is a small, readable patch, and it is the difference between knowing that uuidv7() is “temporally sortable” and knowing exactly which twelve bits make it so and how far that promise reaches.

Your agent is your teacher. If you run on a managed platform, ask it to check that platform's current extension list before you plan around pg_uuidv7 — the figures above were read at one point in time, and availability is exactly the kind of fact that moves.

On spacing

Before lesson 7, try to state the backend-scope caveat out loud from memory, including why it does not matter for the B-tree and does matter for ORDER BY id. That pair of consequences from one fact is the shape most of this topic takes.
