Lesson 0011

Guessability, and a trap between two specs

The security argument is the one most people start with, and its normative source says something much narrower — and much stricter — than the argument usually claims. This lesson ends with a finding that exists only when you read two specifications against each other.

Note first where this argument does not come from. PostgreSQL documents nothing about enumeration, guessability, or id exposure; the stated rationale for the uuid type is uniqueness in distributed systems (lesson 6). The normative language lives in RFC 9562, and it is four paragraphs long.

What the RFC actually says

Three consequences

A UUID is not an authorisation mechanism, and the RFC says so normatively. “MUST NOT be used as security capabilities (identifiers whose mere possession grants access)” is unambiguous.

The most commonly misapplied idea in this subject

If an object is reachable by anyone holding its id, that is a missing ownership check. Swapping bigint for uuid does not fix it — it hides it behind a larger search space. Teams migrate to UUIDs instead of adding the check, and the RFC forbids exactly that reasoning.

The language hardened between revisions. RFC 4122 §6 said “Do not assume that UUIDs are hard to guess”; RFC 9562 restates it as SHOULD NOT / MUST NOT. That is a deliberate strengthening by the working group, not a rewording.

Timestamp exposure is real, and the RFC rates it small. A UUIDv7 carries a plaintext 48-bit millisecond timestamp in its leading bits (lesson 8), so anyone holding one learns when the row was created, and anyone holding two learns their order. The RFC's assessment is the paragraph above; it never uses the words “leak” or “enumeration”.

Whether that matters is a question about your domain, not about the format. A user_id revealing signup time is usually harmless. An invoice_id that lets a competitor measure your order volume by creating two accounts an hour apart is not.

And note who else it applies to

That attack works against any time-ordered scheme, including bigint, ULID and Snowflake. It is the price of sortability, not a defect peculiar to v7. Lesson 3 is where you learned why you wanted sortability; this is its bill.

The RFC names its own escape hatch: UUIDv4, for anything security-adjacent — accepting the index behaviour of lesson 3 for that one index.

Unguessability is a property of your RNG

The fork caveat is the practical one. A pre-forking application server that seeds its RNG before forking hands every worker the same stream, and the resulting “random” ids are neither unguessable nor unique. The RFC calls this out by name because it is a recurring bug, not a theoretical one.

Check yourself

A colleague proposes moving from bigint to uuid ids so that customers cannot fetch each other's orders. What does RFC 9562 §8 say about that?

UUIDs “MUST NOT be used as security capabilities (identifiers whose mere possession grants access)”. If holding the id is what lets a customer fetch the order, the defect is a missing ownership check, and a wider id only makes it harder to notice. Opaque ids are perfectly good defence in depth behind such a check — but that is a different claim from the one being made.

The trap between two specifications

This is the sharpest finding in the topic, and the thing to notice is that both specifications are individually reasonable. It exists only when you read them against each other.

The finding

ULID's monotonic factory is Method 2 with an increment of exactly 1 — the construction RFC 9562 says SHOULD NOT be used where unguessability matters.

The consequence is concrete: given one ULID from a monotonic generator, the next one issued in that millisecond is not merely guessable, it is determined. If you chose ULIDs as public identifiers partly because they are hard to guess, monotonic mode removes that property for any id sharing a millisecond with one an attacker holds.

ULID has no security considerations section (lesson 9), so it issues no warning of its own.

Python Written for this lesson 
CROCKFORD = "0123456789ABCDEFGHJKMNPQRSTVWXYZ"


def decode(text: str) -> int:
    value = 0
    for char in text:
        value = value * 32 + CROCKFORD.index(char)
    return value


def encode(value: int) -> str:
    chars = []
    for _ in range(26):
        value, remainder = divmod(value, 32)
        chars.append(CROCKFORD[remainder])
    return "".join(reversed(chars))


held = "01BX5ZZKBKACTAV9WEVGEMMVRZ"          # one value an attacker has
print(encode(decode(held) + 1))               # the next one, in that millisecond
# -> 01BX5ZZKBKACTAV9WEVGEMMVS0
# Exactly the successor the ULID spec's own worked example prints.
# No entropy was guessed. Adding one is the whole attack.

PostgreSQL's uuidv7() does not have this problem. Per lesson 6 it uses RFC 9562 §6.2 Method 3 — sub-millisecond clock precision in rand_a — leaving all 62 bits of rand_b random on every call.

Check yourself

Why does ULID's monotonic mode undermine the reason many people chose ULIDs?

Within a millisecond the random component is incremented by exactly one bit in the least significant position, so holding one value gives you the next for free — no entropy is guessed. RFC 9562 §6.2 names this construction and says SHOULD NOT use it where unguessability matters. The timestamp still works, the field is not shortened, and no value is reused; the ordering is real. It is the unguessability that quietly goes.

The transferable skill

Neither specification is wrong. ULID's monotonic mode does exactly what it says; RFC 9562's Method 2 warning is clear. The defect appears only in the gap between them — and gaps between specifications are where a surprising share of real security problems live. Reading two documents against each other is a habit worth keeping well beyond this topic.

Where this is going

One question has been circling since lesson 8 without an answer: how likely is a collision, really? Lesson 12 finds that both specifications deliberately refuse to tell you — and then covers the capability that is the honest reason to accept a 128-bit key in the first place.

Read next, from the source

RFC 9562 §8, “Security Considerations” — the whole section is quoted above and is four paragraphs. Read it in place anyway, then read §6.2 immediately afterwards. Holding both in your head at once is what produces the finding in this lesson, and doing that yourself is worth more than being shown it.

Your agent is your teacher. A genuinely useful exercise: describe an endpoint in your own system and work through whether its id is doing authorisation work. The answer is uncomfortable more often than people expect, and the fix is never a change of identifier type.
