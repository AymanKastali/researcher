Lesson 0008

UUIDv4 and UUIDv7

Two formats, one bit-layout difference, and a trade that maps almost exactly onto lesson 3. This is also where the RFC makes its single quantitative claim — and where you get to apply the evidence grading to a specification rather than to a blog post.

Both are 128 bits. Both store in a uuid column at 28 bytes per index entry. Both can be generated anywhere, by anyone, with no coordination. Everything that separates them is which of those 128 bits are random and which are a clock.

UUIDv4: no structure at all

122 random bits out of 128. The other six are the version nibble (0b0100) and the two variant bits (0b10), both of which MUST be set.

Everything good about v4 follows from having no structure: no timestamp, no node id, nothing to correlate, nothing to leak. Everything bad about it follows from the same property, and the RFC is blunt about it:

In PostgreSQL terms, lesson 3 is what “dramatic” means here: about 50% leaf density instead of 90%, a cold leaf page per insert, and the write-amplification inference of lesson 4.

UUIDv7: a clock in the leading bits

Worth taking apart by hand once, because the layout explains both the index behaviour and — in lesson 11 — the security posture:

Python Written for this lesson 
import uuid

u = uuid.UUID("018570bb-4a7d-7123-8abc-000000000000")
bits = u.int                                   # 128 bits, big-endian

unix_ts_ms = bits >> 80                        # bits 0..47
ver        = (bits >> 76) & 0xF                # bits 48..51
rand_a     = (bits >> 64) & 0xFFF              # bits 52..63
var        = (bits >> 62) & 0b11               # bits 64..65
rand_b     = bits & ((1 << 62) - 1)            # bits 66..127

assert ver == 7 and var == 0b10                # both MUST be set

# The timestamp is in plain sight. Anyone holding the value reads it.
print(unix_ts_ms)                              # -> 1672633600637
# -> 2023-01-02 04:26:40.637+00, which is exactly the timestamp the
#    pg_uuidv7 README fed in to produce this prefix (lesson 6).

# 48 + 4 + 12 + 2 + 62 == 128, and 12 + 62 == 74 bits not fixed by format.

The RFC's one number, and how to grade it

Two cautions on that sentence

It is unattributed and unquantified. No experiment, no workload, no engine is named. It is the only magnitude claim in any primary source in this entire topic, which is exactly why it gets repeated everywhere.

It is written for engines that cluster. “Objects are more easily clustered together” describes the mechanism lesson 4 showed PostgreSQL does not have. Treat it as the RFC's motivation for the format, not as a PostgreSQL benchmark.

This is the topic's evidence grading applied to a standards document, and it is worth noticing that the answer is the same as for a blog post: a confident sentence with no experiment behind it does not become an experiment by appearing in an RFC.

Check yourself

RFC 9562 §6.11 says index locality can be worth “one order of magnitude or more”. How should that be used?

The sentence names no experiment, no workload and no engine, and its stated mechanism — objects “clustered together” — is one PostgreSQL does not implement. It explains why the format was designed, which is a perfectly good thing for an RFC to do. It is not wrong; it is simply not a measurement, and quoting it as one is the single most common sourcing error in this subject.

Storage advice you get for free

The most expensive mistake in this area

PostgreSQL's uuid type stores the binary value. Putting UUIDs in a text column instead is not a UUID decision, it is a storage mistake: by lesson 2 it takes the index entry from 28 bytes to 44, more than doubling the leaf pages required, for no benefit whatsoever. It is also the single most common thing this topic will let you spot in someone else's schema.

Notice that the two recommendations are not in conflict. §5.7 is about which time-ordered version to use; §8 is about what to use when the identifier is security-adjacent. Lesson 11 is where that second one gets its proper treatment.

Check yourself

A UUIDv7 and a UUIDv4 occupy the same 16 bytes. Why does the v7 index hold nearly twice as many entries per leaf page?

Both entries are 28 bytes — width is identical. The difference is entirely lesson 3: a v7's leading millisecond timestamp means successive values land at the right edge, where a split leaves the left page at fillfactor rather than 50%. Nothing is compressed, and the smaller random field (74 bits against 122) affects collision arithmetic, not storage.

Where this is going

v7 is not the first identifier to put a millisecond timestamp in front of some random bits. Lesson 9 takes the three designs that got there first or went further — ULID, Snowflake and TypeID — and asks what, if anything, each still offers now that v7 is in the box.

Read next, from the source

RFC 9562, “Universally Unique IDentifiers (UUIDs)” — read §5.4 and §5.7 in full, which is about three pages, then §6.11 and §6.13. This is the single most important reading in the topic, and it is readable: an IETF standards document written after decades of practice, which argues for its choices rather than just stating them.

Your agent is your teacher. Good thing to push on: whether ~50% is really the right figure for a v4 index under your write pattern. It is a tendency the split rule produces over many random inserts, not a guarantee, and a table that is written once and then mostly read will not look like that at all.

On spacing

Before lesson 9, try to draw the UUIDv7 layout from memory — 48 bits, 4, 12, 2, 62 — and then say which of those fields the database uses and which an attacker reads.
