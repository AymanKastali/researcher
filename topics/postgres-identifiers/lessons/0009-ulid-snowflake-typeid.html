Lesson 0009

ULID, Snowflake, and TypeID

Three designs that solved this before UUIDv7 existed, or went further than it does. The useful skill here is judging a specification by its governance as well as its bit layout — which is a different kind of evidence from anything in lessons 2 to 8.

Each of these is a real design with a real argument behind it. Each also answers a question you should ask of any specification: who maintains it, when did they last touch it, and what happens to me if they stop?

ULID: the design UUIDv7 inherited

ULID predates UUIDv7 and solves the same problem. Its stated motivation:

Layout: a 48-bit millisecond timestamp plus 80 bits of randomness, encoded as 26 characters of Crockford's Base32 — 0123456789ABCDEFGHJKMNPQRSTVWXYZ, an alphabet that “excludes the letters I, L, O, and U to avoid confusion and abuse”.

That is a good design. The honest assessment is nevertheless that UUIDv7 has superseded it, and the reasons are about governance rather than bits.

Five findings about the ULID specification itself.
Finding Evidence
The spec is unversioned and dormant. No tags, no releases, no version number, no date inside the document. Last commit to master is d0c7170, 2019-05-23. 74 issues open; a clarifications-jan-2020 branch was opened and never merged. The only stable way to cite it is by commit SHA.
It defines itself by one implementation. “Below is the current specification of ULID as implemented in ulid/javascript”, adding “Note: the binary format has not been implemented in JavaScript as of yet.”
No security considerations section. None at all, and its randomness requirement is softer than the RFC's: “Cryptographically secure source of randomness, if possible”.
“128-bit compatibility with UUID” is bare size equivalence. The spec says nothing about version or variant bits, so a ULID stored in a uuid column is not a conformant RFC 9562 UUID — it carries whatever its randomness produced where the version nibble belongs. It round-trips through PostgreSQL fine (lesson 6: “any UUID, regardless of the origin”), but uuid_extract_version() returns whatever those four bits happen to be.
A real intra-millisecond trap. The headline bullet claims “Monotonic sort order (correctly detects and handles the same millisecond)”, but the Sorting section says “Within the same millisecond, sort order is not guaranteed”. Only the separate monotonicFactory provides ordering — and lesson 11 explains why that mode is worse than it looks.
A fair summary

RFC 9562 §2.1 lists ULID first among the 16 implementations analysed while drafting the standard. It is fair to read UUIDv7 as ULID's design, given a version field, a variant field, a standards body, and a security section — which is a compliment to ULID and still a reason to reach for v7.

Snowflake: the 64-bit constraint

The only 64-bit candidate here that is also time-ordered, and the constraint that produced it is worth reading:

The 5+5 datacenter/worker split and the epoch are not in the README — they are in IdWorker.scala: val twepoch = 1288834974657L, workerIdBits = 5, datacenterIdBits = 5, sequenceBits = 12. The sign bit is stated nowhere; it is only inferable from 41 + 10 + 12 = 63 of a signed Long. Grade two throughout.

Three things make this a poor default in 2026.

It is retired. The repository is archived ("archived": true, last push 2020-07-22), and the master README says: “We have retired the initial release of Snowflake […] We won't be accepting pull requests or responding to issues for the retired release.” What you would adopt is the design, reimplemented by you.

Worker-id assignment is a coordination problem. “worker numbers are chosen at startup via zookeeper”. Ten bits means exactly 1024 concurrent generators, and assigning them uniquely — across autoscaling, container restarts and blue/green deploys — is the actual engineering cost. It is not an uncoordinated scheme; it is a scheme where the coordination happens once at startup instead of once per id.

64-bit ids break JavaScript, which Twitter documented first-party:

Their fix was to serialise ids as strings (id_str), and “In newer versions of the API, all large integer values are represented as strings by default.” Discord reached the same conclusion independently: “Because Snowflake IDs are up to 64 bits in size (e.g. a uint64), they are always returned as strings in the HTTP API to prevent integer overflows in some languages.”

This applies to your bigint too

The 53-bit hazard is not peculiar to Snowflake. It applies verbatim to a bigint primary key that you expose in JSON. It is the one practical hazard bigint shares with Snowflake, and it is entirely avoidable by serialising as a string.

Discord's live variant differs slightly — 42 timestamp bits, 5 worker + 5 process + 12 increment, epoch 1420070400000 (Discord API reference) — a useful reminder that “Snowflake” names a family, not a format.

Check yourself

What is the real engineering cost of adopting Snowflake-style ids?

Ten bits gives exactly 1024 concurrent generators, and each needs a distinct one — Twitter used ZooKeeper for this. Assigning them reliably across autoscaling, restarts and blue/green deploys is the whole cost, and it is why Snowflake is not an uncoordinated scheme. Width is actually its advantage: 64 bits, narrower than any UUID.

TypeID: a presentation layer, sold as a format

Giving user_2x4y6z8a0b1c2d3e4f5g6h7j8k. The prefix regex is ^([a-z]([a-z_]{0,61}[a-z])?)?$ — lowercase alphabetic and underscore only, no digits, no leading or trailing underscore. Total length 26 to 90 characters.

Critically, and unlike ULID, the underlying value is required to be a real UUIDv7:

A TypeID is a UUIDv7 plus a presentation layer, so the storage question has a clean answer: store the uuid, render the prefix.

The official SQL implementation offers two encodings, and neither is that. The text encoding costs ~30 characters per index entry — by lesson 2, roughly 2× a native uuid. The composite stores a varchar(63) prefix on every single row, even though the prefix is a property of the table and is identical for every row in it.

SQL Written for this lesson 
-- The pragmatic reading: TypeID as an API format, not a storage format.
CREATE TABLE users (
    id         bigint GENERATED ALWAYS AS IDENTITY PRIMARY KEY,
    public_id  uuid   NOT NULL DEFAULT uuidv7(),

    CONSTRAINT users_public_id_key UNIQUE (public_id)
);
-- The serialisation layer renders public_id as user_2x4y6z8a0b1c2d3e4f5g6h7j8k.
-- The prefix is a property of the table, so storing it per row buys nothing.

Two caveats on the implementation, both from its own repositories: the SQL implementation tracks spec v0.2 while Go and TypeScript are at v0.3, and the root README still describes UUIDv7 as “the upcoming UUID standard”, linking an expired IETF draft rather than the published RFC.

The bet underneath TypeID

TypeID's acknowledged inspiration is Stripe, and Stripe's own position on their ids is instructive — and opposite:

Two defensible, opposite bets

Stripe classifies changing an id's length, and adding or removing the prefix, as a backward-compatible change that clients must tolerate — the id is opaque, and the prefix is a convenience for humans. TypeID inverts this: its format is fixed and parseable by design, so clients may rely on it.

Both are coherent. What you cannot do is adopt TypeID's ergonomics while making Stripe's promise, and noticing that is the real lesson here.

Check yourself

Why is a ULID stored in a uuid column not a conformant RFC 9562 UUID?

RFC 9562 requires specific bits to carry the version and variant; the ULID spec never mentions either, so those positions hold whatever the randomness produced. It still stores and round-trips fine, because PostgreSQL's uuid type is a container rather than a validator — but uuid_extract_version() on it returns noise. This is exactly the property TypeID was careful to require.

Where this is going

Six candidates down, one to go. Lesson 10 takes the option that needs no invention at all — using data that already means something — and prices the one risk that makes it a schema decision rather than a preference.

Read next, from the source

The ULID specification — it is one README and takes ten minutes. Read it as an exercise in the skill this lesson is really teaching: note the last commit date, look for a version number, look for a security section, and find the contradiction between the headline monotonicity bullet and the Sorting section. Doing that to a specification yourself is worth more than being told the findings.

Your agent is your teacher. If TypeID appeals — and its ergonomics genuinely are pleasant — ask for the trade-offs of doing the prefixing at the serialisation boundary versus in the database. The answer is not only about storage; it is about where a wrong-type id gets caught.
