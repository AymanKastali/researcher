Lesson 0007

Identity columns and the gap myth

The first candidate, and the baseline every other one is measured against. It is the narrowest key available with the best index behaviour available — and its two limits are exactly the two things the rest of this topic is shopping for.

BIGINT GENERATED ALWAYS AS IDENTITY is the SQL-standard spelling of an autoincrementing column. By lesson 2 it is the narrowest index entry at 20 bytes; by lesson 3 it is strictly ascending, so the rightmost fastpath applies on every single insert. Nothing else in this topic beats it on either count.

What the clause actually does

Why ALWAYS and not BY DEFAULT

Read the UPDATE paragraph again. ALWAYS makes the key immutable at the schema level — the engine refuses the update rather than trusting you not to write it. Lesson 5 showed exactly what a mutable key costs; this is the one-word declaration that makes that cost unpayable.

The docs describe the INSERT half as “protection against accidentally inserting an explicit value”. The UPDATE half is the part worth choosing it for.

And a trap, stated outright by the manual:

Also worth knowing for partitioned schemas, from the same page: “Partitions inherit identity columns from the partitioned table; they cannot have their own.”

SQL Written for this lesson 
CREATE TABLE orders (
    id          bigint GENERATED ALWAYS AS IDENTITY PRIMARY KEY,
    placed_at   timestamptz NOT NULL DEFAULT now()
);

-- Rejected: the column is ALWAYS, and no override was requested.
INSERT INTO orders (id) VALUES (42);

-- Accepted, and this is the escape hatch a data migration needs.
INSERT INTO orders (id) OVERRIDING SYSTEM VALUE VALUES (42);

-- Rejected: ALWAYS refuses any UPDATE to a value other than DEFAULT.
UPDATE orders SET id = 43 WHERE id = 42;

Gaps are guaranteed, and are not a security feature

With CACHE > 1, values additionally go out of order across sessions:

The default is CACHE 1, at which “it is safe to assume that nextval values are generated sequentially”.

The myth, and the honest summary

Gaps are sometimes offered as a reason sequential ids are “not really enumerable”. They are not that. A bigint identity column is sequential by default; gaps exist but are incidental, unpredictable in the wrong direction, and nothing in this design is intended to make the next value hard to guess. If you need unguessability, you need a different column — not a hopeful reading of this one.

Check yourself

Why can a PostgreSQL sequence never produce a gapless run of values?

nextval deliberately does not reclaim a value when the calling transaction aborts, precisely so that it never has to block concurrent transactions — the gap is the price of the concurrency. Caching does widen gaps and reorder values across sessions, but it is off by default at CACHE 1 and is not the root cause. Vacuum and replication have nothing to do with it.

There is a third hazard that is not a limit of the type but of how you serialise it. A bigint does not survive JavaScript's number type, which is the same problem Twitter documented for Snowflake in lesson 9 — and the fix is the same: serialise it as a string.

Range, for completeness: −9223372036854775808 to +9223372036854775807. The docs note that bigserial “should be used if you anticipate the use of more than 2³¹ identifiers over the lifetime of the table”, which is the reason to skip integer entirely for anything that grows.

A note on bigserial

The docs are more neutral about serial versus identity than is usually claimed. §8.1.4 says only: “This section describes a PostgreSQL-specific way to create an autoincrementing column. Another way is to use the SQL-standard identity column feature.”

There is no documented recommendation of one over the other. The documented advantages of identity are the PG10 release note's “SQL standard compliant”, plus the ALWAYS immutability above — and that second one is the reason to prefer it.

Check yourself

Which property does GENERATED ALWAYS add that GENERATED BY DEFAULT lacks?

Under ALWAYS, “any update of the column to any value other than DEFAULT will be rejected”, which makes the key immutable without relying on discipline. Uniqueness still needs its own constraint — the manual says so explicitly. Gaps are guaranteed under either spelling, and the storage width is identical.

Where this is going

The baseline is set: narrowest, fastest, immutable if you ask for it, and unable to do either of the two things lessons 11 and 12 will want.

Lesson 8 takes the two candidates that can do them — and shows that the choice between v4 and v7 is, almost exactly, the choice between the two halves of lesson 3.

Read next, from the source

PostgreSQL 18 manual, §5.3 “Identity Columns” — a short page, and worth reading alongside §9.17, whose paragraph on gaps is one of the more quietly opinionated things in the manual. Note that it explains why gaps happen rather than apologising for them.

Your agent is your teacher. A worthwhile exercise: ask it to walk you through what actually happens to the sequence when an INSERT … ON CONFLICT DO NOTHING conflicts. The manual names this case specifically, and it surprises most people who assume a no-op statement consumes nothing.
