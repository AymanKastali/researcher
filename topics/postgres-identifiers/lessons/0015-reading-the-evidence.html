Lesson 0015

Reading the evidence

The last lesson, and the one most likely to outlive the rest. PostgreSQL 19 will change some of the answers in this topic. It will not change how to check them — so the grading itself becomes the object of study here, along with every single thing the sources refused to say.

Fourteen lessons have carried a label on every number: documented guarantee, source-code fact, or derived arithmetic. This lesson makes that discipline explicit, and then does the thing almost no technical writing does — lists what could not be established, rather than quietly filling the gaps.

The most important absence

There are no benchmark numbers in this topic

Not because they were omitted for brevity, but because no primary source provides any. The PostgreSQL manual publishes no performance comparison of bigint, uuid and text keys — not for insert throughput, not for index size, not for cache behaviour.

The only magnitude claim anywhere in the primary sources is RFC 9562 §6.11's “one order of magnitude or more”, which is unattributed, names no workload and no engine, and is framed around clustering behaviour that lesson 4 showed PostgreSQL does not have.

Every performance statement in this topic is therefore either a quoted mechanism or labelled arithmetic.

This is worth sitting with, because it explains the state of the literature. A subject where everyone has an opinion, the mechanism is documented, and nobody published a measurement is a subject that will generate confident blog posts indefinitely.

Everything that could not be verified

These are gaps in the sources, not omissions from the lessons. Each is grouped by what kind of gap it is.

Claims made here that are inference, not documentation

Claim Status Lesson
Random keys increase WAL volume. The docs establish the full_page_writes mechanism and the rightmost-page behaviour separately, and never connect them. The chain is reasoning from two quoted facts. 4
Wider join keys cost something. The docs make no claim that join-key width affects join performance. The work_mem spill argument is inference, and describes a step function rather than a per-row tax. 14
A random key does not fragment the table. Follows from three quoted facts — CLUSTER is one-time, each relation is its own file, all indexes are secondary — but the manual never states the conclusion. 4
Store a TypeID as a uuid column. TypeID's “binary representation” is not specified — the spec defines only the canonical lowercase string encoding. The recommendation is inference from the requirement that the suffix decode to a valid UUIDv7. 9
No padding between a bigint and a uuid. storage-page-layout.html covers page and tuple header layout and the t_hoff MAXALIGN rule, but says nothing about inter-column padding or column ordering. Both types are fixed-width, so no padding is expected — inference. 2

Things the sources simply do not say

  • PostgreSQL documents nothing about enumeration, guessability, or ID exposure. The stated rationale for the uuid type is uniqueness in distributed systems, not security. The entire “expose a UUID so attackers cannot enumerate rows” argument has no support in the project's documentation. It may well be sound — lesson 11 sources it to RFC 9562 instead, which is where the normative language lives.
  • avg_leaf_density and leaf_fragmentation are undefined. The quoted one-line descriptions are complete: no computation, no units, no threshold for “bad”. Any target figure for them does not come from PostgreSQL.
  • Neither UUID specification states a collision probability. RFC 9562 never mentions the birthday problem. The familiar “a billion a second for a century” figures are not in it, and this topic does not attribute them to it.
  • The ULID specification cannot be cited by version. No tags, no releases, no version number, no internal date. Lesson 9 cites it by commit SHA because that is the only stable reference that exists.
  • ULID's case-insensitivity is a feature bullet, not a specified behaviour. “Case insensitive” appears only in the README's headline list; the Encoding section defines a single uppercase alphabet and says nothing normative about accepting or emitting lowercase. The same applies to “No special characters (URL safe)”.
  • The introducing version of uuid_extract_timestamp() and uuid_extract_version() was not established. Both are present in 18; the PG17 release notes were not fetched, so no version is claimed for them.
  • Supabase's support for pg_uuidv7 could not be determined. Its docs do not enumerate extensions, and there is no first-party page. Absence of a page is not evidence of absence of the extension, so lesson 6 claims nothing either way.
  • Instagram's sharded-ID design could not be retrieved. The host refused the connection and the archive API rate-limited, so no Instagram bit layout appears anywhere in this topic.

Sourcing caveats worth carrying

  • Two Twitter sources are archive captures, not live pages. The 2010 announcement returns HTTP 403 at its live URL, and the developer documentation on Twitter IDs has been removed. Capture dates are given on every page that quotes them. An archived copy of an original is still a primary source; a blog post describing it would not be.
  • Codd is quoted from a university mirror of the scan, not the ACM Digital Library, whose full text is paywalled. The scan's page footer matches the citation, and two OCR run-together artifacts were corrected.
  • The uuidv7() commit message cites “RFC 9652”. That is a typo in the commit itself; the uuid type page and the function docs both correctly say RFC 9562. A primary source being wrong in a detail is not a reason to distrust it — it is a reason to read it rather than a summary of it.
  • Two widely-repeated assumptions turned out to be false. The uuid-ossp page contains no statement that gen_random_uuid() is preferable — only the generic “this module is only necessary for special requirements”. And §8.1.4 does not recommend identity columns over serial; it calls identity “Another way”, and the only documented advantage is the PG10 release note's “SQL standard compliant”.
Check yourself

Someone cites RFC 9562 for the claim that time-ordered keys are ten times faster in PostgreSQL. What are the two separate problems?

First, §6.11 names no experiment, workload or engine — it is motivation for a format, not a measurement. Second, its stated mechanism is objects being “clustered together”, which describes storage PostgreSQL does not have (lesson 4). Both problems have to be raised; fixing only one leaves the citation looking usable. RFC 9562 is current, and nothing here contradicts §8.

The habit worth keeping

Four questions, in order
  1. Is this quoted or recalled? If the writer cannot point at the sentence, neither can you.
  2. Which grade is it? A manual page, a header file, and someone's arithmetic carry three different weights, and merging them into one confident voice is how folklore forms.
  3. Which engine was it written for? Lesson 4 is the single highest-yield application of this question in this subject.
  4. What does the source decline to say? RFC 9562's refusal to state a collision probability, and the manual's silence on leaf_fragmentation thresholds, are both deliberate — and both are routinely filled in by other people.

That fourth question is the one this lesson exists for. An absence in a careful source is usually information: it means the authors judged the number to be workload-dependent, or implementation-defined, or not theirs to give. Somebody supplying it anyway has not done extra work — they have skipped the step where the source declined.

Check yourself

Why does this topic contain no benchmark comparing bigint and uuid keys?

The topic's rule is that every claim is quoted, cited to source, or labelled arithmetic — and no primary source publishes a measurement here. The difference is real and substantial (lesson 3 derives the magnitude from quoted constants), so it is certainly measurable. Nothing forbids benchmarks; there simply is not one to cite, and inventing a number would be exactly the failure this whole topic is built to avoid.

You are done

Fifteen lessons: the shape of the decision, four on the physical mechanics, one on what the engine supplies, four on the candidates, two on security and distribution, two on the pattern and the decision, and this one.

The topic index lists five reference documents, and those are the ones built to be come back to — the candidate comparison, the index arithmetic with its measuring commands, the feature ledger with working DDL, the glossary, and this lesson's list in lookup form. Lessons are read once; reference documents are read for years.

One last recall exercise

Before you close this, try to answer without looking: why does a UUIDv7 index hold nearly twice as many entries per leaf page as a UUIDv4 one, when both are 16 bytes? If you can reconstruct that from the split rule rather than recall it as a fact, the topic did its job.

Read next, from the source

PostgreSQL 18 manual, §65.1 “B-Tree Indexes” — the whole section, now that you know what it does and does not contain. Read it specifically for its silences: notice where it hands you to the source README, and notice that the behaviour lesson 3 turns on is not on the page at all. That reading is the skill; the facts you already have.

Your agent is your teacher, and this is where that matters most. When PostgreSQL 19 ships, ask it to re-check the feature ledger in lesson 6 and every source-code citation in lessons 2 and 3 — a header file can change without a release note, which is exactly why those claims were labelled grade two. Bring it any identifier argument you meet, and ask which grade each claim in it is.

On spacing, one last time

The real test is not today. Come back in a month and try to reconstruct the ladder from lesson 14 and the split argument from lesson 3 without opening either. What you cannot rebuild, re-read — and re-read the lesson, not this summary, because the argument is what sticks and the conclusion is what fades.
