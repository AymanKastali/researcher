Reference

Unverified claims

Everything in this topic that is inference rather than documentation, every constant that is grade two, and every question the primary sources decline to answer. Reach for this when someone cites a number.

The headline

This topic contains no benchmark numbers, because no primary source provides any. The PostgreSQL manual publishes no performance comparison of bigint, uuid and text keys — not for insert throughput, index size, or cache behaviour. The only magnitude claim anywhere is RFC 9562 §6.11's “one order of magnitude or more”, which is unattributed, names no workload and no engine, and is framed around clustering behaviour PostgreSQL does not have.

The three grades

GradeSourceWeight
Documented guarantee The manual, an RFC, a vendor specification. May be stated flatly. A change will be announced.
Source-code fact A REL_18_STABLE header, README or commit, where the manual is silent. Could change without a release note. A #define is not a promise.
Derived arithmetic Computed from quoted constants. As good as its inputs and stated assumptions. Checkable — and in this topic, checked.

Claims here that are inference, not documentation

ClaimWhy it is inferenceLesson
Random keys increase WAL volume. The docs establish the full_page_writes mechanism and the rightmost-page behaviour separately and never connect them. 4
Wider join keys cost something. The docs make no claim that join-key width affects join performance. The work_mem spill argument is a step function at a threshold, not a per-row tax. 14
A random key does not fragment the table. Follows from three quoted facts, but the manual never states the conclusion. The one inference this topic makes flatly, because each premise is documented and the step is definitional. 4
Store a TypeID as a uuid column. TypeID's binary representation is not specified — only the canonical lowercase string encoding. Inferred from the requirement that the suffix decode to a valid UUIDv7. 9
No padding between a bigint and a uuid. Per-attribute alignment and column-ordering advice is not documented. Both types are fixed-width, so none is expected. 2
A v4 index settles at ~50% leaf density. A tendency the split rule produces over many random inserts, not a documented figure. The source comment states 50% as the outcome being avoided at the right edge. 3

Questions the sources decline to answer

QuestionWhat the source actually says
What is the collision probability? Neither RFC 9562 nor the ULID spec states one. RFC 9562 never mentions the birthday problem — zero hits for “birthday”, and “probability” appears four times, never attached to a figure. It offers an impact framing (§6.7) instead. The familiar “a billion a second for a century” figures are not in it.
What is a healthy leaf_fragmentation? “Leaf page fragmentation” is the complete documented description. No computation, no units, no threshold. Same for avg_leaf_density: “Average density of leaf pages”.
Should I expose UUIDs to prevent enumeration? PostgreSQL documents nothing about enumeration, guessability or ID exposure. The stated rationale for the uuid type is uniqueness in distributed systems. The normative language is RFC 9562 §8, and it says UUIDs MUST NOT be used as security capabilities.
How fast is a v7 index versus a v4 one? Nobody published a measurement. Derive it from the split rule and label the derivation as yours.

Sourcing caveats

  • The ULID spec cannot be cited by version. No tags, no releases, no version number, no internal date. Cite commit d0c7170 (2019-05-23).
  • ULID's “case insensitive” and “URL safe” are feature bullets, not specified behaviour. The Encoding section defines a single uppercase alphabet and says nothing normative about lowercase.
  • Two Twitter sources are Wayback captures. The 2010 announcement returns HTTP 403 live; the developer documentation on Twitter IDs has been removed. An archived original is still a primary source; a blog post describing it would not be.
  • Codd is quoted from a university mirror of the scan, not the paywalled ACM copy. Two OCR run-together artifacts were corrected. The paper does not use the term “surrogate key”.
  • The uuidv7() commit cites “RFC 9652”. A typo in the commit; the type page and function docs both say RFC 9562.
  • The uuid-ossp page does not recommend gen_random_uuid() — only the generic “this module is only necessary for special requirements”.
  • §8.1.4 does not recommend identity columns over serial — it calls identity “Another way”. The only documented advantage is the PG10 note's “SQL standard compliant”.
  • Supabase's pg_uuidv7 support is undetermined. Its docs do not enumerate extensions. Absence of a page is not evidence of absence of the extension.
  • Instagram's sharded-ID design could not be retrieved. No Instagram bit layout appears anywhere in this topic.
  • The introducing version of uuid_extract_timestamp() and uuid_extract_version() was not established.

The four questions

Ask these of any claim in this subject
  1. Is this quoted or recalled? If the writer cannot point at the sentence, neither can you.
  2. Which grade is it? Manual, header file, and arithmetic carry three different weights.
  3. Which engine was it written for? The highest-yield question in this subject, because PostgreSQL has no clustered index.
  4. What does the source decline to say? An absence in a careful source is usually information.
