Function catalogue

FunctionWhat it does
uuidv7([shift interval]) Version 7 UUID: Unix ms + sub-ms + random. Optional shift moves the timestamp; it must stay within the 48-bit range, 1970-01-01 to approximately year 10889.
uuidv4() / gen_random_uuid() Version 4 UUID. Aliases; the second predates the first.
uuid_extract_timestamp(uuid) timestamptz from a v1 or v7; null for other versions. “Not necessarily exactly equal to the time the UUID was generated” — for a client-generated id it reports the client's clock.
uuid_extract_version(uuid) The version nibble. On a ULID stored in a uuid column this returns whatever those four random bits happen to be.
gen_random_bytes(n) pgcrypto. “Cryptographically strong random bytes”, at most 1024 per call.
The monotonicity guarantee, exactly

From commit 78c5e141e: “the monotonicity of generated UUIDs is ensured within the same backend.” A backend is one connection's server process. The guarantee does not extend across a connection pool, across application instances, or across servers.

Good for index locality — inserts land near the right edge either way. Not good for ORDER BY id — same-millisecond rows from different connections have no defined order.

Extensions

ExtensionStatusStill worth installing for
pgcrypto Its gen_random_uuid() is marked “(Obsolete, this function internally calls the core function of the same name.)” gen_random_bytes(). Not UUID generation.
uuid-ossp “Only necessary for special requirements beyond what is available in core PostgreSQL.” v1, v3, v5 — the only in-tree source. Note its own warning that v1 “reveal[s] the identity of the computer that created the identifier and the time at which it did so”.
pg_uuidv7 Third-party, MPL-2.0, v1.7.0 (2025-10-13), not archived. Its README: “As of Postgres 18, there is a built in uuidv7() function, however it does not include all of the functionality below.” uuid_timestamptz_to_v7(ts, true) — the range-boundary constructor, which core has no equivalent for. Not available on AWS RDS.
SQL Quoted from the pg_uuidv7 README 
-- for date range queries set the second argument to true to zero the random bits
SELECT uuid_timestamptz_to_v7('2023-01-02 04:26:40.637+00', true);
-- 018570bb-4a7d-7000-8000-000000000000

That turns a time range into a WHERE id >= … AND id < … predicate against the primary key index, with no secondary index on created_at at all.

Platform availability: AWS RDS/Aurora lists uuid-ossp (1.1) and pgcrypto; pg_uuidv7 appears in no major version's supported list. Neon lists pg_uuidv7 at 1.6 for PG14–18. Supabase does not enumerate its extensions, so nothing is claimed either way.

DDL recipes

Rung 1 — single narrow key

SQL Written for this topic 
CREATE TABLE orders (
    id          bigint GENERATED ALWAYS AS IDENTITY PRIMARY KEY,
    created_at  timestamptz NOT NULL DEFAULT now()
);
-- ALWAYS rejects INSERT of an explicit value without OVERRIDING SYSTEM VALUE,
-- and rejects ANY update to a value other than DEFAULT. That immutability is
-- the reason to prefer it over BY DEFAULT and over bigserial.
-- Serialise id as a STRING: 64-bit integers do not survive JavaScript.

Rung 2 — the dual-identifier pattern

SQL Written for this topic 
CREATE TABLE orders (
    id          bigint GENERATED ALWAYS AS IDENTITY PRIMARY KEY,
    public_id   uuid   NOT NULL DEFAULT uuidv7(),      -- PG18+
    created_at  timestamptz NOT NULL DEFAULT now(),

    CONSTRAINT orders_public_id_key UNIQUE (public_id)
);

CREATE TABLE order_lines (
    id        bigint GENERATED ALWAYS AS IDENTITY PRIMARY KEY,
    order_id  bigint NOT NULL REFERENCES orders (id)   -- id, never public_id
);

-- NOT created automatically. The docs: "it is often a good idea to index
-- the referencing columns too."
CREATE INDEX order_lines_order_id_idx ON order_lines (order_id);

-- Rules: id is never serialised. public_id never appears in a foreign key.

Rung 3 — single UUID key, offline generation

SQL Written for this topic 
CREATE TABLE orders (
    id          uuid PRIMARY KEY DEFAULT uuidv7(),
    created_at  timestamptz NOT NULL DEFAULT now()
);
-- The client may supply id instead of taking the DEFAULT. Treat a
-- client-supplied value as hostile input, exactly like any other field.
-- RFC 9562 6.4: you MUST be willing to rely on every host's RNG.

Natural key — constrain it, do not key on it

SQL Written for this topic 
CREATE TABLE users (
    id     bigint GENERATED ALWAYS AS IDENTITY PRIMARY KEY,
    email  text NOT NULL,
    CONSTRAINT users_email_key UNIQUE (email)
);

-- If the column is nullable, know that by default "two null values are not
-- considered equal", so any number of null rows are permitted. PG15+:
--   CONSTRAINT users_email_key UNIQUE NULLS NOT DISTINCT (email)
-- The docs warn this default is implementation-defined across databases.

Storing a UUID as text — what not to do

SQL Written for this topic 
-- WRONG: 44-byte index entries instead of 28, for no benefit.
-- RFC 9562 6.13: UUIDs SHOULD be stored "as the underlying 128-bit binary value".
CREATE TABLE bad (id text PRIMARY KEY DEFAULT uuidv7()::text);

-- If you genuinely must store an identifier as a string, use text with a
-- CHECK. varchar(n) buys nothing: the docs say there is "no performance
-- difference among these three types".
CREATE TABLE ulid_keyed (
    id text PRIMARY KEY CHECK (id ~ '^[0-9A-HJKMNP-TV-Z]{26}$')
);

The covering-index optimisation — usually premature

SQL Written for this topic 
CREATE UNIQUE INDEX orders_public_id_idx
    ON orders (public_id) INCLUDE (id);

-- Three documented caveats:
--   1. Needs the visibility map's all-visible bits -- slowly-changing data only.
--   2. "INCLUDE indexes can never use deduplication."
--   3. Only helps if the query touches nothing else:
--        SELECT id   FROM orders WHERE public_id = $1   -- qualifies
--        SELECT *    FROM orders WHERE public_id = $1   -- does not
-- Most application code issues the second. Measure before adding this.

Sequence behaviour

BehaviourDetail
Gaps are guaranteed “PostgreSQL sequence objects cannot be used to obtain ‘gapless’ sequences.” An aborted transaction never returns its value, and INSERT … ON CONFLICT consumes one before detecting the conflict.
Order across sessions At the default CACHE 1, “it is safe to assume that nextval values are generated sequentially”. Above 1, sessions reserve blocks and values interleave out of order.
Uniqueness “An identity column does not guarantee uniqueness; a PRIMARY KEY or UNIQUE constraint is needed for that.”
Range bigint: −9223372036854775808 to +9223372036854775807. Use it rather than integer for anything expected to exceed 2³¹ rows over its lifetime.
Partitions “Partitions inherit identity columns from the partitioned table; they cannot have their own.”
Security None. Gaps are incidental. Nothing here makes the next value hard to guess.
