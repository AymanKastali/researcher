MAXALIGN is 8 on 64-bit. The manual never states the value, only that t_hoff “must always be a multiple of the MAXALIGN distance for the platform”. Treat it as a platform fact.

The model — grade three

Assumptions: 8 kB pages, MAXALIGN 8, single-column NOT NULL key, no INCLUDE columns, ASCII text.

Python Written for this topic 
PAGE = 8192
USABLE = PAGE - 24 - 16      # page header, BTPageOpaqueData  -> 8152
TUPLE_HEADER = 8             # IndexTupleData, from itup.h
LINE_POINTER = 4             # ItemIdData, from the manual
MAXALIGN = 8                 # 64-bit platform assumption


def per_entry(key_bytes: int) -> int:
    body = TUPLE_HEADER + key_bytes
    padded = -(-body // MAXALIGN) * MAXALIGN
    return padded + LINE_POINTER


def entries_per_leaf(key_bytes: int, fillfactor: int = 100) -> int:
    return (USABLE * fillfactor // 100) // per_entry(key_bytes)

The validation

The pageinspect docs print two real leaf pages (§F.23.3), both on oid keys: bt_multi_page_stats('pg_proc_oid_index', 5, 2) gives live_items | 367, free_size | 808; and bt_page_stats('pg_cast_oid_index', 1) gives live_items | 224, free_size | 3668. Both print avg_item_size | 16.

Python Written for this topic 
>>> per_entry(4)              # oid: 8 + 4 -> 16, matching avg_item_size
20
>>> USABLE - 367 * 20         # pg_proc_oid_index, a full page
812                           # PageGetFreeSpace withholds one more line
                              # pointer: 812 - 4 = 808. Exact.
>>> USABLE - 224 * 20         # pg_cast_oid_index, about half full
3672                          # 3672 - 4 = 3668. Exact again.
>>> 367 / entries_per_leaf(4)
0.9017...                     # the documented fillfactor, unprompted

The free-space prediction lands to the byte on two different indexes — one packed at ~90%, one barely half full — and on the packed one the documented fillfactor falls out unprompted. None of those numbers was used to build the model. That is what licenses the uuid and text rows, which no manual page prints.

Key width is a size problem, not a depth problem. A 28% fan-out reduction usually buys zero extra levels. The real consequence of size is cache pressure against shared_buffers.

Measure instead

SQL Written for this topic 
-- How wide is my index entry, really? Per-leaf, empirical.
CREATE EXTENSION IF NOT EXISTS pageinspect;   -- superuser only
SELECT blkno, live_items, avg_item_size, free_size
FROM bt_multi_page_stats('orders_pkey', 1, -1)
LIMIT 20;

-- Whole-index summary.
CREATE EXTENSION IF NOT EXISTS pgstattuple;   -- pg_stat_scan_tables role
SELECT * FROM pgstatindex('orders_pkey');

-- On-disk size, no extension needed.
SELECT pg_size_pretty(pg_relation_size('orders_pkey'));
Two cautions

Access is restricted. pgstattuple defaults to the pg_stat_scan_tables role; of pageinspect the manual says “All of these functions may be used only by superusers.”

avg_leaf_density and leaf_fragmentation are undefined by the manual. “Average density of leaf pages” and “Leaf page fragmentation” are the complete documented descriptions — no computation, no units, no threshold for “bad”. Anyone quoting a target number for these is not quoting PostgreSQL. Use live_items, avg_item_size and free_size instead, which mean exactly what they say.

Related mechanics, in one place

FactConsequence
“All indexes in PostgreSQL are secondary indexes” (§11.9); each relation is its own file (§66.1); CLUSTER is one-time. No clustered index. A random key's cost is confined to the B-tree on that key; it does not fragment the table.
HOT requires that “the update does not modify any columns referenced by the table's indexes” (§66.7). A mutable key forfeits HOT and forces a new entry in every index on the table.
full_page_writes costs one ~8 kB image per distinct page first dirtied after a checkpoint (§20.5.1). More scattered inserts plausibly mean more WAL. Inference — no PostgreSQL page connects this to key ordering. wal_compression (default off) targets these images.
INCLUDE indexes “can never use deduplication” (§65.1.4.3). A covering index forfeits the absorb-version-churn benefit. Nil cost on a static table, a real trade on a hot one.
TOAST triggers above ~2 kB (§66.2). bigint and uuid are not TOAST-able at all; a 36-char text id is two orders of magnitude below the trigger. TOAST never enters this decision.
The docs make no claim that join-key width affects join performance. Argue narrow keys from cache residency, not join speed. The work_mem spill argument is inference and is a step function, not a per-row tax.
