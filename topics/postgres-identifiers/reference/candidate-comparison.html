Candidate comparison

All seven candidates side by side: width, ordering, bit layout, spec status, and the one sentence that most decides against each. For lookup, not for reading.

Index behaviour

Entries per leaf are derived from the quoted constants in Index arithmetic, assuming 8 kB pages and MAXALIGN 8. Density is the level the split rule tends toward, not a guarantee.

Key Entry width Settles at Entries per leaf Relative
bigint sequence 20 B ~90% ~366 1.00
uuid, v7 / ULID / Snowflake-in-uuid 28 B ~90% ~262 0.72
uuid, v4 28 B ~50% ~145 0.40
text, 26 chars (ULID or TypeID suffix) 44 B ~90% if time-ordered ~166 0.45
The one-line version

Width takes a uuid from 366 entries to 262. Insert ordering takes it from 262 to 145. Most of the cost of a random key is the split behaviour, not the eight extra bytes.

Bit layouts

Format Layout Source
UUIDv4 122 random bits + 4-bit version (0b0100) + 2-bit variant (0b10). Both MUST be set. RFC 9562 §5.4
UUIDv7 unix_ts_ms 48 bits (0–47) · ver 4 bits = 0b0111 (48–51) · rand_a 12 bits (52–63) · var 2 bits = 0b10 (64–65) · rand_b 62 bits (66–127). 74 bits not fixed by format. RFC 9562 §5.7
ULID 48-bit ms timestamp + 80 random bits, rendered as 26 chars of Crockford's Base32 (0123456789ABCDEFGHJKMNPQRSTVWXYZ, excluding I, L, O, U). No version or variant bits. ULID spec, commit d0c7170
Snowflake (Twitter 2010) 41 bits time (custom epoch, 69 years) · 10 bits machine id (1024 machines) · 12 bits sequence (4096/ms/machine). Sign bit implied: 41+10+12 = 63 of a signed Long. README at snowflake-2010; the 5+5 datacenter/worker split and epoch 1288834974657 are in IdWorker.scala only
Snowflake (Discord) 42 bits time · 5 worker · 5 process · 12 increment, epoch 1420070400000. A family, not a format. Discord API reference
TypeID prefix (^([a-z]([a-z_]{0,61}[a-z])?)?$) + _ + 26-char base32 suffix that MUST decode to a valid UUIDv7. Total 26–90 chars. First suffix char MUST be ≤ 7. TypeID spec v0.3.0

The deciding sentence for each

Candidate What most decides for it What most decides against it
bigint identity Narrowest key, strictly ascending so the rightmost fastpath always applies, and ALWAYS makes it immutable at the schema level. nextval() is a call into one database — no offline or client-side generation at any price. Sequential by default, so it leaks volume and order if exposed.
UUIDv4 No structure at all: nothing to correlate, nothing to leak. RFC 9562 §8's own choice for anything security-adjacent. ~50% leaf density, a cold page per insert. The RFC calls the effect on B-trees “dramatic”.
UUIDv7 Offline generation with ~90% leaf density. Native in PG18. The RFC's own recommendation over v1 and v6. Carries a plaintext creation timestamp, and PostgreSQL's monotonicity is guaranteed only within one backend — not across a connection pool.
ULID Character-efficient 26-char rendering; a genuinely good design that UUIDv7 inherited from. Spec unversioned and last committed 2019-05-23, no security section, no version/variant bits, and its monotonic mode increments by exactly 1 — the construction RFC 9562 §6.2 says SHOULD NOT be used where unguessability matters.
Snowflake 64 bits and time-ordered — the only candidate that is both. Repo archived (last push 2020-07-22); worker-id assignment across autoscaling is the real cost; 64-bit ids break JavaScript's 53-bit numbers.
TypeID A real UUIDv7 underneath, plus type-safe ergonomics at the API boundary. Both official SQL encodings are worse than necessary — the text one is ~2× a native uuid, the composite stores a varchar(63) table-constant prefix per row. Adopt it as an API format, not a storage format.
Natural key One less column, no join to read the meaningful value, and the uniqueness constraint expresses a real business rule. The issuing authority controls the format and will change it on a date it chooses — ISBN went 10→13 digits on 2007-01-01, and the migration is a rewrite under ACCESS EXCLUSIVE propagated to every referencing table.

The ladder

# Situation Choice
1 Single-node, ids not publicly meaningful bigint GENERATED ALWAYS AS IDENTITY. Serialise as a string.
2 Ids in URLs or third-party hands Dual-identifier: bigint internal + uuidv7() external
3 Client-side or offline generation required Single uuid primary key holding a v7
4 Id is a security-relevant surface UUIDv4 for the external id, on RFC 9562 §8's advice
What survives every rung

Key on something you control, never update it, and put a unique constraint on anything that must be unique — including the identifier your framework already thinks is unique.
