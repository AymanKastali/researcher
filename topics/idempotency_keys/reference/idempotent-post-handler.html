The Idempotent POST Handler

The algorithm, the decision table and the vocabulary, compressed onto one printable page. Built from Lesson 01, Lesson 02, Lesson 03 and Lesson 04.

The one-sentence problem

A client whose request times out cannot distinguish never arrived from still running from completed, response lost — so it must either risk a duplicate or risk a loss. An idempotency key is a name the client picks in advance, so the question becomes a lookup the server can answer.

The algorithm

  1. Claim. INSERT … ON CONFLICT DO NOTHING on (caller, key). Never read-then-write.
  2. Branch on the conflict — see the decision table.
  3. Work + record, in one transaction. Business write, completed state, and the stored response commit together. Holds only while the work is local — if it calls another system, see atomic phases.
  4. Return the stored response — same status code and body, original and every replay.

Decision table

State of the keyResponse
Absent — claim succeeded Process normally. Whatever the operation's own status code is.
Present, completed, same payload Replay the stored response_code and response_body. Never re-execute.
Present, in_progress, same payload 409 Conflict. Nothing to replay yet; the client retries shortly.
Present, payload fingerprint differs 422 Unprocessable Content. A client bug — the key was reused.
Header absent on an endpoint that requires it 400 Bad Request, with a link to your idempotency documentation.

Status codes from draft-ietf-httpapi-idempotency-key-header-07 §2.6–2.7. All are SHOULD, and the draft is expired — convention, not standard.

Stored, or not stored

The guarantee covers only what the endpoint produced. Everything in front of the idempotency layer is outside it — "We save results only after the execution of an endpoint begins."

ResponseCached against the key?
2xx successYes — replayed until reaped.
4xx from the endpoint (decline, business rule) Yes. Same key returns the same refusal. Fix the request → new key.
500 from inside the endpoint Yes, and permanently. Treat as indeterminate, not failed.
400 / 401 / 429 raised in front of the layer No. Nothing executed; the same key may answer differently later.
409 concurrent retry No — the layer emitted it. Safe to retry unchanged.

Scope, fingerprint, or ignored

Every field of an incoming request is in one of three buckets. The first two are both decisions, and they are not interchangeable.

BucketMeaning, and what moving a field there does
Scope — you look up with it Same key, different scope value ⇒ a different operation, which executes. Must be derived server-side from the authenticated caller — draft §5 requires attributes "known only to the resource". AWS scopes on Region/Zone on purpose.
Fingerprint — you compare after the lookup Same key, different value ⇒ a key reuse, so 422. Never put it in the lookup itself.
Ignored — in neither A field a client can change between attempts without you noticing. Fine, as long as it is a choice.

Scope also has a time axis: Stripe requires keys unique "within your account over the last 24 hours, at a minimum" — so the retention window is the temporal half of the scope, not housekeeping.

The table

CREATE TABLE idempotency_key (
    user_id        bigint      NOT NULL,   -- scope: never key on the bare string
    key            text        NOT NULL,
    request_hash   text        NOT NULL,   -- fingerprint -> the 422 case
    state          text        NOT NULL,   -- 'in_progress' | 'completed'
    response_code  int,                    -- the two columns people forget
    response_body  jsonb,
    created_at     timestamptz NOT NULL DEFAULT now(),
    PRIMARY KEY (user_id, key)
);

When the work leaves your database

A foreign state mutation is any step your transaction cannot roll back. The test is not who operates the system — a broker you own, a cache, another of your own services behind HTTP all count. "Once we make our first foreign state mutation, we're committed one way or another."

Cut the request into atomic phases, each committing a recovery point onto the key row. Three mechanical rules:

  1. "Upserting the idempotency key gets its own atomic phase."
  2. "Every foreign state mutation gets its own atomic phase."
  3. Everything else groups into the phases between them — local writes are free.
Commit before you call out "Atomic phases should be safely committed before initiating any foreign state mutation." Putting the call inside the transaction means a failed commit rolls back the record but not the charge — and the key row vanishes too, so the retry looks new and double-charges. It also holds a row lock across a network call.
A resumed phase reloads A retry re-enters at its recovery point, not at the top, so no local variable from an earlier phase exists. Carrying state down works on the first attempt and crashes on every resume.
Replay is the terminal state A finished key enters the loop, breaks immediately, returns the stored response. Duplicate detection was never bolted on the front — it is the last node of the machine.
Put a derived key on your own outbound calls Now you are the client. Derive it from something stable (the key row's id) — a value generated at call time differs on the retry and buys nothing. The recovery point tells you the call may have happened, never whether it did, so your correctness becomes a property of the far side's API.
Defer what you can — the deferral is a transactional outbox Stage the work as a row in the same transaction and let a separate process drain it: "we get a guarantee that the operation commits along with the rest of the transaction." The send stops being a foreign call and becomes a local write.
"Indeterminate" inverts To a client of an API that accepts a key, a timeout means retry. To a caller of one that does not: "Indeterminate errors like a connection reset or timeout will have to be marked as failed." The rule never depended on the error — only on whether the far side can absorb a duplicate. Ambiguity is not permission.

Rules that are easy to get wrong

One transaction Claim state, stored response and business write commit together. Mark-first loses the work silently; work-first double-executes. A marker is only trustworthy if it commits with the thing it marks.
Fingerprint is a check, not a lookup Look up on (caller, key), then compare. Fold the fingerprint into the lookup and a reused key with a changed payload finds nothing, claims a new row and executes twice. Hash the method and path too, not just the body.
Store the body The retrying client never saw the original result. Skipping the work but returning an empty acknowledgement leaves it just as stuck.
Cache failures too Stripe stores the status and body "regardless of whether it succeeds or fails", 500s included. The endpoint becomes a function of the key.
Scope the key Composite lookup key (caller + key), and the caller half must be derived server-side — anything the client sends, an attacker sends too. Otherwise a guessed key reads another client's stored response (draft §5). Remember why it matters here and not elsewhere: a replay returns before the endpoint runs, so the ownership checks inside your handler never execute.
Scope vs entropy Scope defends you against other people; entropy defends you against yourself. Two of one account's own operations colliding on a short key means the second silently never happens — and it looks exactly like idempotency working. Validate the key against a published format before using it in a lookup.
Two replay contracts Byte-identical replay (Stripe) vs idempotent effect with a current body (Google AIP-155: "permissible to substitute the historical success response with a similar response that reflects more current data"). Know which one you promise.
Reap old keys Two independent requirements: longer than any client's retry window, and long enough that a Friday incident is repairable on Monday. The larger wins. Past the horizon a retry silently becomes a new request. Stripe 24h; Brandur ~72h. Publish it (draft §2.3) — and flag rows still in_progress at the cutoff for a human rather than deleting them.
A cached 500 can stay wrong The stored response never changes, but the underlying state may later be reconciled forward into a real charge. The correction must reach the client out of band — a webhook. Same answer every time ≠ the right answer.
One key per operation, not per attempt A fresh UUID per click makes a double-submit two honest operations. Derive the key from a stable object (cart id) when the duplicate you fear is the user, not the network.
The layer has a front door Rate limiting, auth and request validation run before it, so those responses are not stored and are not replayable.
POST only GET and DELETE are already idempotent per RFC 9110 §9.2.2. A key on them does nothing.

Vocabulary

Idempotency key "A unique value generated by the client which the resource uses to recognize subsequent retries of the same request." One per logical operation, not per attempt.
Idempotency fingerprint A hash the server derives from the request payload, used alongside the key to detect the 422 case. Draft §2.4.
Replay Returning the stored response instead of executing. Stripe flags it with the response header Idempotent-Replayed: true.
Scope The other half of the composite lookup key — the caller identity, plus in some APIs a location (AWS Region/Zone) and always a time window. Decides what counts as the same request.
Atomic phase Brandur's term: local state mutations that occur in transactions between foreign state mutations.
Foreign state mutation Work inside the handler that touches another system and cannot be rolled back — an email, a card charge, a partner API. The case the single transaction does not cover.
Recovery point "A name of a check point that we get to after having successfully executed any atomic phase or foreign state mutation." Stored on the key row; a retry resumes there.
Completer A process that finishes requests whose clients dropped mid-flight. The reaper's opposite number — one ends requests, the other abandons them. Needs an internal auth path that can retry anyone's request, so keep it small and never let it return a body to a caller.
Enqueuer Drains staged job rows to the real queue after their transaction commits — the drain half of a transactional outbox. Also called a relay or a dispatcher.
Indeterminate Stripe's word for the state a 500 leaves you in. Not "failed" — unknown. What you should do about it depends on the far side, not on the error.
