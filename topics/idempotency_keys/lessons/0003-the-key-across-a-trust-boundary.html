Lesson 03 · Idempotency Keys

The Key Across a Trust Boundary

The key is a string the client chooses, and Lesson 02 filled a table with response bodies addressed by it. One column decides whether that table is a cache or a disclosure — and the same column decides what "the same request" even means.

First, from memory

Two from last lesson, before anything new. One attempt each.

  1. Why is a 400 raised by the endpoint stored against the key, when caching a rejection sounds like a bug?

    Correct. The retry exists because the first response was lost. If the rejection is not stored, the retry is an entirely new request and the server re-runs the whole operation with no memory of the decision it already made. Storing it makes the endpoint a function of the key in the failure case too.

    It does have that effect, but stopping the client is not the reason — the client is retrying precisely because it does not know anything yet.

    Cost is never the argument in this topic. The answers turn on what the client can and cannot know.

    A matching fingerprint is what gets you onto the replay path; it is not a reason to have stored anything.

  2. Your window is 24 hours and a client retries with the same key 30 hours later. What does it get?

    There is no row left to compare against, so there is nothing that could raise an error.

    Pruning deletes. There is no archive behind it, and these rows are explicitly not a permanent record.

    The row is gone, so nothing is held. A conflict needs a live claim.

    Correct, and the silence is the whole danger. Expiry does not fail loudly — it just stops protecting you. Hold on to that, because in a moment the window turns out to be part of the key's scope, not a separate housekeeping setting.

The win for this lesson: by the end you can answer "what is your idempotency key scoped to?" with a column, a reason, and a threat — and you can explain why the same field put in the scope rather than the fingerprint changes the API's behaviour rather than its security.

What you actually built last lesson

Line the two facts up next to each other, because separately they are unremarkable and together they are a problem.

  • The table stores the full response body of every request — Lesson 02.
  • The row is addressed by a string the client picked — Lesson 01.

So you have built a cache of real, per-customer payloads, and you have handed the address bar to the caller. The draft's security section names the consequence directly:

When an idempotency implementation allows low entropy keys, attackers MAY determine other keys and use them to fetch existing idempotent cache entries, belonging to other clients. draft-ietf-httpapi-idempotency-key-header-07 §5

Make it concrete. A client generates readable keys — order-1001, order-1002 — which is a reasonable-looking choice and satisfies "unique". An attacker with any account on your API sends a POST with Idempotency-Key: order-1002. The key is found, it is marked completed, so the server does the thing you designed it to do: it replays the stored status code and body. Which belongs to somebody else.

The replay path never reaches your authorisation code

This is worse than an ordinary leaky query, and the reason is structural. Walk Lesson 01's handler again: on a duplicate, the server returns Response(existing.response_code, existing.response_body) and returns before the endpoint runs at all. Every ownership check you wrote — does this caller own this order? — lives inside the endpoint. On the replay path none of it executes. It cannot: the whole point of a replay is to skip the work.

So the idempotency layer is the one place in your API where a request can be answered with data your handler never computed for this caller. It has to carry its own access control, because it sits in front of everybody else's.

The leak is the draft's claim. Why it evades authorisation is argued here from the mechanism, not quoted — no source examined spells that step out.

The fix is one column, and where its value comes from matters

The draft's recommendation is three bullets long. This is the third, and it is the one worth memorising:

On the resource, implement a unique composite key as the idempotent cache lookup key. For example, a composite key MAY be implemented by combining the idempotency key sent by the client with other client specific attributes known only to the resource. draft-ietf-httpapi-idempotency-key-header-07 §5

Known only to the resource is the load-bearing phrase, and it is a statement about provenance rather than about the column. A scope value that arrives in the request is not a scope at all — it is another field the attacker fills in.

# Where the scope value comes from is the entire security property.

scope = request.headers["X-Tenant-Id"]     # WRONG — forgeable. Name any tenant, read their replay.

scope = request.headers["Authorization"]   # WRONG — too narrow. Rotate the credential and every
                                           #         in-flight retry misses and re-executes.

scope = principal.account_id               # RIGHT — derived server-side from the authenticated
                                           #         caller, on the same boundary as the data.

The first line is the draft's threat restated as code. The second is not from any source examined — it is the consequence of choosing a credential rather than an identity, and it is worth arguing about rather than accepting. The third is the shape Brandur Leach's schema takes.

That schema makes the scope a real constraint rather than a convention:

CREATE UNIQUE INDEX idempotency_keys_user_id_idempotency_key
    ON idempotency_keys (user_id, idempotency_key);

His reason is stated the positive way round, which is the more useful way to remember it: "We've made idempotency_key unique, but across (user_id, idempotency_key) so that it's possible to have the same idempotency key for different requests as long as it's across different user accounts." Scope is not only a wall between tenants; it is what stops one tenant's choice of key from constraining everyone else's. He also hangs a foreign key off it — REFERENCES users(id) ON DELETE RESTRICT — so the scope is enforced by the database.

Lesson 01's table already had user_id in the primary key, so nothing here changes the code. What changes is that you can now say why it is there, and the harder question is which identity belongs in it. No source examined settles that. The rule that survives scrutiny: the scope should be the boundary the data itself is drawn on — the thing that determines who is allowed to see this response — and not the credential that happened to authenticate the call, because credentials rotate and retries outlive them.

Scope is not only a security decision

Here is the turn, and it is the part most people have never considered. AWS uses the same mechanism under a different name — a ClientToken parameter rather than a header — and documents its scope as a feature, with named modes. The first is called Regional:

Requests are idempotent in each Region. However, you can use the same request, including the same client token, in a different Region. Amazon EC2 — Ensuring idempotency in API requests

Read that as a user and it sounds like a bug report. The same token, the same parameters, two instances launched — spelled out in their own example: "if you send an idempotent request to launch an instance in the us-east-1 Region, and then use the same client token in a request in the eu-west-1 Region, we launch instances in each of those Regions." The mechanism did not fail. It was scoped to a Region, and two Regions are two scopes.

Now put that beside the mismatch rule from the same page, with the exception italicised:

If you retry a successful request using the same client token, but one or more of the parameters are different, other than the Region or Availability Zone, the retry fails with an IdempotentParameterMismatch error. Amazon EC2 — Ensuring idempotency in API requests

Region and Availability Zone are parameters of the request that are deliberately excluded from the comparison — because they are in the scope instead. That one sentence is the whole design decision, written down.

Every field is scope, fingerprint, or ignored — and you choose

Lesson 02 established the fingerprint: the thing you compare after the lookup to catch a reused key. Scope is the thing you look up with. Each field of an incoming request falls into one of three buckets, and the same field in the same API can legitimately go in either of the first two:

Region in the fingerprint → the same token in two Regions is a key reuse, and the second call errors. Region in the scope → the same token in two Regions is two separate operations, and both succeed. AWS chose the second. Neither is wrong; they answer different questions, and the question is what counts as the same request?

That is why "what is your key scoped to?" is a sharper interview question than "do you use idempotency keys?" — the first one has a design behind it.

Part of a RunInstances callBucket, and what moving it would do
ClientToken The key itself. Nothing to decide.
Region / Availability Zone Scope. Move them into the fingerprint and a client that retries into a different Zone gets IdempotentParameterMismatch instead of an instance.
ImageId, InstanceType, KeyName Fingerprint. Move them into the scope and two genuinely different launches under one token would both execute — the duplicate you were preventing.
Anything in neither bucket Ignored — which is a decision too. A field you compare on neither side is one a client can change between attempts without you ever noticing.

Scope also has a cost, and AWS prices it in the open. A wider scope deduplicates across more of your system and therefore depends on more of it:

If one of the Availability Zones in the requested Region is not available, RunInstances requests that use regional idempotency could fail. … we recommend that you use zonal idempotency when launching instances. Amazon EC2 — Ensuring idempotency in API requests

Narrower scope, more availability, weaker deduplication. That trade is the honest answer to "why not just scope everything globally?" — a global scope is a global dependency.

The scope has a time axis too

Stripe states the client's obligation in a single sentence, and it is worth reading twice because two different dimensions are hiding in it:

If you decide to send idempotency keys manually, make sure the tokens being used are sufficiently unique to unambiguously identify a single operation within your account over the last 24 hours, at a minimum. Stripe — Advanced error handling

Uniqueness is not required absolutely. It is required within a scope (the account) and within a window (the retention period from Lesson 02). Those are the two axes of the same lookup, and the retention window you chose last lesson turns out not to be housekeeping at all — it is the temporal half of the scope. Shorten it and you are not just freeing disk, you are narrowing the region in which a key means anything.

Validate the key before you look it up

The draft's other two bullets are about the key as a string arriving from outside, and the first failure they name is not a leak:

When the resources does not validate the idempotency key in the client request and performs a idempotent cache lookup, there can be security attacks (primarily in the form of injection), compromising the server. draft-ietf-httpapi-idempotency-key-header-07 §5

Quoted verbatim, grammar included. The draft is an expired Internet-Draft and reads like one in places.

The remedy is two more bullets — "Establish a fixed format for the idempotency key and publish the key's specification" and "Always validate the key as per its published specification before processing any request" — and the moment you go looking, you find that every vendor already did exactly this. The limits that look like trivia are the published specification the draft is asking for:

APIIts published key specification
Stripe "Idempotency keys are up to 255 characters long." Generous, because the key is a header on an authenticated request.
AWS EC2 "A client token is a unique, case-sensitive string of up to 64 ASCII characters." Character set as well as length.
Google Two lines of a comment on the request_id field: "Restricted to 36 ASCII characters" and "A random UUID is recommended". 36 is the length of a hyphenated UUID — here the format is the validation.

Entropy gets recommended by everyone and justified two different ways, which is worth keeping straight. Stripe frames it as an accident: "we suggest using V4 UUIDs, or another random string with enough entropy to avoid collisions." The draft frames it as an adversary — low-entropy keys let an attacker "determine other keys". Google's rationale is the accident again: "standardizing on a universally unique identifier drastically reduces the chance for collisions when done correctly."

Same advice, two problems, and they are solved by different columns. Scope defends you against other people; entropy defends you against yourself. Once the lookup is (account, key), no amount of guessing reaches another tenant's rows — but two requests from the same account that collide on a short key still merge into one, and the second operation silently never happens. That failure is invisible, because from the outside it looks exactly like idempotency working.

What the boundary actually promises

One last thing crosses this boundary, and it is the promise itself. Lessons 01 and 02 have been saying replay the stored response, and Stripe means that literally — byte-identical body, plus Idempotent-Replayed: true so the client can tell. Google's guidance explicitly permits something else:

In some unusual situations, it may not be possible to return an identical success response. For example, a duplicate request to create a resource may arrive after the resource has not only been created, but subsequently updated; because the service has no other need to retain the historical data, it is no longer feasible to return an identical success response. Google AIP-155 — Request identification
In this situation, the method may return the current state of the resource instead. In other words, it is permissible to substitute the historical success response with a similar response that reflects more current data. Google AIP-155 — Request identification
"Replay the stored response" is one contract, not the only one

There are two promises in circulation and they are not interchangeable. Byte-identical replay (Stripe) says: the second call returns exactly what the first one did, whatever has happened since. Idempotent effect (Google) says: the second call performs no further action, but the body you get back may reflect the world as it is now.

A client that diffs a replayed response against its original is correct on one of those APIs and broken on the other. And note that AWS lands in the same place as Google without ever framing it as a contract — "the result might contain updated information, such as the current creation status."

So the question to ask of any API, including your own: on a duplicate, do you promise the old bytes or the current truth? Answering "the stored response" without noticing there was a choice is the tell that you have implemented one and read about the other.

What you can now do

Explain why a client-chosen key addressing a response cache is an access-control problem, and why the replay path cannot rely on your handler's ownership checks; state the composite-lookup rule and insist that the scope value be derived server-side; sort any request field into scope, fingerprint or ignored, and say what moving it between the first two does to the API's behaviour; price a wider scope against availability; name the two axes of uniqueness Stripe requires; and distinguish the two replay contracts that vendors quietly disagree about.

Say it out loud

60 seconds, no notes. The prompt is the one that follows any confident description of the algorithm: "how would you scope idempotency keys in a multi-tenant API?" Cover what goes in the lookup and where that value comes from, the attack it prevents, why the replay path needs its own access control, and the fact that scope also decides what counts as the same request.

"The lookup key is composite — the caller's account id plus the client's key — and the account id is derived server-side from whatever authenticated the request. It must never come out of the request itself, because anything the client sends, an attacker also sends.

The attack it prevents is a read, not a write. The table holds full response bodies addressed by a string the client chose, so with low-entropy keys someone can guess another tenant's key and get their response replayed back. And that path is nastier than a normal leaky query, because the replay returns before the endpoint runs — so every ownership check I wrote is inside code that never executes. The idempotency layer sits in front of my authorisation, so it has to carry its own.

Scope and entropy solve different halves. Scope stops other people reaching my rows. Entropy stops one account colliding with itself, where the second operation just silently doesn't happen and looks exactly like idempotency working. So I'd require UUIDv4, publish the format, and validate it before I use it in a lookup.

The part people miss is that scope isn't only security — it decides what 'the same request' means. AWS scopes client tokens per Region, so the same token in two Regions launches two instances on purpose, and Region is excluded from the parameter comparison because it's in the scope rather than the fingerprint. Every field is scope, fingerprint, or ignored, and moving one between the first two changes behaviour, not just safety. Wider scope also means a wider dependency — AWS actually recommends the narrower zonal scope because a regional one can fail if a single Zone is down.

And there's a time axis: Stripe asks for keys unique within your account over at least 24 hours, so the retention window is the temporal half of the scope, not housekeeping."

Score what you dropped. The three most costly omissions are "derived server-side", "the replay returns before the endpoint runs", and scope-versus-fingerprint deciding behaviour.
