Lesson 04 · Idempotency Keys

Foreign State Mutations

Every lesson so far assumed the work inside the key's transaction was a database write, so a failure could be rolled back. The moment that work is a call to somebody else's API, ROLLBACK stops being an answer — and the handler has to be cut into pieces that each commit on their own.

First, from memory

Two questions, both from earlier lessons. Answer before you check: retrieving a thing you half remember is what makes it stick, and rereading it is not.

The win for this lesson: by the end you can take any handler that calls an external service and cut it into phases at the right places, name what each retry re-enters, and say precisely what happens when the far side does not support idempotency keys — which is the question that separates people who have read about this from people who have shipped it.

Where the single transaction stops working

Lesson 01's handler had a shape you could hold in your head: claim the key, do the work, store the response, commit. It was safe because every step was a write to one database, so a crash anywhere meant the whole thing vanished and the retry started clean.

Brandur Leach — who built this at Stripe — gives the thing that breaks it a name:

To shore up our backend, it's key to identify where we're making foreign state mutations; that is, calling out and manipulating data on another system. This might be creating a charge on Stripe, adding a DNS record, or sending an email. Brandur Leach — Implementing Stripe-like Idempotency Keys in Postgres

And then the sentence the whole lesson hangs off:

unlike a local set of operations where we can leverage an ACID store to roll back a result that we didn't like, once we make our first foreign state mutation, we're committed one way or another … We've pushed data into a system beyond our own boundaries and we shouldn't lose track of it. Brandur Leach — Implementing Stripe-like Idempotency Keys in Postgres

The blunt version, worth keeping in your head for the rest of this lesson: ROLLBACK does not un-send an email.

Your own infrastructure is foreign too

The instinct is to read "foreign" as "third party" and conclude this lesson is about payment providers. It is not:

It's tempting to treat emitting records to Kafka as part of atomic operations because they have such a high success rate that they feel like they are. They're not, and should be treated like any other fallible foreign state mutation. Brandur Leach

This has a name — the dual-write problem: one logical operation changing two systems, with no transaction spanning both, so any crash in the gap leaves them disagreeing. A broker you own, a cache, a search index, another one of your own services behind HTTP — all foreign. The test is not who operates it. The test is whether your transaction can roll it back.

The tempting fix, and the two ways it fails

The obvious move is to keep the one-transaction shape and put the API call inside it. Almost everyone tries this first, and it is worth being able to say exactly why it is wrong, because "it just is" does not survive follow-up.

# WRONG. Both failure modes below are worse than the problem being solved.

with db.transaction():
    key_row = claim(idempotency_key, principal.account_id)
    ride = Ride.create(user_id=principal.account_id)
    charge = stripe.charges.create(amount=2000, currency="usd")   # <-- foreign, inside the tx
    key_row.set_response(201, {"ride_id": ride.id})

Failure one: the rollback lies. Suppose the charge succeeds and the commit then fails — a deadlock, a connection drop, the process being killed. Postgres dutifully rolls back the ride and the key row. The charge does not roll back. You have taken the customer's money and kept no record that you did, and because the key row vanished too, the retry is indistinguishable from a first attempt and charges them again.

Failure two: the transaction is held open across a network call. The row lock taken when you claimed the key is now held for as long as the third party takes to answer. A provider having a slow afternoon becomes your database running out of connections. Brandur states the rule as a positive instruction:

Atomic phases should be safely committed before initiating any foreign state mutation. If the call fails, our local state will still have a record of it happening that we can use to retry the operation. Brandur Leach — Implementing Stripe-like Idempotency Keys in Postgres

The contention argument is mine, not Brandur's — he gives the correctness reason above and does not discuss lock duration. It follows from Lesson 01's SELECT … FOR UPDATE claim step, and like everything in this topic it is unmeasured.

Cut the request into phases

If one transaction cannot span the call, use several, and make the boundaries deliberate. Two definitions carry the design:

An atomic phase is a set of local state mutations that occur in transactions between foreign state mutations. We say that they're atomic because we can use an ACID-compliant database like Postgres to guarantee that either all of them will occur, or none will. Brandur Leach
A recovery point is a name of a check point that we get to after having successfully executed any atomic phase or foreign state mutation. Its purpose is to allow a request that's being retried to jump back to the point in the lifecycle just before the last attempt failed. Brandur Leach

So a request is no longer one transaction. It is a chain of them, with the foreign calls in the gaps, and a marker on the key row saying how far it got. Where to cut is not a judgement call — there are three rules, and they are mechanical:

RuleWhat it means in practice
"Upserting the idempotency key gets its own atomic phase." Claiming the key commits on its own, before any work at all. If everything after it dies, the claim survives and the retry has something to resume from.
"Every foreign state mutation gets its own atomic phase." Each external call is bracketed: commit, call, then commit the result. Two calls never share a phase, because after the first one succeeds you can no longer undo it.
Everything else groups into the phases between them. "Even if there are 100 operations against an ACID database between two foreign state mutations, they can all safely belong to the same phase." Local work is free — the database makes it atomic for you.

The key row grows one column to hold the marker, and it is a plain string:

recovery_point TEXT NOT NULL
    CHECK (char_length(recovery_point) <= 50),

From Brandur's idempotency_keys schema — the same table Lesson 02 filled in, which already carried response_code, response_body and locked_at. Every request starts at started and ends at finished.

The handler becomes a state machine

Once phases have names, the handler stops being a straight line and becomes a loop over them. Brandur's states form "a directed acyclic graph (DAG)" — it moves one direction only and never cycles back.

def handle(key_row, principal):
    while True:
        if key_row.recovery_point == "started":
            with db.transaction():                              # tx2 — local writes only
                Ride.create(idempotency_key_id=key_row.id, user_id=principal.account_id)
                key_row.set_recovery_point("ride_created")

        elif key_row.recovery_point == "ride_created":
            ride = Ride.find(idempotency_key_id=key_row.id)     # reload: a retry enters HERE
            charge = stripe.charges.create(                     # foreign — outside any transaction
                amount=2000, currency="usd",
                idempotency_key=f"{key_row.id}-charge",         # our key, stable across retries
            )
            with db.transaction():                              # tx3 — record what already happened
                ride.update(charge_id=charge.id)
                key_row.set_recovery_point("charge_created")

        elif key_row.recovery_point == "charge_created":
            ride = Ride.find(idempotency_key_id=key_row.id)
            with db.transaction():                              # tx4 — receipt staged, not sent
                StagedJob.insert(job_name="send_receipt", job_args={"ride_id": ride.id})
                key_row.set_response(201, {"ride_id": ride.id})
                key_row.set_recovery_point("finished")

        elif key_row.recovery_point == "finished":
            break

    return Response(key_row.response_code, key_row.response_body)

Shape, not a benchmarked implementation — nothing in this topic has been run. Brandur's original is Ruby and wraps each phase in a SERIALIZABLE transaction; this is the same structure in this course's language. Note the reloads: a retry re-enters at its recovery point, not at the top, so no local variable from an earlier phase exists any more. Carrying ride down from the first branch would work on a first attempt and crash on every resume.

The replay from Lesson 01 is just one more state

Look at what happens when a completed key arrives: the loop is entered, the finished branch breaks immediately, and the stored response is returned. Brandur describes it exactly that way — "An idempotency key that was already finished will enter the loop, break immediately, and send back whatever response was stored onto it."

So the duplicate-detection you learned in Lesson 01 was never a special case bolted on the front. It is the terminal state of a machine that was always there; you just could not see it while every request finished in one transaction. A half-finished request and a finished one are handled by the same code — one resumes, one returns.

Notice which key is on the outbound call

The line worth stopping on in that handler is idempotency_key=f"{key_row.id}-charge". You are now on the other side of the mechanism this whole course has been teaching: a client sending a key to somebody else's server. Everything Lesson 01 said about callers applies to you.

It has to be derived from something stable — the key row's own id — rather than generated fresh, because a value generated at call time would be different on the retry and would buy you nothing. That is what makes this specific failure survivable:

A server process dies while waiting for a response from Stripe: Luckily, the call to Stripe was also made with its own idempotency key. The client retries and a new call to Stripe is invoked with the same key. Stripe's own idempotency guarantees ensure that we haven't double-charged our user. Brandur Leach

This is the most uncomfortable moment in the design and it is worth sitting with. The atomic phase tells you the call may have happened. It cannot tell you whether it did. The only reason the retry is safe is that the far side deduplicates it for you — which means your correctness is now a property of somebody else's API, not of your database.

Do not make the call at all, if you can avoid it

Before engineering around a foreign call, check whether it needs to be in the request:

In-band foreign state mutations make a request slower and more difficult to reason about, so they should be avoided when possible. In many cases it's possible to defer this type of work to after the request is complete by sending it to a background job queue. Brandur Leach

The charge cannot be deferred — you need to know whether it worked before you answer the caller. The receipt email absolutely can. And look at what deferring it does in the handler above: the email never becomes a foreign call at all. It becomes a row.

CREATE TABLE staged_jobs (
    id       BIGSERIAL PRIMARY KEY,
    job_name TEXT  NOT NULL,
    job_args JSONB NOT NULL
);
This table has a name

Brandur's justification for it: "because we're using a transactionally-staged job drain, we get a guarantee that the operation commits along with the rest of the transaction." A separate process — he calls it the enqueuer — moves rows out to the real queue after the transaction commits.

That shape is the transactional outbox: a table written in the same transaction as the business state, drained to its real destination by a separate process once that transaction has committed. The work is recorded locally before it is ever attempted remotely, so a crash in between loses nothing — the row is still there to retry from. Different write-ups call the drainer an enqueuer, a relay, or a dispatcher; it is one pattern.

Hence the instruction: "Work should always be offloaded to background queues wherever possible." Every foreign call you turn into a staged row is one fewer phase that can strand a request halfway.

Someone has to finish what the client abandons

The phase machine resumes a request when the client retries. It has no answer for a client that simply stops — and clients stop all the time: the user closed the tab, the mobile app was killed, the calling service was redeployed mid-flight. That request is now sitting at charge_created, money taken, no receipt, no response ever delivered.

A stretch goal is to implement a completer. Its only job is to find requests that look like they never finished to satisfaction and which it looks like clients have dropped, and push through to completion. Brandur Leach

Lesson 02 already gave you a reaper that deletes expired keys. The completer is its opposite number and they must not be confused — one ends requests, the other abandons them. Note what Brandur says the completer needs: "a specialized internal authentication path that allows it to retry anyone's request." Read that next to Lesson 03 and it should make you slightly nervous. It is a process that deliberately steps around the scope you spent a whole lesson building, which means it is exactly the sort of component that needs to be small, audited, and incapable of returning a response body to anyone.

That last observation is mine. Brandur raises the internal auth path without comment, and no source examined discusses its risk.

When the far side has no idempotency key

Everything above assumed the external API is either naturally idempotent or accepts a key. When it does neither, the pattern reaches its limit, and being honest about that limit is worth more than a clever workaround.

If we try to make a non-idempotent foreign state mutation and we see a failure, we may have to persist this operation as permanently errored. In many cases we won't know whether it's safe to retry or not, and we'll have to take the conservative route and fail the operation. Brandur Leach
"Indeterminate" flips meaning depending on which side you are standing on

Lesson 01 taught Stripe's rule to clients: a 500 or a timeout is indeterminate, so retry it with the same key. Now read Brandur's rule to callers of a non-idempotent API: "Indeterminate errors like a connection reset or timeout will have to be marked as failed."

Same evidence, opposite instruction. The advice never depended on the error — it depended on whether the far side can absorb a duplicate. With an idempotency key, indeterminate means retry. Without one, indeterminate means stop, and get a human, because a retry is a coin-flip between a lost operation and a doubled one.

The only exception Brandur allows is an explicit signal: an error that "tell us explicitly that it's okay to retry." Which is precisely what Stripe's Stripe-Should-Retry header from Lesson 02 is for. Ambiguity is not permission.

Both quotes are sourced; putting them side by side and drawing the inversion is this lesson's argument, not a claim either source makes.

Which yields the one-line conclusion, and Brandur puts an exclamation mark on it: "This is why you should implement idempotency and/or idempotency keys on all your services!" Every service that accepts a key removes a permanently-errored state from somebody else's system. That is the real reason to build what this course has been describing — not your own retries, but everyone downstream of you.

One prerequisite, stated plainly

It's worth mentioning that none of this is possible on a non-ACID store like MongoDB. Without transactional semantics a database can't ever guarantee that any two operations commit atomically — every operation against your database becomes equivalent to a foreign state mutation because the notion of an atomic phase is impossible. Brandur Leach

Written in 2017. MongoDB added multi-document transactions in 4.0 (2018), so the specific example has aged; the structural claim has not. If two writes cannot commit together, there is no atomic phase, and every step is a foreign state mutation. Worth saying out loud if an interviewer names a store — the reasoning is what is being tested, not the trivia.

What you can now do

Define a foreign state mutation and explain why the test is rollback-ability rather than ownership; say what goes wrong when an API call is placed inside the transaction, in both the correctness and the contention sense; cut a handler into atomic phases using the three rules and name the recovery points between them; explain why a resumed phase must reload rather than carry state; recognise the duplicate-replay you learned first as the terminal state of that machine; put a derived idempotency key on your own outbound calls and say why it must be stable; distinguish the completer from the reaper; and state what changes when the far side has no key — including why "indeterminate" reverses meaning.

Say it out loud

60 seconds, no notes: "your endpoint has an idempotency key and it needs to charge a card. Walk me through it." Cover why the call cannot be in the transaction, where the phases cut, what a retry re-enters, which key goes on the outbound call, and what changes if the far side has no key.

"The charge is a foreign state mutation — once it lands I can't roll it back, and the test isn't whether it's a third party, it's whether my transaction can undo it. Kafka and my own services count.

So the call can't go inside the transaction. If the charge succeeds and the commit then fails, I've taken the money and rolled back the record — including the key row, so the retry looks brand new and charges them twice. It also holds a row lock across a network call, which turns their slow afternoon into my connection pool.

Instead I cut the request into atomic phases. Claiming the key is its own phase, every foreign call is its own phase, and all the local work in between groups together — local writes are free because the database already makes them atomic. Each phase commits a recovery point on the key row, so the handler is a loop over states: started, ride created, charge created, finished. A retry re-enters at its recovery point rather than at the top, which means a phase has to reload what it needs — nothing carries over from an earlier phase.

The nice part is that the replay from Lesson 01 is just the terminal state. A finished key enters the loop, breaks immediately, and returns the stored response.

On the outbound charge I send my own idempotency key, derived from the key row's id so it's stable across retries. That's the only reason resuming is safe — the recovery point tells me the call may have happened, never whether it did, so the far side has to collapse the duplicate. My correctness is a property of their API.

Anything that can be deferred should be. The receipt email goes into a staged jobs table inside the phase and an enqueuer drains it after commit — a transactional outbox — so the send stops being a foreign call and becomes a local row.

And if the partner has no idempotency key, the advice inverts. A timeout is still indeterminate, but now indeterminate means mark it failed and get a human, because a retry is a coin-flip between losing the operation and doubling it. I'd only retry on an error that explicitly says it's safe to."

Score what you dropped. The three most costly omissions are "commit before you call out", the derived key on the outbound call, and the inversion at the end.
