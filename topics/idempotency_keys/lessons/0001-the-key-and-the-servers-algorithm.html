Lesson 01 · Idempotency Keys

The Key and the Server's Algorithm

One failure the network cannot resolve, one string that resolves it, and the four steps a server runs when the same string arrives twice.

The win for this lesson: by the end you can state the problem in one sentence, walk the server's algorithm step by step without notes, and name what happens in each of the three ways a duplicate can arrive. That is the whole interview question.

The failure with no safe answer

A customer taps Pay £40. Your app sends POST /charges. Then the train enters a tunnel and nothing comes back.

You now have to decide whether to send it again — and here is the entire difficulty: from the client, all three of these look identical.

What actually happenedWhat the client saw
The request never arrived. No charge exists. A timeout.
The request arrived and is still running. The charge is half-made. A timeout.
The charge completed. The response was lost on the way back. A timeout.

Retry, and in the third case you charge the customer twice. Don't retry, and in the first case you took their order and never charged them. There is no third option and no amount of client-side cleverness produces one, because the information needed to choose is on the other side of the broken connection.

When intermittent problems occur, clients are usually left in a state where they don't know whether or not the server received the request. Stripe — Advanced error handling

Why the method matters

HTTP already solved this for some requests. RFC 9110 is precise about which:

A request method is considered "idempotent" if the intended effect on the server of multiple identical requests with that method is the same as the effect for a single such request. Of the request methods defined by this specification, PUT, DELETE, and safe request methods are idempotent. RFC 9110 §9.2.2 — Idempotent Methods

POST is absent from that list, and the consequence is stated as a rule for clients:

A client SHOULD NOT automatically retry a request with a non-idempotent method unless it has some means to know that the request semantics are actually idempotent, regardless of the method, or some means to detect that the original request was never applied. RFC 9110 §9.2.2

Read that clause again — "unless it has some means to know that the request semantics are actually idempotent, regardless of the method." RFC 9110 does not forbid retrying a POST. It tells you the price of admission: a means. An idempotency key is that means. If you say one sentence about RFC 9110 in an interview, say that one.

The same section carries a caveat worth holding onto: idempotency "only applies to what has been requested by the user; a server is free to log each request separately, retain a revision control history, or implement other non-idempotent side effects." Idempotent never meant "leaves no trace". It means the intended effect lands once.

What an idempotency key is

An idempotency key is a unique value generated by the client which the resource uses to recognize subsequent retries of the same request. draft-ietf-httpapi-idempotency-key-header-07 §2

On the wire it is one header, and the value is conventionally a UUID — the draft "RECOMMENDED that a UUID or a similar random identifier be used" (§2.2):

POST /v1/charges HTTP/1.1
Host: api.example.com
Idempotency-Key: 8e03978e-40d5-43e8-bc93-6894a57f9324
Content-Type: application/json

{"amount": 4000, "currency": "gbp", "customer": "cus_9s6X"}

Three things are doing work here. The key is generated by the client, not the server — the server cannot mint it, because the whole point is that it must survive the client's retry. It is generated once per logical operation, not once per attempt: the retry reuses it. And it is opaque to the server, which never interprets it, only looks it up.

What the key actually buys

It converts an unanswerable question into a lookup.

"Did my charge go through?" cannot be answered — the evidence was lost with the connection. "Have you seen key 8e03978e before?" is a primary-key read against a table the server owns. The key does not prevent duplicate requests; duplicates still arrive, by design. It makes the second one recognisable.

The server's algorithm, step by step

This is the part to be able to produce on a whiteboard. Four steps.

1 · Claim the key

Insert the key. Do not read it first and then decide — that read-then-write is a race, and two concurrent retries will both read "not found" and both proceed. Let the unique constraint arbitrate:

CREATE TABLE idempotency_key (
    user_id        bigint      NOT NULL,
    key            text        NOT NULL,
    request_hash   text        NOT NULL,   -- fingerprint of the request payload
    state          text        NOT NULL,   -- 'in_progress' | 'completed'
    response_code  int,                    -- filled in at step 3
    response_body  jsonb,                  -- filled in at step 3
    created_at     timestamptz NOT NULL DEFAULT now(),
    PRIMARY KEY (user_id, key)
);

user_id leads the primary key for a reason covered under the traps below — it is a security property, not a modelling nicety. response_code and response_body are the columns most people forget, and they are the difference between a server that skips the duplicate and one that answers it.

2 · Branch on what the claim tells you

The insert either succeeded or conflicted, and the conflict splits into the three cases the draft enumerates (§2.6, §2.7):

CaseWhat the server does
New key
insert succeeded		 First time you have seen it. "The resource SHOULD process the request normally and respond with an appropriate response and status code." Go to step 3.
Key exists, completed
the retry after the lost response		 The work is already done. "The resource SHOULD respond with the result of the previously completed operation, success or an error." Replay the stored response_code and response_body. Do not run the work again.
Key exists, in_progress
the retry that overtook the original		 Someone is mid-flight with this key. "The resource SHOULD respond with a resource conflict error" — 409 Conflict. There is no stored response to replay yet, and running the work concurrently is exactly the duplicate you are preventing.
Key exists, different payload
a client bug		 The key was reused for a different request. 422 Unprocessable Content. The draft is blunt: the key "MUST NOT be reused with another request with a different request payload" (§2.2).

3 · Do the work and record the response — together

The claim and the work commit in one transaction

Mark the key completed, store the response, and write the business change in a single transaction. One commit, both or neither.

Split them and you get back exactly the two failures the key exists to prevent. Mark the key completed first and crash: the key says "done", the retry gets replayed a response for work that never happened, and nothing reports an error. Do the work and commit first, then record: the key is not there when the retry arrives and you charge the card twice — you built the mechanism and it does not work.

The general form is worth saying out loud in an interview: a record that something happened is only trustworthy if it commits with the thing it is recording. Any deduplication scheme that writes its marker in a separate step has one of these two holes.

4 · Return the stored response

Both the original and every replay return the same bytes and the same status code. Stripe is explicit that this includes failures:

Stripe's idempotency works by saving the resulting status code and body of the first request made for any given idempotency key, regardless of whether it succeeds or fails. Subsequent requests with the same key return the same result, including 500 errors. Stripe API Reference — Idempotent requests

That is a stronger promise than "we won't double-charge". It says the endpoint becomes a function of the key: ask twice, get the same answer, whatever the answer was.

The whole thing in Python

from sqlalchemy import update
from sqlalchemy.dialects.postgresql import insert
from sqlalchemy.ext.asyncio import AsyncSession

async def handle_charge(session: AsyncSession, user_id: int, key: str, payload: dict) -> Response:
    fingerprint = hash_payload(payload)

    async with session.begin():                          # ONE transaction for both writes
        claimed = await session.execute(
            insert(IdempotencyKey)
            .values(
                user_id=user_id,
                key=key,
                request_hash=fingerprint,
                state="in_progress",
            )
            .on_conflict_do_nothing()                    # 1 · claim, never read-then-write
        )

        if claimed.rowcount == 0:                        # 2 · branch on the conflict
            existing = await session.get(
                IdempotencyKey, (user_id, key), with_for_update=True
            )
            if existing.request_hash != fingerprint:
                return Response(422, {"error": "key reused with a different payload"})
            if existing.state == "in_progress":
                return Response(409, {"error": "a request with this key is outstanding"})
            return Response(existing.response_code, existing.response_body)  # 4 · replay

        result = await charge_the_card(session, payload)  # 3 · the work

        await session.execute(
            update(IdempotencyKey)
            .where(IdempotencyKey.user_id == user_id, IdempotencyKey.key == key)
            .values(state="completed", response_code=201, response_body=result)
        )

    return Response(201, result)                          # both writes committed together

Two details carry the correctness. on_conflict_do_nothing() with a rowcount check makes the claim atomic — the database, not your code, decides who is first. And the with_for_update=True on the conflict path serialises concurrent retries against each other, so two duplicates arriving together cannot both read in_progress and race onward. Everything inside session.begin() commits or rolls back as one.

Three real APIs, three shapes

The pattern is universal; the spelling is not. Knowing that the same idea wears three names is what separates "I read the Stripe docs" from "I understand the mechanism".

APIHow it does it
Stripe
Idempotency-Key header		 Up to 255 characters, UUIDv4 suggested. Keys expire after 24 hours. A replay is flagged with the response header Idempotent-Replayed: true. The scope rule is stated as a client instruction: keys must "unambiguously identify a single operation within your account over the last 24 hours." And on method: "All POST requests accept idempotency keys. Don't send idempotency keys in GET and DELETE requests because it has no effect."
AWS EC2
ClientToken request parameter		 Not a header at all — a normal parameter, "a unique, case-sensitive string of up to 64 ASCII characters." Mismatch is a named error: "If you retry a successful request using the same client token, but one or more of the parameters are different … the retry fails with an IdempotentParameterMismatch error." And it is unusually explicit about scope: keys are Regional or Zonal, so the same token deliberately launches an instance in us-east-1 and another in eu-west-1.
Google APIs
request_id message field		 A field in the request body: "A unique identifier for this request. Restricted to 36 ASCII characters. A random UUID is recommended." The justification for replaying is the cleanest one-liner in this topic: "If a duplicate request is detected, the server should return the response for the previously successful request, because the client most likely did not receive the previous response."

Note what varies and what does not. Placement varies (header, parameter, field). Length limits vary (255, 64, 36). Expiry varies — and is sometimes unspecified. What never varies: the client generates it, the server stores the outcome against it, and a duplicate gets the stored outcome rather than a second execution.

Three traps

Keying on the bare string leaks other people's data

If your lookup key is just the client-supplied string, then any client who guesses another client's key reads their stored response body. The draft flags this directly:

When an idempotency implementation allows low entropy keys, attackers MAY determine other keys and use them to fetch existing idempotent cache entries, belonging to other clients. draft-ietf-httpapi-idempotency-key-header-07 §5

The fix is the primary key in step 1: "implement a unique composite key as the idempotent cache lookup key … combining the idempotency key sent by the client with other client specific attributes known only to the resource." Scope every key to the authenticated caller. It also stops one customer's "retry-1" from colliding with another's.

The key must not live forever

This table is insert-only and grows with every request you ever serve, and nobody has derived the right retention — they have only chosen one. Stripe expires at 24 hours. Brandur Leach, who built Stripe's implementation, argues for longer:

Idempotency keys are meant to act as a mechanism for guaranteeing idempotence, and not as a permanent archive of historical requests. After some amount of time a reaper process should go through keys and delete them. Brandur Leach — Implementing Stripe-like Idempotency Keys in Postgres

His suggestion is roughly 72 hours, on the grounds that a bug shipped on a Friday should still be recoverable on Monday. Both numbers are judgements. The rule behind them is the defensible thing to say: keep keys longer than the longest retry window any client of yours could plausibly use — past that horizon, a retry is silently a new request. Stripe says so outright: "We generate a new request if a key is reused after the original is pruned."

Some errors happen before the idempotency layer

The promise "the same key always returns the same response" is narrower than it sounds. Stripe: "We save results only after the execution of an endpoint begins." A request rejected by rate limiting, authentication, or request validation never reaches the layer, so it is not stored and the same key can legitimately return something different next time. Their practical advice is to "always generate a new idempotency key" after a 4xx you intend to fix — because you are about to change the payload, which is the 422 case anyway.

What you can now do

State the ambiguous-failure problem in one sentence; quote RFC 9110's retry rule and explain that a key is the "means" it asks for; walk claim → branch → work-and-record → replay; attach 409, 422 and "replay the stored response" to the right cases; justify the single transaction; and name three real APIs with three different key shapes.

A caveat on the sources

There is no RFC for Idempotency-Key. The document quoted throughout is draft-ietf-httpapi-idempotency-key-header-07, which expired on 18 April 2026 and is listed by the IETF datatracker as expired and archived. It never became a standard, and its requirements are SHOULD, not MUST, nearly throughout.

That is not a reason to ignore it — it is the clearest written statement of what the industry converged on, and Stripe, AWS and Google all predate it. But cite it as convention, never as standard. Only RFC 9110 is normative here, and it is normative about methods, not about this header. Being the candidate who knows that is worth more than the header itself.

Check yourself

One attempt per question — guessing until it turns green is recognition, not recall.

  1. A client's POST times out. Why can it not simply ask the server whether the request succeeded before deciding to retry?

    Nothing is deduplicating anything yet — that is the mechanism we have not built. The blocker comes earlier.

    A GET would do fine if there were something to GET. The missing piece is not the method.

    Correct, and this is the cleanest way to see what the key is for. The server may have created a charge with an id the client never received, so the client cannot name the thing it wants to ask about. The idempotency key is a name the client chooses in advance, which is why it survives the lost response.

    The opposite is the dangerous case: the work completed and was durably stored, and only the response was lost.

  2. A retry arrives while the original request is still executing. What should the server return?

    An empty success is a lie — the client would record a charge it cannot identify. Never invent a response you do not have.

    Correct. The draft: "The request was retried before the original request completed. The resource SHOULD respond with a resource conflict error." There is nothing stored to replay yet, and executing concurrently is precisely the duplicate you are preventing. The client retries again shortly.

    422 is for a key reused with a different payload — a client bug. This payload is identical; the client is doing exactly the right thing.

    Tempting, but 202 claims you accepted a new unit of work. You accepted nothing; you are already busy with the first one.

  3. A server marks the key completed and commits, then performs the charge in a second transaction. What is the failure mode?

    Double-charging is what the other ordering (work first, record after) causes. This ordering fails the opposite way.

    A real consequence of the timing, but not the failure. A spurious 409 costs a retry; this ordering costs the money.

    True and untidy, but survivable on its own. The fatal part is what happens to the work, not to the body.

    Correct, and it is the same silent loss the inbox table has. The key says "done", so every retry is replayed a success for a charge that never happened, and nothing anywhere raises an error. Claim and work must share one transaction.

  4. Why store the response body against the key, rather than just a flag saying the work was done?

    Correct. The client retried because it never saw the response — it has no charge id, no receipt, nothing. Skipping the work but returning an empty acknowledgement leaves it just as stuck. Stripe saves "the resulting status code and body" for exactly this.

    The fingerprint is taken from the request payload, not the response.

    A second flag would cover that. It still would not give the client the charge id it is missing.

    If anything the reverse — stored bodies are the reason the table grows and needs a reaper at all.

  5. Why is the lookup keyed on (user_id, key) rather than on the client-supplied key alone?

    A single text column indexes perfectly well. The reason is a security property, not a performance one.

    Correct. The draft warns that with low-entropy keys "attackers MAY determine other keys and use them to fetch existing idempotent cache entries, belonging to other clients", and prescribes a composite key combining the client's key with attributes known to the server. It also stops two customers' identical "retry-1" strings from colliding.

    The reaper works on age, and would work the same with either key.

    That is the bug being prevented, described as though it were a feature.

Say it out loud

Whiteboard, no notes, 90 seconds. The prompt is: "what's an idempotency key and what does your server do with it?" Cover the ambiguous failure, what the key is and who makes it, the four steps, the three duplicate cases with their codes, and the transaction boundary. Then reveal and score what you dropped.

"The problem is that a client whose request times out can't tell three situations apart: the request never arrived, it's still running, or it finished and the response was lost. All three look like a timeout. So it either retries and risks charging twice, or doesn't and risks losing the order. The information needed to choose is on the far side of the broken connection.

RFC 9110 says PUT, DELETE and the safe methods are idempotent and POST isn't, and that a client shouldn't auto-retry a non-idempotent method unless it has some means to know the semantics are idempotent regardless of the method. An idempotency key is that means.

It's a unique value the client generates — usually a UUID — once per logical operation, not per attempt, and sends on every retry. Stripe puts it in an Idempotency-Key header; AWS calls it ClientToken and takes it as a parameter; Google calls it request_id in the body. Same mechanism.

Server side, four steps. One: claim the key by inserting it, with ON CONFLICT DO NOTHING — never read-then-write, because two concurrent retries would both read 'not found'. Key on (caller, key), not the bare string, or one client can guess another's key and read their stored response.

Two: branch. Insert succeeded, it's new, do the work. Key exists and is completed — that's the retry after a lost response — replay the stored status code and body and don't re-run. Key exists and is in progress, the retry overtook the original, return 409, because there's no stored result yet. Key exists but the payload fingerprint differs — that's a client bug — 422.

Three: do the work, and write the business change, the completed state and the stored response in one transaction. Split them and it fails the way a split inbox insert does: mark-first silently loses the charge while replaying success, work-first double-charges.

Four: return the stored response, same bytes and status as the original — including if the original failed. The endpoint becomes a function of the key.

Then the operational parts: the table needs a reaper, because a key that's been pruned makes a retry a brand-new request — Stripe expires at 24 hours, Brandur argues for about 72. And the guarantee only covers errors raised after execution begins; rate limiting and auth happen in front of the layer.

Worth knowing: there's no RFC for the header. The draft expired in April 2026 — it's the written-down convention, not a standard."

Score the parts you dropped, not the wording. The three most costly omissions are the single transaction, replaying the stored body rather than just skipping the work, and the 409-versus-422 distinction.
