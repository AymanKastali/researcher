Lesson 02 · Idempotency Keys

What You Store, and For How Long

Three columns from Lesson 01 were left as names with no contents. Filling them in is where the design decisions actually live — and where the guarantee turns out to be narrower than it first sounds.

First, from memory

Before reading anything new. One attempt each — this is the spacing, not a test.

  1. Why does the server insert the key before doing the work, rather than reading to check whether it exists?

    Both are primary-key operations. Cost is not the argument; correctness under concurrency is.

    True, and it is why the response is written in step 3 rather than step 1 — but it is not why the claim must be an insert.

    Correct. Read-then-write is a race with a window between the two statements. Two retries arriving together both see nothing, both proceed, and you have built the duplicate you were preventing. The unique constraint arbitrates because only one insert can win.

  2. The key exists and is marked completed. What does the server send back?

The win for this lesson: by the end you can say exactly what goes in request_hash, response_code and response_body, defend a retention window rather than quoting one, and state the limit of the guarantee out loud — the part most people who have "used idempotency keys" have never thought about.

The fingerprint: what exactly do you hash?

Lesson 01 called hash_payload(payload) and moved on. The draft names the concept but deliberately refuses to pick for you:

An idempotency fingerprint MAY be used in conjunction with an idempotency key to determine the uniqueness of a request. Such a fingerprint is generated from request payload data by the resource. draft-ietf-httpapi-idempotency-key-header-07 §2.4

Note by the resource — the fingerprint is the one part of this the server derives for itself. The client cannot be trusted to say "this is the same request as before"; that claim is precisely what is being checked. The draft then lists five approaches, in decreasing strictness:

Approach (§2.4)What it costs you in practice
"Checksum of the entire request payload." Strictest, and the default choice. But it is a checksum of bytes: a client that reorders its JSON keys or changes whitespace between attempts now fails the comparison and gets a 422 for a request that is semantically identical.
"Checksum of selected element(s) in the request payload." Survives cosmetic churn, but you now own a list of which fields matter. Forget one that changes behaviour and two genuinely different requests hash the same — the key silently swallows the second.
"Field value match for each field in the request payload." Comparison rather than hashing, so the error can say which field differed. The cost is storing the whole payload instead of 32 bytes.
"Field value match for selected element(s)." Same trade as above, with the same list of fields to keep correct.
"Request digest/signature." Only available if you already sign requests. Free when you do, absent when you don't.

Brandur Leach's schema resolves it by storing the payload rather than a hash, and — the detail worth stealing — by storing more than the payload:

-- parameters of the incoming request
request_method  TEXT  NOT NULL CHECK (char_length(request_method) <= 10),
request_params  JSONB NOT NULL,
request_path    TEXT  NOT NULL CHECK (char_length(request_path) <= 100),

Method and path, not just the body. A key generated per logical operation can otherwise be replayed against a different endpoint with an identical body, and a body-only fingerprint will not notice. His stated reason for keeping the params at all is narrower — "stored mostly so that we can error if the user sends two requests with the same idempotency key but with different parameters" — but the columns are the ones to copy.

The fingerprint is a check, not part of the lookup

This is the subtle one, and it is worth being able to say precisely. The draft describes a duplicate as "idempotency key and fingerprint has been seen" (§2.6), which reads like the pair is the lookup key. Implement it that way and the 422 case disappears.

Look up on (caller, key) alone. A reused key with a different payload then misses the fingerprint comparison and is caught — §2.7 requires 422 for exactly this. Look up on (caller, key, fingerprint) and that same request finds no row, claims a new one, and executes a second operation — under a key the client believes protects it.

Lesson 01's handler already had this right: the primary key is (user_id, key), and request_hash is a column it compares after the lookup. That is not an accident, and reading §2.6 literally would have broken it.

The response columns: store the failures too

The instinct is to cache successes. Stripe caches everything:

Stripe's idempotency works by saving the resulting status code and body of the first request made for any given idempotency key, regardless of whether it succeeds or fails. Subsequent requests with the same key return the same result, including 500 errors. Stripe API Reference — Idempotent requests

A cached 400 looks like a bug until you see what caching it prevents. The retrying client is retrying because it never saw the first answer. If a rejected request is not stored, the retry is a brand-new request — and now the server runs validation, authorisation and business logic again, with no memory that it already made a decision about this operation. Caching the rejection makes the endpoint a function of the key in the failure case too:

For a POST operation using an idempotency key, as long as an API method began execution, Stripe's API servers will cache the results of the request regardless of what they were. A request that returns a 400 sends back the same 400 if followed by a new request with the same idempotency key. Generate a fresh idempotency key when modifying the original request to get a successful result. Stripe — Advanced error handling

The last sentence is the client-side consequence, and it follows from the 422 rule rather than being a separate rule: fixing a rejected request means changing the payload, which changes the fingerprint, which is a key reuse. A new attempt at a corrected request is a new operation and deserves a new key.

What is not stored

Here the guarantee narrows, and this is the paragraph to be able to recite:

We save results only after the execution of an endpoint begins. If incoming parameters fail validation, or the request conflicts with another request that's executing concurrently, we don't save the idempotent result because no API endpoint initiates the execution. You can retry these requests. Stripe API Reference — Idempotent requests

Two things fall out of that. First, everything in front of the idempotency layer is outside the promise — "a request that's rate limited with a 429 can produce a different result with the same idempotency key because rate limiters run before the API's idempotency layer. The same goes for a 401 that omitted an API key, or most 400s that sent invalid parameters."

Second — and this refines Lesson 01 — the 409 is not stored either. It is emitted by the layer itself before any endpoint runs, which is exactly why it is safe for the client to retry a 409 unchanged, and not safe to retry a cached 400 unchanged. The two look similar on the wire and mean opposite things.

What the client gotStored?
2xx — the operation succeeded Yes. Replayed forever, or until reaped.
4xx raised by the endpoint (declined card, business rule) Yes. Execution began. Retry with the same key gets the same refusal.
500 from inside the endpoint Yes — and this is the hard case, below.
400/401/429 from in front of the layer No. No endpoint ran. The same key may answer differently later.
409 — a retry overtook the original No. The layer emitted it. Retrying unchanged is the correct move.

One more piece of the contract, cheap to add and easy to forget: tell the client it got a replay. Stripe: "To identify a previously executed response that's being replayed from the server, look for the header Idempotent-Replayed: true." The body is byte-identical to the original, so without this header the client cannot distinguish "my retry did the work" from "my retry was answered from a cache" — which is exactly the distinction it went to the trouble of sending a key to establish.

The 500 that stays wrong

Everything so far assumes the stored response is true. For a 500 it may not be, and no amount of care in your handler fixes that.

You should treat the result of a 500 request as indeterminate. Stripe — Advanced error handling

Not failed — indeterminate. The word is the whole point. A 500 means the server stopped partway and does not itself know how much landed. And because the response is now cached under the key, the client cannot learn any more by retrying:

Stripe engineers examine failed requests and try to appropriately reconcile the results of any mutations that result in 500s. While the idempotency-cached response to those requests won't change, we'll try to fire webhooks for any new objects created as part of Stripe's reconciliation. … For example, if creating a charge returns a 500 error but we detect that the information has gone out to a payment network, we'll try to roll it forward. If not, we'll try to roll it back. Stripe — Advanced error handling
The cached response can be permanently, knowingly wrong

Read that quote again: the idempotency-cached response won't change, but the underlying state might be rolled forward into a real charge. The key promises the same answer every time. It does not promise the right answer, and after a 500 those two come apart and stay apart.

This is not a flaw to design out — it is the honest boundary of what a stored response can do. The repair has to arrive out of band, which is why Stripe's advice is to "configure webhook handlers to receive event objects that you never receive in normal API responses." Your integration must be able to hear about a charge it was told did not happen.

Saying this in an interview is a strong signal, because it shows you know the mechanism's limit rather than just its happy path.

It also settles a question clients ask constantly — should I retry a 500 with a fresh key? Stripe's answer: "The client can retry the request with a new idempotency key, but we advise against it because the original key may have produced side effects." A new key is a new operation, and a new operation on top of an indeterminate one is how you get two charges.

How long to keep the row

The specification declines to choose, and says something more useful instead:

The resource MAY require time based idempotency keys to be able to purge or delete a key upon its expiry. The resource SHOULD define such expiration policy and publish it in the documentation. draft-ietf-httpapi-idempotency-key-header-07 §2.3

Publishing it is the requirement, because the window is half of a contract: it tells a client how long its retries remain safe. An unpublished window is a trap with a timer on it.

The two public numbers disagree, and the reasoning matters more than either figure. Stripe prunes at 24 hours and is explicit about the consequence: "You can remove keys from the system automatically after they're at least 24 hours old. We generate a new request if a key is reused after the original is pruned." Past the horizon, a retry silently becomes a fresh operation — the protection does not fail loudly, it just stops.

Brandur argues for three times that, on grounds that have nothing to do with networks:

I'd suggest a threshold of about 72 hours so that even if a bug is deployed on Friday that errors a large number of valid requests, an app could still keep a record of them throughout the weekend and onto Monday where a developer would have a chance to commit a fix and have the completer push them through to success. Brandur Leach — Implementing Stripe-like Idempotency Keys in Postgres

Notice what happened to the question. Stripe is sizing for a client's retry window; Brandur is sizing for a human's repair window — the table is also the record of what went wrong, and deleting it deletes your ability to fix it. Those are two different requirements that happen to be satisfied by the same column, and the larger one wins. Neither number is derived from anything; both are judgements, and the defensible answer in an interview is the rule rather than the figure: longer than the longest retry window any client of mine could plausibly use, and long enough that a Friday incident is still repairable on Monday — then published.

The reaper itself is unglamorous and deserves one more property than "delete old rows":

An ideal reaper might even notice requests that could not be finished successfully and try to do some cleanup on them. If cleanup is difficult or impossible, it should put them in a list somewhere so that a human can find out what failed. Brandur Leach — Implementing Stripe-like Idempotency Keys in Postgres 
from datetime import datetime, timedelta, timezone
from sqlalchemy import delete, select

RETENTION = timedelta(hours=72)          # published in the API docs, or it is not a contract

async def reap(session: AsyncSession) -> None:
    cutoff = datetime.now(timezone.utc) - RETENTION

    async with session.begin():
        # Anything still in_progress at the cutoff never finished. Deleting it
        # quietly is how a stuck charge becomes a thing nobody ever knew about.
        stranded = await session.scalars(
            select(IdempotencyKey).where(
                IdempotencyKey.created_at < cutoff,
                IdempotencyKey.state == "in_progress",
            )
        )
        for row in stranded:
            await flag_for_a_human(row)   # the list Brandur asks for

        await session.execute(
            delete(IdempotencyKey).where(IdempotencyKey.created_at < cutoff)
        )

The in_progress pass is the part that earns its keep. A row left mid-flight means a request that claimed a key and then died — so the work may be half-done, and the client has been getting 409s ever since. Deleting it on age alone destroys the only evidence. Nothing here has been run; treat it as the shape, not a benchmarked implementation.

A note on what goes in the key

The key is a string the client picks, which makes it tempting to make it meaningful. Two warnings, both from Stripe, and they point in opposite directions.

Don't make it meaningful in a way that leaks: "Avoid using sensitive data (for example, email addresses or personal identifiers) as idempotency keys." The key ends up in server logs, error reports and support tickets — everywhere a request identifier goes.

But do consider deriving it from something stable. Stripe names two strategies: "Use an algorithm that generates a token with enough randomness, like UUID v4", or "Derive the key from a user-attached object, like the ID of a shopping cart. This provides a relatively straightforward way to protect against double submissions."

Two different problems wearing the same header

A random UUID protects against one client retrying. A key derived from the cart id protects against the user pressing Pay twice — two genuinely separate requests, from two separate page loads, possibly from two devices, that a per-attempt UUID would treat as two legitimate charges.

Same mechanism, different unit of "the same operation". Choosing it is a product decision about what a duplicate means to you, not a technical one — and it is the question to ask when someone says "we already use idempotency keys" and double charges are still happening.

What you can now do

Name the five fingerprint strategies and the trade in each; explain why the fingerprint is compared after the lookup rather than folded into it, and what breaks if you fold it in; say which responses are stored and which are raised in front of the layer, including the 409; explain why a 500 is indeterminate and why the cached answer can stay wrong; and defend a retention window on two independent grounds instead of quoting 24 hours.

  3. Stripe reconciles a request that returned 500 and the charge ends up going through. What does the retrying client see?

    Correct, and it is the most important limit of the whole mechanism.     Correct, and it is the failure the mechanism cannot see. The key must be minted once per logical operation — generate it per attempt and two clicks are two honest, distinct operations. Stripe's other strategy is the fix: "Derive the key from a user-attached object, like the ID of a shopping cart. This provides a relatively straightforward way to protect against double submissions."

    A genuine race, and it would produce this symptom — but only for requests sharing a key, which these two do not.

Say it out loud

60 seconds, no notes. The prompt is a follow-up an interviewer reaches for after you have described the algorithm: "so what exactly do you store against the key, and how long do you keep it?" Cover the fingerprint and why it is not part of the lookup, which responses are stored and which are not, the 500 problem, and how you would pick a retention window.

"Three things: a fingerprint of the request, and the status code and body of the response.

The fingerprint is derived by the server from the request — usually a checksum of the payload, plus the method and path, because the same key against a different endpoint with the same body should not match. The important detail is that it is not part of the lookup key. You look up on (caller, key) and compare the fingerprint afterwards. If you fold it into the lookup, a reused key with a changed payload finds nothing, claims a fresh row and executes a second operation — the exact thing you were preventing.

For the response, you store it whether it succeeded or failed. A cached 400 sounds wrong but it is right: the client never saw the first answer, so without it the retry is a whole new request. The exception is anything raised in front of the idempotency layer — rate limits, auth, parameter validation, and the 409 for a concurrent retry. Nothing executed, so nothing is stored, which is why a 409 is safe to retry unchanged and a cached 400 is not. I'd also set Idempotent-Replayed on replays so the client can tell.

The hard case is a 500. You cache it, but you should treat it as indeterminate rather than failed — the server stopped partway and doesn't know how much landed. And once it is cached it never changes, so if the underlying state later gets reconciled forward into a real charge, the cached response is permanently wrong. That correction has to reach the client out of band, by webhook. Same answer every time isn't the same as the right answer.

For retention: it has to be longer than the longest retry window any client plausibly uses, because past expiry a retry silently becomes a new request — no error, it just stops protecting you. Stripe prunes at 24 hours. Brandur argues about 72, for a different reason: the table is also your record of what broke, so a Friday-night bug should still be repairable on Monday. That second requirement is the bigger one, so I'd size to it. And publish the window — the draft says so, and it is half the client's contract. The reaper should also flag rows still in progress at the cutoff rather than just deleting them, because those are requests that died mid-flight."

Score the parts you dropped. The three most costly omissions are the fingerprint not being in the lookup, the 409 being unstored, and "indeterminate" rather than "failed".
